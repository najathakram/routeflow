## Key design decisions (all confirmed with routeflow-c4, not just self-derived)

- **`ADVANCE` is never grouped with `CREDIT_NOTE` for cash-flow/lifetime-received purposes** —
  bookkeeping never reads `AdvancePayment`, so an advance application's `InvoicePayment` row is
  the only place that already-real cash is ever recorded. `RECEIVED_METHOD_FILTER = { not:
CREDIT_NOTE_METHOD }` (excludes only credit notes) is the one to use for a "cash received"
  figure; `CASH_METHOD_FILTER` (excludes both) is for an invoice-level cash-only figure.
  `statement.service.ts` and `customers.service.ts`'s per-invoice-balance code correctly groups
  them together instead — different semantic, both live in `payment-confirmation.ts`'s own doc.
- **Balance/outstanding/status figures use the FULL confirmed total** (cash + credit + advance),
  never cash-only — a credit note or advance genuinely reduces what's owed. Confirmed correct
  as-is at: `invoices.service.ts` `balanceDue`, `customers.service.ts`'s `withPaid` (outstanding),
  `bookkeeping.service.ts`'s `outstandingReceivables`/`totalOutstanding`/`getPeriodSummary.due`,
  `import.service.ts`'s status recompute, `payment-requests.service.ts`'s allocation `balanceDue`.
- **`totalRevenue`** (`bookkeeping.service.ts`, an `invoice.aggregate` on `status=PAID`) is
  accrual revenue recognition, never touches `InvoicePayment.method` — NOT part of B421. A real,
  separate revenue-recognition question (a RETURN credit note settling an invoice still counting
  its full total as that month's revenue) is being filed by the owner separately.
- **`bookkeeping/invoice-template.tsx`** (a second customer-facing PDF, flagged by review) reads a
  `Transaction.totalPaid` STORED column. Traced every write to the `Transaction` Prisma model in
  the whole api tree: exactly one (`bookkeeping/invoice.service.ts:104`, sets only `pdfUrl`) plus
  `prisma/seed.ts` demo data (comment admits it "mimics what orders service does on delivery" —
  nothing does anymore). No live code path populates `totalPaid` there from real activity — this
  whole pathway is dead/vestigial, confirmed independently by routeflow-c4, who found the actual
  live bug this masks (a broken PDF download for real tenants — id-space mismatch between the
  Invoice-backed ledger and the Transaction-backed lookup) and is filing it separately, not B421.
- **All-or-nothing fallback discipline (L-159):** a fallback that re-derives several related
  figures from raw data must gate ALL of them on ONE presence check, never per-field — this exact
  bug was caught by independent review in the PDF template, then independently reproduced by me
  in the very next surface (web detail page) before it even shipped. `resolveConfirmedAmounts` in
  `@routeflow/pricing` is the one shared implementation now; both the API facade and web's
  hand-rolled mirror in `invoices/page.tsx` (list) and `invoices/[id]/page.tsx` (detail) call it.

## Two lesson candidates raised, NOT yet written (asked routeflow-c4 how to handle)

1. A plain object-literal Prisma filter constant needs `as const` proven against a REAL call
   site — `CASH_METHOD_FILTER` sat with a silent type bug (Prisma's generated enum filter type
   rejects a widened `string`/`string[]`, and `@routeflow/pricing` can't import Prisma to check
   against directly) for a whole commit because nothing had used it in a query yet; only found
   because its sibling `RECEIVED_METHOD_FILTER` hit the same wall first.
2. A shared helper that re-derives a precondition generically (e.g. `splitConfirmed` re-checking
   `.status`) will silently no-op for a caller whose `select`/test fixture never populated that
   field for its own prior reasons (a `where` clause already enforcing it). Caught in
   `statement.service.ts`'s refactor only because its EXISTING test suite was run and went red
   before trusting the swap — not because anything type-checked wrong.
