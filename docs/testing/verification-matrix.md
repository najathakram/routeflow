# Verification matrix — 2026-08-20 UX expansion batch

Every feature shipped in the batch (`docs/plans/ux-expansion-batch-2026-08-19.md` PR-A…PR-F,
the `.claude/pipeline/plans/2026-08-20-b7-b14-backlog.md` B4–B14 fixes, in-app pack size, and
the boxed-pieces/D1 money fixes), against the four verification layers, so a gap in coverage is
a documented decision rather than a silent hole.

## The four layers

| #   | Layer                 | Command                                                                       | What it proves                                                                                                                                                                                                                                                 |
| --- | --------------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **Unit**              | `npm run verify` (Jest — API + mobile, per `turbo run check-types lint test`) | Logic is correct, mocked at the Prisma boundary. ~3,100 specs.                                                                                                                                                                                                 |
| 2   | **Post-deploy check** | `npm run post-deploy-check`                                                   | The deployed API is reachable, auth works, list endpoints respond, money fields carry no float artifacts, invoice/order↔invoice math reconciles. **Read-only.**                                                                                                |
| 3   | **Feature smoke**     | `npm run feature-smoke`                                                       | The deployed API's WRITE paths from this batch actually work end-to-end, with money-invariant assertions, against the `e2e-routeflow` test tenant. Provisions `E2E-SMOKE-` fixtures, cleans up in `finally`. See `scripts/feature-smoke.mjs` — sections S1–S9. |
| 4   | **E2E (Playwright)**  | `cd apps/web && npx playwright test`                                          | The new UI surfaces render and behave correctly. Specs `13`–`16` are read-only-or-cancel by construction (never submit/commit/apply) so repeated runs never mutate the tenant.                                                                                 |

`npm run regression` chains **1 → 2 → 3** and is what a human runs locally before every push
(`feedback_rebuild_routine`). `.github/workflows/nightly.yml` runs **2 + 3 + 4** against
production, but — see "Known gaps" below — it only fires while the repo is temporarily public
during a ship window, so it is **dormant** the rest of the time; the recurring gates in normal
operation are the post-deploy Railway webhook (layer 2) and a human running `npm run regression`
before pushing.

Web has no Jest/unit layer of its own (Playwright only, per `CLAUDE.md`) — a web-only UI change
below that shows "—" in the Unit column is not a gap unless the E2E column is also "—".

## Known gaps (honest, not silently assumed handled)

- **AI statement parse** (PR-F) needs a real Anthropic key and a real statement document.
  Nothing in `npm run verify`, `npm run feature-smoke`, or CI ever calls the model — S9 proves
  only that the routes exist and reject an empty scan request. The matcher and apply
  transaction are unit-tested against hand-built fixtures, never against a real model response.
- **Driver-role e2e/smoke does not exist.** A4 and B13 are both driver-specific fixes; unit
  specs cover the driver branch directly, but no e2e or feature-smoke run authenticates as a
  DRIVER and exercises it end-to-end against a live API.
- **`nightly.yml` only fires while the repo is public** (CI needs a public repo; the repo is
  private the rest of the time — see `CLAUDE.md` "Canonical deploy flow"). It is **dormant**
  between ship windows. The recurring gates in normal operation are the post-deploy Railway
  webhook (layer 2, `post-deploy-check`) and a human running `npm run regression` locally
  before every push (`feedback_rebuild_routine`).
- **Mobile (RN) has no e2e layer at all** — Playwright drives the web dashboard only. A1, B4,
  B6, and the mobile halves of pack-size and D1 rely on Jest pure-logic specs plus manual QA
  for anything that touches actual rendering or gestures.
- **B10 (returns over-return race) and B11 (PO-receive STANDARD-cost clobber)** have solid
  unit coverage but no feature-smoke section this batch — returns and purchase-order receiving
  are outside WP1's scenario list. A future verification-suite pass could extend S3-adjacent
  coverage to purchase orders, and add a dedicated returns section.
- **B14 (list debounce)** has no automated coverage at any layer — it is a network-call-count
  assertion that would need a purpose-built Playwright spec, which does not exist yet.
- **Web has no unit/Jest layer** (per `CLAUDE.md` — Playwright only), so every web-only UI fix
  in this batch (A2, A3, B14, the web pack-size UI beyond spec 14) is either e2e-covered or not
  covered at all; there is no third option to fall back on.
