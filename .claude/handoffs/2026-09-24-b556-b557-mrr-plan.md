## What genuinely remains — three items, all named precisely in `mrr.service.ts`'s own doc
comment (lines 39-49) and independently confirmed by reading the two implicated functions

### Item 1 (B557a) — `BillingService.reconcilePriceLedger()`'s filter gap

`billing.service.ts:488-521`. Current guard: `if (!sub || sub.planKey == null) return;` — only
checks `planKey != null`, never `tenant.status`/`tenant.deletedAt`/`tenant.class`. A price
resync on a non-ACTIVE-but-still-PRODUCTION tenant (or a non-PRODUCTION tenant) with a resolved
`planKey` books a delta live `mrr` never sees, so `ledgerMrr` drifts above `mrr` permanently.

**Fix**: widen the guard to the full 4-part paying-set check (see "shared predicate" below).
The query already only selects `planKey`/`basePriceSnapshot` from `tenantSubscription` — needs
widening to also pull the tenant's `status`/`deletedAt`/`class` (a one-hop `include`/select on
the relation, no schema change).

### Item 2 (B557b) — `PlatformAdminService.updateTenantClass()`'s retroactive-import gap

`platform-admin.service.ts:1884-1927`. `ledgerAgg` (`mrr.service.ts:163-166`) sums
`BillingEvent.amountDelta` `WHERE tenant.class = 'PRODUCTION'` — a join evaluated against the
tenant's **current** class, not class-at-event-time. The moment a tenant flips into PRODUCTION,
its entire historical `amountDelta` stream (accumulated under whatever class it was before)
becomes visible to this SUM in one step. `updateTenantClass()` already emits a
`TENANT_CLASS_CHANGED` event on any boundary crossing (line 1908-1915), but with no
`amountDelta` (defaults to `null` via `BillingEventService.emit()`'s `opts?.amountDelta ?? null`
— confirmed by reading the signature), so nothing compensates for the import.

Direction analysis:
- **Entering PRODUCTION** (`!wasProd && isProd`): needs a compensating entry. Proposed
  `amountDelta` = `priceTenant(tenantId)` (this tenant's live contribution, right now) **minus**
  Σ(this tenant's pre-existing `BillingEvent.amountDelta`, read inside the same transaction,
  before the class write). This makes the tenant's post-flip ledger contribution land exactly at
  its live `mrr` contribution — matching `mrr` and `ledgerMrr` at the instant of the transition,
  not importing unrelated pre-PRODUCTION history, and not assuming what pre-existing total
  "should" be.
- **Leaving PRODUCTION** (`wasProd && !isProd`): **no fix needed**. `ledgerAgg`'s current-class
  join automatically excludes ALL of this tenant's `BillingEvent` rows (past and future) the
  instant `class` flips away from PRODUCTION — the same reason `payingWhere`'s `class` condition
  drops it from live `mrr` simultaneously. Both go to zero contribution together, for the same
  underlying reason. Confirmed by re-reading the query; not assumed.

No migration required for either direction — application logic only (a `SUM` read +
`billingEventService.emit()` call, inside the transaction `updateTenantClass()` already opens).

### Item 3 (B556) — one source of truth for tenant "plan" **display**

`_formatTenant()` (`platform-admin.service.ts:1732-1747`) is the one shared formatter behind
BOTH `listTenants()` (line 194) and `getTenant()` (line 230) — i.e. every tenant-facing "what
plan is this tenant on" read in the platform-admin API funnels through this one function
already. It currently returns `plan: t.plan` — the raw legacy `TenantPlan` enum — never
consulting `TenantSubscription.planKey`. This is the literal mechanism behind B556's original
evidence (`e2e-routeflow`: `Tenant.plan=PROFESSIONAL`, `planKey=NULL`, admin UI shows a
"Business" badge, contributes $0).

The dashboard overview (`platform-admin.service.ts:1216-1222`) already has the CORRECT
resolution one call away — `planCounts` for the plan-breakdown widget uses
`normalizePlanKey(t.subscription?.planKey) ?? planKeyFromEnum(t.plan)` — but this expression is
inlined there only, not shared with `_formatTenant()`. Two independent copies of "what plan is
this tenant on" already exist in the same file, one correct (aggregate breakdown) and one naive
(every per-tenant display row) — this is L-167's exact pattern.

**Fix**: extract `normalizePlanKey(t.subscription?.planKey) ?? planKeyFromEnum(t.plan)` into one
shared helper (e.g. `resolveDisplayPlanKey(tenant: { plan; subscription?: { planKey } | null })`)
and use it in both `planCounts` and `_formatTenant()`'s `plan:` field. `listTenants()`'s query
(line 179-181) selects `subscription: { select: { currentPlan, periodEnd, cancelAtPeriodEnd } }`
— **missing `planKey`** — needs adding to the select, or `_formatTenant()` silently resolves
`undefined` for list rows (L-169's exact caution: a shared helper re-deriving a precondition is
only as good as the caller's own `select`). `getTenant()`'s query already `include:
{ subscription: true }` (full include), so no select change needed there.

**Naming choice**: `resolveDisplayPlanKey` returns the *resolved* plan key (STARTER/GROWTH/
SCALE/ENTERPRISE-shaped), not the raw legacy enum value — this changes the shape of the `plan`
field in list/detail API responses for a drifted tenant (was e.g. `"PROFESSIONAL"`, becomes
whatever `planKeyFromEnum`/`normalizePlanKey` resolves to). Need to confirm with whoever owns
the web admin UI whether the `plan` field's consumers expect the legacy enum shape specifically,
or treat it as an opaque display string — **flagging this as a compatibility check to do during
implementation, not assuming it's a pure win**. Worth grep'ing `apps/web`'s admin pages for how
they render this field before landing.

## Which filter becomes the single shared predicate (the Mac Lead's question, answered)

Before this fix, the "is this tenant currently in the paying set" question is answered
independently in at least two places already, and my two fixes above would add two more copies
if done naively:
1. `mrr.service.ts`'s `payingWhere` (a Prisma `where` object, DB-side).
2. `platform-admin.service.ts`'s `updateStatus()` — inline `payingBase`/`wasPaying`/`isPaying`
   booleans (JS-side, on an already-fetched row).
3. (new, if unguarded) `reconcilePriceLedger()`'s widened guard.
4. (new, if unguarded) `updateTenantClass()`'s compensating-entry boundary check.

**Proposed single builder**: add one exported pure function to `mrr.service.ts` —
`isPayingRow(tenant: { status; deletedAt; class }, planKey: string | null): boolean` — the same
four conditions `payingWhere` expresses as a Prisma filter, expressed once as a plain JS
predicate for every in-memory (already-fetched-row) call site. `payingWhere` itself stays a
Prisma `where` object (Prisma's DSL can't call a JS function), but:
- `updateStatus()`'s existing inline booleans get replaced with calls to `isPayingRow()` (pays
  down the existing duplication, not just avoids new duplication).
- `reconcilePriceLedger()`'s widened guard calls `isPayingRow()`.
- `updateTenantClass()`'s compensating-entry boundary calls `isPayingRow()`.
- A new spec (`mrr-paying-predicate.parity.spec.ts` or folded into `mrr.service.spec.ts`) pins
  that `isPayingRow()`'s four conditions match `payingWhere`'s four conditions for a table of
  representative fixture rows — the practical version of L-167's "one shared builder" given a
  Prisma `where` object and an in-memory predicate can't literally be the same function
  reference.

## Red-first test plan

— the bug is already there), then the fix, then green:

1. **Item 1**: a `reconcilePriceLedger()` unit spec — a tenant with `planKey` set but

   rows (created while `class !== PRODUCTION`) flips into PRODUCTION — pin that **today**
   `ledgerAgg`-equivalent sum jumps by the full historical total with no compensating entry
   (red), then after the fix the compensating delta lands and nets to `priceTenant()`'s value
   (green). Likely needs a `.db.spec.ts` (real Postgres) to prove the `ledgerAgg` join behavior
   itself, not just the emit call in isolation — flagging that this item may need DB proof,
   which per the standing rule I post as NEED-DB and don't run myself.
3. **Item 3**: a `_formatTenant()`/`listTenants()`/`getTenant()` spec — a tenant with
   `Tenant.plan=PROFESSIONAL`, `subscription.planKey=null` (the exact B556 evidence shape) —
   pin that **today** the API response's `plan` field is the raw `"PROFESSIONAL"` (red), then
   after the fix it resolves through `resolveDisplayPlanKey()` (green). Pure unit-level (mocked

4. **Shared-predicate parity spec**: fixture table of tenant/planKey combinations, asserting
