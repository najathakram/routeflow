# B762/B785 contract: multi-order stop delivery payload (SA-093a)

**Payload shape** (unchanged wire shape, changed sending rule): `CompleteStopDto.deliveries` stays
`{ orderItemId, quantityDelivered }[]`. New rule — the client sends an explicit entry for **every
order-item on every order at the stop**, never omitting an order the driver actually handled.
Server-side (`assertDeliveriesFitStop` today just early-returns on an empty array and enforces
nothing about coverage): an order with **zero** entries in `deliveries` is read as **fully
UNDELIVERED** (SA-093a), not "assume delivered" (today's silent behavior via the stop-completion
status flip regardless of what — or whether anything — was sent for that order).

**Case 1 — all delivered**: every order-item, across every order on the stop, gets an entry at
`quantityDelivered = orderedQty` (full).

**Case 2 — one order entirely refused/skipped**: that order's items each get an _explicit_ entry
at `quantityDelivered: 0` (never simply absent from the payload — omission now means
"undelivered" server-side, so an accidentally-omitted order would already read correctly, but the
client must never rely on that: an explicit 0 is the only way to distinguish "driver refused this"
from "this order's data hadn't loaded yet").

**Case 3 — partial/mixed**: order A's items are all at full qty; order B has one short/refused
line (`quantityDelivered` reduced or 0) — order B's _other_ lines still get their own explicit
full-qty entries, never omitted just because one line in that order is short.

Client-side (B762): `payment.tsx`'s `closeStop` currently builds `reconciledFirst` only for
`orders[0]` and defaults every other order to full via a raw `o.lineItems` map — that raw-map
branch is the "one order entirely skipped" gap this fixes. The rewrite builds each order's own
delivery entries from that order's own (per-order-loaded) line items, defaulting an untouched
line to full — never omitting an order wholesale.
