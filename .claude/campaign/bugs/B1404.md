# B1404 · CSV import decode is lossy: a stray leading byte garbles the first header, and a parse error returns an empty file silently

**Location** `apps/api/src/import/import.service.ts (parseCsv, :290-310; 7 callers in the file)` · **Severity** medium · **Batch** F65 · **State** queued

## Summary

_Not yet analysed._

## What this feature is for

_Not yet analysed._

## Root cause

One lossy decode and a swallow-and-return-empty catch, repeated across 7 callers.

## User impact

_Not yet analysed._

## Fix approach and UX

One decode helper for all 7 callers: strip a leading 0xA0 or BOM from the header line only; refuse non-UTF-8 input with a clear 400 naming the byte offset; rethrow a parse error as a 400 with the record number. SA-1295's new legacy-import/parse/** does not reuse parseCsv and is not affected.

## Test plan

T2 red first on synthetic bytes: a 0xA0-led header, a 1252 byte in a name, and a malformed quote, each with its expected 400 or clean key.

## Reported evidence

(a) buffer.toString('utf8') with bom: true strips only a real BOM. A file whose first byte is a lone 0xA0 decodes to U+FFFD, so the first header key misses every lookup; on the invoice import every row becomes 'missing invoice id'. Executed on synthetic bytes (SA-1295 pack section 4). (b) A csv-parse error is logged and returns [], so the caller reports 0 rows instead of the parse error. (c) Any other non-UTF-8 byte becomes U+FFFD in names and descriptions with no warning.
