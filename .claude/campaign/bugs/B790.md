## Root cause

P1, from SA-104a's read (fleet lead filing request, 2026-09-23). Verified on origin/master 2ed80789: submitEntry (adjust.tsx :235) creates a change request (createCr) and then resolves it at the stop (resolveCr). On a resolve failure only the REGULATED-guard branch records createdCrId in blockedCrRef (:259-260) so the exits can decline it; CHANGE_REQUEST_ALREADY_RESOLVED returns true (:265); every other 409 (credit block, LINE_ALREADY_DELIVERED, STOP_ALREADY_COMPLETED, CHANGE_WINDOW_CLOSED, generic — and B753's coming 'cannot be merged at the door' refusal) just toasts and returns false, leaving the just-created CR PENDING after the BUYER WAS ALREADY NOTIFIED. processDiff then resumes at the SAME index on retry (:~288), so submitEntry creates ANOTHER change request — orphans accumulate. FIX: after any at-stop 409 other than ALREADY_RESOLVED, DECLINE the just-created CR with the server's reason (reuse the blockedCrRef/declineOrphanedBlockedCr pattern, :114-133), show the message, and never create a second CR on retry; key on the 409's stable code (SA-104a: B753's refusal carries a stable code). Also update the stale comment at :196-201 (it describes the server's ADD_ITEM merge as a raw piece delta, which B753/SA-104 changes). Ships AFTER B753's server refusal. Owner: R-ui (mobile), after B784/B788.
