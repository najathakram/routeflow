# B263 · Mobile order edit: price control lives inside the scan flow over a paused camera (B246 option B)

**Location** `Orders - mobile operator order edit (scan flow)` · **Severity** high · **Batch** F30 · **State** done

## Summary

Editing a scanned line's price on mobile required leaving the scanner entirely (5 taps, 2 camera lifecycles) because edit-items.tsx swapped the picker and the line list as mutually exclusive branches, so every price control was structurally unreachable from the picker. Fixed via #675 (f52005f3) by mounting PriceOverrideModal inside the picker branch over a paused, not torn-down, camera.

## What this feature is for

The mobile operator order-edit screen lets an operator scan barcodes to add lines to a draft order, and separately adjust a line's price (e.g. a negotiated price, mirroring web's inline price edit) without re-keying the order. The scan flow (ProductPicker) and the price-override control (PriceOverrideModal) are both pre-existing, separately-built pieces of the same screen.

## Root cause

edit-items.tsx:806 renders {showPicker ? <ProductPicker/> : <line list>} as mutually exclusive branches -- every price affordance (chip :937/:1279, margin-floor block :1220-1228, PriceOverrideModal :734-748) lives only in the line-list branch, so changing price mid-scan meant leaving the picker (killing the live camera, since BarcodeScanner's inline absoluteFill swap is not a Modal) and re-opening it afterward (cold start). A second, independent defect compounded it: BarcodeScanner (native :90-101, web :76-87) never rendered ScanFeedback.action, so the picker's scanner could never hand an ambiguous/create scan to onAmbiguous/onCreate; PriceOverrideModal also wrote the typed price unrounded (:1409) where web's PriceEditRow rounds.

## User impact

From a live scan, changing the just-scanned line's price and resuming scanning cost 5 taps and 2 camera lifecycles (close scanner, leave picker, price chip, Apply, FAB, cold camera) -- a friction tax on every price correction made mid-scan, on the operator's primary mobile-first surface. The unrounded price write (PriceOverrideModal :1409) was a latent money-math gap independent of the navigation cost.

## Fix approach and UX

Mount the same PriceOverrideModal inside the picker branch too (state pickerPriceEditItem), over the live camera paused via a new active prop threaded BarcodeScanner -> ScanCamera (active={!pickerPriceEditItem}) -- no remount, no track teardown. Apply routes through a new pure helper lib/price-override.ts applyPriceOverride(item, {unitPrice, reason}), which rounds with roundMoney and recomputes lineTotal via computeLineSubtotal (also fixes the list-branch modal's missing rounding); needsMarginAck is the same pure helper backing the margin-floor ack in both branches, and the picker strip's label derives from the same computeMarginFraction/classifyMargin calls DraftItemCard uses (round-3 light-loop fix) so the two surfaces cannot disagree on wording. BarcodeScanner now also forwards active to ScanCamera and renders feedback.action as a pressable pill (folded-in fix for the dead onAmbiguous/onCreate hand-off). Result: scan -> Edit price -> Apply -> scan next = 2 taps, 0 remounts (down from 5 taps / 2 camera lifecycles). No new gate: canEditPrice and tier/SPECIAL handling unchanged.
