## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** A business migrating in stages its catalogue through Settings → Migration → “Add products (CSV)”, and a spreadsheet-exported price of 1,234.56 commits at 1234.56 — the same guarantee F17 established for the Zoho/CSV importers.

**Actually does.** Two independent defects on one path. (1) parseProductsCsv splits each line with a bare line.split(",") and has no quoted-field handling, so an Excel export’s quoted "1,234.56" becomes two fields: the price cell is the fragment "1 and every subsequent column shifts by one, landing unit/category in the wrong fields. (2) Even unshifted, the API’s MigrationService.optNum does Number(v), and Number("1,234.56") is NaN, so the price is silently dropped to undefined. The staging step then reports success and the operator confirms a catalogue with wrong or missing prices.

**The gap.** F17 fixed exactly this bug class (B98) in import.service.ts, but the Migration Hub reaches the database through MigrationService, not through those importers — so the hub kept the defect while the batch that fixed it declared comma money handled. Nothing surfaces the loss: no warning, no skip count, and the confirm step is not transactional.

**Evidence.** Evidence · apps/web/app/(dashboard)/settings/migration/page.tsx parseProductsCsv (its own docstring admits “Naive comma split — a robust parser (quoted fields) is a follow-up”); apps/api/src/import/migration.service.ts optNum (Number(v)) and the pricePerUnit commit in the product committer; contrast apps/api/src/import/parse-import-number.ts (F17’s fix, used only by import.service.ts). Found by F17’s Fable final pass, 2026-08-31, master@26037bd4.

**Suggested fix (register).** parse quoted fields on the web side (a comma inside quotes must not split, "" is one literal quote — and drop cell()’s legacy outer-quote strip at the same time, or it double-strips and eats a trailing inch-mark, turning Pipe 2" into Pipe 2), and make the API tolerate the same money formats. ⚠️ A fix was attempted inside F17 and deliberately REVERTED — read this before retrying: routing pricePerUnit through a lenient parser changed a present-but-unparseable price ("n/a") from a loud products.create throw into a silent $0.00 commit, and parseFloat leniency admitted -$5 and 12abc — on a path that calls ProductsService.create() in-process, so the class-validator DTO never runs to reject either. An unpriceable row must be flagged or SKIPPED, never zeroed. Also note the exact Decimal string is currently passed straight to Prisma; round-tripping it through a JS number can emit exponential notation into a Decimal column. Proof needs an e2e (there is no web unit runner — campaign decision D1): upload a CSV with a quoted comma-thousands price and assert the staged price.
