# B841 · Inline-return approve() reverses the regulated ledger holding only the Return row lock, so it can double-book against a line's remaining; the lock families don't exclude each other

## Root cause

Fleet lead relay 2026-09-24 (Lane IR found it while building #1324); VERIFIED by the Mac Lead on origin/master 4b00381e. reverseReturnEntries (regulated-ledger.service.ts:683) takes no lock of its own; it reads the line's remaining balance (buildLineRemainingBalances) and books against it, so its caller's lock is the only serialisation. The live callers differ: inline-return CREATE takes the carrying Order ROW lock (SELECT … FROM "Order" … FOR UPDATE, inline-returns.service.ts:191) before reverseLedgerForReturn (:313); CANCEL does the same (:610) before unreverseReturnEntries (:650); but APPROVE of a held return (~:430-545) locks only the Return row (:516) and then reverses (:545), with NO Order lock. So two approvals on one order, or an approve racing a create/cancel, can read the same remaining and both book: an over-reversal in the regulated (filing) ledger. Separately, #1324's parked-reversal resolution took withAdvisoryLock(order-merge, orderId), an advisory lock that does NOT exclude a FOR UPDATE row lock; the Mac Lead asked the SA (SA-089a(c): take the SAME lock the live path takes) to confirm the resolution should take Order FOR UPDATE instead. Severity filed HIGH pending the SA's confirmation (the lead's first read was MED).

## Fix approach and UX

Proposed (SA to rule): approve() takes the carrying Order FOR UPDATE inside its tenantTransaction BEFORE reverseLedgerForReturn, in the same lock order as create/cancel (Order, then Return, or whatever order create uses, to avoid deadlock). Pin: a real-Postgres concurrency spec with two approvals on one order (and approve vs create) serialising, and Σ reversal ≤ the sale. Owner: unassigned (Lane IR owns the file's other work).

SA-139 (2026-09-24) CONFIRMED: approve() takes the carrying Order FOR UPDATE after its Return lock and before reverseLedgerForReturn, re-reading the items under the lock; real-Postgres two-approval pin. The companion SA-089b: #1324's resolution takes the Order row FOR UPDATE after its conditional claim, instead of the advisory lock (acyclic: resolution = Order only; cancel = Return → Order). Owner (fleet lead): Lane IR after #1324 and #1246, unless a lane frees up sooner.
