## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** A courtesy price an operator set by hand on a line is the agreed price for those goods; a buyer adding more of the product should not silently revoke it.

**Actually does.** The CUSTOMER branch re-prices every catalog line through resolveBuyerLinePrice and never reads the payload's unitPrice. So a MANUAL line at $4.00 (tier $5.00, qty 10) on the buyer's active order re-creates at $5.00 when the buyer adds 2 more — a $12.00 charge above the agreed price, with the MANUAL priceType and the override attribution erased.

**The gap.** Ignoring a client-supplied price is correct and deliberate (B13: a buyer must never set a price). The defect is that the branch cannot tell a client-supplied price from a STORED one, so it discards both. Pre-existing — the naive merge dropped the price too — but F06 routed this caller behind a module whose contract explicitly promises a merge is never where an operator's override disappears, so the mismatch is now written down in two places.

**Evidence.** Evidence · apps/api/src/orders/orders.service.ts, the CUSTOMER-branch catalog pricing block (resolveBuyerLinePrice, no read of item.unitPrice); apps/api/src/orders/merge-items.ts foldMergeItems R0/R11 price-survival contract; apps/api/src/buyer/buyer.controller.ts, the fold call site (carries the caveat in a comment). Sticky-upsell carry-forward does NOT cover this: getCustomerPriceHistory only returns previously invoiced prices, not an override on the current order. Found by F06's Fable final pass, 2026-09-01.

**Suggested fix (register).** Honour a STORED override on the buyer path — read the pre-edit line's priceType/unitPrice inside the branch and keep a MANUAL one across the re-create, exactly as the staff replaceAll block now does for a BOGO snapshot — while still never trusting a client-supplied unitPrice. The branch is in F07's file region, so it belongs to that batch or later.
