## Reported evidence

Partial, low. applyStopOutcomes builds its candidates (:35) and fills the outcomes map (:52-54) from the order status read BEFORE the transaction (routes.service.ts:2129-2136 completeStop, :2328 completeWithPayment); lockStopOrdersAndFit (apps/api/src/routes/complete-payment-reconcile.ts:29-42) takes the Order row locks but nothing re-reads the status for the outcome, and a guarded updateMany that matches 0 rows leaves the map entry in place. OUT_FOR_DELIVERY to CANCELLED is legal (apps/api/src/orders/order-status-transitions.ts:26) and cancelOrderInTx (apps/api/src/orders/order-cancel-tx.ts:97) checks nothing about a run or a stop, so the office can cancel while the driver close is in flight. A non-draft cancel marks every line CANCELLED and orderOutcomeAfterStop drops cancelled lines and returns DELIVERED when none are left (packages/pricing/src/delivery-plan.ts:593-603), so the customer gets a DELIVERED notice (notifyStopOutcomes :81-106) with the full pre-transaction Order.total (completeStop passes no totals; resolvePostReconcileOrderTotals :2559 finds no live invoice, the cancel voided them, and falls back to Order.total), and the dashboard socket (RouteRealtime.stopCompleted, filtered on the stale status) announces DELIVERED too. The database stays CANCELLED and no money or stock moves. A driver who sends quantity above 0 for that order gets a 400; one who sends 0 gets through. Fix: in applyStopOutcomes read the candidates status under the lock already held, build the set and the map from that, and pass the same set to stopCompleted. Source: bug hunt 2026-11-06, verify-api V1 (partial, read at 7be372afed).
