## Reported evidence

The Apply credit sheet (ApplyCreditSheet.handleApply, onError) toasts e?.response?.data?.message ?? e?.message ?? "Try again." verbatim (the comment says "surface them verbatim"). Two things reach the user: (1) the server message "Cannot apply credit note to invoice with status ${inv.status}" leaks the enum (for example "PAID"); (2) a timeout or no-response falls to the axios e.message instead of the unconfirmed-result sentence. The route (POST /credit-notes/:id/apply, apps/mobile/lib/api/credit-notes.ts:139) already returns coded refusals (CREDIT_NOTE_NOT_APPLICABLE, EXPIRED, INVOICE_NOT_APPLICABLE, CUSTOMER_MISMATCH, NOTHING_TO_APPLY: apps/api/src/credit-notes/credit-notes.service.ts:1058-1088) and fixed copy exists for all five and for the unconfirmed case (apps/mobile/lib/credit-note-error-copy.ts, creditNoteErrorCopy, "B921: the Apply refusals"); the web and mobile credit-note screens use it, this sheet does not. Impact is wording, not money: a re-tap after a committed apply is refused server-side. The same file has about 20 other raw data.message toasts (lines 276-1306) but only this one has a coded counterpart. Fix: showToast(creditNoteErrorCopy(e, "Try again.")) and drop the stale comment. Source: bug hunt 2026-11-06, verify-ui C-1 (confirmed, read at 7be372afed).
