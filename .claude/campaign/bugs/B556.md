## User impact

SEVERITY UPGRADE, DB-confirmed (Lane F, 2026-09-18): submitting the REAL tenants/new form (the primary/normal onboarding path, not just seeded or historical tenants) produces a tenant with TenantSubscription.planKey = NULL by default. This moves the bug from 'some historical tenants drift' to 'every new tenant is wrong until someone explicitly touches its plan' -- the default onboarding path itself generates a $0-MRR tenant. Repro: create any tenant via POST /platform-admin/tenants or the tenants/new form, check TenantSubscription for that tenant's id -- no row, or planKey: NULL. Severity field bumped high -> critical to reflect this is the DEFAULT path, not an edge case.

## Fix approach and UX

Fix landed (B707 lane, branch fix/b556-b557-mrr-plan-source-of-truth off origin/master b6e6bc7f, sha 14c9eb38, SA-140 verdict BUILD): _formatTenant() (backing listTenants()/getTenant()) gets a new planKey field via resolveDisplayPlanKey() -- subscription.planKey first, planKeyFromEnum(Tenant.plan) fallback -- fixing the exact evidence shape (Tenant.plan set, subscription.planKey null, shown as a paying customer via the badge alone). plan's own shape is unchanged (SA precision: don't change plan's shape, add planKey alongside it). listTenants()'s subscription select gained planKey (never fetched before -- L-169). Web: admin/tenants list + detail pages and AdminBadge's plan-variant callers now read planKey with a fallback to plan, same PR. Historical backfill for tenants already drifted before this fix is NOT included -- both records call that an owner decision. listTenants()'s filter/sort still operates on the raw legacy plan enum, not the resolved planKey -- a separate, real gap found while reading, flagged as a follow-up, not fixed here. Frozen, not pushed -- push on the Mac Lead's GO.

## Reported evidence

DB-verified (Lane F, 2026-09-18): Tenant.plan (legacy display field, what the admin UI's plan badge reads) and TenantSubscription.planKey (the field MrrService.priceTenant() actually gates MRR on) can drift. Any tenant onboarded outside the 'Change Plan' UI action has a real Tenant.plan value but no resolved planKey, so it reports $0 MRR forever while the admin UI shows it as a paying customer (e.g. a 'Business' plan badge). Prod has 26 tenants and shows MRR $0.00 -- if most never passed through that control, the platform revenue figure is structurally wrong. Evidence: e2e-routeflow tenant (Tenant.plan=PROFESSIONAL, TenantSubscription.planKey=NULL, contributes $0 permanently); the test tenant before/after a plan-change round-trip (EST. MRR $0 -> $499, planKey resolved PROFESSIONAL->SCALE per the legacy-label-to-catalog-key mapping); two real BillingEvent rows this created (plan.changed $0.00 for Enterprise's custom/no-catalog-price, then plan.changed $499.00 for SCALE's real price); dashboard MRR then read $499.00 reconciled to ledger $499.00, matching (this repro doesn't itself show a live-vs-ledger divergence -- that is a separate, still-open hypothesis being tested next on a throwaway tenant, may be filed as a follow-up). All repro against approved test tenants only (test, e2e-routeflow).
