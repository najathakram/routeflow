## Reported evidence

From SA-606s (#2554 5945656748), via Mac Lead; pre-existing on master; VERIFIED BY READING master's buyer.controller.ts (not executed). A buyer create with forceNew skips the active-order merge block (if (!dto.forceNew) at ~:535), creates a new order (~:710), and then ALWAYS runs the post-commit mergeAllPendingForCustomer sweep (buyerInitiated) and returns 'merged ?? created' (~:746). So a forceNew buyer, who explicitly asked for a NEW order, has it folded into the customer's other PENDING orders and the response can be a DIFFERENT order than the one created (and the merged quantity can earn BUY_N_GET_M free units). The existing spec claims 'forceNew skips the lock entirely: no merge' but only covers the pre-create lock, not this sweep. Fix to be ruled (SA): skip the sweep for forceNew, or return the created order explicitly. Medium, order integrity.
