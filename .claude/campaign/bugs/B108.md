## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** A credit note the operator attached to an order with an explicit amount is applied to the order's invoice at delivery, so the customer owes only the post-credit balance.

**Actually does.** If the Serializable settle transaction fails (40001/deadlock/timeout), delivery succeeds with only a warn; send() and sendEmail() both exclude explicit-amount credit ids from auto-apply, so nothing ever applies the credit.

**The gap.** The catch's justification comment is false: the claimed catch-up path deliberately excludes every credit the swallowed settle was responsible for.

**Evidence.** Evidence · apps/api/src/orders/orders.service.ts:2296-2307 (swallow + false comment); apps/api/src/invoices/invoices.service.ts:3384-3394 and 3558-3559 (explicitIds excluded in send and sendEmail); apps/api/src/credit-notes/credit-notes.service.ts:465,492 (notIn filter), 914-1000 (explicit-intent apply pass); only other settle callers: invoices.service.ts:1244, orders.service.ts:2017, 3563 — none re-run for a delivered drafted order.

**Suggested fix (register).** On settle failure, retry with backoff or enqueue a reconcile job instead of warn-and-drop; alternatively stop excluding an explicit intent from send()'s auto-apply when it has no matching CREDIT_NOTE payment yet (the settle clamp already makes re-application safe).

> ⚠️ Treat this as a hypothesis, not a plan. On F11 the adversarial pass refuted the
> suggested fix for every one of the four bugs while confirming every diagnosis.

**Verifier's note.** Not a duplicate of B85 (createPartialFromOrder never settles) but shares the same false assumption that send() catches up. Recovery today is manual: editing order items re-settles (orders.service.ts:3563), or the operator applies the credit by hand. Triggering requires the settle tx to actually fail, so it is contention/timeout-gated.
