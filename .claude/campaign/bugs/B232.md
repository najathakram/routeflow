## Reported evidence

The freshness guard compares each Jest/Playwright report's mtime against the current commit, so every merge commit and every squash invalidates every prior report and forces a full regen -- observed as 3 full Jest runs per bookkeeping landing (api + web, twice: once pre-merge on the fix branch, again on the docs follow-up branch). Proposal: key freshness on a content hash of the workspace's test files + the relevant ledger shards, recorded inside the report itself, so a commit that touches neither invalidates nothing -- only an actual test-file or ledger change would force a regen.

- 2026-11-10 · **note** · Swarm triage 2026-11-09, PARKED (lead ruling: its own future row, no fix tonight). The row's premise (merge-only commits make the report stale) is already handled: newestCommit() in scripts/campaign-check.mjs (~:532) uses git log -1 --first-parent over the test pathspecs, so a merge that touches no input is pruned. The real trigger is any PR merge that DOES touch test files: its committer time becomes the cause and is newer than a report generated on the PR branch, although the content is identical. Time keying cannot tell same content from new content. Design for the future row: scripts/jest-campaign-reporter.cjs (~:121) stamps the report with a hash of the workspace test-input tree (git ls-tree or content hash over the same pathspecs) plus the ledger shards; campaign-check compares that hash instead of time in all three places (~:561, ~:854, ~:993), keeping the time check only as the fallback for reports with no hash (old reports); self-test fixtures updated (hash match = fresh, input edited after the report = stale, merge that changes no input = fresh). Spans reporter + campaign-check + fixtures, well over 60 lines, so it is not a swarm bug. <!--note-1794272638159-->
