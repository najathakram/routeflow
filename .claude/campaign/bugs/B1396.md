# B1396 · A staff payment can be recorded on a DRAFT invoice (201, and the status jumps to PARTIAL or PAID)

**Location** `apps/api/src/invoices/invoices.service.ts writeInvoicePayment (:4215); apps/api/src/invoices/invoice-send-guard.ts paymentRefusal (:75)` · **Severity** medium · **Batch** F65 · **State** queued

_Not yet analysed._

## Root cause

paymentRefusal has no DRAFT case; the web and mobile UI only hide Record payment on a DRAFT. Counter sale and pickup issue every invoice before recording payment, so one shared refusal is safe (SA-1299 3.1 step 0).

## User impact

_Not yet analysed._

## Fix approach and UX

SA-1299 3.1: ONE shared refusal in paymentRefusal for every writeInvoicePayment caller; INVOICE_NOT_PAYABLE with reason DRAFT, VOID or WRITTEN_OFF on both writers; STRIPE_SETTLE stays exempt; invoices.service.ts net 0 lines. Rides with the #4512 test-1a rewrite and the N3 toast copy (P4).

## Test plan

T1 red first: (a) DRAFT payment 400 INVOICE_NOT_PAYABLE reason DRAFT (today 201); (b) VOID and WRITTEN_OFF coded on both writers; (c) test-1a asserts the code and is red as a value diff when the guard is exempted; (d) the web toast shows its own sentence. Green guards: a counter sale and a pickup completion still record payment.

## Reported evidence

writeInvoicePayment refuses only VOID and WRITTEN_OFF. Staff POST /invoices/:id/payments on a DRAFT invoice returns 201 and the status jumps. The refusals for VOID and WRITTEN_OFF are uncoded 400s.
