## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** A workspace sees only the delivery products it signed up for: order_delivery puts Order delivery and Drivers under Dispatch, recurring_routes puts Routes and My Routes there, and a tenant holding both sees both. The platform-admin toggles are the control.

**Actually does.** Both client composition helpers read devMode || feature, so an active developer_mode addon unlocked BOTH delivery products regardless of the toggles &mdash; turning Recurring routes off in platform admin had no visible effect. Server-side there was no enforcement at all: /routes, /route-runs, /trips, /drivers and route-optimization carried only JWT + role guards, so the gate was cosmetic even where the UI hid it.

**The gap.** An admin reading the Addons & Features tab could not tell what a tenant would actually see, and the &ldquo;UI-only&rdquo; gate meant a hidden surface stayed fully reachable by direct API call.

**Evidence.** Evidence · Reported live on routeflow-demo (Order delivery ON, Recurring routes OFF, Developer Mode ON) which still rendered Routes under Dispatch. apps/web/lib/api/addons.ts + apps/mobile/lib/api/addons.ts (useRoutesAccess/useDeliveryAccess = dev.enabled || feature.enabled); apps/web/app/(dashboard)/layout.tsx (nav filter + RouteGuard GATED_PREFIXES); apps/api/src/routes/routes.controller.ts, trips.controller.ts, drivers.controller.ts, route-optimization.controller.ts (JwtAuthGuard/RolesGuard only, no addon guard); apps/api/scripts/demo-seed.js (feature addons upserted with update: { active: true }, so a reseed re-enabled what an admin had turned off).
