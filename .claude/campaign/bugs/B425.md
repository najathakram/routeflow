## Reported evidence

snapshotKey = editItemsSnapshotKey(id, userId) is computed at render time; on cold open/deep link userId is undefined until auth resolves (the screen's own comment at :522 says so), so the restore effect at :429 (AsyncStorage.getItem(snapshotKey), deps=[snapshotKey]) fires FIRST against the anon-prefixed key, then fires AGAIN once userId resolves and snapshotKey changes to the real user-scoped key. The WRITE path is guarded (:525 returns early while userId==null), but the READ is not -- if a stale or another-session's anon-scoped snapshot exists, it can populate the screen briefly before the correct user-scoped read overwrites it moments later. Follow-up: guard the read effect the same way the write effect already is (skip AsyncStorage.getItem until userId has resolved, or never write/leave a readable anon-scoped snapshot in the first place once the store migrates per B424).
