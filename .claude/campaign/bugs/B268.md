# B268 · Fallback CSV importer mints INV-<year>-#### from a local seq=1; collision is swallowed as a per-row import error

**Location** `Import - fallback invoice importer` · **Severity** medium · **Batch** F31 · **State** done

## Summary

Refuted as filed - no P2002 ever throws. The fallback mint collides with a live invoice number and the importer silently UPDATES that unrelated invoice's status/dueDate/paidAt, reporting it as updated - a worse defect than filed.

## What this feature is for

CSV invoice import. Rows with no source Invoice Number get a synthesized fallback number so the invoice can still be created.

## Root cause

import.service.ts's local seq counter starts at 1 every run instead of reading the tenant's true max. The resulting collision with an existing INV-<year>-#### hits the existing-invoice branch first, which updates that live invoice instead of erroring - a silent cross-document data corruption on a money object, not a swallowed error.

## User impact

A fallback-numbered import row can silently overwrite the status, due date and paid-at of an unrelated live invoice; the import report shows a clean updated count with no error signal.

## Fix approach and UX

Fallback rows (no source number) reserve via NumberingService.reserveNext(INVOICE, { year, tenantId }) standalone, per row. Rows carrying a source Invoice Number keep it verbatim and alone use the existing-invoice update branch. The class docblock gets an amending clause distinguishing no-source-number (a live mint) from has-source-number (a preserved import).

## Test plan

DB-lane import-numbering.db.spec.ts (REG-B268 A/C/D): fallback rows reserve fresh numbers and leave the live invoice untouched; re-importing the same source-numberless PAID row twice does not double-book AR; a numberless row and a source-numbered row in the same file each land correctly regardless of order. Green-only sibling pin: source-numbered rows still keep their original number.

## Reported evidence

F16b/B100 cause refutation + engine final pass, 2026-09-08: the fallback importer's invoice-number mint (import.service.ts:541 let seq = 1; :631 invoiceNumber = first["Invoice Number"] || `INV-${year}-${String(seq++).padStart(4,"0")}`) never reads the tenant's existing max INV-<year>-* the way the real mint sites do - every run starts counting from 0001. A fallback import (rows with no "Invoice Number" column) into a tenant that already holds INV-<year>-0001 throws P2002 on the first synthesized number; caught and swallowed as a per-row import error at :807 (this.pushRowError(errors, invoiceNumber, e)) rather than surfaced as a numbering problem - the row fails with no signal that renumbering, not bad data, was the cause.
