## Reported evidence

Two independent failure directions from the same root cause: merged-detection decides 'merged' by ancestry (is the branch head an ancestor of origin/master), which is the wrong test on a repository that squash-merges everything. Direction 1 (over-removal, found first tonight): a merged-and-clean worktree with a live prover process rooted in it still got ranked among the top reclaim actions -- git calls the tree clean, but nothing checks for a process cwd'd inside it. It also only enumerated routeflow-clean's worktrees, so a live tree in the routeflow checkout was safe by accident. Passing --target made the planner reach for the biggest object rather than the safest, widening eligibility rather than just ranking within it. Direction 2 (under-removal, found later, more damaging because it's silent): because this repo squash-merges, a landed branch's head is NEVER an ancestor of master post-merge, so the ancestry check is effectively dead for the common case. Seven worktrees were protected as 'branch not merged' including rf-lane-b707, whose PR #1245 merged hours ago at f10bf3b5 and whose branch is already deleted from origin. Fix for both directions: drop ancestry entirely. Query the pull request's actual state via the GitHub API, or compare tree/content, never commit ancestry -- the same remedy in both directions, and the same trap the inline-returns mobile lane will hit when it rebases after #1250 squashes onto master (its branch head will also never be an ancestor). Guard for direction 1: before proposing 'remove whole worktree', require no process cwd inside the tree, no recent mtime inside, no keep-marker, and enumerate every checkout on the box, not just one. A --target size parameter must rank among already-eligible actions and never widen eligibility. Report-only (the current default) is why direction 1 never actually deleted anything -- that discipline is why report-only should stay the default until both directions are fixed. With 30.6 GB free tonight there is no pressure to apply anything.
