## Reported evidence

A DRAFT PO edited once, re-opened, then edited again touching only a plain (non-boxed) line is rejected by the API with: 'items.1.property caseCost should not exist; items.1.property cases should not exist; items.1.property loosePieces should not exist; items.1.qtyOrdered must not be greater than 9999999'. Item 1 is the OTHER, untouched boxed line -- the client round-trips it back to the server carrying case-shape fields (caseCost/cases/loosePieces) it should not have, plus a malformed qtyOrdered value. The user sees a generic 'Couldn't update the purchase order.' and nothing partial lands -- the whole save is rejected, so this is a blocked-save bug rather than a silent-corruption one, but it is the same family as B689: an untouched line's state does not round-trip cleanly between the stored shape and the shape the client sends back on save. Found by Mac F2 during the Release 1 RC proof on a test tenant. Disposition: fast-follow, not release-blocking, per the lead's ruling alongside B689 -- untraced cause, not fixed same-day.
