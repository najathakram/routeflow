## Fix approach and UX

PR #899 (2026-09-18) added a client-side warn-and-confirm on the Feature Console 'Enable as add-on' path (EnableAddonModal.tsx) when driver_payments' requires (recurring_routes/order_delivery) is unmet -- the check reads FEATURE_REGISTRY[key].requires, not a hardcoded key list. This is a PARTIAL mitigation only, NOT a closure: still open per the commit's own scope note -- (1) server-side enforcement in AddonService.enableAddon / FeatureOverrideService.create is untouched, still accepts an invalid grant from any other caller (tracked as B524); (2) FeatureOverridesSection's '+ New Override' GRANT form can also satisfy the guard and is not covered; (3) the reverse direction (a prerequisite later removed from a tenant that already has driver_payments) triggers no warning. Keeping state uncampaigned -- do not close B519 on this PR alone.

## Reported evidence

The feature registry declares driver_payments requires anyOf [recurring_routes, order_delivery], but nothing enforces that dependency client-side: the legacy toggle card and the new Feature Console 'Enable as add-on' modal both POST /platform-admin/tenants/:id/addons/enable for driver_payments unconditionally, with no check for whether the tenant already holds one of its two prerequisite addons. A super-admin can enable driver_payments alone, leaving the tenant billed/flagged for at-door payment collection with no route surface (Dispatch or Deliveries) where a driver would ever reach the gated endpoint (POST /route-runs/:id/stops/:stopId/complete-with-payment). Pre-existing behavior, carried forward unchanged by B2b (PR #872) rather than introduced by it -- found during that ticket's B2b/ticket-4 analysis, filed per lead allocation.
