# B157 · A removed customer stays on scheduled routes and is still dispatched to a driver

**Location** `Routes · route stops + dispatch run` · **Severity** medium · **Batch** F15 · **State** in-flight

## Summary

PARTIALLY FIXED by PR #693 (692bdf8): the dispatch half — createRun (apps/api/src/routes/routes.service.ts:808-836) drops a removed customer's stops in the query, so no RouteRunStop and no swept order, with a warn and spec REG-B131 T15. Still open at master@2d35375, the planning half: RouteStop / RouteCustomer rows survive (by design, restore-symmetric) and every planning read renders them as live — findOneRoute :192-204 selects only `{ id, businessName }`, getPackingList :628-658 sweeps the removed customer's PENDING/CONFIRMED orders into the manifest, getCustomerRouteAssignments :704-728 counts them as assigned (feeds B156 and the "Currently in" hint), the optimizer / analysis includes (route-optimization.service.ts:418, :628; route-analysis.service.ts:48, :225) route through the ghost stop, and addStop :450-487 never looks the customer up at all. Re-scope B157 to those reads plus a "Removed" badge; with no driver dispatched any more, medium is generous — low would also be defensible.

## What this feature is for

After Remove, the customer stops appearing on route planning surfaces (route detail / builder, map, packing list, optimizer, the "Currently in" hints) and is never handed to a driver as a stop. Restore should put them back on their routes with no other write, so the stop rows themselves are kept and the reads carry the signal.

## Root cause

Verified at master@2d35375. FIXED by #693: createRun's route include filters `stops: { where: { OR: [{ customerId: null }, { customer: { deletedAt: null } }] } }` (:817-820) and the order sweep runs off run.stops, so a removed customer gets neither a RouteRunStop nor an order on the run; a suppressed count is warned once per dispatch (:828-836); routes.service.spec.ts:859 covers it. STILL OPEN: (1) customers.service.ts soft branch :2044-2047 leaves RouteStop / RouteCustomer rows (the hard branch :2141+ deletes them) — correct for restore symmetry, so the reads must carry the signal; (2) findOneRoute :192-204 `customer: { select: { id, businessName } }` — no deletedAt, so web and mobile route pages show the stop as live; (3) getPackingList :628-658 builds `customerIds` from ALL stops (:640) and pulls their open orders (:642-658); (4) getCustomerRouteAssignments :704-728 has no customer filter, so a removed customer reads as assigned; (5) addStop :450-487 writes `routeStop.create({ customerId: dto.customerId })` with no customer lookup — a removed (or nonexistent) customer can be added, only the FK stands in the way; (6) route-optimization.service.ts:418 / :628 and route-analysis.service.ts:48 / :225 include stops with no deletedAt. Class: the same soft-delete filter omission as B131 / B141, on the read side; the report's line numbers have drifted (was :167-179 / :787-791 / :896-953) and are re-anchored above.

## User impact

Post-#693 no driver is sent to a removed customer, so the original "wasted stop" cost is gone. What remains is planning noise: the stop sits on the route page and map with no signal, the optimizer sequences around it, the packing list tells the warehouse to pack the removed customer's still-open orders, "Unassigned only" and the "Currently in" hint treat them as assigned, and an operator can add a removed customer to a route by id. Frequency: every removed customer that was on a route, until someone deletes the stop by hand; cost: confusion and mis-packed goods — no wrong document, no wrong money.

## Fix approach and UX

Keep the rows (matches #693's stateless rule). (a) Select `deletedAt` in the stop→customer selects at findOneRoute :198, getPackingList :633, route-optimization :420 / route-analysis :50, and surface `customer.deletedAt` in the route response; the web route detail / builder and mobile (operator)/routes/[id].tsx grey the row with a "Removed customer" badge and keep "Remove stop" available. (b) getPackingList: filter the stop list with the same `OR [{ customerId: null }, { customer: { deletedAt: null } }]` createRun uses — extract that where to one named constant in routes.service.ts and reuse it in createRun, getPackingList and the optimizer loads, so the three cannot drift. (c) getCustomerRouteAssignments: add `customer: { deletedAt: null }` to its where (:711) — this is also B156's predicate, so land the two together. (d) addStop: `customer.findUnique({ where: { id: dto.customerId, deletedAt: null }, select: { id: true } })` → NotFound "Customer not found" (the shape #693 used for the create doors — no state leak). UX consequence: a removed customer's stop is visibly dead but recoverable; restore un-greys it with no write; the packing list and optimizer stop seeing it. Structural: same `soft-delete-omission` signature as B131 — a stop→customer select without deletedAt is exactly the pattern a schema-derived rule catches.

## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** After Remove customer, the customer stops appearing on route planning screens and is not handed to a driver as a stop.

**Actually does.** RouteStop and RouteCustomer rows survive the soft delete, the route detail renders the stop with no deletion signal, and createRun copies every route stop onto the new run and sweeps the customer's open orders onto it.

**The gap.** The hard-delete branch clears the three route tables; the soft-delete branch clears none, and nothing in the routes module reads deletedAt.

**Evidence.** Evidence · apps/api/src/routes/routes.service.ts:167-179 (the stop include selects only id and businessName), :787-791, :896-905 (every route stop mapped 1:1 onto the run), :922-953 (the order sweep filters on customerId, status and fulfilPath only); apps/api/src/customers/customers.service.ts:1880-1882 (the hard branch deletes routeRunStop/routeCustomer/routeStop) vs :1786-1792 (the soft branch does not); grep deletedAt across apps/api/src/routes/*.ts returns no matches.

**Suggested fix (register).** Delete or flag the customer's RouteStop and RouteCustomer rows in the soft-delete transaction, and have the route read select customer.deletedAt so the route builder can badge a stop whose customer was removed.
