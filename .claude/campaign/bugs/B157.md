## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** After Remove customer, the customer stops appearing on route planning screens and is not handed to a driver as a stop.

**Actually does.** RouteStop and RouteCustomer rows survive the soft delete, the route detail renders the stop with no deletion signal, and createRun copies every route stop onto the new run and sweeps the customer's open orders onto it.

**The gap.** The hard-delete branch clears the three route tables; the soft-delete branch clears none, and nothing in the routes module reads deletedAt.

**Evidence.** Evidence · apps/api/src/routes/routes.service.ts:167-179 (the stop include selects only id and businessName), :787-791, :896-905 (every route stop mapped 1:1 onto the run), :922-953 (the order sweep filters on customerId, status and fulfilPath only); apps/api/src/customers/customers.service.ts:1880-1882 (the hard branch deletes routeRunStop/routeCustomer/routeStop) vs :1786-1792 (the soft branch does not); grep deletedAt across apps/api/src/routes/*.ts returns no matches.

**Suggested fix (register).** Delete or flag the customer's RouteStop and RouteCustomer rows in the soft-delete transaction, and have the route read select customer.deletedAt so the route builder can badge a stop whose customer was removed.

> ⚠️ Treat this as a hypothesis, not a plan. On F11 the adversarial pass refuted the
> suggested fix for every one of the four bugs while confirming every diagnosis.

**Verifier's note.** Downgraded from High: no financial record is created and the stale stop is plainly visible by name on the route page before Dispatch, so the operator has a checkpoint the crons do not give. Real, but the blast radius is a wasted driver stop rather than a wrong document. The register's existing route-delete entry (B96) is about hard-deleting a route with delivered runs — a different bug.
