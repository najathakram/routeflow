## Root cause

Seen by F2 on the mini, 2026-09-23: the full test:db at #1310's 1c615285 was 40/41 suites, with 6 failures all in publish-and-repin.db.spec.ts (D5 'confirmation text did not match' expected, got empty stderr; D6/K3 exit expected 0, got 3; D7/D9 +12 unexpected rows). The same file ALONE at the same sha: 13/13 PASS twice. Mechanism (Mac Lead, from the log plus the script): exit 3 with EMPTY stderr is the --only-test-tenants refusal (~:880-890), which reports via say() on STDOUT and refuses when ANY applicable loss in the WHOLE DB targets a non-test slug. So under --maxWorkers=2 another DB spec's non-test-slug tenant with plan losses was alive at that moment. The spec's docstring claims robustness to other tenants, but this refusal is DB-global. Fix options: scope the spec's --apply to its own tenants (a --tenant filter), have every DB spec create only test-pattern slugs (qa-*/e2e-*) and assert that in a shared helper, or mark this file serial (runInBand / its own jest project). Also consider printing the refusal on stderr. Owner: unassigned; the fleet lead routes it.

Raised to HIGH by the fleet lead 2026-09-24: it recurred 2/2 at --maxWorkers=2 on #1321's landing proof (b10c280b; K3 'Expected 0, Received 1', a different extra-keys diff each run), isolated 13/13 both times, and --runInBand 239/239 clean. It makes every full DB-lane proof at the standing worker count unreliable. Owner: Mac F2 prover. Done = a fix plus 3 consecutive clean full runs at maxWorkers=2.

## Fix approach and UX

Fix (B707 lane, branch fix/b824-publish-repin-k3-flaky off origin/master b6e6bc7f): added --only-tenants <comma slug list> to publish-and-repin.mjs, narrowing computeDiff()'s Tenant query to an explicit slug allowlist (in addition to the existing class='PRODUCTION' AND deletedAt IS NULL filter); never printed to stdout (NO PII rule unaffected). publish-and-repin.db.spec.ts's runCli now bakes --only-tenants <its own 3 e2e-pr0b-* slugs> into every single CLI invocation it makes (report, apply preview, and apply --live alike), so this spec's reads/writes are fully independent of whatever else the shared compose DB is running under --maxWorkers=2 -- no more whole-database scan for it. --only-test-tenants stays as defense in depth on every --live call (now effectively a no-op safety net once scoped, never refusing on a foreign tenant again). applyLiveWithRetry's retry-on-phrase-mismatch loop is unchanged, kept as defense in depth, though the stale-count drift it was built for should no longer occur once scoped. Verified without touching any DB: node --check syntax, tsc --noEmit (apps/api), npm run lint -w apps/api (0 errors), prettier --check, and the new flag's own argument-parsing paths exercised directly (empty-list refusal exit 2, valid list passes through to a real connection attempt, mutual-exclusion with existing flags unaffected) -- all exit codes/messages as expected. Per the assignment I do NOT run DB specs myself; F2 proves it with 3 consecutive clean full test:db runs at --maxWorkers=2. F2's diagnostic head start (#938 comment 5808219427) and the Mac Lead's follow-up (the leaking ~7-key pool spans different concurrent specs, not one culprit) both confirm the fix targets the right mechanism: isolating this spec from ANY foreign tenant, not chasing one.
