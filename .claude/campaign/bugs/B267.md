# B267 · Credit-note numbering (nextCnNumber) is cross-tenant on a raw tx, same 9999 wall B100 fixed for invoices

**Location** `Finance - credit notes (nextCnNumber mint)` · **Severity** high · **Batch** F31 · **State** done

## Summary

nextCnNumber is a hand-copied max+1 scan. On a null-tenant request it reads the unwrapped Prisma client and mints across tenants; the same TEXT lexicographic sort caps the series at 9999.

## What this feature is for

Mints the customer-visible credit-note number (CN-<year>-####) when a credit note is created.

## Root cause

tenantTransaction() returns the raw unwrapped client when getTenantId() is falsy (prisma.service.ts:60), so nextCnNumber's findFirst/orderBy-desc scan has no tenant filter; the padStart(4) lexicographic sort pins the wall at 9999. The create tx is SERIALIZABLE, so an in-tx reservation aborts under concurrency (P2034) rather than waiting.

## User impact

A super-admin token (null tenant) can mint a credit-note number that collides with another tenant's; a tenant past 9999 in a year gets a permanent 500 on every credit-note create.

## Fix approach and UX

Widen NumberingService's YearScopedDocType/findTaken/scanMaxForYear with a literal CREDIT_NOTE branch (no data-driven map). credit-notes.service.ts reserves via reserveNext(CREDIT_NOTE, { year, tenantId }) standalone, hoisted above the SERIALIZABLE tx, tenantId explicit from the caller's context (null throws); P2002 mapped to 409.

## Test plan

DB-lane credit-note-numbering.db.spec.ts (REG-B267 A-G): null-tenant refusal, 9999 wall now mints, lazy sequence seed continues correctly, validate-before-reserve burns no number on rejection, 5 parallel creates all succeed distinctly, collision guard skips a taken number, cross-tenant customer lookup 404s with no number burned.

## Reported evidence

F16b/B100 cause refutation + engine final pass, 2026-09-08: nextCnNumber (credit-notes.service.ts:34-43) is a hand-copied max+1 generator in B100's diagnosed shape - db.creditNote.findFirst({ where: { creditNoteNumber: { startsWith: prefix } }, orderBy: { creditNoteNumber: "desc" } }), no tenantId filter of its own, relying entirely on db being tenant-scoped. Its caller passes tx from this.prisma.tenantTransaction(...) (credit-notes.service.ts:102 into :244). prisma.service.ts tenantTransaction (:48-62): when getTenantId() is falsy, it returns fn(rawTx) - the UNWRAPPED client, skipping _wrapTxWithTenant (:60 if (!tenantId) return fn(rawTx)). On that path nextCnNumber scans creditNoteNumber across every tenant, and the same padStart(4) + lexicographic desc sort B100 diagnosed pins the series at CN-<year>-9999. Fix: route through NumberingService.reserveNext(docType: CREDIT_NOTE) (numbering.service.ts - CREDIT_NOTE is already a DOCUMENT_NUMBER_TYPES member) like F16b is wiring invoices/estimates, rather than patch nextCnNumber in place.
