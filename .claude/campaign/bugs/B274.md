## Reported evidence

F16b/B100 cause refutation + engine final pass, 2026-09-08: runCreation (invoices.service.ts:1230-1252) mints one baseNumber via generateInvoiceNumber(db) (:1222, itself B100's diagnosed generator) then derives every sibling as ${baseNumber}-R${i} (:1234) with no existence check of its own before tx.invoice.create (:1235-1250) - it relies entirely on the base number itself being free; a P2002 on the base self-heals (B100's evidence notes the create path's P2002-to-409 retry), but nothing re-checks or retries a specific -R{i} suffix. If any out-of-band row already holds <baseNumber>-R1 (a prior partial run, a manual insert, an import) the base mint can still succeed while the first sibling's create throws unhandled, wedging the whole split-invoice batch with a 409 that a base-number retry cannot clear.
