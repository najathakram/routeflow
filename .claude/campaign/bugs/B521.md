# B521 · Order edit-mode line-item name column starves to unreadable width at 390px

**Location** `apps/web/app/(dashboard)/orders/[id]/page.tsx` · **Severity** medium · **State** uncampaigned

## Summary

The order-detail page's edit-mode line-item row (apps/web/app/(dashboard)/orders/[id]/page.tsx:1237-1330) renders a plain flex row for each editable line: product name (flex-1 min-w-0), Qty (a label wrapping a fixed-width number input), a live line-total price column (w-20 shrink-0), and action buttons (Substitute/Undo, content-sized). None of the non-name columns are flexible, so under viewport pressure flex-shrink has nowhere else to go — the name column, the only flex-1 element without a real minimum, gets crushed toward its min-w-0 floor. For an unlisted/custom item, the name is an <input> (also min-w-0 flex-1), so this manifests as a ~16-18px-wide, effectively empty text box at 390px, even though its scrollWidth (the full typed name) is over 700px.

## What this feature is for

The order-detail edit flow lets staff correct order line items before invoicing -- change quantity, substitute a product, cancel a line, or (for a non-catalog item) type a free-text custom name. It's a core operator screen, used on both desktop and, per this mobile-audit ticket, on-phone.

## Root cause

Distinct from B513 (page-level horizontal overflow from a fixed-width element wider than the viewport): this row has no fixed-width element wide enough to overflow the page. It's pure flexbox content starvation -- every column's rendered width is individually reasonable, but the accumulated non-flexible width (icon 32px + Qty ~93px + price 80px + action buttons ~80-120px + gaps) leaves too little of a 390px-minus-padding row for the one flex-1 column, and CSS flexbox's default behaviour lets a flex-1 item shrink all the way to its content's min-content size (or 0, with min-w-0) before any sibling gives up space.

## User impact

No functional access is broken -- the input is still focusable and editable, just visually unreadable. An operator on a phone correcting a custom-name line item cannot see what they typed or verify the existing name before editing it, which risks a wrong edit going out on an invoice.

## Fix approach and UX

Give the name column a real floor (min-w-[140px] instead of min-w-0) so flex-shrink can no longer crush it, and let something else yield the pressure instead: the outer row switches from a single unbreakable line (flex items-center) to flex flex-wrap, so Qty/price/action-buttons overflow onto a second line when the row is too narrow to fit everyone at once, rather than fighting the name column for the same line. No visual change at desktop widths (everything still fits on one line there). No copy change.

## Test plan

No dedicated unit/RTL test exists for this page (order-detail edit mode is proven via manual/Playwright touch-viewport passes in this mobile-audit batch, matching B513/B514's pattern) -- verified via tsc + eslint (both clean) and the same document.elementFromPoint()-style reasoning the sibling tickets used, applied to the measurements already captured for this ticket (scrollWidth 738px vs clientWidth 16px at 390px).

## Reported evidence

Flex row with no wrap: Qty (label+input), the price column (w-20 shrink-0), and action buttons all hold their content width, so the one flexible column (product name, flex-1 min-w-0) absorbs all shrink pressure. With a long custom item name the name input collapses to 16-18px wide (scrollWidth 738px vs clientWidth 16px) -- visually empty and unreadable. Content starvation, a different mechanism from B513's page-level overflow.
