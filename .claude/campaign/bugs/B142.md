# B142 · The mobile product picker offers deactivated SKUs, and no write path rejects them

**Location** `Products · mobile operator + API` · **Severity** high · **Batch** F20 · **State** done

## Summary

The manual product-picker (not the barcode scan path, which is already guarded) lets a driver/operator add a NEW order line for an archived product, because ProductPickerSheet never filters on isActive — web's equivalent picker already does.

## What this feature is for

_Not yet analysed._

## Root cause

ProductPickerSheet queries products without isActive: true, unlike web's SearchableProductPicker.tsx:117-122; 12 server write paths independently accept an archived product, and updateOrderItems already computes addProductIds for NEW lines only (orders.service.ts:3740-3761), giving a single hook point for a server-side guard.

## User impact

_Not yet analysed._

## Fix approach and UX

Reject NEW lines for an archived product at the interactive edges ONLY — updateOrderItems (via addProductIds), staff order create, buyer order create, invoice/estimate create from a controller request — with BadRequestException("Product <sku> is archived"); qty edits/removals of an EXISTING archived line keep working. Batch paths (recurring generation, estimate→invoice convert, templates apply) ALLOW and append a warning note on the document — billing must never pause on a catalog flag (would give the cycle back per REG-B106). Mobile: ProductPickerSheet passes isActive: true (web parity); stock-count/PO-receive/variant-parent callers keep the unfiltered query.

## Test plan

API unit pins REG-B142-A (new archived line -> 400), REG-B142-B (qty edit of an existing archived line OK), REG-B142-C (recurring generation with an archived SKU still bills and records the note). Mobile source-text pin REG-B142-D (ProductPickerSheet passes isActive: true).

## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** Deleting a product removes it from the catalog: it disappears from the buyer shop and from the places staff build orders and invoices, on every surface.

**Actually does.** Delete sets isActive:false. Mobile's shared ProductPickerSheet queries products with no isActive filter and renders no Inactive marker, and neither orders nor invoices validate isActive when a line is written.

**The gap.** An operator on a phone silently adds a deleted SKU to an order or invoice, and stock moves against a product the tenant removed.

**Evidence.** Evidence · apps/api/src/products/products.service.ts:1103-1112 (remove → isActive:false), :221 (the filter is applied only when asked for); apps/mobile/components/ProductPickerSheet.tsx:56-59 (useAdminProducts with no isActive), :125-151 (no Inactive pill); contrast apps/mobile/app/(operator)/products/index.tsx:386-390 (mobile's own list does render one) and apps/web/components/SearchableProductPicker.tsx:117, :311-314, :380-384; write paths: grep isActive in apps/api/src/orders/orders.service.ts returns only :93 (promotions) and zero hits in invoices.service.ts, with the line-build lookups selecting only pricing/unit fields (orders.service.ts:231-234, invoices.service.ts:324-331).

**Suggested fix (register).** Add an activeOnly prop to ProductPickerSheet (default true, passed false by the stock-count, PO-receive, vendor-bill and variant-parent callers) and render an Inactive pill when a row comes back inactive; belt-and-braces, reject isActive:false productIds in the order and invoice line-create/edit paths.

> ⚠️ Treat this as a hypothesis, not a plan. On F11 the adversarial pass refuted the
> suggested fix for every one of the four bugs while confirming every diagnosis.

**Verifier's note.** Caller list corrected and widened during verification: ProductPickerSheet has 10 call sites, not 5 (invoices/new.tsx:1556, invoices/[id]/edit.tsx:463, orders/[id]/edit-items.tsx:1885, standing-orders/new.tsx:174, NewOrderScreen.tsx:2202, products/stock-count/[id].tsx:565,575, purchase-orders/record.tsx:207, vendor-bills/scan.tsx:524, plus the inline-create sheet). That matters for the fix — the last four legitimately need inactive products, so a blanket isActive:true inside the sheet would regress them. Mitigating: remove() refuses while active order items exist, so a freshly deleted SKU has no open lines; the damage is new lines, not existing ones.
