# B452 · Platform email sender hard-codes wrong domain / no platform SMTP transport

**Location** `apps/api/src/email/email.service.ts:318,205; apps/api/.env.example:79` · **Severity** high · **State** uncampaigned

## Summary

Two related sender-identity defects in `EmailService`: (1) the tenant-branded SMTP From-address
fallback hard-codes `noreply@routeflow.app` — a domain RouteFlow does not own (the real domain is
`routeflow.info`) — whenever a tenant has a `businessName` configured but no explicit From-email
under Settings → Email; (2) the platform has no Google Workspace SMTP transport at all, only
per-tenant SMTP and platform Resend, even though the owner's actual platform mailbox is Google
Workspace (`noreply@routeflow.info`), not a third-party ESP.

## What this feature is for

`EmailService.send()` picks a transport (tenant SMTP → platform) and a From-identity for every
transactional email RouteFlow sends — invoices, verification, password resets, account-merge,
etc. The From-address must be a real, deliverable, domain-aligned address or the message either
bounces, fails SPF/DKIM alignment, or (worse) silently "succeeds" from an address nobody can
reply to.

## Root cause

`getTenantFromAddress()` (used when the tenant's per-tenant SMTP is configured but no
`smtpFromEmail` is set) special-cased the "businessName but no From-email" branch with a literal
string instead of deriving it from the platform's own verified `EMAIL_FROM` address — a
copy-paste-era placeholder that was never corrected to the real domain. Separately, the platform
transport was designed around Resend from the start (constructor only ever checked
`RESEND_API_KEY`), so when the owner's actual mail infrastructure turned out to be Google
Workspace, there was no code path for it — SMTP env vars existed only for per-tenant use.

## User impact

Any tenant that set a `businessName` in `TenantConfig` but never configured a From-email under
Settings → Email would have their per-tenant SMTP sends carry a From-address on a domain RouteFlow
doesn't control — at best a confusing display, at worst a bounce/spam-classification risk since
nothing can ever authenticate `@routeflow.app` for RouteFlow's actual domain. Separately, until
this fix, RouteFlow had no way to route platform-level transactional mail through the owner's
actual Google Workspace mailbox without also paying for/maintaining Resend.

## Fix approach and UX

(1) `getTenantFromAddress()`'s fallback now uses `"<businessName> via RouteFlow <address-of-EMAIL_FROM>"`
instead of the hard-coded literal. (2) `EmailService` gained a platform-SMTP transport
(`SMTP_HOST`/`SMTP_PORT`/`SMTP_SECURE`/`SMTP_USER`/`SMTP_PASS`), selected in the constructor
whenever `SMTP_HOST` is set — Resend remains available as an alternative when it isn't, and the
two are never both active for the same send. `.env.example`, `docker-compose.yml` (a local
`mailpit` catch-all under the `app` profile), and a new read-only `check-email-sender.mjs`
diagnostic were added alongside. No end-user-visible UX change beyond the sender identity itself.

## Test plan

`apps/api/src/email/email.service.spec.ts`: new describe blocks "sender resolver never hard-codes
a domain (B452)" (2 tests — tenant SMTP send with no fromEmail uses the platform address, and the
domain-less-tenant fallback), "platform SMTP transport (B452 owner ruling 2026-09-16)" (4 tests —

is configured. All 61 tests in the email module pass. Manually verified end-to-end against the
local docker-compose stack with `mailpit` as the SMTP target — see
`local-assets/email-proof-2026-09-16/`.

## Reported evidence

getTenantFromAddress() falls back to a hard-coded noreply@routeflow.app (wrong domain — RouteFlow's domain is routeflow.info) whenever a tenant has a businessName but no configured From email; .env.example's EMAIL_FROM default carries the same wrong domain. Additionally, the owner's platform mail is Google Workspace SMTP, not Resend, but EmailService has no platform-level SMTP transport — only per-tenant SMTP and platform Resend.
