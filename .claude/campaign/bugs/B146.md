# B146 · Skipping a customer's stop is invisible to their tracking card and never reconciles the order

**Location** `Route stops · API + buyer app` · **Severity** high · **Batch** F11 · **State** done

## Summary

Skipping a route stop writes one column and nothing else: `RoutesService.updateStopStatus` (apps/api/src/routes/routes.service.ts:1716-1762) ends at a lone `routeRunStop.update({ data: { status, driverNote?, arrivedAt? } })` — no linked-Order write, no `skipReason`, no gateway emit, no notification. The buyer's tracking card therefore keeps rendering "You're next on the route" (apps/mobile/app/(customer)/orders/[id].tsx:249-277) for a delivery that is never coming, because `stopStatus` is emitted at apps/api/src/orders/orders.service.ts:5353 and read by nobody. The adversarial pass REFUTED 1 of 3 lenses (verdict SURVIVES) and this analysis is adjusted for it: two claims in the investigation are wrong and change the fix — `reopenStop` explicitly accepts SKIPPED stops (routes.service.ts:2695-2697) and demotes DELIVERED/OUT_FOR_DELIVERY→CONFIRMED at :2775, so at the API level the order is not stranded "permanently" — **but B211's analysis refutes the "only until a human intervenes" half of that: no human can reach it.** The endpoint's only client is `useReopenStop` (apps/mobile/lib/api/routes.ts:674-683), its only caller renders the control exclusively for `s.status === "COMPLETED"` (apps/mobile/app/(operator)/route-runs/[id].tsx:461-463), and apps/web has no stop-reopen caller at all. A SKIPPED stop has no reopen affordance anywhere, so the intervention this sentence relied on does not exist in the product; and `SKIPPED → IN_PROGRESS` is a deliberate, tested allowance (routes.service.stop-state-guards.spec.ts:365-373), so a fix that demotes on skip without re-promoting on un-skip kills the buyer's 20s poll for good (apps/mobile/lib/api/buyer.ts:613-617 returns `false` for any status but OUT_FOR_DELIVERY/PARTIALLY_DELIVERED) and is worse than the bug.

## What this feature is for

The buyer order-tracking card is the customer's only window into a live delivery run: it shows which driver has the order, how many stops are still ahead, and the estimated arrival window, polled every 20s while the order is out for delivery. It exists so a buyer can stop calling the depot to ask "where is my order". The promise it makes — the order is on a truck and moving toward you — must break the moment that stops being true.

## Root cause

Defect class: **state-change-without-cascade**, paired with its read-side twin **emitted-but-unread-field**. Both live at HEAD 07cba140.

WRITE SIDE. `updateStopStatus` (routes.service.ts:1716-1762) is a pure column write. Its guards are all _entry_ guards — stop exists, run exists, driver ownership (:1733-1740), B71 from-COMPLETED conflict (:1746-1751), terminal-run conflict (:1754-1756) — and then :1758-1762 writes `{ status }` and returns. No Order row, no `skipReason` (a column F01 landed for exactly this batch, apps/api/prisma/schema.prisma:1245-1247, with zero writers and zero readers repo-wide), no `emitStopCompleted`, no `notifyEvent`. Its sibling `updateRunStatus` at least calls `emitDriverStatusUpdated` (:1458). Nothing downstream repairs it: `updateRunStatus`'s COMPLETED branch (:1419-1466) _requires_ every stop be COMPLETED or SKIPPED (:1424) — it observes the skip at the one moment reconciliation is trivial — and then writes only the run row.

READ SIDE. `getOrderTracking` (orders.service.ts:5301-5361) computes `stopsAhead` as `s.stopNumber < currentStopNumber && s.status === "PENDING"` (:5341-5343) — a position-only counter that never inspects the customer's own stop in any branch. It emits `stopStatus: stop.status` at :5353, and repo-wide the only occurrences of `stopStatus` in apps/mobile are two interface fields (lib/api/buyer.ts:597, lib/api/orders.ts:614). Zero reads. The card branches on `stopsAhead === 0` alone.

CORRECTION TO THE FILED MECHANISM: the register says the skip "leaves stopsAhead at 0". It does not — `stopsAhead` is 0 because every earlier stop is by then COMPLETED/SKIPPED (not PENDING); the skip itself contributes nothing. An _out-of-order_ skip (earlier stops still PENDING) renders "3 stops ahead of you", equally false. A fix that special-cases only the `=== 0` branch does not close the bug.

SIBLING SITES, same class, same file: `updateRunStatus` CANCELLED writes only the run row, stranding orders that still hold `routeRunStopId` so the dispatch sweep (:941-946, requires `routeRunStopId: null`) can never re-collect them (that is B129); `deleteRun` (:1343-1346) and `deleteRoute` (:563-566) null the pointers but never revert `Order.status`, which is worse than no cascade — the pointer is gone so nothing can reconstruct what the status referred to. Different domain, same shape: `returns.service.ts` `approve()`:206-212 / `reject()`:214-221 / `markInTransit()`:223-230 are each findUnique + a bare status update; `inventory.service.ts` `closePurchaseOrder()`:1263-1267 has no existence check and no short-receipt reconciliation. Paired dead-producer siblings: `emitStopCompleted` (gateways/routeflow.gateway.ts:209) and `emitLowStock` (:221) have zero callers repo-wide; `NotificationEvent.FAILED_DELIVERY` is fully configured (messaging-config.service.ts:22/66/84) with zero automatic firers — a skip is precisely a failed delivery.

NEW DEFECT FOUND IN THE SAME METHOD, worse consequence: routes.controller.ts:249-259 types the body as a bare inline TS type `{ status: "IN_PROGRESS" | "SKIPPED"; driverNote?: string }` with no DTO class. The global ValidationPipe (main.ts:193-197) skips validation when the metatype is plain `Object`, and `updateStopStatus` guards only the FROM-state, never the TO-state — so an OPERATOR or the run's assigned DRIVER can `PATCH {"status":"COMPLETED"}` on a PENDING stop and mark it delivered with no DeliveryMutation, no POD, no regulated-delivery gate, no idempotency and no order cascade.

## User impact

Reachable today on the live operator surface, not a hypothetical. `PATCH /route-runs/:id/stops/:stopId` is wired to `useUpdateStopStatus` (apps/mobile/lib/api/routes.ts:374-382) whose only caller is `handleSkip` on apps/mobile/app/(operator)/route-runs/[id].tsx:164-182 — a "Skip stop?" confirm dialog that is NOT dev-gated (the devMode gate in apps/mobile/app/_layout.tsx:174-188 fires only for `activeRole === "driver"`). The buyer half is equally live: `/buyer/orders/:id/tracking` (buyer.controller.ts:502-517) delegates to the same `getOrderTracking`, and _layout.tsx:76-80 routes an authenticated buyer straight into `(customer)`.

Who hits it: every buyer whose stop is skipped — the daily case is a closed shop, nobody at the door, or a full truck. Frequency scales with route density; on a 20-stop run a single skip is one affected customer per occurrence, and skips are routine ops, not exceptions. What it costs: the buyer's card affirmatively tells them "You're next on the route" while the truck drives past, so they wait, then call the depot — the exact call the feature exists to prevent, now with the vendor's own app as the source of the false promise. The 20s poll (buyer.ts:613-617) keeps refetching indefinitely and `trackingStepIndex(order.status)` (orders/[id].tsx:235) pins the step bar on "Out for delivery" forever, so the lie is durable across app restarts, not a transient stale render.

Severity evidence, with the refuted lens's correction applied: the order is NOT permanently stuck — `reopenStop` (routes.service.ts:2696, :2775) and the `changeStatus` matrix (orders.service.ts:2441) both allow OUT_FOR_DELIVERY→CONFIRMED. But every existing exit is operator-initiated and nothing surfaces the need for it: no notification, no gateway event, no ops alert. The order sits mis-stated until a human happens to notice, which is a workaround, not a guard. Two aggravating amplifiers: (1) `Order.status` never moving means the order is invisible to reporting-by-status and to any redispatch triage; (2) B34 (the driver's own "Skip stop" button is dead at apps/mobile/app/(driver)/route/stop/[stopId]/index.tsx:330-341 — `confirm()` whose onConfirm only calls `router.replace`) is in this same batch, so the moment B34 lands the blast radius multiplies from one operator screen to every driver on every run. B146 and B34 are coupled and must ship together.

## Fix approach and UX

Four parts. Parts 1 and 2 are inseparable — shipping the write-side demotion alone introduces a new defect.

1. WRITE SIDE — cascade both directions. In `updateStopStatus` (apps/api/src/routes/routes.service.ts:1716-1762), wrap the stop write in `tenantTransaction()` and, when `dto.status === "SKIPPED"`, also persist `skipReason` (schema.prisma:1245-1247, currently dead) and demote the linked order from OUT_FOR_DELIVERY to CONFIRMED. **Then do the reverse**: on `SKIPPED → IN_PROGRESS` (a documented, tested allowance — routes.service.stop-state-guards.spec.ts:365-373) re-promote the order to OUT_FOR_DELIVERY and clear `skipReason`. Skipping this half permanently kills the buyer's poll, since `useBuyerOrderTracking`'s `refetchInterval` (apps/mobile/lib/api/buyer.ts:613-617) returns `false` for anything other than OUT_FOR_DELIVERY/PARTIALLY_DELIVERED, so the card could never recover when the driver comes back and delivers. Do not route the order write through `changeStatus` (it re-runs the notification map at orders.service.ts:2682-2738 and would double-fire); write it directly, as `completeStop` does at :2130-2135, and fire the signal explicitly.

2. READ SIDE — guard on own-stop status, never on order.status. `getOrderTracking` (apps/api/src/orders/orders.service.ts:5301-5361) early-returns only on `!order.routeRunStop` (:5330-5332), so a demoted CONFIRMED order still linked to its stop keeps returning non-null tracking with `runStatus: "IN_PROGRESS"`, the mobile block at orders/[id].tsx:251 keeps rendering, and the `order.status === "CONFIRMED"` fallback at :276 stays unreachable. So the card must branch on `stopStatus`. Extract a pure `trackingLine({ runStatus, stopStatus, stopsAhead })` into apps/mobile/lib/order-tracking-logic.ts (which already exports `trackingStepIndex`) and consume it at orders/[id].tsx:256-262. Order of precedence: `stopStatus === "SKIPPED"` wins over any `stopsAhead` value — this is what closes the out-of-order-skip case that a `stopsAhead === 0` special-case would miss.

3. VALIDATION — create apps/api/src/routes/dto/update-stop-status.dto.ts (it does not exist today) with `@IsIn(["IN_PROGRESS","SKIPPED"])` on `status` plus an optional `skipReason`, and use it at routes.controller.ts:255 in place of the inline `@Body()` object type. The DTO is needed anyway to carry `skipReason`; pinning the enum there closes the `{"status":"COMPLETED"}` injection for free.

4. OPS SIGNAL — fire `NotificationEvent.FAILED_DELIVERY` on skip. It is fully configured (messaging-config.service.ts:22/66/84) with zero automatic firers. Note it is INTERNAL-only by design, so it alerts the tenant's ops team, not the buyer — do NOT widen its channel matrix in this fix. The buyer-facing signal is the card (part 2), which is polled; the ops alert is what turns "nobody noticed" into "someone can act".

UX CONSEQUENCE, stated explicitly. The card must stop promising and start explaining, without becoming a dead end. On a skip it reads as a delivery that did not happen and a next action — e.g. "Your stop was skipped today" plus the reason when `skipReason` is set — and the step bar (orders/[id].tsx:235, driven by `trackingStepIndex`) drops back off "Out for delivery" as a consequence of part 1, so the two surfaces agree. The 20s poll stops, which is correct: there is nothing left to tick down, and continuing to poll would be the same false promise in a different form. If the driver returns and un-skips, part 1's re-promotion restores OUT_FOR_DELIVERY, the poll restarts, and the card returns to live tracking with no user action — that recovery path is the acceptance bar, not a nice-to-have. Do not silently demote with no copy change: an order that quietly drops from "Out for delivery" back to "Confirmed" with the same card text is more confusing than the bug.

NO WEB MIRROR EXISTS. apps/web/lib/api/buyer.ts exposes no tracking hook and apps/web/app/buyer/portal/[seller]/orders/[id]/page.tsx renders no tracking card (its only "tracking" match is a Tailwind `tracking-wider` class). The house rule "web is golden, mobile mirrors it" gives no reference here — this fix DEFINES the contract. Also note apps/mobile/lib/api/orders.ts:608-627 (`OrderTracking` + `useOrderTracking`) is a complete second client with zero callers anywhere; it duplicates the buyer type field-for-field, so any shape change has two mirrors to move. Delete it or wire it — do not leave a third copy.

**Structurally preventable — yes.** Two new scan signatures in .claude/skills/bug-hunt/scripts/scan-signatures.mjs, plus one real lint rule. None of the 26 existing signatures covers either half.

(a) LINT RULE — `routeflow/no-inline-body-type` in packages/eslint-config, HIGH signal, near-zero false positives, and it makes the injection class literally unwritable. Fail any parameter decorated `@Body()` whose TS type annotation is a `TSTypeLiteral` (or a `TSUnionType` of string literals) rather than a class reference. NestJS's global ValidationPipe (apps/api/src/main.ts:193-197) silently skips validation when the metatype is plain `Object`, so every such site is unvalidated by construction — routes.controller.ts:255 is one, and a repo sweep for `@Body()\s+\w+:\s*\{` will find the rest. A type cannot express this (the inline type IS the type); it has to be a lint rule.

(b) SIGNATURE `terminal-status-no-cascade`, medium signal. For each API service method whose name matches /^(update\w*Status|approve|reject|cancel|close|skip|void)/, count writes in the body: flag when the body contains exactly one `.update(` whose `data` object's only non-timestamp key is `status`, AND contains no second `.update(`/`.updateMany(`/`.create(`, AND no `notifyEvent(`/`emit\w+(` call. Register refs B32/B129/B146; would also have caught returns.service.ts:206-230 and inventory.service.ts:1263-1267. Model the write/read passes on `dead-model-guard`'s normalization (join `.forTenant()\n  .model.op(` chains, accept any receiver) so aliased clients count.

(c) SIGNATURE `dead-payload-field`, medium signal — the read-side twin, and the one that would have caught B146 at the moment `stopStatus` was written. For each key in an object literal returned from an `apps/api` service method, grep apps/web + apps/mobile for a read of that key (`\.key\b` or `key` inside a destructuring pattern), EXCLUDING occurrences inside `interface`/`type` declaration bodies — a type field is not a reader. Flag keys with producer=1 and readers=0. Run against HEAD today it flags four of `getOrderTracking`'s eight fields: `runId`, `routeName`, `stopNumber`, `stopStatus`. Same pass, extended to `emit\w+\(tenantId` definitions in apps/api/src/gateways/, flags `emitStopCompleted` and `emitLowStock` (11 of 13 emitters have exactly one caller; those two have none) — which is exactly the blind spot that let `updateStopStatus` emit nothing without anyone noticing.

## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** If the driver bypasses this customer's stop, the buyer's "you're next" messaging should stop implying the delivery is still coming, and the order should leave OUT_FOR_DELIVERY.

**Actually does.** updateStopStatus writes only routeRunStop.status. stopsAhead counts only stops before the customer's own, so a skipped own-stop leaves it at 0 and the card reads "You're next on the route". The tracking payload carries stopStatus, and no client reads it.

**The gap.** The one field that would expose the skip is emitted and then ignored by every consumer, and the order's own status is never reconciled.

**Evidence.** Evidence · apps/api/src/routes/routes.service.ts:1405-1433 (updateStopStatus writes status/driverNote/arrivedAt and never touches the linked order); apps/api/src/orders/orders.service.ts:4665-4671 (the stopsAhead filter structurally excludes the customer's own stop), :4681 (stopStatus emitted); repo-wide grep for stopStatus in apps/mobile returns only the two type declarations (lib/api/buyer.ts:562, lib/api/orders.ts:581) — zero reads in apps/mobile/app/(customer)/orders/[id].tsx:251-278, which renders driverName, runStatus, stopsAhead and estimatedArrivalWindow only; apps/mobile/lib/api/buyer.ts:575-581 (the poll continues because order.status is still OUT_FOR_DELIVERY).

**Suggested fix (register).** Have getOrderTracking short-circuit on the customer's own stop status (returning a skipped/cancelled tracking shape), render tracking.stopStatus in the buyer card, and decide whether a SKIPPED stop should revert the order to CONFIRMED so it can be re-swept.
