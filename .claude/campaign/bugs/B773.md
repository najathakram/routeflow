## Root cause

Ruled by SA-085i(c) (2026-09-23, from the Opus review of #1281); verified on origin/master 2ed80789: splitFromPrev (lib/sale-line.ts:31-36) returns normalizeBoxesPieces({ qty: prev.qty, unitsPerBox }) when the line has no boxes/pieces, i.e. it reads a bare qty as PIECES. But a box-unaware line on a boxed product carries qty in the LINE's own unit — boxes (SA-060(1)/SA-043; the server's create() reads a bare qty on a boxed product as a BOX count, B673). It feeds setLineBoxes/setLinePieces/incrementLine on the CREATE screen (NewOrderScreen ~:1008/:1022, reachable via a resumed legacy draft line) and the manual-invoice screen (invoices/new.tsx :489-490, :519/:529 — a plain-qty line switched to boxes): incrementLine({qty: 3}, true, 12) yields 1 box + 3 pieces instead of 4 boxes (under-bills 33 pieces). The client-side twin of the B644 class. The EDIT screen's master inline rule (qty = boxes × upb + pieces, typed box count replaces) is correct and stays until this is fixed. FIX: for upb > 1, splitFromPrev returns { boxes: qty, pieces: 0 } for a no-split line — never normalizeBoxesPieces({ qty }). PINS: setLineBoxes({qty: 3}, 4, 12) → boxes 4 / pieces 0 / qty 48; incrementLine({qty: 3}, true, 12) → 4 boxes; setLinePieces({qty: 3}, 2, 12) → 3 boxes + 2 pieces. Once fixed, the edit screen may route through the lib again. Not #1281 (round 4 on units already). Money — carve-out parked.
