# B202 · The mobile-web camera kept the pre-F30 scan engine: frames dropped mid-lookup, and no scan confirmation at all

**Location** `Scanning · mobile web (camera)` · **Severity** critical · **Batch** F30 · **State** done

## Summary

The mobile-web camera (browser-based operator scanning) ran a stale pre-F30 scan engine after #555 rewrote the native camera path and deliberately skipped ScanCamera.web.tsx, so the one operator who reported B190-B201 (scanning on a phone browser) kept every symptom that batch was meant to fix, plus had zero scan-accept feedback of any kind. Fixed by #562 (2026-08-31, e2bc8b33), which ported the shared scan-engine sequencing seam onto the web camera path and added an audible+haptic accept/reject cue.

## What this feature is for

Camera-based barcode scanning inside an operator's mobile-web session -- the browser fallback camera path alongside native ScanCamera.tsx. Decode a frame, resolve the code against the catalog, add the matched line, and give the operator feedback that a scan registered, without ever silently dropping a code that arrives while a prior scan is still resolving.

## Root cause

Three stacked faults in the pre-#562 ScanCamera.web.tsx, none present in the native ScanCamera.tsx #555 already fixed: (1) decode starvation -- the rAF decode loop held its in-flight guard across the FULL server resolve (fire(code) awaited before releasing inFlightRef), so no new frame was even decoded while a scan was resolving; (2) drop-not-queue -- fire()'s busyRef boolean bailed BEFORE the sequencing gate, discarding any code that arrived mid-resolve with zero feedback (the exact B192 defect, left unfixed on web); (3) legacy single-slot re-anchor -- the finally block wrote gateRef.current = {lastCode, lastAt: Date.now()} on every settle, pinning the gate to the single-slot shape and reopening the two-code-carton runaway (B190 class) for locally cached products. Separately, lib/haptics.ts's scanHaptic returns early on web, so there was no accept/reject cue of any kind on this platform.

## User impact

The one operator who reported B190-B201 by scanning on a phone browser had their entire fix batch silently skipped -- they kept losing scans mid-lookup and had no way to tell a scan had registered without watching the screen instead of the goods being scanned.

## Fix approach and UX

#562 (2026-08-31) ported the platform-free lib/scan-engine.ts sequencing seam (already built for native) onto the web path: ScanCamera.web.tsx's busyRef+gateRef collapsed into one engineRef = useRef(createScanEngine()); fire() split into a synchronous handleFrame/handleManual (thread one event through the engine) plus an async recursive resolveCode; the decode loop's .then() now calls handleFrame SYNCHRONOUSLY and releases inFlightRef in .finally() as soon as decode settles, no longer nested inside the resolve's own await -- which is what starved the decoder. Added an audible+haptic accept/reject cue: new lib/scan-cue.ts (native no-op) / lib/scan-cue.web.ts (WebAudio blip -- 1000Hz/80ms accept, 300Hz/180ms reject -- over one lazily-created, reused AudioContext, plus navigator.vibrate), decided by the pure lib/scan-feedback.ts cueForOutcome(outcome) helper and called by ScanCamera.web.tsx as a read-only observation on an already-resolved outcome, never inside the engine -- a cue is pure ergonomics and must never be able to fail a scan.

## Test plan

apps/mobile/**tests**/scan-engine.test.ts (REG-B202/W1-W4 + REG-B202 buffer-overflow and rejected-frame-clock pins) and apps/mobile/**tests**/scan-feedback.test.ts (REG-B202/CUE1-CUE14: accept/reject/none cue decisions, safePlay swallows a throwing AudioContext/navigator.vibrate) -- both pure-logic Jest, no camera or DOM harness needed. Residual gap, filed as a new low-severity row this session: nothing in mobile Jest exercises ScanCamera.web.tsx's own adapter wiring (the synchronous handleFrame call site, the inFlightRef release in .finally, the unconditional scanSettled drain, the playScanCue call site) since mobile Jest is pure-logic only.
