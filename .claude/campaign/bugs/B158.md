# B158 · The customers CSV export ignores the soft-delete and supplier-only filters the list applies

**Location** `Customers · CSV export` · **Severity** medium · **Batch** F15 · **State** in-flight

## Summary

CONFIRMED at master@2d35375 exactly as reported, plus a third drift the report missed. apps/api/src/customers/customers.service.ts:1635-1657 `exportCustomers` seeds `where = {}` while `findAll` :122-127 seeds `supplierOnly: false, deletedAt: null`; the export also lacks findAll's `regulated` clause (:151-153). The web button passes nothing (`exportCustomers.mutate({})`, apps/web/app/(dashboard)/customers/page.tsx:701) although the hook accepts params (apps/web/lib/api/customers.ts:632-644) and the controller validates a ListCustomersDto (customers.controller.ts:67-75). So customers.csv is every Customer row in the tenant — removed customers and supplier-only contacts included, with Receivables and Credits — and ignores the search / status / type / tag the operator applied. Fix: one shared where-builder for findAll and exportCustomers, and the button sends the screen's params. B156 and B170 extend that builder, so B158 lands first.

## What this feature is for

The Export button on the Customers list downloads "the list I am looking at" as CSV (Business Name, Contact Name, Email, Phone, Customer Type, Status, Receivables, Credits — :1683-1706) for accountants, CRMs and mailings. The list itself hides vendors imported from expense CSVs (`supplierOnly`) and removed customers, and applies the operator's chips; the export must apply the same rules or the file misstates who the customers are and what they owe.

## Root cause

Two hand-rolled copies of the same where-clause: findAll (:122-153) and exportCustomers (:1636-1657) duplicate the search OR, status, customerType and tag clauses line for line, but only findAll carries the two seed keys and the regulated clause. The export's findMany (:1659-1673) is unpaginated and includes open invoices + advance balances, so the extra rows carry money columns. Web side: page.tsx:701 `mutate({})` — the params object the list already builds (:321-331) is never passed; the controller (:69) already validates ListCustomersDto, so sending the screen params needs no API change. Class: duplicated where-builder drift between a list and its export — L-081's lesson ("keep every status set in one named module with the reason each differs written beside it") is the same rule for filters. No scan signature. Sibling check: the only other `async export*` in the API is apps/api/src/invoices/invoices.service.ts:5742 `exportPayments`, which takes its own params rather than a list DTO — a different shape, worth a glance but not this drift.

## User impact

Every export. A CSV handed to a bookkeeper or loaded into a CRM lists removed customers and vendor-only contacts with receivable balances — the file's AR total exceeds the dashboard's, removed customers get re-contacted, and "export the overdue ones" (status chip) exports everyone. Frequency: whenever Export is used; cost: wrong external numbers and wasted outreach; no write, so medium holds.

## Fix approach and UX

API: extract `private buildListWhere(query: ListCustomersDto)` from findAll (seed `supplierOnly: false, deletedAt: null` + search / status / customerType / tag / regulated) and call it from both findAll and exportCustomers; delete the export's copy. B156 (`unassigned`) and B170 (`removed`) then extend one function — which is the structural fix: with a single builder, list / export drift becomes unwritable rather than merely tested. Web: build `exportParams` from `customersQueryParams` minus page / limit (keep sortBy / sortDir — findAll's allow-list makes them safe, and a sorted CSV matches the screen) and call `exportCustomers.mutate(exportParams)`. UX consequence: the file matches the screen — same rows, same filters; with B170's "Removed" chip on, the export IS the removed set (consistent with "export what I see"), which the shared builder gives for free. Guard beyond the builder: the parity spec below pins findAll.where === exportCustomers.where for one query, so anyone re-inlining a clause goes red.

## Test plan

## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** Export downloads the customer list the operator is looking at.

**Actually does.** findAll seeds its where clause with supplierOnly:false and deletedAt:null; exportCustomers seeds an empty object and layers only the identical search/status/type/tag clauses, so removed customers and vendor-only contacts appear in customers.csv with their receivables.

**The gap.** Two seed keys are simply absent from the export's where clause, and the web button also passes no filters at all.

**Evidence.** Evidence · apps/api/src/customers/customers.service.ts:~103 [re-anchored master@6c8f1401; was :108-113 at hunt round master@0b2c3a0a] (findAll seed) vs :1463-1464 (exportCustomers seeds {}), :1465-1485 (the identical downstream clauses), :1486-1501 (unpaginated findMany), :1511-1537 (rows include Receivables and Credits); apps/web/app/(dashboard)/customers/page.tsx:306 and :657 (the Export button mutates with an empty param object).

**Suggested fix (register).** Extract the findAll where-builder and reuse it in exportCustomers so both start from supplierOnly:false and deletedAt:null, and have the Export button pass the screen's current search/status/type/tag params.
