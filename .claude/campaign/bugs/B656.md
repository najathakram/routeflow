## Root cause

PER-UNIT LEVY BASIS 12x ON SPLIT-LESS QTY-ONLY LINES (lead's ruling; no new id). The formula pieceQty = boxes != null ? qty : upb > 1 ? qty * upb : qty at apps/api/src/invoices/manual-invoice-lines.ts:88 (create) and apps/api/src/invoices/invoices.service.ts:3442 (update()) is the unitBasisQty for per-unit levies. computeCategoryTax (packages/pricing/src/pricing.ts:318-336) charges rate x unitBasisQty for EXCISE_PER_UNIT, PER_VOLUME and DEPOSIT_PER_CONTAINER; PERCENT_OF_SALE uses the subtotal. So a qty-only line on a boxed regulated product is OVER-taxed 12x. Worked example: upb 12, $0.10 per piece, 6 boxes at $40: correct levy $7.20; Duplicate/edit gives $86.40; a percentage levy is also 12x wherever the subtotal is wrong. CONDITION FOR THE FIX PR: it must assert the LEVY, not just the subtotal. A test that pins $240 and ignores $7.20 passes while the levy is still 12x wrong. See B659 for the four-paths framing. Code-read only, NEVER RUN.

## Reported evidence

(a) Server duplicate() copies boxes, pieces, the BUY_N_GET_M snapshot and the subtotal verbatim, but its itemsData map has NO unitsPerBox key, so a duplicated manual boxed line is stored boxes 6 / unitsPerBox NULL. (b) The mobile invoice edit screen hydrates unitsPerBox: it.unitsPerBox ?? null with no live-product fallback, and invoiceLineDto only sends boxes/pieces when upb > 1. (c) The PATCH therefore carries {qty: 72, unitPrice: 40} and update() prices per piece: $2,880 instead of $240, on ANY save including a due-date-only edit (the save resends every line). The web edit page has the fallback (it.unitsPerBox ?? it.product?.unitsPerBox). RELATION TO B644: B644's fix carries unitsPerBox in duplicate() (the lead's ruling: required scope of B644); B656 stays OPEN as the defence-in-depth fix: mobile must not depend on a snapshot always being present when the web page already has the fallback. ROOT-CAUSE NOTE (shared with B641/B643/B644/B645/B646/B647/B655): the family is wider than callers omitting the split. COPIERS ALSO OMIT unitsPerBox (a snapshot), and anywhere a line is reconstructed from a bare {qty, unitPrice}/{productId, qty} without boxes/pieces/unitsPerBox, money or quantity is wrong by unitsPerBox; helpers such as computeLineSubtotal and normalizeBoxesPieces silently fall back to per-piece math.
