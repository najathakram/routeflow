# B34 · “Skip stop” never records the skip

**Location** `Driver app · stops` · **Severity** high · **Batch** F11 · **State** queued

## Summary

"Skip stop" in the driver app is a dead control: the confirm dialog's accept callback at apps/mobile/app/(driver)/route/stop/[stopId]/index.tsx:337 is `() => router.replace("/(driver)/route")` and nothing else — no mutation, no status write. Still present at 07cba140 and byte-identical on master d9688f38. The adversarial pass upheld the defect but REFUTED the fix as scoped (1 of 3 lenses) and trimmed one impact claim: leaving `skipReason` un-cleared on reopen is a real gap, and an `@IsEnum(RouteRunStopStatus)` DTO — the shape the neighbouring update-run-status.dto.ts models — would leave the COMPLETED-forgery hole exactly as open as it is today; both are folded into fixApproach below.

⚠️ **This record's original fix step 4 (unpin the skipped stop's orders) is REFUTED and must not be built.** The strand it was trying to solve is real, but the remedy is B129's reader policy plus B211's extension of it, not a write from B34 — see `contestedBy` in the front matter, step 4 below, and `.claude/pipeline/2026-09-02-F11-run-cancel-skip/discovery.md` Risks §1. A builder working from this record alone would otherwise ship the regression AND a green test for it.

## What this feature is for

A driver standing at a door that cannot be delivered (shop shut, nobody home, access blocked, customer refuses) needs a one-tap way to record "not delivered, here's why" so dispatch sees it live, the order can be rerouted onto a later run or trip, completion metrics stay honest, and the driver can close out the run without a phone call. SKIPPED is a first-class terminal-for-this-run stop state: routes.service.ts:1418-1428 accepts COMPLETED-or-SKIPPED as the precondition for closing a run, and the operator screen already writes it (apps/mobile/app/(operator)/route-runs/[id].tsx:164-183).

## User impact

Who: every driver on a tenant with the `developer_mode` addon enabled (apps/mobile/app/_layout.tsx:172-197) — a per-tenant config flag, not dead code; the sibling comment at apps/mobile/lib/api/addons.ts:56-62 shows the at-the-door driver flow is switched on for real client tenants. The screen is one tap from the run list (route/index.tsx:155, :433).

How often: once per undeliverable stop — closed shop, nobody home, refused delivery — which is routine on a delivery round, not an edge case. There is no rescue anywhere: SKIPPED has exactly one writer in the API and nothing infers a skip.

What it costs, with the severity evidence:

1. Silent no-op with a lie in the copy. The dialog says "Mark this stop as skipped? You can reopen it later." The driver taps Skip, is navigated back to the run, and the stop is still PENDING. Nothing on the operator route-runs view or in completion metrics ever learns of it.
2. The driver has no self-serve exit. REFUTED and corrected from the original report: the driver never sees routes.service.ts:1428's "Complete or skip all stops first." — the whole completion hero, including the COMPLETED sender at route/index.tsx:397-398, renders only under `{!nextStop ...}` (:368) and `nextStop` is any PENDING/IN_PROGRESS stop (:322-331). So the complete-run control is simply absent while the stuck stop exists. The cost is therefore not a misleading error but two mis-recording workarounds: open Partial return and refuse every line (records a COMPLETED delivery instead of a skip), or phone dispatch to skip it from the operator screen (which does work). Not a hard stall — a wrong-semantics stall.
3. Privilege gap on the same endpoint (class B, above): any authenticated driver can forge a COMPLETED stop with no POD/invoice/stock movement. Independently high on its own.
4. Blast radius is bounded, and that is the one thing holding this at high rather than critical: the driver surface is addon-gated, and an operator can unblock the run today.

## Fix approach and UX

Land as ONE PR with B146 (same F11 batch, .claude/campaign/status/F11.jsonl) — B34 is what first makes a driver-initiated SKIPPED reachable, so shipping it alone converts a dead button into a wrong-state button.

API:

1. NEW apps/api/src/routes/dto/update-stop-status.dto.ts — `@IsIn(["IN_PROGRESS", "SKIPPED"]) status: string`, `@IsOptional() @IsString() @MaxLength(500) driverNote?`, `@IsOptional() @IsString() @MaxLength(200) skipReason?`. Do NOT copy the sibling update-run-status.dto.ts's `@IsEnum(RouteRunStatus)` shape: `@IsEnum(RouteRunStopStatus)` admits COMPLETED and PENDING (schema.prisma:99-104) and leaves the to-state hole untouched. The validator must be a value SUBSET.
2. routes.controller.ts:249-259 — type `@Body() body: UpdateStopStatusDto` so main.ts:192-197's pipe actually runs (whitelist + forbidNonWhitelisted now apply). Sweep :113/:266/:276 in the same file while there; that is cheap and keeps the file consistent.
3. routes.service.ts updateStopStatus (1716-1762) — widen the dto type; persist `skipReason` when status === "SKIPPED"; null it when status === "IN_PROGRESS" (a re-attempt must not carry the old reason). Keep F10's from-state guards untouched.
4. **REFUTED — DO NOT IMPLEMENT.** This step read "unpin the skipped stop's orders so they are re-dispatchable: clear `Order.routeRunStopId`". F11's synthesis overturned it (`.claude/pipeline/2026-09-02-F11-run-cancel-skip/discovery.md` Risks §1) and B129 — sequenced FIRST for exactly this reason — states the policy this batch obeys: **links are never nulled; readers gate on run/stop status.** Three independent reasons, each re-verified at HEAD:
   - **It would silently disarm reopenStop's delivery reversal.** `reopenStop` (routes.service.ts:2682) loads the stop WITH its orders (`stops: { where: { id: stopId }, include: { orders: { include: { lineItems: true } } } }`, :2686) and iterates `stop.orders` at :2769 to zero `deliveredQty` and demote DELIVERED/OUT_FOR_DELIVERY → CONFIRMED (:2772-2777). The comment above it (:2757-2768) states the cost of getting this wrong: leaving `deliveredQty` standing "bills the UNDONE delivery". Unpinning empties that relation, and `reopenStop` explicitly accepts SKIPPED stops (:2695-2697) — so the very path B34 makes reachable would reverse nothing, with no error.
   - **It would break B146's re-promotion.** B146 part 1 re-promotes the linked order on SKIPPED → IN_PROGRESS; with the pin cleared there is no order to find, so the un-skip half of the same batch becomes a no-op.
   - **It would move money.** `settleRun`'s expected figure derives from run linkage AT SETTLEMENT TIME (`getRunCashCollections` :1484-1496, called from :1684), so clearing `routeRunId` retroactively shrinks a run's expected cash and silently changes its variance — the identical defect B129's guard 3 exists to prevent.

   **Do instead: B34 ships NO order write at all.** Leave `Order.routeRunStopId`/`routeRunId` exactly as `createRun`'s sweep wrote them (routes.service.ts:966) and let the READERS decide. B129 widens `createRun`'s sweep predicate (:945) and TripsService's filter (trips.service.ts:189, `checkEligibility` :112-125) to admit orders pinned to a CANCELLED run; B211 extends that same predicate to the COMPLETED-run-with-a-SKIPPED-stop case that this bug makes reachable for the first time. That is the whole of B34's dependency on B129 landing first — and the reason B34 must not be built from this record alone.

5. reopenStop (routes.service.ts:2831-2847) — add `skipReason: null` to the reset block. It already clears status/completedAt/arrivedAt/driverNote/POD/identity but not skipReason, reopenStop accepts SKIPPED (:2695-2697), and B34 is the change that first gives the column a writer — so skip -> reopen -> deliver would otherwise leave a skip reason attached to a COMPLETED, delivered stop.

Mobile (mirrors apps/mobile/app/(operator)/route-runs/[id].tsx:78 + 164-183, not web — web has no SKIPPED writer): 6. apps/mobile/lib/api/routes.ts:374-388 — add `skipReason?: string` to the mutation vars. 7. apps/mobile/app/(driver)/route/stop/[stopId]/index.tsx — import `useUpdateStopStatus`; replace the :331-341 navigate-only handler with `chooseAction` (apps/mobile/lib/confirm.ts:67 — already cross-platform, no new component) offering a short fixed reason list (Nobody home / Closed / Refused delivery / Access blocked / Cancel), each calling `mutate({ runId, stopId, status: "SKIPPED", skipReason })`. 8. Delete .claude/skills/bug-hunt/scan-ignore.json:74 — with the site fixed the baseline entry can be removed outright (it is the only `confirm-navigate` entry), restoring scanner coverage for this class.

UX consequence, stated explicitly:

- The yes/no confirm becomes a one-screen reason picklist: ONE extra tap at the door, no keyboard, no free text, no new sheet component. That is the deliberate cost of making skipReason real; a free-text prompt would be the wrong trade for a driver holding a crate.
- Failure must stop being invisible: on error, show the toast and STAY on the stop screen. The current code navigates unconditionally; navigating on a failed mutation reproduces B34's exact deception at a lower rate.
- On success, invalidate the run query and only then `router.replace("/(driver)/route")`, so the run screen paints the stop as skipped rather than re-showing it as next.
- Once the last blocking stop is skipped, `nextStop` goes null and the "All stops done" hero with Mark route complete appears (route/index.tsx:368) — the driver regains a self-serve close-out that today requires calling dispatch.
- The skipped stop's orders KEEP their pin, by design (see step 4). They do not return to dispatch the moment the driver skips — the run is still live and the stop can be un-skipped or reopened. They become re-dispatchable when the run reaches a terminal state, through the READER widening B129 lands for CANCELLED runs and B211 extends to COMPLETED runs carrying a SKIPPED stop. ## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** Driver taps Skip stop to mark a stop as skipped so dispatch/operators can see it wasn't delivered and can follow up or reroute.

**Suggested fix (register).** Wire the Skip-stop confirm handler to call useUpdateStopStatus({runId, stopId, status: "SKIPPED"}) before navigating back, matching the operator route-runs screen's usage.
