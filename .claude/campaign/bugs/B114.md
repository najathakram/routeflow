## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** After a disconnect/reconnect cycle (API redeploy, network blip, sleep/wake) the client should refetch queries that could have changed, since the socket is its only live-update channel.

**Actually does.** Web registers no "connect" handler at all; mobile's is log-only. With refetchOnWindowFocus:false (web) and an unconfigured QueryClient with no NetInfo/AppState wiring (mobile), missed events never surface until manual navigation/reload.

**The gap.** Reconnect is treated as invisible; no invalidateQueries fires, so the dashboard silently shows pre-outage data while appearing live.

**Evidence.** Evidence · apps/web/lib/hooks/useRealtimeUpdates.ts:13-133 (per-event handlers only, no on("connect")); apps/mobile/hooks/useSocket.ts:131-133 (connect handler = dbg log) and :55-197 (no reconnect invalidation); apps/web/app/providers.tsx:48-49 (staleTime 30s, refetchOnWindowFocus:false); apps/mobile/app/_layout.tsx:38 (new QueryClient() default config); grep of apps/mobile: zero onlineManager/focusManager wiring.

**Suggested fix (register).** Add socket.on("connect") handlers that skip the very first connect and otherwise invalidate the realtime-fed query key families; wire mobile's focusManager/onlineManager to AppState/NetInfo.

> ⚠️ Treat this as a hypothesis, not a plan. On F11 the adversarial pass refuted the
> suggested fix for every one of the four bugs while confirming every diagnosis.

**Verifier's note.** Worse than claimed on web: lib/socket.ts:25 sets reconnectionAttempts:5, so a deploy outlasting ~5 attempts (or an expired token rejected on reconnect, per R3-3-1) kills realtime for the tab permanently with only a toast. Mobile's three refetchOnWindowFocus:true queries (lib/api/admin.ts) are inert on native without focusManager wiring. Distinct from B76/B86 (event-handler coverage gaps, not reconnect catch-up).
