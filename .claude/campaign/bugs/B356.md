# B356 · Buyer and staff JWTs share one signing secret and carry no identity-type claim (F5-003)

**Location** `Auth · api (JWT signing/verification)` · **Severity** medium · **Batch** F48 · **State** queued

## Summary

_Not yet analysed._

## What this feature is for

_Not yet analysed._

## Root cause

Buyer and staff issuance share the secrets; discrimination is a payload type check only.

## User impact

A key exposure or a strategy bug collapses the buyer/staff boundary at once; refresh tokens cannot be told apart by construction.

## Fix approach and UX

Per-family keys derived via HKDF from the existing secret (no new env vars, same pattern as STORAGE_URL_SIGNING_SECRET) plus aud/typ claims verified in both strategies; refresh records carry the family.

## Test plan

T1: staff-family token fails buyer verification even with a matching payload type and vice versa; cross-family refresh rejected; existing auth security specs green.

## Reported evidence

Both token families are minted with the same JWT_SECRET/JWT_REFRESH_SECRET; only a payload type check separates them. Expected: per-family keys and an aud/typ claim verified by both strategies.
