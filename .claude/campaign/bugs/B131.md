# B131 · Removing a customer doesn't stop their standing orders or recurring invoices

**Location** `Customers · remove customer + order-template / recurring-invoice crons` · **Severity** high · **Batch** F15 · **State** queued

## Summary

ALREADY FIXED on master by PR #693 (692bdf8, merged 2026-09-11, "run D final-pass follow-ups — every removed-customer door"); the ledger row is stale because that commit carries `Bookkeeping-Follow-Up: pending` and no follow-up has run `prove`. Verified at master@2d35375: both crons filter `customer: { deletedAt: null }` and log a per-tenant suppressed count; the create doors for standing orders, recurring invoices, manual invoices and staff/driver/self orders refuse a removed customer; the authorization-expiry sweep skips them. Once B131 and B141 are proven, F15 holds no money-tagged workable row — the carve-out that parks the other five lifts.

## What this feature is for

"Remove customer" (soft delete: Customer.deletedAt + User.status INACTIVE, customers.service.ts:2039-2049) ends the relationship going forward while keeping history: no new standing-order Order from the 06:00 template cron, no new Invoice (or auto-send email) from the recurring-invoice sweep, and no operator invoicing or ordering for them by hand. Restore (:1965-1984) must bring everything back with no other write — which is why the fix is a stateless read-side filter rather than flipping isActive on the templates (train4 cause-ruling.md:17).

## Root cause

At the hunt sha (0b2c3a0a) both crons selected on isActive alone and nothing outside the delete branch read Customer.deletedAt. Verified FIXED at master@2d35375 by #693: apps/api/src/order-templates/order-templates.service.ts:319-342 (`where: { isActive: true, daysOfWeek: { has }, customer: { deletedAt: null } }` + a suppressed count + per-tenant warn), apps/api/src/recurring-invoices/recurring-invoices.service.ts:403-426 (same shape on nextRunAt <= now, before the autoSend email), create doors order-templates.service.ts:131-137 and recurring-invoices.service.ts:84-90 (`customer.findUnique({ where: { id, deletedAt: null } })` → not-found, no state leak), apps/api/src/invoices/invoices.service.ts:348-350 (create() checks deletedAt on the row it just read — the L-081 shape), apps/api/src/orders/orders.service.ts:1925-1953 (staff/driver/self create) plus every buyer-session door (:343, :497, :2749, :3318, :3468, :5849, :5876, :5922), apps/api/src/authorizations/authorization-expiry.service.ts:102-122. The soft-delete/restore code itself is untouched (:2044-2047, :1977-1982), so restore is symmetric; the first tick after restore generates at most one current cycle (B46 rule, recorded in #693). Class: soft-delete filter omission — a `deletedAt` written by one branch and read by no consumer. No scan signature covers it (scan-signatures.mjs has `unscoped-tenant` for the tenantId analogue at :798-854, nothing for deletedAt); B141, B157 and B170 are the same class in this batch.

## User impact

Pre-fix: every removed customer with an active template got an Order every scheduled weekday, and every active recurring schedule minted an Invoice per cycle — emailed when autoSend was on — real documents in the tenant's books and AR. The owner's read-only train-4 damage report (.claude/pipeline/2026-09-10-train4-damage-report/build-plan.md:193) bounds the historical count (templateOrders / recurringInvoices / recurringInvoicesEmailed as LOWER bounds, manualInvoices as an UPPER bound); a removed-then-restored customer's window is invisible to it. Post-fix: no new rows for new removals; the historical rows are a data-repair decision for the owner, not code. High stands for the pre-fix window; what is left is bookkeeping.

UX today: the operator sees nothing new — suppression is a per-tenant warn line (`REG-B131: N standing-order template(s) suppressed — customer removed`), which is the ruling's intent (stateless, restore-symmetric). Structural (the real win for this batch): add a `soft-delete-omission` signature to scan-signatures.mjs — for every model whose schema block has `deletedAt` (Customer, User, SalesAgent, Expense, BuyerAccount, Tenant …), flag a `findMany` / `findFirst` / `count` on a model that carries a relation to it (schema-derived, the way `unscoped-tenant` derives its scoped set) whose captured `where` span does not filter that relation's `deletedAt`; run it `--only` per module. Cheapest first cut with near-zero noise: restrict to methods decorated `@LeaderCron` and to guards' `canActivate` — the two places this class costs money or access.

## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** Remove customer ends the relationship: past orders and invoices are kept, but no new order and no new bill is minted for a customer who has vanished from the Customers list.

**Actually does.** Both daily crons select on isActive alone. A removed customer keeps getting a generated order every scheduled weekday and a freshly created invoice — emailed to them when autoSend is on.

**The gap.** The soft delete writes two rows and stops there; nothing in the crons, the invoice create path, or anywhere else in the API reads deletedAt.

**Evidence.** Evidence · apps/api/src/customers/customers.service.ts:1761-1792 (soft branch updates only Customer.deletedAt and User.status) vs :1867-1882 (the hard branch does tear down recurringInvoice, orderTemplate and the route rows); apps/api/src/order-templates/order-templates.service.ts:252 (@Cron 0 6 * * *), :271-274 (where { isActive: true, daysOfWeek: { has } }); apps/api/src/recurring-invoices/recurring-invoices.service.ts:228, :242, :184, :205-213 (autoSend → sendEmail); apps/api/src/invoices/invoices.service.ts:312-316 (create() looks the customer up with no deletedAt filter); grep deletedAt across apps/api/src/{invoices,orders,routes,order-templates,recurring-invoices} → zero hits, and there is no global soft-delete filter in prisma.service.ts.

**Suggested fix (register).** In deleteCustomer's soft branch, set the customer's OrderTemplate and RecurringInvoice rows isActive=false inside the same transaction and restore them on restoreCustomer; belt-and-braces, add customer: { deletedAt: null } to both cron selection queries.
