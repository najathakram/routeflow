## Reported evidence

recomputeOrderFromInvoices ends with an orphan loop (~:2402): 'Order lines billed by no invoice: cancel (they weren't actually sold)', which sets status CANCELLED, qty 0, subtotal 0, boxes null, pieces null, invoicedQty 0 on every order line no non-void invoice bills, then rewrites the order total to the billed sum. Its docblock's design assumed whole-order coverage, but partial invoicing is a supported flow (POST /invoices/from-order/:orderId/partial, createPartialFromOrder, per-line invoicedQty). Callers: :3540 (update), :3601 (discount/shipping change) and :6359 (applyPriceAdjustment). The only guard is 'no non-void invoices: return' (:2284-2285). So editing, discounting or price-adjusting a DRAFT PARTIAL invoice cancels every order line that invoice does not bill: remaining = qty - invoicedQty becomes 0 and the line is CANCELLED with qty 0 and no stock return, so it can never be invoiced. No spec covers partial + recompute. Reachability is medium until the prod query runs (orders with at least one non-void invoice and a non-cancelled line with invoicedQty < qty). FIX SHAPE (NOT a fix): restrict the orphan cancel to invoicedQty = 0 AND a full-coverage precondition, or skip it when the order is partially invoiced. NOBODY IMPLEMENTS IT until a red-first DB spec exists; repro on test tenants only. HOW KNOWN: R-ui's trace; the orphan loop and the guard were re-read by the Mac Lead and again by the filer on origin/master f05222b1; code-read only, NEVER RUN. See the note on this record for the cancelled-line resurrection mechanism.
