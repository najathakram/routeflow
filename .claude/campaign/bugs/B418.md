## Reported evidence

expect(res.status).toBe(2) fails with 'Received: null' under severe concurrent host load. Node's spawnSync kills the child and returns status:null when its timeout option fires -- a real, correct exit code silently becomes indistinguishable from a hang. A generous 30s bound was still exceeded under this session's own multi-worktree concurrent-verify load. Sibling of B225/B244 (ci-freshness-guard-script.spec.ts's own host-load timing flakes, tracked separately) -- same underlying class (a test's bounded wait is still an ambient-machine-load assumption), different mechanism (subprocess timeout vs an in-test wall-clock assertion). Fix direction: raise the timeout with documented rationale, assert res.signal===null as a precondition surfacing a distinguishable 'harness timeout' message, or a bounded retry.
