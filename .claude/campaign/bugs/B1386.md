# B1386 · Server accepts a buyer line quantity above the 100,000-piece bound on edit, change request and template

**Location** `apps/api/src/orders/buyer-edit-lines.ts (applyBuyerEditLines); orders/change-requests.service.ts CUSTOMER branch; order-templates/order-templates.service.ts` · **Severity** high · **Batch** F65 · **State** queued

## Summary

_Not yet analysed._

## What this feature is for

_Not yet analysed._

## Root cause

The bound lived only in the buyer create DTO and the clients; the edit, change-request and template writers never compared a line's resolved pieces with it. A raw dto.qty check would miss a box-split line (cases x unitsPerBox).

## User impact

_Not yet analysed._

## Fix approach and UX

SA-1285: a service-level, caller-keyed check on each line's RESOLVED piece total against BUYER_LINE_QTY_MAX from @routeflow/pricing, rise-only (a line already above the bound can be left alone), own error code, no number in the message; the CUSTOMER template branch is in scope; the cart fold does not cap. Words per SA-1299 P1.

## Test plan

T1, SA-1285 section 1's six cases: 100,001 pieces refused on both edit routes and both change-request routes; 8,334 cases on a 12-pack box-split line refused; an order holding a 120,000 line accepts an edit to another line; a staff edit at 240,000 stays 200; 100,000.001 refused; a client at 8,333 x 12 accepted.

## Reported evidence

UpdateOrderItemsDto qty has no @Max and CreateChangeRequestDto uses a different 1,000,000 limit, so a buyer edit, change request or template can carry a line far above BUYER_LINE_QTY_MAX that the create path already refuses (found with B1382, #4509).
