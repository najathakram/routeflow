## Fix approach and UX

PR #744 added a named terminal-status set, STRIPE_TERMINAL_STATUSES = new Set(['canceled', 'incomplete_expired']) (subscription-mutation.service.ts:105), and a private stripeSubIsTerminal(stripeSubId) helper (:1101-1108) that re-reads the subscription via stripe.getSubscription() and tests sub.status against that set (a 404 on the re-read also counts, via isStripeResourceMissing -- the object is gone entirely, equally nothing left to cancel; any other read failure returns false so the caller still surfaces the 503). cancelReadOnlyStripeSubImmediately() (:1039-1082) now branches on stripeSubIsTerminal() as a THIRD outcome alongside the existing resource-missing and hard-failure branches: a terminal Stripe status is treated as the desired end state (log + proceed), not an error. Whichever of the three branches confirms the subscription is gone/terminal, the SAME single local write runs once at the end -- prisma.tenantSubscription.updateMany({where:{tenantId, stripeSubId}, data:{stripeSubId:null}}), scoped to the same stripeSubId so a concurrent re-subscribe's new pointer is never clobbered -- making a repeat cancel() a true no-op. UX unchanged: the READ_ONLY short-circuit still returns {cancelled:'already_read_only'} unconditionally; the fix is entirely about which Stripe states stop throwing a 503 on retry, not about any user-visible copy. No new statuses were added carelessly: active/trialing/past_due/unpaid/paused/incomplete stay deliberately NON-terminal, and an unrecognised future status fails CLOSED. ## Reported evidence

The cancel path treats only status === "canceled" as success, so incomplete_expired and every other terminal Stripe status still falls to the generic branch, throws 503 on every retry, and leaves stripeSubId intact so the tenant can never get out. Fix the whole terminal SET, never one member at a time. Claimed by 03 (W1 lane).
