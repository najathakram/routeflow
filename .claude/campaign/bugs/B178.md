## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** Switching Language to Español translates the sidebar nav, which is exactly what the nav.* keys were authored for.

**Actually does.** The three nav definitions hardcode English label literals and the renderer prints those literals; the four nav.* keys have zero read sites in the entire web tree.

**The gap.** Keys shipped in both locale tables when the i18n foundation landed and were never wired to the shell that owns them.

**Evidence.** Evidence · apps/web/lib/i18n/messages.ts:62-65 (en) and :108-111 (es); grep for the four keys across apps/web returns only those 8 definition lines and no call site; apps/web/app/(dashboard)/layout.tsx:86,89,107,149 (operator nav literals), :154,157,165, :170,172, :406 and :486 (the renderer prints item.label / group.label); git log -S shows the keys were introduced in the i18n foundation PR and untouched since.

**Suggested fix (register).** Either give each nav leaf and group an optional message key and render the translation with the literal as a fallback, or delete the four unused keys from both locale tables so the catalog stops advertising coverage it does not have.

> ⚠️ Treat this as a hypothesis, not a plan. On F11 the adversarial pass refuted the
> suggested fix for every one of the four bugs while confirming every diagnosis.

**Verifier's note.** Genuine dead code, verified by grep across the whole web tree. Impact is narrow: even if wired, only 4 of roughly 30 nav labels have translations, so the visible effect overlaps the i18n coverage entry. The catalog header names the shell as part of the Phase-1 set, which is why these keys were written — the shell nav is precisely the piece that was never connected.
