## Reported evidence

HARDENING, not a defect today. On the merge path (willMerge = !forceNew && activeOrder != null, ~line 54) handlePlaceOrder awaits createOrder.mutateAsync and then does router.push to orders/${activeOrder.id} (~183-184): the order the client ASSUMED its items would land in, not the id the server returned in result. If the server ever declines to merge (a lock, a race, a future change to forceNew), the buyer is silently shown a different order than the one their items were added to. Fix direction: navigate to the id in result. HOW KNOWN: read by the lead and re-read by the filer on origin/master; code-read only, NEVER RUN. DISPROVEN CLAIM RECORDED SO NOBODY RE-RAISES IT: R-ui's unitLabel sweep (local-assets/proofs/2026-09-21/unitlabel-sweep.md, section B, lower list) said the buyer cart 'says added to your existing order but creates a new one and navigates to the old' (a double-order risk). That did NOT hold: handlePlaceOrder passes forceNew through to createOrder.mutateAsync (~177), and the buyer createOrder is a documented customer-level auto-merge path serialised through withAdvisoryLock, so navigating to the existing order when willMerge is true is CORRECT and there is no double-order. The sweep also cited the wrong path ((buyer)/cart instead of the real buyer/portal/[seller]/cart): the sweeper inferred the claim from UI text without checking the server contract. Severity LOW as the lead ruled.
