# B111 · POD photo attach failures are silently swallowed — photo recorded nowhere

**Location** `POD · mobile driver + API + web` · **Severity** high · **Batch** F19 · **State** done

## Summary

Photo attach failures for POD were silently dropped: transcode-fallback file:// URIs never made the attach set, and a bare catch{} swallowed 4xx attach errors, so a driver-captured photo could vanish with no error surfaced and no server record.

## What this feature is for

_Not yet analysed._

## Root cause

PhotoCapture.tsx filters non-data: URIs out of the attach payload on transcode fallback; payment.tsx wraps the attach call in an empty catch (lines ~264, 270-273), and 3 failed offline replays silently drop the action instead of retrying/flagging.

## User impact

_Not yet analysed._

## Fix approach and UX

Covered by train 1's D1 teardown/persistence work: podStore is persisted (keyed by user+tenant+route/stop) so a killed app can reconcile against the stop's existing podPhotoUrls/artifact ids before any re-attach, and the empty catch is replaced with a surfaced failure state instead of silent success.

## Test plan

Mobile pure-logic pin covers podStore persistence + reconciliation against existing artifact ids (no duplicate re-attach after relaunch).

## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** A photo the driver captures and sees on screen is retrievable by the office after completion, or at minimum flagged as captured-but-undisplayable.

**Actually does.** Three verified drop paths: transcode-fallback file:// URIs are filtered out of the attach set and the completion payload no longer carries photos; a 4xx attach (rasterize failure → BadRequest) is swallowed by an empty catch and permanently dequeued; 3 failed offline replays drop the action. Web then renders no POD block.

**The gap.** Driver sees normal success; office sees a stop visually identical to one with no POD captured — silent evidence loss.

**Evidence.** Evidence · apps/mobile/components/PhotoCapture.tsx:46-70 (catch/no-base64 → onAdd(asset.uri)); apps/mobile/app/(driver)/route/stop/[stopId]/photo.tsx:47 (output="data-url"); apps/mobile/app/(driver)/route/stop/[stopId]/payment.tsx:257 (data:-only filter), :267-269 (empty catch), :278-293 (completion payload carries signatureUrl but no podPhotoUrls); apps/api/src/routes/routes.service.ts:1497-1526 (ingest failure → null), :1580-1581 (null → BadRequestException); apps/mobile/hooks/useNetworkSync.ts:7,22-24 (MAX_RETRIES drop), :55-56 (4xx dequeue); apps/web/app/(dashboard)/routes/[id]/page.tsx:239-245 (hasAnything → render nothing).

**Suggested fix (register).** Surface attach failures to the driver (toast + retry) and persist a failed-attach marker on the stop (or fall back to sending the data URL inline on the completion, which ingestPodCapture already handles durably) so the office sees 'photo captured, upload failed' instead of nothing.

> ⚠️ Treat this as a hypothesis, not a plan. On F11 the adversarial pass refuted the
> suggested fix for every one of the four bugs while confirming every diagnosis.
