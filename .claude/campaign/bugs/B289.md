## Summary

A VOID vendor bill can be paid to PAID/PARTIAL and received to RECEIVED — the guards exist only on the sibling paths

## What this feature is for

Context: Vendor bills · API POST /vendor-bills/:id/payments and /receive (stale page, concurrent void, or direct API). This is part of the F35 batch ("A VOID vendor bill can be paid to PAID/PARTIAL and received …") — see the batch theme in the hunt digest for the surrounding feature's purpose.

## Root cause

A VOID vendor bill can be paid to PAID/PARTIAL and received to RECEIVED — the guards exist only on the sibling paths

Symptom / evidence: Recording a payment on a voided bill flips it back to PAID and re-enters AP; receive() re-adds stock to a voided bill, contradicting the Void dialog's "No further payments can be recorded on it".

Files implicated: apps/api/src/vendor-bills/vendor-bills.service.ts, apps/api/src/vendor-bills/vendor-bills.controller.ts, apps/web/app/(dashboard)/vendor-bills/[id]/page.tsx.

## User impact

## Fix approach and UX

Suggested test: REG-B<id> recordPayment and receive both refuse a VOID vendor bill, matching recordSupplierPayment and payBillFully (filled with this record's own id at filing time).

Coupling constraint: the F35 vendor-bill void/pay/receive guards (A1-conservation#2, A2-state-machines#3, A5-concurrency#3, A5-concurrency#4) land together in one diff — they are three guards on the same VOID/PAID state machine and landing one without the others leaves a bypass through a sibling endpoint.
