## Reported evidence

P-4 ("no 64-hex string in any output except the plan hash") scans the dry run, the refused apply with no backup, the refused stale apply and the committed apply (digestsIn over stdout and stderr). It does not scan the apply that the compare-and-swap refuses ("link <id> has changed since the dry run", rowCount !== 1, ROLLBACK, exit 1). That is the one path that holds a planned digest in scope next to the message, so it is where a later debug line would leak: a digest added to that message stays green in every row. Found by review-a (L-1) on #4232 at ef87ea532f; shipped in 06e41dca24. No leak today, the message prints the link id only. Fix (spec only, two lines): add expect(digestsIn(a.out, [r.hash])).toEqual([]) in R6 (re-issued code) and R10 (replay of the unspent copy); optionally assert in R6 that the plan file still holds its digests after the refusal. Source: #4232 review notes, bookkeeping 2026-11-07.
