# B129 · Cancelling a run strands its orders on a stale stop link — they can never be dispatched again

**Location** `Route dispatch · web + API` · **Severity** critical · **Batch** F11 · **State** queued

## Summary

Cancelling a route run writes `routeRun.status = CANCELLED` and nothing else, so every undelivered order keeps its `routeRunStopId`. Because `createRun`'s sweep and `TripsService`'s picker both require `routeRunStopId: null`, those orders become invisible to all future dispatch, while `getOrderTracking` keeps handing the buyer a driver name and an arrival window for a run that was called off. The adversarial pass CONFIRMED the mechanism on all three lenses but REFUTED the obvious fix: nulling the link on cancel would destroy the un-cancel recovery F10/#591 shipped, silently understate `settleRun`'s expected cash, and break `reopenStop`'s delivery reversal — so this card prescribes relaxing the dispatch READERS, not clearing the link.

## What this feature is for

Cancel is the operator's non-destructive exit from a dispatched run — a breakdown, a driver calling out, a route dispatched by mistake. It exists so the day's undelivered orders go back in the dispatch pool and can ride tomorrow's run, while the delivery history already recorded on that run (deliveryMutations, collected cash) survives for settlement and audit. Delete is the destructive exit and is refused the moment any delivery exists; cancel is what the product tells operators to use instead ("This run has recorded deliveries; cancel it instead of deleting." — routes.service.ts:1334).

## Root cause

MECHANISM (confirmed at master, `updateRunStatus` unchanged since F10). apps/api/src/routes/routes.service.ts:1368 `updateRunStatus` builds `const updates: any = { status: dto.status }` at :1445 and writes only the RouteRun row at :1449 (plus startedAt/completedAt). There is no CANCELLED branch anywhere in the method — no transaction, no `order.updateMany`. The orders pinned by the dispatch sweep at :966 (`data: { routeRunId: run.id, routeRunStopId: s.id }`) keep that link forever, and the sweep's own predicate at :945 (`routeRunStopId: null`) plus TripsService's DB filter (trips/trips.service.ts:189, same key) make them structurally invisible to every later dispatch. `checkEligibility` (trips.service.ts:112-126) names the resulting state out loud: `PREVIOUSLY_DISPATCHED` / "Attached to a finished run (stale link)".

DEFECT CLASS: terminal-transition-without-link-cascade — a status handler writes its own row and leaves every FK that other subsystems key off it pointing at a now-dead parent. The read-model twin is the same class: `OrdersService.getOrderTracking` (orders/orders.service.ts:5301) short-circuits ONLY on a null stop link (:5331) and returns runId/driverName/runStatus/arrival window with no `run.status` gate (:5344-5358) — the lone stop-link reader in the API that skips the house pattern every sibling follows (orders.service.ts:449, :2945, :4720-4728, :5233-5243 which even comments "stale attachments … are harmless", change-requests.service.ts:55/:211, trips.service.ts:112-118).

SIBLING SITES (same class, same file family):
- routes.service.ts:1716 `updateStopStatus` writes only the stop row; `updateRunStatus`'s COMPLETED gate accepts SKIPPED stops (:1424), so skip a stop → complete the run → its orders are stranded identically ON THE HAPPY PATH, no cancel involved. Registered as B146 (tracking half only); the strand half is unrecorded and is the more frequent trigger.
- orders.service.ts:2621-2680 `changeStatus → CANCELLED` cascades stock, invoices and wallet credits but never clears the route link; orders.service.ts:2862 `reopenOrder` restores PENDING (:2919-2925) and leaves the stale link — together a round trip that permanently kills an order's dispatchability.
- drivers/drivers.service.ts:223-227 `changeStatus` writes driver.status only, while `remove()` (:257) guards live runs and nullifies FKs — weaker, same shape.

No permanent strand, so lower severity — but it is the same 'terminal transition writes its own row only' pattern.

## User impact

Severity evidence, not restatement.

WHO: every operator on every tenant that dispatches routes. Cancel is ungated — no flag, no dev gate, no role restriction beyond driver — and reachable from three web surfaces plus mobile. The product ACTIVELY FUNNELS operators into it twice: `createRun` refuses a second run with "Complete or cancel it before dispatching again" (routes.service.ts:869-873), `deleteRun` refuses with "cancel it instead of deleting" (:1334), and routes/page.tsx's own comment at :483-484 reads "Runs are cancelled, never deleted from here."

HOW OFTEN: once per abandoned run. Breakdowns, driver no-shows, weather, and mis-dispatches are routine in a delivery business, so this is a weekly-to-daily event per tenant, not an edge case.

WHAT IT COSTS: the affected orders silently stop existing for dispatch. No error, no banner, no count — the next day's run is simply built without them and comes up short. The escape hatch closes behind the operator: `canDelete = isOperator && run.status === "SCHEDULED"` (routes/[id]/page.tsx:842), so the Delete button that would have unlinked the orders disappears the instant the run goes CANCELLED, and `deleteRun` refuses anyway once a delivery is recorded. `updateFulfillPath` offers only an exit to SHIP (orders.service.ts:5232-5246), not a way back onto a route. That leaves exactly two recoveries, both undiscoverable: un-cancel the same run (only viable while it is still that route, that day), or destroy delivery history via `deleteRoute` — which itself refuses any route carrying an IN_PROGRESS or COMPLETED run (:554-558), so it is unavailable for the mid-route cancel that is the common case.

COMPOUNDING: the buyer keeps seeing a driver name and a delivery window for a delivery that was called off, generating "where is my order" calls against a run nobody is driving. Critical is correct: undelivered goods, unbillable, invisible, with no in-product path back.

## Fix approach and UX

The adversarial pass refuted the unpin fix; do NOT null the link. Nulling `routeRunStopId`/`routeRunId` on cancel would (a) turn un-cancel — the only recovery F10 shipped, documented at routes/dto/update-run-status.dto.ts:18-24 — into a restore of an EMPTY run, since nothing re-sweeps on CANCELLED→SCHEDULED/IN_PROGRESS and `createRun` (:940-967) is the sole sweeper; (b) drop confirmed CASH/CHECK payments out of `settleRun`'s expected figure, which derives from `invoice.order.routeRunId` at settlement time (getRunCashCollections :1484-1496, called :1684) and which explicitly accepts CANCELLED runs by design (:1636-1648); (c) empty `stop.orders`, which `reopenStop` uses to zero `deliveredQty` (:2765-2777, comment: "One order maps to one stop"), re-arming the over-billing bug that comment exists to prevent; (d) invalidate the stated invariant at orders.service.ts:5233-5235 that the link "is never cleared".

FIX THE READERS INSTEAD — three coordinated changes, all API-side:

1. apps/api/src/routes/routes.service.ts:940-965 — widen the sweep predicate from `routeRunStopId: null` to `OR: [{ routeRunStopId: null }, { routeRunStop: { routeRun: { status: RouteRunStatus.CANCELLED } } }]`. CANCELLED only; COMPLETED stops stay off-limits because `reopenStop` owns that path. The sweep already excludes DELIVERED/CANCELLED orders at :944, so the released set is exactly the undelivered remainder.
2. apps/api/src/trips/trips.service.ts:181-195 — same widening in the eligible-orders `where`, and narrow `checkEligibility`'s PREVIOUSLY_DISPATCHED branch (:112-126) to non-CANCELLED finished runs so the picker and the DB filter agree.
3. MONEY GUARD (required, because the re-sweep at :966 overwrites `routeRunId` and would retroactively shrink the old run's expected cash): exclude from both readers any order with a CONFIRMED CASH/CHECK `InvoicePayment` against its current `routeRunId` unless that run carries a `settlementNote`. Those orders stay held until the cancelled run is settled — `settleRun` already accepts CANCELLED for exactly this scenario.
4. apps/api/src/orders/orders.service.ts:5325-5359 — gate the tracking payload on run status: when `run.status` is CANCELLED (or COMPLETED with a SKIPPED stop), return `{ status, tracking: null }` instead of driverName / estimatedArrivalWindow. This is the one half that can ship independently.

UX CONSEQUENCE, stated explicitly:
- Cancel keeps its current meaning and its current recovery. Un-cancel still restores a run with its orders attached, `settleRun` still sees the same cash, `reopenStop` still reverses exactly its own stop. Nothing an operator can do today stops working.
- The cancel modal copy on routes/page.tsx:366 and routes/[id]/page.tsx:888 ("the route can be dispatched again") becomes TRUE for the first time — no copy change needed there. The dispatch modal at dispatch/page.tsx:229 should gain "…and their orders return to dispatch" so the released set is visible rather than inferred.
- NEW, and it must be surfaced: once released orders are re-dispatched onto a new run, un-cancelling the OLD run brings back a run whose stops no longer own those orders. That is visible and non-destructive (no money or history is lost), but the cancel modal must say the release is what makes it possible, and `reopenStop` should refuse a stop whose deliveryMutations exist but whose orders now belong to a different run.
- The buyer's mobile card (apps/mobile/app/(customer)/orders/[id].tsx:251-278) loses the driver name and the arrival window the moment a run is cancelled, which is the intended outcome — no mobile change is required, because the fields simply stop arriving.
- Held-for-settlement orders (guard 3) need a reason string in the dispatch builder's dropped-orders list, or the operator sees a silent short count again — the exact failure this bug is.

**Structurally preventable — yes.** Both halves of this class are mechanically detectable, and neither exists today.

A. NEW SCANNER SIGNATURE `pin-released-only-by-delete` (highest leverage, catches the write half). In .claude/skills/bug-hunt/scripts/scan-signatures.mjs, for every Prisma relation FK name F that appears as a non-null WRITE outside `create` (`F: <expr>` inside a `data:` object — the pin), collect every RELEASE site (`F: null` in a `data:` object) and resolve each site's enclosing method name. Flag F when 100% of its releases sit in methods matching /^(delete|remove|purge|destroy)/i. That is exactly B129: `routeRunStopId` is pinned by `createRun` (routes.service.ts:966) and released only by `deleteRoute` (:565,:572) and `deleteRun` (:1345,:1352). The rule generalizes to every claim/occupancy FK in the schema (driver assignment, shipment attachment, batch membership), and it states a real invariant: any link a non-destructive path can create must have a non-destructive path that releases it — or a documented reader that ignores it. Fixture pair: offender = a create-path pin plus a `delete*`-only null write; clean = the same plus a null write (or a status-gated reader) in a non-delete method. severity high, signal high.

B. NEW SIGNATURE `ungated-stale-parent-read` (catches the read half — getOrderTracking here, and B146). For any API read whose `include`/`select` pulls a parent that has a `status` enum in schema.prisma, flag the function when it returns fields off that parent and contains NO comparison against `<parent>.status` in the same function body. Every sibling reader in this repo already gates (orders.service.ts:449, :2945, :4720-4728, :5233-5243, change-requests.service.ts:55/:211, trips.service.ts:112-118), so the false-positive floor is low and the house pattern is already the majority.

C. TYPE-LEVEL (makes the omission a compile error, narrower but airtight). Replace `updateRunStatus`'s ad-hoc `const updates: any = { status: dto.status }` with an exhaustive effects map typed `satisfies Record<RouteRunStatus, TransitionEffect>`, where `TransitionEffect` declares both the row patch and an explicit `linkedOrders: "keep" | "release" | "reassign"` decision. Adding a status, or leaving CANCELLED undeclared, fails `tsc`. The `any` on :1445 is what let the branch be silently absent; killing it forces the author to answer the question this bug is. Applies equally to `updateStopStatus` (:1716) and `changeStatus` (orders.service.ts, drivers.service.ts) — the same three sibling sites.

## Test plan

**Tier T1** — The whole mechanism is server-side and unit-testable at the module boundary: the sweep predicate passed to order.updateMany, the trips where-clause, the absence of a link-nulling write in updateRunStatus, and the shape getOrderTracking returns. All of it runs pre-merge under Jest via Test.createTestingModule with a mocked PrismaService, which is the only tier that can gate the merge. Two additions cannot be T1 and belong in the batch build-plan as T3 manual rows: the four cancel-surface modal copies (three web, one mobile) and the buyer card's live loss of driverName/arrival window after a cancel.

**Proof token:** `REG-B129: cancelling a run releases its undelivered orders back to dispatch without clearing the stop link`

**Cases:**
1. REG-B129: after a run goes CANCELLED, createRun's sweep where-clause admits orders whose routeRunStopId points at a stop on that cancelled run — assert the `where` handed to order.updateMany carries the OR branch and that the sweep attaches them (attachedOrderCount > 0). Guards routes.service.ts:940-967.
2. REG-B129: the same widening does NOT admit orders on a SCHEDULED or IN_PROGRESS run — the sweep still skips them, so a live run cannot be poached mid-route.
3. REG-B129: TripsService's eligible-orders filter (trips.service.ts:181-195) returns an order pinned to a CANCELLED run, and checkEligibility returns ok for it while still returning ON_ACTIVE_RUN for SCHEDULED/IN_PROGRESS and PREVIOUSLY_DISPATCHED for a COMPLETED run.
4. REG-B129 (pin): updateRunStatus never writes routeRunStopId: null or routeRunId: null on the CANCELLED path — assert order.updateMany is not called at all from the cancel branch. This is the anti-regression for the refuted fix: it protects un-cancel, settleRun's cash basis and reopenStop's deliveredQty reversal.
5. REG-B129: un-cancel still works — CANCELLED → IN_PROGRESS on a run whose orders were never re-dispatched leaves every stop's orders attached, and findOneRun reports them.
6. REG-B129: an order carrying a CONFIRMED CASH payment against the cancelled run is HELD, not re-swept, while the run has no settlementNote — and becomes sweepable once settleRun has written one. Asserts settleRun's expected figure (getRunCashCollections, routes.service.ts:1484-1496) is unchanged across the cancel.
7. REG-B129: getOrderTracking returns { tracking: null } for an order whose linked run is CANCELLED — no driverName, no estimatedArrivalWindow — and still returns the full tracking payload for a SCHEDULED and an IN_PROGRESS run.
8. REG-B129: getOrderTracking on a COMPLETED run whose stop is SKIPPED also returns tracking: null (shares the fix with the B146 sibling; keeps the two from regressing apart).
