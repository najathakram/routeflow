# B775 · Mobile edit-items draft is keyed by productId, so a second line of the same product is overwritten at hydration and a Save with zero edits DELETEs it

## Root cause

Hunt B4 (fleet lead relay). Verified on origin/master 2ed80789 (2026-09-23). hydrateFromOrder writes next[li.productId] = {...} (edit-items-draft.ts:162) — two lines of one product collapse into one draft entry. order-item-diff.ts builds 'surviving' from the draft's lineIds; an original id not surviving becomes droppedDeletes → { id, action: 'DELETE' } (~:110-125). So opening a two-line order and pressing Save with NO edits deletes the collapsed line ($116 → $36 in the hunt's example). A DRIVER can reach it; unit-aware-guard does not catch it. FILER CHECK (fleet lead asked): CAN A NON-UNITS ORDER CARRY TWO SAME-PRODUCT LINES? YES — orders.service.ts create() maps dto.items one OrderItem per entry (:1925) with no dedupe; CreateOrderDto has no uniqueness guard on items; OrderItem (sales.prisma ~:772-852) has only @@index([orderId]) / @@index([productId]), no @@unique([orderId, productId]). (Promo free units live on the SAME line; the pending-order merge consolidates by productId, so neither creates duplicates — but it can inherit them.) Hence CRITICAL, not only a units_v1 case. SA-101: key the draft by LINE id. Owner: B707 lane, red-first on master; per the lead's rule, because CRITICAL it pushes FIRST and #1281 rebases onto it.

## Fix approach and UX

SA-103 FIX SHAPE (2026-09-23): the draft key is the line's identity — li.id, or new:<counter> for a new line — at every site, with a source pin; a scan merges into the first display-order line matching product AND unit as an UPDATE of that line's id; the diff stays keyed by line id, pinned: a zero-edit Save on a two-same-product order sends zero DELETEs and zero UPDATEs.
