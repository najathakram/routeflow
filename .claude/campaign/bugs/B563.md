## Reported evidence

Found during tonight's #926 close-out: post-deploy-check.mjs authenticates only as a tenant OPERATOR (SMOKE_OPERATOR_USERNAME/PASSWORD against the e2e-routeflow tenant) and therefore structurally cannot verify anything behind SUPER_ADMIN auth -- including the exact platform-dashboard MRR reconciliation (mrr vs ledgerMrr) this whole day's B556/B557 work was about. Closing out #926, neither the fleet lead nor the landing coordinator could run that specific check from a session, not because a script is missing but because putting live super-admin credentials into an agent session is correctly the owner's call, never something sessions should arrange between themselves. Same shape as several findings filed today (B540/B559 overflow-detection blind spots, lessons L-202/L-205 -- assertions/checks that don't test what they claim): a gate that reports green while structurally unable to see an entire class of regression, here anything platform-admin/super-admin-only. Tooling/process gap, not a live bug. Recommended fix shape, either: (a) a SEPARATE post-deploy check tier gated on an explicit opt-in with owner-provisioned super-admin credentials (never defaulted/hardcoded), run only when someone with that authorization triggers it; or (b) at minimum, post-deploy-check's own output should say plainly 'platform-admin surface NOT checked' rather than reporting unqualified success, so a green run is never mistaken for full coverage.
