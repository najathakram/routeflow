# B844 · vendor-bill scan claim races nextBillNumber (read-then-write outside the tx), so two concurrent bill creates can collide on the bill number before either reaches the claim

## Root cause

Found by the vendor-bills lane while building #1352's (B710) real-Postgres race spec, fleet lead relay 2026-09-24. nextBillNumber is read-then-write OUTSIDE the transaction that claims the scan, so two concurrent bill-create requests can both read the same next number and collide on it (a P2002 unique-constraint error) before either reaches the scan-claim logic #1352 covers. #1352's own spec stubs the numbering to isolate the claim behaviour, so it does not exercise this. Needs its own fix (numbering allocation moved inside the claiming tx, or a retry-on-P2002 loop) and its own red-first spec. Owner: vendor-bills lane, after #1352.
