# B211 · Completing a run with a SKIPPED stop strands its orders on the happy path, exactly as cancelling does

**Location** `apps/api/src/routes/routes.service.ts — updateRunStatus COMPLETED gate` · **Severity** critical · **Batch** F11 · **State** queued

## Summary

Completing a run is allowed while stops are still SKIPPED — `updateRunStatus`'s COMPLETED gate filters `s.status !== "COMPLETED" && s.status !== "SKIPPED"` (apps/api/src/routes/routes.service.ts:1424), by design — but nothing releases those stops' orders. The run row is the only thing written (:1445-1451), so every order the dispatch sweep pinned to a skipped stop (`data: { routeRunId: run.id, routeRunStopId: s.id }`, :966) keeps that link on a finished run forever. `createRun`'s sweep predicate (`routeRunStopId: null`, :945) and `TripsService`'s DB filter (apps/api/src/trips/trips.service.ts:189) both require a null link, and `checkEligibility` (:112-125) names the result out loud: `PREVIOUSLY_DISPATCHED` / "Attached to a finished run (stale link)".

This is B129's exact mechanism and B129's exact outcome, reached on the HAPPY PATH with no cancel involved. B129 was scoped to CANCELLED runs only and explicitly left COMPLETED "to reopenStop"; this record is the scope extension that closes that gap, and it was filed from the F11 synthesis (`.claude/pipeline/2026-09-02-F11-run-cancel-skip/discovery.md` Risks §9), not from the bug register.

The extension is not optional bookkeeping: B34 and B146 make a driver-initiated skip reachable for the FIRST time, so this batch increases the frequency of the one strand it does not cover.

## What this feature is for

SKIPPED is the run's honest "not delivered today, and here is why" state — the whole point of B34 and B146. A run that ends with skipped stops is a NORMAL, successful day: the driver closed out, the delivered stops are billed, and the goods that could not be dropped are supposed to go back in the pool for tomorrow's run or an ad-hoc trip. That is why the completion gate deliberately accepts SKIPPED alongside COMPLETED (routes.service.ts:1424) rather than forcing the driver to fake a delivery to close the run.

The feature this record protects is therefore the second half of that promise: closing a run must leave its undelivered orders dispatchable. Cancel is the abnormal exit (B129's lane); completing with skips is the routine one, and it is the one with no release path at all.

## Root cause

MECHANISM (verified at HEAD in this worktree).

1. `updateRunStatus` (apps/api/src/routes/routes.service.ts:1368) admits COMPLETED while stops are SKIPPED: `const incomplete = stops.filter((s) => s.status !== "COMPLETED" && s.status !== "SKIPPED")` (:1424), and only blocks on `incomplete.length > 0` (:1425-1429). The R7a/B152 physical-money backstop (:1435-1443) is the only other gate.
2. It then writes ONE row: `const updates: any = { status: dto.status }` (:1445) plus startedAt/completedAt, applied at :1449-1456 to `routeRun` alone. There is no transaction, no `order.updateMany`, and no branch per destination status — the identical shape B129 documents for the CANCELLED path.
3. The pin is therefore permanent. `createRun`'s sweep wrote `{ routeRunId: run.id, routeRunStopId: s.id }` at :966; the only writers of `routeRunStopId: null` repo-wide are `deleteRoute` (:565, :572) and `deleteRun` (:1345, :1352), and `deleteRun` refuses any run carrying a recorded delivery (:1328-1338, "This run has recorded deliveries; cancel it instead of deleting.").
4. Both dispatch readers exclude the pinned order structurally: `createRun`'s sweep predicate `routeRunStopId: null` (:945) and TripsService's DB filter of the same key (trips.service.ts:189, whose comment says the in-memory check would reject them anyway). `checkEligibility` (:112-125) returns ON_ACTIVE_RUN only while the run is SCHEDULED/IN_PROGRESS and otherwise `PREVIOUSLY_DISPATCHED` — "Attached to a finished run (stale link)".

**Defect class:** `terminal-transition-without-link-cascade` — B129's class exactly, at the sibling transition. B129's own record already names this site as its highest-value sibling ("skip a stop → complete the run → its orders are stranded identically ON THE HAPPY PATH") and notes that only the tracking half of it was ever registered (as B146); the strand half is this record.

WHAT THE RECOVERY ACTUALLY IS, AND WHY IT DOES NOT SAVE THE USER. B129 was allowed to leave COMPLETED alone because `reopenStop` "owns that path". `reopenStop` (:2682) does accept a SKIPPED stop (:2695-2697), resets it to PENDING (:2831-2847) and flips a COMPLETED run back to IN_PROGRESS (:2860-2864) — so the API-level escape exists. But it is unreachable from any product surface:

- The endpoint `POST /route-runs/:id/stops/:stopId/reopen` (routes.controller.ts:310-318) has exactly ONE client repo-wide: `useReopenStop` (apps/mobile/lib/api/routes.ts:674-683).
- Its only caller is the operator mobile screen (apps/mobile/app/(operator)/route-runs/[id].tsx:77, :185-202), and the control renders **only** for `s.status === "COMPLETED"` (:461-463). A SKIPPED stop falls through to the `: null` branch at :468 — no reopen button, no skip button, nothing.
- `apps/web` has no stop-reopen caller at all (grep for `/reopen` across apps/web finds only invoices and orders).

So for the state this bug describes, the recovery is API-only and invisible. The user-facing outcome is identical to B129's: no error, no banner, no count — tomorrow's run is simply built short.

## User impact

WHO. Every operator and every driver on every tenant that dispatches routes. Nothing is flag-gated: the completion path is the ordinary end of a delivery day, and closing a run with a skipped stop is the outcome the product explicitly permits (routes.service.ts:1424).

HOW OFTEN — stated honestly, because it changes across this batch:

- **Today**, SKIPPED has exactly one live writer: the operator mobile screen's skip control (apps/mobile/app/(operator)/route-runs/[id].tsx:164-183, :466), because the driver's own Skip button is dead — that is B34. So the strand fires once per operator-skipped stop.
- **After B34 and B146 land**, a driver skips at the door and the same strand fires once per undeliverable stop on every run: closed shop, nobody home, refused delivery. That is routine, not an edge case. This batch is what makes the uncovered path frequent, which is why it must not ship without this record.

WHAT IT COSTS. The skipped stop's orders silently stop existing for dispatch. They are not DELIVERED and not CANCELLED, so the sweep's status filter (:944) would happily take them — only the stale `routeRunStopId` excludes them (:945). No error, no banner, no count; the next day's run is built without them and comes up short, exactly as in B129. The goods stay undelivered and unbillable.

THE ESCAPES ARE ALL CLOSED, WHICH IS WHY THIS IS NOT MERELY UNTIDY:

1. `reopenStop` would work at the API level (:2695-2697) but no surface offers it for a SKIPPED stop — the operator's reopen control renders only for `s.status === "COMPLETED"` (apps/mobile/app/(operator)/route-runs/[id].tsx:461-463) and web has no caller at all. The recovery exists only for someone holding a bearer token and curl.
2. Delete is doubly refused: the web Delete button is gated `canDelete = isOperator && run.status === "SCHEDULED"` (apps/web/app/(dashboard)/routes/[id]/page.tsx:853), and `deleteRun` itself rejects any run with a recorded delivery (:1328-1338) — which a completed run necessarily has.
3. Un-cancel does not apply: this run was never cancelled. The whole B129 recovery story is unavailable here.

COMPOUNDING (shared with B146). `getOrderTracking` (apps/api/src/orders/orders.service.ts:5301) early-returns only on a missing stop link, so the buyer's card keeps rendering off a stop on a run that finished without them. B129's case 8 and B146's read-side branch already own that copy; this record owns the write-side release.

WHY CRITICAL. Permanent wrong state in the database, reached by the normal happy path, invisible at every surface, with no in-product recovery and undelivered goods sitting behind it. The only thing arguing lower is that today's trigger needs an operator action — and this batch removes that limit.

## Fix approach and UX

**This is a SCOPE EXTENSION of B129, not an independent fix. It ships in PR1, with B129, by the same author, in the same edit.** B129's policy is `links are never nulled; readers gate on run/stop status` — B211 adds one branch to the two readers B129 is already rewriting. Landing it separately means two agents editing one `where` clause.

DO NOT "fix" this by tightening the completion gate. Rejecting COMPLETED while a stop is SKIPPED (routes.service.ts:1424) would force a driver to fake a delivery or leave the run open overnight, and it destroys the feature B34/B146 exist to build. The gate is correct; the missing release is the bug.

1. **Sweep predicate** — apps/api/src/routes/routes.service.ts:940-967. B129 widens `routeRunStopId: null` (:945) to an `OR` admitting orders whose stop belongs to a CANCELLED run. Add ONE more branch, narrower than it looks: `{ routeRunStop: { status: "SKIPPED", routeRun: { status: RouteRunStatus.COMPLETED } } }`. Both keys are load-bearing — a COMPLETED stop on a COMPLETED run is delivered work and must stay excluded, and a SKIPPED stop on a SCHEDULED/IN_PROGRESS run must stay excluded because the driver can still come back (the SKIPPED to IN_PROGRESS un-skip is a tested allowance, routes.service.stop-state-guards.spec.ts:365-373, and B146 makes it re-promote the order).
2. **Trips** — apps/api/src/trips/trips.service.ts:181-195 takes the same third branch, and `checkEligibility` (:112-125) narrows its `PREVIOUSLY_DISPATCHED` return by the same predicate so the picker and the DB filter cannot disagree. Today `checkEligibility` decides purely on `run.status` being SCHEDULED/IN_PROGRESS; it must now also read the STOP's status, so the `include` that feeds it needs `routeRunStop.status` alongside `routeRunStop.routeRun`.
3. **Money guard — inherit B129's guard 3 uniformly; do not branch it.** B129 holds any order carrying a CONFIRMED CASH/CHECK payment against its current `routeRunId` until that run has a `settlementNote`. Applied to this branch it is close to a no-op by construction, and that is worth writing down rather than discovering: `updateRunStatus` already refuses to complete a run with unsettled physical money (`getUnsettledPhysicalMoney`, :1435-1443), and a SKIPPED stop's orders were never delivered, so they carry no delivery payment. Keeping the guard shared costs nothing and keeps one predicate instead of two.
4. **No write to `updateRunStatus`.** The COMPLETED path keeps writing only the run row (:1445-1451). This record adds NO order mutation anywhere — same discipline as B34 step 4 and B129 case 4. The pin is what lets `reopenStop` still find `stop.orders` (:2686, :2769).

UX CONSEQUENCE, stated explicitly:

- A run that ends with skipped stops finally does what operators already believe it does: the skipped customers' orders come back in tomorrow's dispatch pool. Nothing an operator can do today stops working, and no copy currently claims otherwise — the completion flow makes no promise about skipped orders at all, and that silence is the bug's cover.
- **New hazard, identical in shape to B129's:** once a released order has been re-swept onto a NEW run, reopening the old skipped stop yields a stop whose orders now belong elsewhere. It is visible and non-destructive (no money or history is lost), but `reopenStop` must state its choice rather than fall into one — either refuse a stop whose orders have moved, or reopen without re-pinning. B129 raises the same question for un-cancel; answer it ONCE, in PR1, for both.
- **OPTIONAL follow-on, deliberately out of scope here:** the operator screen offers a reopen control only for `s.status === "COMPLETED"` (apps/mobile/app/(operator)/route-runs/[id].tsx:461-463), so a SKIPPED stop has no reopen affordance even though the API accepts one (:2695-2697), and `apps/web` has no stop-reopen caller at all. That is a real dead end, but it is a mobile-UI change in a file F11 already lists as a B32/B129 conflict — file it separately rather than widening PR1.

**Structurally preventable — yes, by the signature B129 already proposes.** `pin-released-only-by-delete` (discovery.md Structural opportunities item 3) flags `routeRunStopId` precisely because its only release sites are `deleteRoute` (:565, :572) and `deleteRun` (:1345, :1352). One signature covers B129 and B211 together; do not write a second. `terminal-status-no-cascade` (item 4) is the complementary catch on `updateRunStatus`'s single-row write.

## Test plan

**Tier T1 — ruled, not defaulted.** Every assertion is server-side and unit-testable at the module boundary: the `where` handed to `order.updateMany` by `createRun`'s sweep, the trips `where`, `checkEligibility`'s return, and the ABSENCE of an order write in `updateRunStatus`. All of it runs pre-merge under Jest via `Test.createTestingModule` with a mocked PrismaService, which is the only tier that can gate the merge — and this record's entire content is a predicate, which is exactly what a T1 case pins. It shares B129's spec file (apps/api/src/routes/routes.service.spec.ts) because it shares B129's predicate; a separate file would let the two branches of one `OR` regress apart. Nothing here needs a device or a browser, so there is no T2 and no T3 row.

**Proof token:** `REG-B211: completing a run releases its SKIPPED stops' orders back to dispatch without clearing the stop link`

**Cases:**

1. REG-B211: after a run goes COMPLETED with one SKIPPED stop, `createRun`'s sweep `where` carries the SKIPPED-on-COMPLETED branch and the sweep attaches that stop's order (`attachedOrderCount > 0`). Guards routes.service.ts:940-967.
2. REG-B211: a COMPLETED stop on the same COMPLETED run is NOT admitted — delivered work is never re-dispatched. This is the case that makes branch 1 narrow instead of "any finished run".
3. REG-B211: a SKIPPED stop on a SCHEDULED or an IN_PROGRESS run is NOT admitted, so a live run cannot be poached mid-route and the un-skip allowance (routes.service.stop-state-guards.spec.ts:365-373) still has an order to re-promote.
4. REG-B211: `TripsService`'s eligible-orders filter (trips.service.ts:181-195) returns the SKIPPED-on-COMPLETED order and `checkEligibility` returns ok for it — while still returning `PREVIOUSLY_DISPATCHED` for a COMPLETED stop on a COMPLETED run and `ON_ACTIVE_RUN` for a live one. Picker and DB filter must agree on all three.
5. REG-B211 (pin): `updateRunStatus` never writes `routeRunStopId: null` or `routeRunId: null` on the COMPLETED path — assert `order.update` and `order.updateMany` are not called from it at all. The mirror of REG-B129 case 4 and REG-B34 case 4, and what keeps `reopenStop`'s `stop.orders` (:2686, :2769) non-empty.
6. REG-B211: `reopenStop` on the SKIPPED stop of a COMPLETED run still resets the stop to PENDING and flips the run back to IN_PROGRESS (:2831-2847, :2860-2864) after the widening — and, for an order that has since been re-swept onto a new run, behaves as PR1 decided (refuse, or reopen without re-pinning) rather than silently stealing it back.
7. REG-B211: the completion gate is UNCHANGED — COMPLETED is still accepted with SKIPPED stops (:1424) and still rejected with a PENDING or IN_PROGRESS stop. This is the anti-regression for the tempting wrong fix; without it a builder can turn this record green by breaking B34.
8. REG-B211 (money): completing a run that still holds unsettled cash or checks is still refused (`getUnsettledPhysicalMoney`, :1435-1443), so no release can happen behind unsettled physical money. Pairs with REG-B129 case 6 rather than duplicating it.
