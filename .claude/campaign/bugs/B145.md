## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** Turning on a notification cell in Settings → Notifications makes the customer actually receive it, and a message recorded against a customer means it really went out.

**Actually does.** EMAIL, WHATSAPP and SMS dispatch to a stub provider that logs a line and returns status "queued", never "failed"; PORTAL skips the provider entirely. Both then write a Message row, bump the thread's unread count, and return outcome "sent".

**The gap.** A delivery that never happened is persisted as a delivered message plus an unread-count bump, with no failure signal anywhere.

**Evidence.** Evidence · apps/api/src/messaging/messaging.service.ts:79-81, :139-151 (only status === "failed" aborts), :153-176 (Message.create + thread bump + outcome "sent"); apps/api/src/messaging/providers/stub.provider.ts:15-22; messaging.module.ts:22 (the only MESSAGE_PROVIDER binding in the repo outside specs); messaging-config.service.ts:78-86 (defaults include INVOICE_SENT:EMAIL, OUT_FOR_DELIVERY:PORTAL, DELIVERED:PORTAL); no EmailService import anywhere under apps/api/src/messaging; GET /messaging/threads (messaging.controller.ts:76-84) has zero client readers, and MessageThread is referenced nowhere outside apps/api.

**Suggested fix (register).** Make the un-transported channels honest: have the stub return a non-delivered status (or gate provider channels behind a configured-adapter check) so sendMessage records "skipped"/"failed" instead of writing a Message and bumping the thread, and surface "channel not configured" on the matrix cell.

> ⚠️ Treat this as a hypothesis, not a plan. On F11 the adversarial pass refuted the
> suggested fix for every one of the four bugs while confirming every diagnosis.

**Verifier's note.** Verified on master; the module has bound the stub since the original messaging PR and was never swapped. Two nuances narrow the blast radius without refuting it: the default-ON invoice-sent email cell fires from inside the real invoice-email action, so that customer does get a genuine email from EmailService independently of the engine, and order status changes fire a real push through the notifications service — so DELIVERED is not wholly silent. The engine's own record is false in every case. Distinct from B37, which is the run-chat /messages module.
