## Fix approach and UX

Attempted the 10 safe bumps via npm update / npm overrides (not --force, no major versions touched). Every lockfile-changing npm operation in this sandbox -- even ones scoped to just one unrelated package -- aborts with EBADENGINE on @zxing/library@0.23.0 (apps/mobile, pinned exactly in the committed package-lock.json), which requires Node >=24; this sandbox runs Node 22.22.2 and the repo sets engine-strict=true. That pin predates this session (introduced by #685, a Dependabot minor/patch sweep, landed on 0bfb58b) and is baked into the CURRENT COMMITTED lockfile's own engines field for the exact locked version -- not a registry-metadata artifact of this sandbox. CI pins Node 20 (< 24) with the same engine-strict=true, so this looks like it would also block npm ci there; worth an owner check against actual recent CI runs, since it would affect every contributor's install, not just this fix. Did not attempt a workaround (e.g. --engine-strict=false) since that overrides a deliberate repo setting. Net: the safe 10-package bump is designed and ready but UNAPPLIED -- needs an environment with Node >=24 (or the zxing pin resolved first) to actually run npm install/update and the workspace test suites before this can land.

## Test plan

T1: after the safe 10-package bump lands (in a Node>=24-capable environment), re-run node scripts/ci-audit-critical.mjs (critical, expect 0 unchanged) and node scripts/ci-audit-critical.mjs --level high --report-only (expect 6 remaining, all major-bump-only) plus apps/api + apps/web + apps/mobile jest to confirm no regressions from the transitive bumps.
