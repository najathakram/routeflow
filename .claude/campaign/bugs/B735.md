# B735 · Inline-returns capture screen shows unconditional success even when the ledger reversal was parked

**Location** `apps/api/src/returns/inline-returns.service.ts:93 (reverseLedgerForReturn, returns void) called from capture() line 310; apps/web inline-returns capture dialog (#1250)` · **Severity** medium · **State** uncampaigned

## Summary

INVESTIGATED & CLEARED — side observation from F2's B735 capture fixture (fleet lead + Lane IR read-only check, 2026-09-23): inline-return quotes for orders 2 and 3 of the same customer+product drew goods from order 1's line. NOT A DEFECT. Remaining returnable qty is tracked per (sourceOrderId, productId) and re-derived on every quote — returnedPiecesByProduct is order-scoped (apps/api/src/returns/returns-pieces.util.ts:113-142); priceInlineReturn's remainingByKey = max(0, sold - priorReturned) per sourceOrderId (inline-returns-quote.service.ts:171-201); allocateReturnedPieces caps each line by its OWN order's remaining (inline-returns-pricing.ts:169-197, cap :186). A quote fills newest invoice first (:302) and caps/spills when an order's remaining is exhausted — nothing pooled or double-counted. The per-(order, product) vs per-invoice-line attribution is a documented audit-trail nuance (inline-returns-pricing.ts:161-167), not a qty error — not filed. (B766 was held for this and is released unused.)

## Reported evidence

The inline-returns capture screen (#1250) displays a return number, credit note and refund amount on every successful capture. Underneath, capture() calls reverseLedgerForReturn(), which the B681 park guard (#1255, merged same batch) can now silently PARK instead of reversing when the row's basis can't be safely determined -- the function returns void, and the only signal is a server-side warning log. Neither the capture response type nor the dialog carries any notion of a park, so an operator completing a return has no way to know one happened. The money itself is not wrong -- parking is money-safe by design, that is the point of the guard -- but parked rows accumulate invisibly and surface only much later when a period filing is blocked (see B681), at which point whoever investigates has far less context than at the moment of capture. Neither #1250 nor #1255 introduced this gap alone; it exists only because both landed in the same batch, which is exactly what an individual PR review cannot see. Suggested shape (from the finder, not prescribed): carry a parked count/flag through the capture response and surface it in the dialog.
