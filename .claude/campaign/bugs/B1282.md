# B1282 · Feature overrides: the pilot-ending job keeps the LAST row for a key, allActive() keeps the FIRST (latent; one live row per key is DB-enforced today)

**Location** `apps/api/src/billing/feature-override-review.job.ts:251-260; apps/api/src/billing/feature-override.service.ts:120-126,189-197` · **Severity** low · **State** uncampaigned

## Summary

Latent: two copies of the override rule disagree on a same-key tie (job last-wins, allActive first-wins), but the partial unique index allows one live row per key, so it cannot happen today. Repro (unit only, the DB refuses step 1 with P2002): job prisma mock otherRows = [{K, GRANT, null}, {K, DENY, null}] gives otherOverrides K=DENY; FeatureOverrideService fed the same rows gives allActive() K=GRANT.

## What this feature is for

SA-1100 rule 5 (R25): the nightly pilot-ending job (FeatureOverrideReviewJob.warnBillablePilotsEnding) emails the owner once when a billable free period ends within the horizon. It decides 'paid' with billablePilotEnding(), which needs the business's OTHER live overrides; the served answer (EntitlementAuthority, /tenants/me/addons) reads the same overrides through FeatureOverrideService.allActive().

## Root cause

Two copies of the 'which override applies' rule disagree on a tie. Job: feature-override-review.job.ts:251-260 loops otherRows and calls otherOverrides.set(o.featureKey, o.effect), so for two live rows on one key the LAST row wins. Service: feature-override.service.ts:120-126 rowAt() uses rows.find(), so allActive() (:189-197) keeps the FIRST. Neither query has an orderBy (job :245-248, service activeRows :103-106), so either order is the database's. Class: a second hand-rolled copy of a shared rule (the job re-implements the live filter at :257-258 too). REACHABILITY: the precondition cannot occur today. Migration 20260916050000_tenant_feature_override/migration.sql:32-34 creates the partial unique index TenantFeatureOverride_active_key on (tenantId, featureKey) WHERE revokedAt IS NULL; both readers filter revokedAt: null; and create() auto-revokes an expired-unrevoked row before inserting (feature-override.service.ts:259-268). So at most one non-revoked row per key exists, and the two rules give the same answer on all real data. It becomes live only if that index is dropped or relaxed (e.g. to allow stacked/overlapping grants).

## User impact

None today (unreachable). If the unique index is ever relaxed, the owner could be warned about a free period whose feature the business would still be served by another GRANT (or not warned when it would lose it). Severity low: latent, review finding from #4194 (readers A and B).

## Fix approach and UX

Have the job read the other overrides through FeatureOverrideService (allActive(tenantId) minus the row's own key, or an exported rowAt-equivalent), so one rule exists. Optional structural guard: a census pin that only feature-override.service.ts derives an effect from TenantFeatureOverride rows. No UX change.
