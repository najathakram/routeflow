## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** Marking an order DELIVERED is what makes it billable, so every path that delivers an order should leave it with an invoice — or tell the operator it could not.

**Actually does.** Both driver completion paths flip their linked orders with a raw tx.order.updateMany({ data: { status: DELIVERED } }), bypassing OrdersService.changeStatus — the only status writer that runs the delivery side effects. completeStop ensures no invoice and settles no credits at all. completeWithPayment ensures one only when money is collected: its recordDeliveryPaymentInTx call is guarded if (dto.payment && dto.payment.amount > 0), and payment is @IsOptional() on the DTO.

**The gap.** Whether a delivered order ever reaches AR depends on whether the driver happened to take money at the door — an intermittent hole, not a clean one, which is why it has survived: the paid case works, so the flow looks correct in testing. A stop completed without collection leaves goods delivered and nothing billed, with no error, no flag and no sweep. F07 (#588) made changeStatus's DELIVERED branch conserving — awaited auto-invoice with a ConflictException retry, operator-visible failure, retried credit settle — and none of it applies here.

**Evidence.** Evidence · apps/api/src/routes/routes.service.ts completeStop (the "3. Mark linked orders as DELIVERED" block inside its tenantTransaction) and completeWithPayment (byte-identical block, plus the if (dto.payment && dto.payment.amount > 0) guard on the recordDeliveryPaymentInTx call); apps/api/src/routes/dto/complete-with-payment.dto.ts (@IsOptional() payment); apps/api/src/invoices/invoices.service.ts recordDeliveryPaymentInTx (contract: "ensure a finalized invoice exists — reconcile an open DRAFT, else create one from the order" — findOpenOrderDraft then createInvoiceFromOrder), which is why the PAID case is already covered; apps/api/src/orders/orders.service.ts changeStatus DELIVERED branch (B105/B108, #588). Confirmed on master@7dcf390c. Deliberately NOT in scope: routes.service.ts's other three order.updateMany calls — deleteRoute and deleteRun write {routeRunId: null, routeRunStopId: null}, and createRun uses status only as a WHERE filter while writing routeRunStopId. None writes status; an earlier "five sites" reading was an over-broad grep.

**Suggested fix (register).** Extract the "ensure this delivered order is billed, then settle its credits" side effect into one helper and call it from all three places. Three implementations already exist — changeStatus's inline retry loop, recordDeliveryPaymentInTx's reconcile-else-create, and completeStop's absence — and that triplication is the defect class. Do NOT route through changeStatus: it opens its own transactions (Serializable for the settle), re-runs role gates and the transition matrix and fires notifications, so calling it from inside completeStop's open transaction would nest transactions and re-run guards. Note that F07's ConflictException retry works because each attempt is a fresh transaction — inside an already-open tx a failed statement can abort it, so the helper cannot inherit that retry shape unchanged. Belongs to F11 (routes lane) and should be sequenced after F10, which currently has uncommitted work in both functions.
