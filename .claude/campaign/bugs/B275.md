## Reported evidence

F16b/B100 cause refutation + engine final pass, 2026-09-08: reserveNext's collision-guarded path (numbering.service.ts:196-234) is a read-modify-write loop that calls the caller-supplied exists(candidate) predicate once per candidate number, advancing n and re-checking (capped at 10,000 iterations, :212-222) rather than computing a bulk max in one query. No live mint site wires an exists predicate in yet (the doc comment at :47-51 calls this "a deferred cross-module change"), so today the cost is latent - but B100's history note says F16b will wire this into all five invoice/estimate mint sites, and the collision path is exactly what a lazily-seeded or import-heavy tenant's first live mint will exercise. If the caller's exists predicate itself does a per-candidate table scan (the naive way to answer "does this number exist"), a long collision run repeats that scan up to 10,000 times inside one guarded transaction instead of computing a numeric max once. Recommend backing exists with an indexed exact-match lookup (cheap per call), or seeding nextNumber from a cached/indexed max instead of a pure collision walk, once real volumes hit this path. Note: verified against current code before filing - no function named scanMaxForYear or any regexp_match-based scan exists in this file today; this row describes the real collision-guard mechanism that occupies the same role.
