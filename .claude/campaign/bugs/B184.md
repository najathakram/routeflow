## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** Continuously-written telemetry is bounded by some retention policy so the table and its indexes do not grow forever.

**Actually does.** There is no expiry column, no scheduled prune, and the only deleter is a destructive manual tenant wipe.

**The gap.** A missing retention policy on an append-only telemetry table — a growth and cost concern rather than wrong behaviour.

**Evidence.** Evidence · apps/api/prisma/schema.prisma:919-938 (the model has no expiry field, plus two composite indexes); repo-wide grep for the model in apps/api returns only schema.prisma:427/919, drivers.service.ts:105 (create), routes.service.ts:734 (read) and scripts/wipe-tenant-fresh-start.js:99; none of the nine cron-bearing services reference it; cadence at apps/mobile/lib/location-tracker.native.ts:61-71 (30-second interval, 50-metre distance filter, automatic pausing).

**Suggested fix (register).** Add a nightly cron that deletes breadcrumbs older than a configurable window (e.g. 90 days), keeping a per-run summary or polyline if history is needed for disputes.

> ⚠️ Treat this as a hypothesis, not a plan. On F11 the adversarial pass refuted the
> suggested fix for every one of the four bugs while confirming every diagnosis.

**Verifier's note.** The row-count arithmetic was reproduced (roughly 960 pings per driver-day, so about 14.4M rows a year at 50 drivers) but it is an upper bound only: the distance filter gates delivery and automatic pausing suppresses stationary samples, so real volume is materially lower. No incorrect data and no broken user-visible behaviour — the same missing-enhancement class the register has cleared before.
