# B269 · Third PaymentCounter mint site emits PAY-#### with no tenant segment; the other two emit PAY-<tenantShort>-####

**Location** `Finance - invoices (batch payment allocation numbering)` · **Severity** medium · **Batch** F31 · **State** done

## Summary

Confirmed, severity raised. InvoicePayment.paymentNumber is globally unique but only two of three PAY-#### mint sites embed the tenant segment; the third collides across tenants and can permanently stall a Stripe settlement.

## What this feature is for

Mints the payment reference number (PAY-####) shown on a recorded payment or settlement.

## Root cause

Sites 1/2 in invoices.service.ts format PAY-tenantShort-####; the batch-allocation/settlement site (reached from payment-requests.service.ts's writeSettlement) omits the tenant segment and reuses the same global counter keyed off getTenantId() or singleton - two tenants' first settlements both mint PAY-0001, and the losing create's P2002 is uncaught. Because the mint sits inside the settlement's rolled-back transaction, a Stripe webhook redelivery re-mints the identical colliding number, so the request stays SETTLING forever even though the card was charged.

## User impact

A live cross-tenant 500 on a money path, plus a Stripe settlement that can never complete once it collides - the buyer's card stays charged with no resolution.

## Fix approach and UX

One shared nextPaymentNumber(tenantId) helper in invoices.service.ts used by all three sites - requires a non-empty tenantId (null throws BadRequestException, never singleton), reserves the tenant's PaymentCounter row in a short standalone transaction committed before the payment tx opens, formats PAY-tenantShort-#### everywhere. Not routed through NumberingService.reserveNext, since its PAYMENT default would put sites 1/2 onto the broken format.

## Test plan

DB-lane payment-numbering.db.spec.ts (REG-B269 A-C): two tenants' first settlements mint distinct numbers; a rolled-back booking's reserved counter survives so a retry advances past its start value; a null-tenant booking refuses instead of writing singleton. Green-only sibling pin: sites 1/2's existing format is unchanged. Unit pins assert the helper's tenant requirement, format, and that its counter write is not on the payment tx's client.

## Reported evidence

F16b/B100 cause refutation + engine final pass, 2026-09-08: invoices.service.ts has three PaymentCounter-backed mint sites sharing one counter (tx.paymentCounter.upsert) but formatting it differently. :4683 and :4979 (the latter commented "mirrors recordPayment's counter") both emit PAY-${tenantShort}-${String(counter.next-1).padStart(4,"0")}. :5282, inside the batch-allocation payment path, emits PAY-${String(counter.next-dto.allocations.length+i).padStart(4,"0")} - no tenantShort segment. Two payment-number formats coexist inside one tenant depending on which recording path was used (single vs batch allocation) - the same hand-copied-mirror-drift mechanism L-072 names for enums, here applied to a number format instead of one shared formatter.
