## Reported evidence

On 2026-09-07 (#652, master 1b413d07) the visibility-flip routine flipped the repo private 7 seconds after the api deployment reached BUILDING, per docs/runbooks/deploy-visibility-flip.md step 3 as it read that day. Both the api and web 1b413d07 deployments then FAILED at the code snapshot with no build log -- the same race the runbook already named for INITIALIZING (Railway GitHub App token invalidation mid-clone), just reachable a step later than the existing rule assumed. #650s 3-second flip at BUILDING had succeeded two runs earlier, which was timing luck, not evidence BUILDING is safe. railway redeploy refuses to redeploy a FAILED deployment; railway up is unsafe here (no .railwayignore, and this repos worktrees live under the root checkout). Recovery used: an empty chore(deploy): retrigger ... commit pushed as master from a spare worktree while the repo was still public, producing master e234bc03 (tree identical to 1b413d07), which reached SUCCESS on both services. Fix applied in this bookkeeping pass: docs/runbooks/deploy-visibility-flip.md step 3/4 and Failure modes, plus CLAUDE.md Canonical deploy flow step 4, now require BOTH deployments at SUCCESS (~2.5 min after merge) before the private flip -- never BUILDING.
