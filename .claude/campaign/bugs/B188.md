## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** Generating an invoice PDF for a transaction renders the calling tenant's own invoice, uploads it, and records the object key on that tenant's transaction — with the same tenant scoping its sibling getPresignedUrl gained in the F1-002 security fix.

**Actually does.** generateInvoicePdf fetches the transaction with a bare findUnique (full customer, order, items and payments), renders and uploads the PDF, returns a working presigned URL for it, and persists pdfUrl with a bare update — no step checks tenantId. Handed any other tenant's transactionId, it exfiltrates that tenant's complete invoice as a 15-minute presigned URL and overwrites that tenant's Transaction.pdfUrl.

**The gap.** The F1-002 fix hardened the read path (getPresignedUrl, ten lines below) but never touched the generate path — and because the method runs in a Bull processor with no request context, the job payload carries only transactionId, so there is nothing to scope by even where forTenant() would otherwise apply.

**Evidence.** Evidence · apps/api/src/bookkeeping/invoice.service.ts:37-53 (generateInvoicePdf — bare this.prisma.transaction.findUnique with full include: customer, order, items, payments), :86-89 (bare transaction.update writing pdfUrl), :91 (returns the presigned URL of the rendered PDF); contrast :96-110 (getPresignedUrl via forTenant() with the F1-002 comment); apps/api/src/bookkeeping/invoice.processor.ts:16-22 (sole caller — Bull @Process("generate-invoice"); GenerateInvoiceJobData = transactionId only, invoice.processor.ts:6-8); apps/api/src/bookkeeping/bookkeeping.module.ts:33 (queue registered); apps/api/src/orders/orders.service.ts:78 (@InjectQueue("invoices") injected — and grep across apps/api/src finds NO invoiceQueue.add or .add("generate-invoice") anywhere: the producer was never wired).

**Suggested fix (register).** Carry tenantId in GenerateInvoiceJobData and scope both queries by it — findUnique becomes findFirst({ where: { id, tenantId } }) and the update becomes updateMany({ where: { id, tenantId } }) — refusing the job when no row matches; apply the same guard to any future synchronous caller before the queue gains a producer.

> ⚠️ Treat this as a hypothesis, not a plan. On F11 the adversarial pass refuted the
> suggested fix for every one of the four bugs while confirming every diagnosis.

**Verifier's note.** Currently dormant, and severity is set accordingly: nothing in the codebase enqueues a "generate-invoice" job and no controller calls generateInvoicePdf, so there is no HTTP-reachable exploit today. It is registered at High rather than Low-dead-code because it is a latent cross-tenant read+write of exactly the shape F1-002 was raised for, sitting in the same file as its fixed sibling, and the queue injection in OrdersService shows the producer is intended — the moment it is wired (or anyone with Redis access enqueues a job), this is a Critical cross-tenant invoice exfiltration plus a foreign-tenant write.
