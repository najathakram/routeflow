## Reported evidence

#1257 fixed the 4th caller (rebuildIssuedDepositMirrorOnDelivery) never selecting {orderItemId, unitsPerBox} on its items query, which left the carried pack empty for prepaid/deposit-mirror orders. The new spec file has exactly one query-shape assertion (queryArgs.select.items toEqual {select:{orderItemId:true, unitsPerBox:true}}), and it targets ONLY the just-fixed 4th caller. The other three callers are covered only by output-value assertions (e.g. createdItem.unitsPerBox === 12) against a mocked prisma.invoice.findMany that returns whatever the fixture says regardless of the real select clause -- structurally blind to a lost select, the exact shape of gap #1257 just closed for caller #4. resyncOrderInvoicesForEdit and reconcileSplitOrderDrafts have NO SA-078(b) coverage at all (grepped every .spec.ts referencing either name). Not a defect in shipped code -- verified correct and complete for all four callers by direct trace -- but a real regression-coverage gap: if a future edit strips unitsPerBox from the select on any of the other three, nothing in the current suite would fail. Fix shape (from the reviewer, stated explicitly so nobody re-derives 3 more copies of the same blind test style): ONE spec that greps every caller of the shared rebuildSiblingDrafts core and asserts each one's own items-query select carries both {orderItemId, unitsPerBox}, count-pinned at 4 callers -- so a 5th caller added later without the select fails the build rather than passing silently, rather than writing 3 more per-caller tests that would inherit the same blindness style being replaced.
