## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** A submit either fails visibly or lands exactly once, however flaky the network.

**Actually does.** Three compounding legs: a timeout on a LIVE connection was classified as offline and enqueued (duplicating the order that had in fact been created); a drain replay that timed out re-enqueued itself (queue self-duplication); and the server had no replay protection, so every duplicate submit minted a real order.

**The gap.** At-least-once delivery with no idempotency anywhere in the chain.

**Evidence.** Evidence · apps/mobile/lib/api-client.ts, hooks/useNetworkSync.ts, lib/order-submit-key.ts; api orders.service.ts idempotency block; orders.scan-hardening.spec.ts (REG-B196)
