## Reported evidence

Verified guard.mjs's own logic against the current file: effectiveCwd = typeof cwd === string && cwd ? cwd : process.cwd() trusts whatever cwd the PreToolUse hook payload reports, with no independent verification against the actual current shell directory; looksLikeWorktreeCwd() then just regex-tests that string for /worktree/i to decide whether git checkout -b is exempted from the shared-checkout-stranding block. Reported live (a helper session hit the block and bypassed it with GUARD_ALLOW=1) as: after cd-ing from the main checkout into a worktree, the hook's reported cwd still read as the main checkout root, not the worktree path, so the exemption never triggered and a legitimate worktree-local git checkout -b was blocked. Not independently reproduced by the registry minter this session -- every git checkout -B call here ran with an already-worktree-rooted cwd and was never blocked, so this is a report to verify, not a confirmed repro. Fix direction: have the hook independently resolve the real cwd (e.g. via the tool_input's own cwd field if the harness provides one separately from the session-level cwd, or via git rev-parse --show-toplevel/--git-common-dir from the command's actual execution directory) rather than trusting a single payload field that may lag a mid-session cd.
