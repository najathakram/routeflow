## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** On a device, sessions persist in the OS secure store and the app boots to login or the last session.

**Actually does.** expo-secure-store validates keys against /^[\w.-]+$/ and throws on reads AND writes (ensureValidKey); every app key is colon-namespaced (rf:op:accessToken, rf:buyer:accessToken, rf:currentRole, rf:oauth:pendingState, …), so on a device every session read/write threw. buyer-session-store.initialize was the one boot store with no catch, and the root layout's bootstrapping gate ANDs all three stores — so the throw left the app on the splash spinner forever (on-device view hierarchy: a single ProgressBar). Even past boot, no login could persist: token writes throw identically.

**The gap.** On web these keys go to localStorage, which accepts any string — the failure is impossible on web and certain on native, and no native build had ever run to expose it.

**Evidence.** Evidence · apps/mobile/lib/auth-keys.ts (every key colon-namespaced); node_modules/expo-secure-store/build/SecureStore.js ensureValidKey/isValidKey (applied in getItemAsync); apps/mobile/lib/buyer-session-store.ts initialize (no catch, vs the try/finally in auth-store and tenant-store); app/_layout.tsx bootstrapping gate.
