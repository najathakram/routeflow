## Root cause

Found by Lane B707 during the B305 investigation, confirmed by an Opus verdict pass; re-verified by the Mac Lead on master d007dfec. create() computes total = subtotal + tax + categoryTax - orderDiscount + shippingFee (orders.service.ts:2166). Both edit recomputes use subtotal + tax + categoryTax + shippingFee with NO discount term (:4618,5531): updateOrderItems and the at-door change-request merge. So editing any discounted order (qty change, override, add/remove, at-door merge) overstates Order.total by exactly discountAmount, permanently. The INVOICE still bills correctly (it reads discountAmount directly) — no customer is undercharged. But Order.total feeds assertWithinCreditLimit (the merge path calls it right after the recompute) and the order revision, so an edited discounted order can trip a FALSE credit block where enforcement is on, and any screen showing Order.total shows a wrong figure. Not intentional. UpdateOrderItemsDto carries no discountAmount (an existing comment notes only create() sets one), so the fix threads the order's STORED discountAmount into both recomputes, not a new client field. Severity medium, rated on the credit-guard impact (fleet lead).
