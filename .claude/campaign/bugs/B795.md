## Root cause

Fleet lead relay, 2026-09-23 (Opus notes on #1298). Verified on origin/master 5ae97db7 (2026-09-23). THE DOUBLE-ADD PATH: (1) handleSave builds diff = buildAtDoorChangeRequests({originals: freshOrder lines, edited, added}) and runs processDiff(diff, 0) (adjust.tsx:324-344). (2) Each entry is create->self-resolve; a SUCCESSFUL ADD_ITEM returns true but is NEVER removed from the local 'added' state (setAdded only filters on a manual remove at :233 or a license Remove at :461). (3) A later entry fails and submitEntry returns false: a credit-limit block (the CreditLimitGuardModal is Cancel-only), a generic 409 such as STOP_ALREADY_COMPLETED/CHANGE_WINDOW_CLOSED/LINE_ALREADY_DELIVERED (toast), an offline drop, or a license block whose modal is Cancelled (onClose sets pendingRef = null). processDiff stores pendingRef = {diff, index: i}, but only the license modal's onResolved/onRemoveLines resume from that index. (4) The driver presses Save again, so handleSave runs a FRESH buildAtDoorChangeRequests from index 0. The pre-save refetch protects EDITED lines (CHANGE_QTY compares against the refetched qty, so an applied change diffs to nothing), but the 'added' loop (at-door-diff.ts:63-73) emits ADD_ITEM for every entry in 'added' unconditionally, with no reference to the refetched order. The already-applied ADD_ITEM is created and resolved a SECOND time: the item is on the order twice and the buyer is charged twice. The comment at :282-284 claims resumption avoids this, but that holds only for the license-guard resume, not for a fresh Save. MONEY (overcharge), pre-existing, DRIVER-reachable. Fix direction: drop each ADD_ITEM from 'added' (or mark it submitted, keyed by the created CR id) the moment it resolves, and/or have handleSave resume pendingRef instead of rebuilding when one exists; pin it with a pure-logic spec (a two-entry batch, second fails, re-save sends only the second). Owner: R-ui, after B784/B792/B788.
