## Root cause

Ran the authoritative signal recommended in the prior investigation: PLAYWRIGHT_BASE_URL=https://www.routeflow.info npx playwright test e2e/36-marketing-site.spec.ts -g T13 --project=marketing, using a REAL Chromium (not this session's Browser-pane automation). All 3 T13 sub-tests passed clean (58.6s), including 'scrolling to the bottom of / clears every .reveal-pending node and reaches opacity 1'. Separately, before running that, direct CSSOM inspection on the live production DOM (github.com/najathakram/routeflow apps/web/app/(marketing)/marketing.css:9206-9226 + editorial-motion.tsx) confirmed: real .capability-card/.section-heading nodes matching .editorial-reveal.reveal-pending computed opacity:1 (not the declared 0) ONLY inside the Browser-pane tool session — that session's document reports visibilityState:hidden / hasFocus:false even when fronted, a documented pre-existing limitation of this tool unrelated to this bug (see memory reference-browser-pane-no-compositor, filed 2026-08-26 re: Google Maps never rendering in the pane because requestAnimationFrame never fires on a hidden document). getComputedStyle confirmed only two rules are active for that element (.editorial-reveal opacity:1 at specificity 0,2,0; .editorial-reveal.reveal-pending opacity:0 at specificity 0,3,0, both correctly gated by the active prefers-reduced-motion:no-preference media query) — the pending rule correctly wins by specificity. The apparent stuck opacity:1 is consistent with a CSS transition Web-Animation frozen at its start value because the pane's hidden document never advances requestAnimationFrame, not a cascade defect. CONCLUSION: the mechanism (CSS + editorial-motion.tsx IntersectionObserver) is correctly wired and functioning in production. This bug's own filing evidence ('toggling the class on/off in the live DOM makes no observable difference') was almost certainly gathered under the same Browser-pane limitation. Recommend closing as verified-working / tooling-artifact, no code change. Did not force a state transition via already-fixed (it requires --pr on a queued/in-flight row; B520 was never queued into a batch) — leaving the formal state transition to whoever owns the campaign workflow.

## Reported evidence

Local dev testing (fresh npm run dev, .next cache cleared, prefers-reduced-motion confirmed 'no-preference' via matchMedia) shows .capability-card and .section-heading elements get the '.editorial-reveal reveal-pending' classes added by editorial-motion.tsx's IntersectionObserver setup as expected, but getComputedStyle always reports opacity:1 regardless of whether '.reveal-pending' is present — toggling the class on/off in the live DOM makes no observable difference. Reproduced on BOTH new content (WholesalerCapabilities cards added in PR #871) AND untouched pre-existing content (WorkflowTour's 'SEE YOUR WORKFLOW IN ROUTEFLOW' section-heading, unedited by that PR) — so this is not specific to the new content and predates it. Not yet determined whether the '.editorial-reveal.reveal-pending { opacity: 0 }' rule (marketing.css ~9219) is simply not being reached in the cascade, or something else neutralizes it; not investigated further per instruction. Two possible readings worth distinguishing: (a) a genuine dev-mode-only artifact with no production impact, or (b) the mechanism is already inert in production too, which would mean an earlier fix for a _different_ bug (content stuck invisible at opacity:0) was resolved by disabling the reveal system rather than correcting it, and the safe failure direction (always visible) has been masking that ever since. Needs live verification against a real (non-dev, ideally deployed) build before concluding either way.
