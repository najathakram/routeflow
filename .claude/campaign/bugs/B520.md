## Root cause

Live-production investigation (routeflow.info, direct CSSOM + JS diagnostics, no local build): the .editorial-reveal.reveal-pending CSS rule IS the winning declaration per the browser's own rule engine (verified via element.matches() against every stylesheet rule touching opacity, correct 3-class specificity beating the 2-class base rule, correct media-query match for prefers-reduced-motion:no-preference). A freshly created <div class="editorial-reveal reveal-pending"> appended directly to .rf-marketing immediately computes opacity:0/transform:translateY(28px) as designed -- the CSS itself is correctly authored and wired, ruling out a cascade/specificity tie bug like B504/B507's. However, REAL pre-existing elements on the live page (both new PR #871 content and untouched pre-existing WorkflowTour headings) showed inconsistent opacity readings across repeated checks in this session's browser-automation tool -- sometimes opacity:1 immediately with an active-but-frozen (progress stuck at 0, localTime never advancing) CSS transition per getAnimations(), sometimes opacity:0 at rest. document.hasFocus() was false despite document.visibilityState reporting "visible", and scrolling a real element into view via scrollIntoView() plus a 1.2s wait left it still at opacity:0/reveal-pending present/zero running animations -- i.e. the IntersectionObserver callback never fired even on genuine intersection. This pattern (frozen transitions + non-firing IntersectionObserver, both tied to the browser's rendering/frame-production pipeline) is consistent with the automated browser pane not receiving real paint frames for this tab -- a known category of headless/embedded-automation gap -- rather than a genuine cascade bug, but this is inference, not proof. Attempted to get an authoritative, tool-independent signal via Playwright's own T13 test (e2e/36-marketing-site.spec.ts, built for exactly this: post-deploy scroll-reveal verification) against production, but could not: GitHub Actions is billing-blocked tonight (every deployment_status-triggered CI run fails immediately with 'recent account payments have failed' -- no post-deploy E2E signal exists to check either), and local disk fell to ~4.5GB free with a concurrent lane also reclaiming space, too tight to safely run a fresh npm ci + Playwright browser install. Conclusion: evidence leans toward the mechanism being correctly implemented and NOT dead in production (the CSS/JS wiring is provably correct; the stuck-looking behavior is most plausibly this session's tooling, not the site) -- but this is not proven. Recommend NOT touching the mechanism without that proof (removing working code on inconclusive evidence would be its own regression); instead run T13 from e2e/36-marketing-site.spec.ts against https://www.routeflow.info once either GH Actions billing is restored or local disk permits a clean npm ci + npx playwright install. That single run settles it definitively.

## Reported evidence

Local dev testing (fresh npm run dev, .next cache cleared, prefers-reduced-motion confirmed 'no-preference' via matchMedia) shows .capability-card and .section-heading elements get the '.editorial-reveal reveal-pending' classes added by editorial-motion.tsx's IntersectionObserver setup as expected, but getComputedStyle always reports opacity:1 regardless of whether '.reveal-pending' is present — toggling the class on/off in the live DOM makes no observable difference. Reproduced on BOTH new content (WholesalerCapabilities cards added in PR #871) AND untouched pre-existing content (WorkflowTour's 'SEE YOUR WORKFLOW IN ROUTEFLOW' section-heading, unedited by that PR) — so this is not specific to the new content and predates it. Not yet determined whether the '.editorial-reveal.reveal-pending { opacity: 0 }' rule (marketing.css ~9219) is simply not being reached in the cascade, or something else neutralizes it; not investigated further per instruction. Two possible readings worth distinguishing: (a) a genuine dev-mode-only artifact with no production impact, or (b) the mechanism is already inert in production too, which would mean an earlier fix for a *different* bug (content stuck invisible at opacity:0) was resolved by disabling the reveal system rather than correcting it, and the safe failure direction (always visible) has been masking that ever since. Needs live verification against a real (non-dev, ideally deployed) build before concluding either way.
