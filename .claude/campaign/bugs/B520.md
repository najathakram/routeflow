## Reported evidence

Local dev testing (fresh npm run dev, .next cache cleared, prefers-reduced-motion confirmed 'no-preference' via matchMedia) shows .capability-card and .section-heading elements get the '.editorial-reveal reveal-pending' classes added by editorial-motion.tsx's IntersectionObserver setup as expected, but getComputedStyle always reports opacity:1 regardless of whether '.reveal-pending' is present — toggling the class on/off in the live DOM makes no observable difference. Reproduced on BOTH new content (WholesalerCapabilities cards added in PR #871) AND untouched pre-existing content (WorkflowTour's 'SEE YOUR WORKFLOW IN ROUTEFLOW' section-heading, unedited by that PR) — so this is not specific to the new content and predates it. Not yet determined whether the '.editorial-reveal.reveal-pending { opacity: 0 }' rule (marketing.css ~9219) is simply not being reached in the cascade, or something else neutralizes it; not investigated further per instruction. Two possible readings worth distinguishing: (a) a genuine dev-mode-only artifact with no production impact, or (b) the mechanism is already inert in production too, which would mean an earlier fix for a *different* bug (content stuck invisible at opacity:0) was resolved by disabling the reveal system rather than correcting it, and the safe failure direction (always visible) has been masking that ever since. Needs live verification against a real (non-dev, ideally deployed) build before concluding either way.
