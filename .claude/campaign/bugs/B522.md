# B522 · Demo-booking internal notification recipient should be a configurable list, not one address

**Location** `apps/api/src/demo-booking/demo-booking.config.ts` · **Severity** low · **State** uncampaigned

## Summary

The internal demo-booking notification (B518) defaulted to a single hardcoded address (hello@routeflow.info). Direct owner feedback: that address, while functional, is not where they want it -- they check admin@routeflow.info -- and they want a second (colleague) recipient too. A single string can't express a list. Changed DemoBookingConfig.demoBookingAdminEmail (string) to demoBookingAdminEmails (string[]), parsed from a comma-separated DEMO_BOOKING_ADMIN_EMAIL, defaulting to [admin@routeflow.info] and sent to one-email-per-recipient.

## What this feature is for

Same feature as B518: the internal notification that fires alongside the booker's confirmation on create/cancel/reschedule, so staff learn about a demo booking without checking the calendar.

## Root cause

Not a code defect -- B518's single-address default worked exactly as built. This is a requirements change from the owner after using it: the wrong default address, and a second recipient that a single string can't hold.

## User impact

None -- the booker's own confirmation is unaffected. Until DEMO_BOOKING_ADMIN_EMAIL is set in Railway, admin@routeflow.info alone keeps receiving notifications (same as before, new address).

## Fix approach and UX

demoBookingAdminEmails: string[] parsed from a comma-separated env value -- trimmed, empties dropped, case-insensitively de-duplicated, each address validated (an invalid one is skipped with a logged error, not corrupting the rest). Falls back to [admin@routeflow.info] whenever the parsed result would be empty. sendConfirmation now sends one email per admin address via Promise.allSettled, so one bad/failing recipient never costs the others theirs. The colleague's real address is configuration (a Railway env var), not code -- not hardcoded here.

## Test plan

demo-booking.config.spec.ts (REG-B522): multi-address parse/trim/dedup/invalid-skip/all-invalid-and-unset fallback. demo-booking.service.spec.ts (REG-B522): every configured admin address receives the notification; a send failure to one admin recipient doesn't abort the others or the booking. 58/58 existing + new demo-booking tests green; tsc/eslint clean.

## Reported evidence

B518 shipped a single-address code-side default (hello@routeflow.info) for the internal demo-booking notification. Owner feedback: point it at admin@routeflow.info instead, and add a second (colleague) recipient -- which a single-string config value cannot express.
