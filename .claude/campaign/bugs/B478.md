# B478 · Override drawer's unwired-gate warning never shows (stale local type)

**Location** `apps/web/app/(platform-admin)/admin/tenants/[id]/page.tsx` · **Severity** low · **State** uncampaigned

## Summary

The platform-admin tenant-detail page's Feature Overrides drawer redeclares a stale local type (flat 'via') instead of the real API contract (nested 'gate.via'), so its amber 'no wired gate, this override has no effect' warning never renders for any registry key. Fix: drop the local type, import FeatureRegistryRow from @routeflow/types, read gate.via. Low severity, UI-only, no data/security impact — parked by the tenancy carve-out pending owner sign-off since it touches the tenant-detail admin page.

## What this feature is for

Super-admin-only tenant-detail page's 'New Feature Override' drawer. Lets a platform admin grant/deny a FeatureRegistryRow key for one tenant. The registry select is meant to warn when the chosen key has no wired gate (gate.via === "none", i.e. catalog metadata only, no @RequireAddon/@RequirePlanFlag/guard actually reads it) — such an override would be silently inert.

## Root cause

The component redeclares a local FeatureRegistryOption interface with a FLAT 'via: string' field instead of importing the shared FeatureRegistryRow type from @routeflow/types, whose real shape is 'gate: { via, state }' (packages/types/api/features.ts). The API (GET /platform-admin/features/registry, platform-admin.controller.ts:384-390) returns the nested gate.via shape. selectedRegistryEntry?.via therefore reads a field that never exists on the response — always undefined, so the '=== "none"' check is always false and the amber warning never renders, for ANY registry key, including genuinely unwired ones. Broken since #795 (per the lead's report) when FeatureRegistryRow's contract moved gate fields under a nested 'gate' object.

## User impact

Cosmetic/informational only — no data is mutated and no gate is actually bypassed by this bug (the SERVER-side @RequireAddon/@RequirePlanFlag/guard still enforces or doesn't enforce exactly as before; this warning is advisory UI only, telling the admin their override may be a no-op). A SUPER_ADMIN could create a feature override against a key with no wired gate, believing it takes effect, and be confused later when tenant behavior doesn't change. No tenant data, billing, or entitlement state is at risk; the blast radius is admin confusion, not correctness or security.

## Fix approach and UX

Delete the local FeatureRegistryOption interface; import FeatureRegistryRow from @routeflow/types and use it for the registry useState. Change the read from 'selectedRegistryEntry?.via === "none"' to 'selectedRegistryEntry?.gate.via === "none"'. No other field the local type declared (area, kind) was actually read anywhere in the component, so nothing else needs remapping. No UX/copy change — same warning text, now it can actually render. Diff is 3 lines touched (delete 8-line interface, one useState generic, one property-access) in apps/web/app/(platform-admin)/admin/tenants/[id]/page.tsx.

## Test plan

T1 (jest/RTL). New file apps/web/app/(platform-admin)/admin/tenants/[id]/feature-overrides.test.tsx, exported FeatureOverridesSection for direct render. REG-B478 case 1: registry row with gate.via:'none' -> opening 'New Override' shows the 'no wired gate' warning text. REG-B478 case 2: a row with gate.via:'RequirePlanFlag' -> opening the drawer does NOT show the warning. Both assert against the real FeatureRegistryRow shape (gate: {via, state}), not the removed flat one.

## Reported evidence

Local FeatureRegistryOption flattens gate.via, so selectedRegistryEntry?.via is always undefined and the amber 'no wired gate' warning never renders, even for a catalog-only key with gate.via: none
