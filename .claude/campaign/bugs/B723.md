## Reported evidence

B717's control query (run against production to attribute the exposure report's zero rows) surfaced that the most recent invoice-line edit is stamped 2026-09-22T23:47:51Z while the database's transaction clock (now()) read 2026-09-22T20:41:20Z at query time -- a row stamped roughly three hours in the future. Did not affect B717's own answer, because a future stamp is still after B717's cutoff and was therefore correctly included in the exposure window (the safe direction). Matters independently: every time-window query, audit trail, dunning schedule and filing-period boundary in the product trusts these stamps -- a writer with a fast clock, or a code path that sets updatedAt from client-supplied time instead of the DB clock, would corrupt them quietly and invisibly. A read-only characterisation query is written and waiting at local-assets/handoff/2026-09-22/b717-clockskew.sql, runnable with the same wrapper (run-b717-exposure.mjs b717-clockskew.sql). Cause not yet established -- do not speculate, that is what the characterisation query is for.
