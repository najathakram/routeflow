## Reported evidence

RETRACTION of this id's original filing: the original "invoice-line edit stamped ~3 hours ahead of the DB clock" finding was a misread, not a defect. `InvoiceItem.updatedAt` (`apps/api/prisma/schema/finance.prisma`) is a plain `DateTime` with no `@db.Timestamptz`, mapping to Postgres `timestamp WITHOUT time zone`. node-postgres parses a naive timestamp as LOCAL time of the machine running the script (the owner's PC, UTC-5) and prints it with a trailing Z regardless -- a stored 18:47:51 displays as 23:47:51Z. `now()` is a real timestamptz and printed correctly. Comparing the two manufactured a 3-hour gap that does not exist.

The REAL finding, now with hard evidence rather than a concern: exactly ONE column in the entire schema is timestamptz -- `platform.prisma:853`. Every other timestamp, including every `createdAt`/`updatedAt` on money tables, is naive. Two demonstrated consequences: (1) a query comparing a naive column against a timestamptz literal resolves using the session timezone -- B717's exposure query was correct only because that session happened to be UTC (confirmed directly: `session_timezone = UTC`), which nothing in the repo asserts or tests; (2) any tool reading these values over a driver shifts them by the reading machine's offset, demonstrated tonight at exactly the owner's PC's 5-hour offset (`LOCALTIMESTAMP` of 20:45:55 printed as `2026-09-23T01:45:55Z` when the session was forced to UTC) -- the same shift that produced the original phantom 3-hour gap. A report can silently disagree with itself depending on who ran it.

Suggested guard, not a prescribed fix: a spec asserting the session timezone, or `@db.Timestamptz` on the money tables -- both options named, neither chosen here.
