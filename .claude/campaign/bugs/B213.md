# B213 · AI invoice scan returned 403 on every scan route and the web toast hid the server message (OCR add-on gate)

**Location** `apps/api/src/billing/addon.guard.ts` · **Severity** high · **State** uncampaigned

## Summary

Incident: PR #475 (2026-08-29) added @RequireAddon("ocr") to four live routes with no grant/backfill for tenants already using them: POST /vendor-bills/scan-invoice, POST /bookkeeping/expenses/:id/extract-items, POST /import/batch/:id/scan, POST /supplier-statements/scan. Every tenant not hand-granted the ocr add-on was denied (403) on all four for about five days before a client reported it (OCR-1). The web ScanInvoiceModal single-scan toast discarded the server's message and showed a generic "Please check the file and try again." hint, so the outage read as a bad file rather than a missing entitlement (OCR-2). Fixed by PR #616 (fix(api,web): observe-first add-on gates — registry, ocr dark, scan toast fidelity), merged to master at 7281e4d7: new apps/api/src/billing/addon-gate-registry.ts registers ocr as dark (allow + would-deny warn, reviewBy 2026-10-15) and AddonGuard now allows-and-warns a fully-dark key set while still denying any enforced/mixed/unregistered set with a structured 403 (code ADDON_GATE); apps/web/components/ScanInvoiceModal.tsx now surfaces the server's own message. Regression coverage: REG-OCR-1 (apps/api/src/billing/addon.guard.spec.ts, T1-T8) and REG-OCR-2 (apps/web/e2e/02-operator.spec.ts, OP-17g). Lesson L-071 (.claude/lessons/LESSONS.md) records the pattern: a new entitlement gate on an existing route ships observe-first or it is an outage.
