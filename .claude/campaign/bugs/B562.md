## Reported evidence

Found incidentally during units/PO planning work, NOT part of that plan -- live production money bug, should be fixed well before any purchase-order edit work begins since that design depends on replay being trustworthy. Mechanism: recordPurchase/recordAdjustment called with a backdated effectiveDate, and vendor-bill receive with a billDate earlier than an existing movement, both call recomputeProductInTx. That replay starts stock at 0 and is BLIND TO RAW ORDER DECREMENTS -- order creation and edits decrement stock without writing a StockMovement row. So the replay computes a sales-blind average, overwrites Product.averageCost with it, and rewrites every stockAfter value -- erasing the very evidence that would let anyone detect or reconstruct the true figure afterwards. Severity critical/money: misstates inventory valuation and therefore COGS. Already-corrupted products are NOT recoverable from the ledger, which is what makes this worse than an ordinary arithmetic bug -- the corruption destroys its own audit trail. Same shape one layer down as the B523-family verification-gate problem (a check/replay that reports a confident number while structurally unable to see half the inputs) -- see also B556/B557 (same mrr/inventory-adjacent subsystem family, live-vs-recorded-state divergence from an incomplete view of writes). MUST go through bug-pipeline on its own merits and be fixed BEFORE any purchase-order edit work begins.
