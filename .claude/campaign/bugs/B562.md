## User impact

EXPOSURE UPGRADE (round-3 review, 2026-09-18) -- this is materially worse and wider than originally filed: POST /inventory/recompute-costs is guarded only by @Roles(OPERATOR) and is surfaced as a button in BOTH the mobile warehouse tab and the web client. Detector note: the plan's proposed detector ('avgCostAfter changed') is UNOBSERVABLE for this path since a deliberate recompute changing the value IS the expected/intended behavior of the button -- a GAP-based detector (missing StockMovement rows against known order decrements) is the one that actually works here. ## Reported evidence

Found incidentally during units/PO planning work, NOT part of that plan -- live production money bug, should be fixed well before any purchase-order edit work begins since that design depends on replay being trustworthy. Mechanism: recordPurchase/recordAdjustment called with a backdated effectiveDate, and vendor-bill receive with a billDate earlier than an existing movement, both call recomputeProductInTx. That replay starts stock at 0 and is BLIND TO RAW ORDER DECREMENTS -- order creation and edits decrement stock without writing a StockMovement row. So the replay computes a sales-blind average, overwrites Product.averageCost with it, and rewrites every stockAfter value -- erasing the very evidence that would let anyone detect or reconstruct the true figure afterwards. Severity critical/money: misstates inventory valuation and therefore COGS. CORRECTION (round-3 review, 2026-09-18): originally stated as not recoverable from the ledger -- that was written from the narrower backdated-movement mechanism alone and is corrected here. `Order` rows constitute a second ledger a repair could reconstruct from, which is the most hopeful thing about this bug -- already-corrupted products' true averageCost is plausibly recoverable via that path, not permanently lost. The destroyed StockMovement audit trail is still real and still the reason a naive "diff before/after" detector can't see this bug; recovery, where possible, has to go through Order history instead, not the corrupted movement rows themselves. Same shape one layer down as the B523-family verification-gate problem (a check/replay that reports a confident number while structurally unable to see half the inputs) -- see also B556/B557 (same mrr/inventory-adjacent subsystem family, live-vs-recorded-state divergence from an incomplete view of writes). MUST go through bug-pipeline on its own merits and be fixed BEFORE any purchase-order edit work begins.
