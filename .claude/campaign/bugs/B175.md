## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** Sitting beside a live stops-ahead counter under "Delivery tracking", an "Estimated: 9:00 – 11:00" line reads as a projection of when the driver will actually arrive today.

**Actually does.** The field is copied verbatim from the customer's delivery-window profile fields — the same standing preference staff edit and the optimizer consumes as a solver constraint. It never varies with stops ahead, run progress or clock time.

**The gap.** A static preference is surfaced under an "Estimated" label; the value itself is truthful, only the word is not.

**Evidence.** Evidence · apps/api/src/orders/orders.service.ts:4633 (the select) and :4683-4686 (copied straight through, no other input); apps/api/src/customers/customers.service.ts:648-653 (a plain profile update, confirming it is a standing preference); apps/api/src/route-optimization/route-optimization.service.ts:211-228 (used elsewhere only as a feasibility constraint); apps/mobile/app/(customer)/orders/[id].tsx:263-270 (rendered as "Estimated: {start} – {end}").

**Suggested fix (register).** Relabel the field and the UI line to "Delivery window" — what it actually is — or compute a genuine per-run arrival estimate and only then keep the "Estimated" wording.

> ⚠️ Treat this as a hypothesis, not a plan. On F11 the adversarial pass refuted the
> suggested fix for every one of the four bugs while confirming every diagnosis.

**Verifier's note.** Downgraded from High and the second half of the claim refuted: the argument that a real computed ETA exists but was never wired does not hold, because the ETA pass runs off route template stops with a config-driven default start time — a planning-time projection, not a live position-aware ETA — so wiring it in would swap one non-live number for another. That half also restates the cleared "route-run ETA analysis never wired to a screen" entry. What survives is a naming defect.
