# B451 · Strix scan: 4 unreviewed coverage gaps (mass assignment on POST /customers + invoice create; SQL injection on list search params; financial-total manipulation)

**Location** `local-assets/security/strix_runs-2026-09-16/openapi_515f/findings.sarif (4 results, level none, rules strix-coverage/*)` · **Severity** high · **Batch** F54 · **State** queued

## Summary

A Strix (v1.6.2) automated security scan against the OpenAPI-enumerated attack surface (local-assets/security/strix_runs-2026-09-16/openapi_515f/findings.sarif) reported 4 coverage-only findings (level: none, rules strix-coverage/*) where the assigned specialist agent ran out of budget or could not obtain an auth token before dynamic testing began: (1) mass assignment on tenantId/role/isAdmin/creditLimit via POST/PATCH /api/v1/customers, (2) SQL injection on search/filter params across GET /customers, /orders, /products, /invoices, (3) financial-total manipulation (negative amounts, discount abuse) across POST/PATCH invoices, orders, credit-notes, estimates, vendor-bills, (4) mass assignment on totalAmount/subtotal/taxAmount/status/tenantId via POST/PATCH /api/v1/orders. This is a REVIEW task, not a confirmed vulnerability -- no exploit was attempted or demonstrated against any of these surfaces; the row exists to track that these 4 areas still need a real security pass (manual or a re-run scan with budget to complete dynamic testing).

## Root cause

Not a defect in the codebase -- a coverage gap in the Strix scan's own dynamic-testing budget:
the specialist agents assigned to these 4 risk areas ran out of budget or could not obtain an
auth token before any attack payload was sent, so the scan closed with 4 open, untested surfaces
rather than a pass/fail verdict on them. A follow-up Phase A manual/attack-test pass (see the
Strix lane, code PR lands separately with a `Bookkeeping-Follow-Up: pending` trailer) has since
refuted 3 of the 4 and confirmed a real gap on the 4th: (1) mass assignment REFUTED -- the global
ValidationPipe's whitelist/`forbidNonWhitelisted` rejects any body field not declared on the DTO,
so `tenantId`/`role`/`isAdmin`/`creditLimit` and `totalAmount`/`subtotal`/`taxAmount`/`status`
are not attacker-settable via POST/PATCH customers or orders; (2) SQL injection REFUTED -- every
list `search`/filter param goes through Prisma's parameterized `contains`, the only raw SQL in
scope is a bound tagged template, and `sortBy` is either allow-listed or absent; (3)
financial-total manipulation CONFIRMED on 3 of 6 endpoints checked -- POST /orders never compares
its discount to the subtotal (a total can go negative), POST /estimates has no DTO at all
(`@Body() dto: any`, so discount/taxAmount are fully unvalidated), and vendor-bill line items
(qty/unitCost/unitPrice) carry no `@Min(0)`; invoices and credit notes already guard this
correctly, which is why those two escaped detection.

## Fix approach and UX

One shared `assertMoneyInvariants` helper in `@routeflow/pricing`, used by orders create + PATCH
items, estimates create/PATCH/convert, and vendor-bills -- consistent with the package's existing
money-discipline convention (no per-app mirrors) -- to close gap 4's 3 confirmed holes: a
discount-never-exceeds-subtotal / total-never-negative check for orders and estimates, and a
`@Min(0)` constraint on vendor-bill line items (qty/unitCost/unitPrice). Estimates additionally
need a real `CreateEstimateDto` (replacing the current `@Body() dto: any`) matching the web
client's actual payload shape, so `forbidNonWhitelisted` can do for estimates what it already does
for customers/orders. The 28 attack tests from the Strix lane's Phase A refutation pass become the
regression suite (spec files listed under Test plan below); no UX change -- this is
server-side validation only. Gaps 1-3 (mass assignment, SQL injection) need no fix -- they were
refuted, not confirmed. Fix code lands in a separate PR (Strix lane), tracked here with a
`Bookkeeping-Follow-Up: pending` trailer on its HEAD commit.

## Test plan

The 28 attack tests written for the Strix lane's Phase A refutation pass become the regression
suite for gap 4's fix: an `orders.service` / `estimates.service` / `vendor-bills.service` spec
covering discount-exceeds-subtotal / negative-total rejection, plus a `CreateEstimateDto`
whitelist spec proving `forbidNonWhitelisted` now rejects the same unvalidated fields customers/
orders already reject. Gaps 1-3's attack tests stay as permanent regression coverage proving the
existing ValidationPipe/Prisma-parameterization guarantees, even though no fix was needed for
them.
