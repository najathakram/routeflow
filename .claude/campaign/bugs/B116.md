## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** A large multi-SKU order should be created and its stock decremented the same as a small one, regardless of line count.

**Actually does.** One tenantTransaction (no timeout/maxWait options) row-locks all products, then awaits one tx.product.update per line sequentially; Prisma 7's default 5s interactive-transaction ceiling governs, and only P2002 is retried — a timeout fails the order outright.

**The gap.** Large orders (or lock contention, which also consumes the 5s budget) hit the default timeout, roll back, and are not retried.

**Evidence.** Evidence · apps/api/src/orders/orders.service.ts:1846-1902 (loop + sequential per-line update 1897-1902, tenantTransaction with no options at 1850), :1961 (P2002-only retry); apps/api/src/prisma/prisma.service.ts:10-12 (no transactionOptions in constructor), :36-51 (options forwarded verbatim to $transaction); apps/api/package.json:49 (@prisma/client ^7.10.0, default timeout 5000ms/maxWait 2000ms).

**Suggested fix (register).** Pass an explicit { timeout, maxWait } to tenantTransaction sized for the largest realistic order, and replace the per-line loop with a single set-based raw UPDATE joining a VALUES list of (productId, qty).

> ⚠️ Treat this as a hypothesis, not a plan. On F11 the adversarial pass refuted the
> suggested fix for every one of the four bugs while confirming every diagnosis.

**Verifier's note.** Mechanism fully confirmed; severity downgraded from high because at same-region latency (~1-3ms/round-trip) 500 sequential updates cost ~1-2s, so the practical trigger is very large orders, latency spikes, or FOR-UPDATE lock waits from concurrent orders — which count against the same 5s budget.
