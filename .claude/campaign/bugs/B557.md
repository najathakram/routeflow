## Fix approach and UX

Fix landed (B707 lane, branch fix/b556-b557-mrr-plan-source-of-truth off origin/master b6e6bc7f, sha 14c9eb38, SA-140 verdict BUILD): the two named remaining gaps in mrr.service.ts's own ledgerMrr doc comment are closed. (1) reconcilePriceLedger() now gates the ledger EMIT (not the basePriceSnapshot write) on the shared isPayingRow predicate -- a suspended/non-PRODUCTION tenant's price change still updates the snapshot (so a later reactivation books the right price) but books no ledger delta while mrr excludes it. (2) updateTenantClass() now books a compensating TENANT_CLASS_CHANGED delta on ENTERING PRODUCTION only = priceTenant(tx, called AFTER the class write) minus the tenant's pre-existing ledger sum -- landing its post-flip contribution exactly at its live value instead of importing its whole pre-PRODUCTION history; LEAVING PRODUCTION needs no compensating entry, ledgerAgg's current-class join already drops the tenant's history the same instant mrr does. Both updateStatus() and updateTenantClass() now SELECT...FOR UPDATE the tenant row first, closing a race between concurrent admin actions. Architecture: PAYING_TENANT_CONDITIONS + isPayingRow() (mrr.service.ts) is now the ONE place the 4-part paying-set predicate is decided -- replaces 4 independently hand-rolled copies (emitPayingDelta, reconcilePriceLedger, updateStatus, and updatePlan -- updatePlan's copy never checked class/deletedAt at all, a real previously-undetected gap found while wiring this). A parity + grep-pin spec (mrr-paying-predicate.parity.spec.ts) locks this down. A real-Postgres DB spec (update-tenant-class-ledger.db.spec.ts) proves the compensating-delta math against actual ledgerAgg behavior -- NOT run by this lane, needs F2/the prover. ## Reported evidence

DB-verified reproduction (Lane F, 2026-09-18), exact live-vs-ledger divergence reproduced, not just the hypothesis. Root cause: computeOverview()'s two queries use different filters -- live MRR (payingWhere) gates on 4 conditions (planKey not null + tenant status=ACTIVE + deletedAt=null + class=PRODUCTION), ledger MRR (ledgerAgg, sums BillingEvent.amountDelta) gates on only 1 (tenant.class=PRODUCTION). A tenant billed once then moved off ACTIVE (suspended/cancelled) with no compensating event leaves a permanent residue in the ledger while live correctly drops. Exact repro on a throwaway qa-mrr-drift-test tenant (created, tested, then soft-deleted): resolved a real plan -> booked a +$499 BillingEvent -> baseline MRR $998/ledger $998 matched -> flipped status to SUSPENDED with zero new BillingEvent created (DB-verified) -> result: MRR $499.00 / 'Reconciled to ledger: $998.00 - differs by $499.00' -- the exact shape reported in prod, screenshot captured. Full writeup with exact API calls + DB queries + fix-shape options at local-assets/proofs/2026-09-18/mrr-ledger-drift-repro/REPRO.md in worktree rf-sweep-390. Severity critical: this is very likely prod's actual bug -- 26 tenants, some plausibly billed-then-suspended, meaning the platform dashboard's headline revenue figure may be silently wrong right now. Repro only on throwaway qa-mrr-drift-test tenant, created/tested/soft-deleted, per approved test-tenant policy.
