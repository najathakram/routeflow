## Fix approach and UX

Fix shape (lead's explicit steer, per Lane F): option (b) ONLY -- do NOT narrow ledgerAgg's filter to match payingWhere's 4-part gate. That would make the two numbers agree by construction, but deletes the entire value of the reconciliation check: live and ledger are supposed to be derived independently precisely so disagreement reveals a real inconsistency. Narrowing the ledger query silences the detector rather than fixing what it detects -- the check would never catch anything again, including genuine billing errors. Correct fix: emit a compensating negative BillingEvent on any transition that removes a tenant from the paying set (updateStatus() at minimum, and the class-change path) -- preserves the ledger's audit-trail meaning, makes the figures agree because the underlying data is correct rather than because the query was narrowed, and keeps the reconciliation check functional for the next real issue. Same family as the already-filed activateManualSubscription() mirror-image gap (B551 -- reactivation with no delta, overstating live): same root pattern, opposite direction.

## Reported evidence

DB-verified reproduction (Lane F, 2026-09-18), exact live-vs-ledger divergence reproduced, not just the hypothesis. Root cause: computeOverview()'s two queries use different filters -- live MRR (payingWhere) gates on 4 conditions (planKey not null + tenant status=ACTIVE + deletedAt=null + class=PRODUCTION), ledger MRR (ledgerAgg, sums BillingEvent.amountDelta) gates on only 1 (tenant.class=PRODUCTION). A tenant billed once then moved off ACTIVE (suspended/cancelled) with no compensating event leaves a permanent residue in the ledger while live correctly drops. Exact repro on a throwaway qa-mrr-drift-test tenant (created, tested, then soft-deleted): resolved a real plan -> booked a +$499 BillingEvent -> baseline MRR $998/ledger $998 matched -> flipped status to SUSPENDED with zero new BillingEvent created (DB-verified) -> result: MRR $499.00 / 'Reconciled to ledger: $998.00 - differs by $499.00' -- the exact shape reported in prod, screenshot captured. Full writeup with exact API calls + DB queries + fix-shape options at local-assets/proofs/2026-09-18/mrr-ledger-drift-repro/REPRO.md in worktree rf-sweep-390. Severity critical: this is very likely prod's actual bug -- 26 tenants, some plausibly billed-then-suspended, meaning the platform dashboard's headline revenue figure may be silently wrong right now. Repro only on throwaway qa-mrr-drift-test tenant, created/tested/soft-deleted, per approved test-tenant policy.
