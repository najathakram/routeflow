## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** Driving is opt-in. An admin who never drives is not in the Drivers list and gets no &ldquo;My Routes&rdquo;; deleting a driver profile removes that profile and it stays removed.

**Actually does.** Platform-admin createTenant and createTenantAdmin both minted a Driver row for the admin and hardcoded canActAsDriver: true, so every workspace shipped with its admin in the Drivers list and &ldquo;My Routes&rdquo; in the nav. Deleting that row hard-deleted the linked User in the same transaction: for an admin with RESTRICT-FK children (messages, stock counts, device tokens) the user-delete failed and rolled the whole transaction back, so the driver &ldquo;kept coming back&rdquo;. The delete also never cleared canActAsDriver, leaving the Settings toggle reading ON and able to recreate the row.

**The gap.** The only reason the owner&rsquo;s repeated deletes appeared to do nothing is the FK rollback &mdash; had it succeeded it would have deleted the tenant&rsquo;s admin login. Separately, canActAsDriver was never copied into req.user by the JWT strategy, so RolesGuard&rsquo;s dual-role branch could never fire and the capability was client-gated only.

**Evidence.** Evidence · Reported live on acme-distribution, whose Drivers list held a single &ldquo;admin&rdquo; row that returned after every delete; a read-only prod audit showed exactly one driver row per platform-admin-created tenant. apps/api/src/platform-admin/platform-admin.service.ts (both auto-create blocks + hardcoded canActAsDriver: true); apps/api/src/drivers/drivers.service.ts remove() (unconditional tx.user.delete, no canActAsDriver clear, no role check); apps/api/src/users/users.service.ts toggleDriverPermit (recreates the Driver row on every OFF&rarr;ON flip); apps/api/src/auth/strategies/jwt.strategy.ts (claim dropped).
