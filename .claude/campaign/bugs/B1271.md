## Reported evidence

Owner 2026-10-27: when the check number is added at a pickup hand-over it gives an error, and pickup orders should hand over without a check number. Repro on the local compose stack, api image build sha d2ae41db7d0bf44022cf2023963a0a00f8215907 (master d2ae41db7), approved test tenant, through the web hand-over dialog with the network recorded. (a) CHECK with a fresh check number, named customer: POST /orders/:id/pickup-complete 200 paymentRecorded:true (also with the order invoiced first). (a2) the SAME check number and amount again for the SAME customer: HTTP 200 with paymentRecorded:false, paymentErrorCode COUNTER_PAYMENT_NOT_RECORDED, paymentCauseCode DUPLICATE_PAYMENT_REF (SA-837b; rule = same tenant, customer, method, normalised reference and amount, no time window, payment-ref-dedupe.ts:10-16). The dialog shows 'Payment not recorded. The order is handed over, but the payment was not saved. Retry to record it.' plus 'A payment with this reference was already recorded on <date> for <amount> (<invoice>).' with Retry, Record anyway, Done. Retry resends the same body and gets the same refusal (dead end, the copy promises otherwise); Record anyway (recordAnyway:true, staff) records it. The order is already DELIVERED and invoiced at that point. The same check number for a DIFFERENT customer is not deduped (200). (b) no check number: a named customer On account sends payment {method:ON_ACCOUNT}, 200, balanceDue stays; payment omitted at the API, 200 on account. A walk-in has no On account in the dialog; payment omitted = 400 WALK_IN_NO_ACCOUNT; CHECK with no number = client 'Enter the check number.' (no request) and at the API 400 COUNTER_CHECK_NUMBER_REQUIRED (counter-sale-payment.ts:38-39), so a check hand-over needs a number by design. (c) walk-in CHECK with a number: 200. Not observed (not reachable from the dialog or not triggered on a fresh key): PICKUP_KEY_CONFLICT, COUNTER_SALE_DAY_CLOSED, LockTimeoutError counter-tender, COUNTER_CHECK_POSTDATED (the dialog never sends checkDate), W-774 refusal; the DTO whitelist is ruled out. Root cause (most likely, observed): the dedupe refusal is returned as a 200 'handed over but payment not saved', so a reused or test check number reads as an error on the hand-over, and Retry cannot clear it. Setup note: the test tenant needed fulfilment_model=pickup_ship and counter_sales=on (else 409 COUNTER_COMPLETE_UNAVAILABLE, a config refusal, not the reported error). No fix here: the fix ruling folds into the SA cheque-optional spec.
