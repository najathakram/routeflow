# B156 · Customers "Unassigned only" filters one page while the count and pager still describe the full list

**Location** `Customers list · web` · **Severity** medium · **Batch** F15 · **State** queued

## Summary

CONFIRMED at master@2d35375, unchanged since the hunt. "Unassigned only" is the only client-side filter on the Customers list: apps/web/app/(dashboard)/customers/page.tsx:352-355 filters the CURRENT SERVER PAGE against the tenant-wide assignment map, while the footer (:1011-1013), pager (:1033-1069) and page clamp (:335) read `meta.total` / `meta.totalPages` from the unfiltered server query (:321-335). Toggling the chip also never resets the page (:286-292 omit `unassignedOnly`). Fix: a server-side `unassigned` filter in ListCustomersDto/findAll (Customer has `routeStops RouteStop[]`, prisma/schema/sales.prisma:180) that the chip sends, sharing the exact "assigned" predicate getCustomerRouteAssignments uses (apps/api/src/routes/routes.service.ts:704-728: a RouteStop on a SCHEDULED route). Land with B158's shared where-builder and B157's assignment change.

## What this feature is for

Route planning: an operator toggles "Unassigned only" to see the customers no SCHEDULED route visits yet, then adds them to a route. Every other chip on this list (status, type, tag, regulated) is a server filter, so the header count (:686), the footer "Showing a–b of N" and the page buttons describe the filtered set. The chip is meant to behave the same way.

## Root cause

page.tsx:265 `unassignedOnly` state → :352-355 `visibleCustomers = customers.filter(c => !assignments?.[c.id]?.length)`, where `customers` is one server page (`result?.data`, :333) and `assignments` is the tenant-wide map from `useCustomerRouteAssignments()` (apps/web/lib/api/routes.ts:299-304 → GET /routes/customer-assignments → routes.service.ts:704-728, every RouteStop with a customer on a `RouteKind.SCHEDULED` route). The Table renders `visibleCustomers` (:949) but the footer (:1011-1013), pager (:1033-1069) and `useClampPage` (:335) use `meta` from the unfiltered query. The server has no such filter: ListCustomersDto (apps/api/src/customers/dto/list-customers.dto.ts:6-17) has search / status / tag / customerType / regulated / sortBy / sortDir only; findAll (customers.service.ts:117-202) builds `where` from those and counts the same `where` (:201) — the count is right for what the server was asked. Secondary: `useResetPageOnChange` deps (:286-292) omit `unassignedOnly`, so toggling on page 7 stays on page 7, usually empty. Class: client-side filter over a paginated server page — no scan signature. Siblings with the same `…Only` state shape worth a glance: apps/web/app/(dashboard)/vendor-bills/page.tsx:935 `needsMappingOnly` and apps/web/app/(dashboard)/inventory/page.tsx:2640 `missingCostOnly` (each needs checking against whether its list is server-paginated).

## User impact

Every operator using the chip on a tenant with more than one page of customers: "Showing 1–20 of 340 customers" over three rows — or the "No unassigned customers" empty state on a page whose unassigned customers sit on page 9 — page buttons that walk unfiltered pages, and no way to reach the unassigned customers except paging through everyone with the chip on. With 20 per page and most customers assigned, the chip is effectively page-1-only. Cost: time, plus a wrong belief that everyone is assigned (the empty state literally says "Every customer is already assigned to a route").

## Fix approach and UX

Server: add `@IsOptional() @IsIn(["1"]) unassigned?: string` to ListCustomersDto and, in the shared where-builder B158 introduces, `if (query.unassigned === "1") where.routeStops = { none: { route: { kind: "SCHEDULED" } } }` — the SAME predicate getCustomerRouteAssignments uses, extracted to one named constant so the "Currently in" hint and the filter cannot drift (L-081's one-named-module rule applied to a filter); with B157 the assignment map also drops removed customers, and the list's own `deletedAt: null` already keeps them out of this filter. Web: put `unassigned: unassignedOnly ? "1" : undefined` into `customersQueryParams` (:321-331), delete `visibleCustomers` and render `customers`, add `unassignedOnly` to the `useResetPageOnChange` deps, keep the chip (:902-920) and its empty state (:956-966), and persist it in the URL like the other chips (the header promises "your current filters are saved in the page link", :686). UX consequence: the chip becomes a server round-trip with the same loading state as the other chips; count, pager and rows agree; the export (B158) inherits the filter for free. Structural: a scan signature `client-filter-paginated` — a `useMemo(() => <x>.filter(` where `<x>` derives from `result?.data` / `data?.data` in a file that also reads `meta.total` — is cheap, would have caught this, and would flag the two siblings above for triage.

## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** Toggling "Unassigned only" shows the customers with no route assignment, with the row count and pager describing that filtered set — as the server-side status, tag and regulated chips do.

**Actually does.** The visible rows are filtered client-side from the current server page, while the footer count and every page button are computed from the server's unfiltered totals.

**The gap.** The table shows a handful of rows, or none, under a footer claiming "Showing 1–20 of N customers", with no way to jump to pages that hold unassigned customers.

**Evidence.** Evidence · apps/web/app/(dashboard)/customers/page.tsx:256, :319-322 (client filter over one page), :859-877 (the chip), :905, :967-969 (count from meta.total/limit/page), :988-1030 (page buttons from meta.totalPages); the assignment map itself is tenant-wide (apps/web/lib/api/routes.ts:280-281), so only the customer rows are page-limited.

**Suggested fix (register).** Add an unassigned filter to the customers list DTO and service (a routeAssignments-is-none equivalent) and drive the chip from it, so rows, count and totalPages all describe the same set.
