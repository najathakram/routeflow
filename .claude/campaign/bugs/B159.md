## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** After removing a customer the operator can add that business back — or add a different customer at the same shop email or username — like any new customer.

**Actually does.** Soft delete sets customer.deletedAt but only marks the User INACTIVE; the row keeps its email and username, and create()'s uniqueness probe filters neither, so re-adding fails with "Email or username already taken".

**The gap.** The blocking row is excluded from every list by the deletedAt filter, so the error names a conflict no filter or search can surface.

**Evidence.** Evidence · apps/api/src/customers/customers.service.ts:1789-1790 (soft branch), :392-395 (the unfiltered probe and its BadRequestException), :112 (findAll hard-codes deletedAt: null), :1723-1741 (restoreCustomer); apps/api/prisma/schema.prisma:690-731 (User.deletedAt at :706 and the two @@unique constraints at :723-724); apps/api/src/customers/dto/create-customer.dto.ts:35 (username required); apps/web/app/(dashboard)/customers/[id]/page.tsx:1978,1993 (restore wired only to the 8-second Undo toast).

**Suggested fix (register).** Free the identity on soft delete — rename the User's email and username to a namespaced tombstone inside the same transaction — or add a persistent restore path plus a probe filtered on deletedAt:null that offers "restore instead?" when the collision is a removed customer.

> ⚠️ Treat this as a hypothesis, not a plan. On F11 the adversarial pass refuted the
> suggested fix for every one of the four bugs while confirming every diagnosis.

**Verifier's note.** Two corrections carried from verification. An un-delete does exist (restoreCustomer), but it is wired only to the 8-second Undo toast — after that window the row is genuinely unreachable, which is when this bites. And filtering deletedAt in the probe alone will NOT fix it: the two database-level unique constraints still throw, so the identity must actually be released. The email half only collides when the removed customer had a real email (a placeholder is minted otherwise), so the guaranteed collision is the username.
