# B159 · A removed customer's User row keeps its email and username, blocking any re-add

**Location** `Customers · API create/delete` · **Severity** medium · **Batch** F15 · **State** queued

## Summary

CONFIRMED at master@2d35375. The soft branch (apps/api/src/customers/customers.service.ts:2044-2047) leaves User.email, User.username and User.googleId in place (status INACTIVE only, User.deletedAt untouched) while `@@unique([tenantId, email])` / `[tenantId, username]` / `[tenantId, googleId]` (prisma/schema/tenancy.prisma:279-281) hold; create()'s probe (:477-480) sees the row and returns "Email or username already taken", and even a deletedAt-aware probe would still hit the DB constraint at :499. Username is required (dto/create-customer.dto.ts:36), so re-adding the same shop collides every time after the 8-second Undo. The CSV import path side-steps the same collision by suffixing `_1` (apps/api/src/import/import.service.ts:405-411, :604-613) — it creates a duplicate rather than failing. Fix: release the identity inside the soft-delete tx with a deterministic tombstone and reverse it on restore (Customer.email keeps the real email; the username suffix is strippable); no migration.

## What this feature is for

After removing a customer, an operator can add that business back later — or add a different customer at the same shop email / username — exactly like a new customer, and a restore brings the original login back unchanged. Identity (email / username / googleId) is per-tenant unique on User, so a removed customer must not keep it occupied.

## Root cause

customers.service.ts:2039-2049: the soft branch writes `customer.deletedAt` and `user.status = "INACTIVE"` only — no rename, and User.deletedAt stays null (auth.service.ts:60-61 and :245 refuse non-ACTIVE users anyway, so login is closed, but the unique keys stay taken). create() :474-480 probes `user.findFirst({ OR: [{ email }, { username }] })` with no status / deletedAt filter and throws 400 "Email or username already taken"; the message names a conflict the operator cannot see because findAll hides the removed row (:126). Filtering the probe alone cannot fix it (the verifier's note holds): `tx.user.create` at :499 would fail on the unique index. The guaranteed collision is the username (required, :36); email collides only when a real one existed (:485 mints `no-email+<uuid>@placeholder.local` otherwise); googleId collides on a Google-linked re-add. Merge is not affected — it hard-deletes the secondary User (:1922-1923). restoreCustomer (:1965-1984) exists but is reachable only from the Undo toast (B170). Class: a soft delete that leaves a unique identity occupied — the write-side variant of the soft-delete omission class; sibling candidates to check: SalesAgent soft delete (sales-agents.service.ts, has deletedAt) and any Driver / User soft-delete path that keeps email / username.

## User impact

Any re-add after the 8-second window (seasonal churn, a shop that comes back, a wrong removal noticed the next day): the Add dialog fails with an error naming nothing visible; the operator's outs are a mangled username (fine) or a fake email (not fine — the shop's real address is the collision), or support with DB access. CSV re-import "works" by creating `acme_1`, leaving two customer records for one shop. Frequency: low–moderate; cost: support time and duplicate / dirty identities — no money write, medium holds.

## Fix approach and UX

Inside the existing soft-delete tenantTransaction (:2044-2047), release the identity on the User row: `username = "<username>~removed~<customerId first 8>"`, `email = "removed+<customerId>@placeholder.local"`, `googleId = null`, and set `User.deletedAt` for consistency with the auth checks. Nothing customer-facing changes: the real email already lives on Customer.email (:512, untouched by the delete) and the real username is the prefix before `~removed~` — deterministic, so no new column and no migration; `isInternalEmail` (apps/api/src/common/internal-email.ts:14) already treats `@placeholder.local` as non-routable, so nothing can email the tombstone. restoreCustomer (:1977-1982): strip the suffix, restore email from Customer.email (or mint a fresh placeholder when null), clear User.deletedAt; if the username / email is now held by a newer customer, throw 409 "That username is now used by another customer — restore with a different username" and accept an optional `username` in the restore body; tolerate pre-fix removed rows (no suffix → nothing to strip, email left as is). create()'s probe stays as is — a tombstoned row no longer matches. Optional UX sugar once B170's restore surface exists: when the probe's hit is a removed customer, return `{ code: "REMOVED_CUSTOMER", customerId }` so the web Add dialog can offer "Restore <name> instead?". UX consequence: re-add just works; restore is unchanged in the normal case and asks for a new username only on a real clash. Cross-tenant login lookups (users.service.ts:39, :52) filter ACTIVE + deletedAt null, so a tombstoned username is never loggable. Structural: a T1 invariant per soft-deleted model — "soft-deleting X releases every @@unique key on its User"; a scan signature is impractical here (it would need to know which update IS the soft delete).

## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** After removing a customer the operator can add that business back — or add a different customer at the same shop email or username — like any new customer.

**Actually does.** Soft delete sets customer.deletedAt but only marks the User INACTIVE; the row keeps its email and username, and create()'s uniqueness probe filters neither, so re-adding fails with "Email or username already taken".

**The gap.** The blocking row is excluded from every list by the deletedAt filter, so the error names a conflict no filter or search can surface.

**Evidence.** Evidence · apps/api/src/customers/customers.service.ts:1789-1790 (soft branch), :392-395 (the unfiltered probe and its BadRequestException), :112 (findAll hard-codes deletedAt: null), :1723-1741 (restoreCustomer); apps/api/prisma/schema.prisma:690-731 (User.deletedAt at :706 and the two @@unique constraints at :723-724); apps/api/src/customers/dto/create-customer.dto.ts:35 (username required); apps/web/app/(dashboard)/customers/[id]/page.tsx:1978,1993 (restore wired only to the 8-second Undo toast).

**Suggested fix (register).** Free the identity on soft delete — rename the User's email and username to a namespaced tombstone inside the same transaction — or add a persistent restore path plus a probe filtered on deletedAt:null that offers "restore instead?" when the collision is a removed customer.

**Verifier's note.** Two corrections carried from verification.
