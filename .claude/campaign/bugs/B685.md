## Reported evidence

Verified across all six GitHub Actions workflow files on master: zero references to test:db, db.spec, or --db-specs -- the DB-backed jest lane never runs in any CI workflow. Demonstrated concretely on #1221 (Lane F's return-axis fix): with the fix reverted on a merged tree, all 395 unit tests in regulated and returns still pass, because the only real regression guard for that fix lives in a .db.spec.ts file that no CI job executes. This is not hypothetical for this one PR -- DB-backed specs are exactly what people reach for when a fix involves real transactions, so this is potentially a lot of the money-family work running genuinely unprotected against a future refactor silently deleting the fix, with every CI gate green. Not assumed to be an oversight -- CI may simply have no Postgres service, making the local-only DB lane a deliberate tradeoff -- but the consequence (unenforced regression guard) holds either way. Two candidate directions, neither chosen here: (1) give CI a Postgres service so the DB lane actually runs, or (2) make it policy that every fix carries at least one default-lane (non-DB) pin alongside its DB spec, so the regression guard exists somewhere CI executes. The existing repo idiom already solves the related problem and is the shape that works here: the copier-contract spec and the unit-line-writers AST scanner both fail the build when a new writer appears unregistered -- whatever direction is chosen should fail the build the same way, not merely document a convention. Third instance of this same class found in one release-night sweep (see B682 for the sibling dead-guard finding); filing now while the evidence is fresh rather than letting it be rediscovered later. Fast-follow, not release-blocking. Filed per the fleet lead's request during Release 1.
