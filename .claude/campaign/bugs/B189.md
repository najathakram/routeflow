## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** Purging an order (or a customer with orders) removes credit-note links first, then the notes, so the transaction completes and the purge lands.

**Actually does.** All three purge sites deleted creditNote rows before the orderCreditNote join rows that reference them, so the FK rejected the delete and rolled back the entire purge transaction — a 500 on an operation the UI presents as routine.

**The gap.** Deletion order was written against the object model, not the FK direction; the join table's constraint makes the inverse order the only legal one.

**Evidence.** Evidence · apps/api/src/orders + customers purge sites (three call sites; REG-B189 ×3 describe blocks pin the invocationCallOrder in each)
