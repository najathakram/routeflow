## Reported evidence

Found during #1264's review as the live 4th consumer that PR's own fix (lineUnitFor/CartRow priceBase) doesn't reach. trayRowsFrom iterates the ENTIRE cart every time the barcode-scan camera modal opens (gated on scanOpen, NewOrderScreen.tsx:2459) -- routine operator behavior, not an edge case. Its catalogRow() computes each row's subtotal via computeLineSubtotal, but the caller's priceFor callback supplies tierPriceFor(product) directly with zero unit-price awareness (TrayLine/TrayProduct don't even carry a unitLabel field). Traced the arithmetic: for a unit-sold line with no manual override, computeLineSubtotal takes the boxes==null&&pieces==null branch and returns unitPrice(pack tier price) * qty(case count) -- e.g. $24 x 1 = $24, while the cart row and footer correctly show $220. Opening the scan camera with a Case line already in the cart shows the wrong price in the tray beneath it. Fix (from the finder): route scan-tray.ts's priceFor callback through unitPriceBase/the line's own unitBasePrice, same shape as the fix #1264 already applies to lineUnitFor/CartRow -- small, mechanical. Also check edit-items-draft.ts#draftTrayRows's priceFor while touching this: it reads a stored catalogPrice field that is ALSO wrong for a hydrated unit-sold line (hydrateFromOrder sets catalogPrice = product.pricePerUnit, never unitPriceBase) but is currently latent, not live, because catalogRow's ternary prefers line.unitPrice whenever set and a hydrated line's unitPrice is always the server's real stored price -- cover both call sites of trayRowsFrom in one pass rather than leaving the latent one for a fifth discovery.
