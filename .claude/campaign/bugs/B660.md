## Reported evidence

AMENDED IN PLACE: R-ui traced both return paths, so the earlier 'untraced link' is now traced and half of the old premise was wrong. THIS STANDS FOR INLINE CAPTURES against box-unaware regulated lines: inline capture stores ReturnItem.qty as TRUE PIECES (inline-returns.service.ts:260 'qty: c.pieces'; inline-returns-pricing.ts:133-145 returnRequestPieces: boxes != null is taken as pieces, otherwise multiplied by the unitsPerBox snapshot) while the regulated-ledger SALE row's qty is BOXES for a box-unaware line (qty 6 = 6 BOXES; see B647 and B658 for how such a line is stored), and reverseReturnEntries (regulated-ledger.service.ts ~209-350) compares the two. A return of 12 pieces closes the row (closesRow = remaining >= rowRemaining, :331) and books the WHOLE remaining net and tax (:344-345): 100% of net sales and category tax reversed instead of 16.7%; a 3-piece return reverses 50% instead of 4.2%. receive() (returns.service.ts ~495-510) builds returnedByProduct as the sum of Number(item.qty) per product and passes it to reverseReturnEntries UNCONVERTED (traced by the Mac Lead). STANDARD RETURNS DO NOT OVER-REVERSE: they store the typed qty in the order line's own unit (BOXES for a box-unaware line, pieces for a box-aware one), which is unit-consistent with the ledger SALE qty. returns-pieces.util.ts:1-11 ('OrderItem.qty is ALWAYS stored as total PIECES') is still false for box-unaware lines, but on this path it does not cause an over-reversal (it does cause B665, the restock). ACCEPTANCE CONDITION for the fix PR: the reversal spec must run BOTH return paths (standard and inline), asserting the standard path stays correct and the inline path reverses only the returned fraction. HOW KNOWN: R-ui traced both paths and verified the arithmetic; the receive() hop was traced by the Mac Lead; code-read only; NEVER RUN. Class: invisible and accruing (regulated filing source, over-reversed net sales and category tax). NO LEGAL CONCLUSION is drawn: a compliance question for the owner's advisor, paired with the ledger soldAt question (not an id). Severity HIGH as ruled by the lead.
