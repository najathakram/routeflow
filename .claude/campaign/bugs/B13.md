# B13 · No way to apply a customer advance on web

**Location** `Invoices / advances · web` · **Severity** medium · **Batch** F09 · **State** queued

## Summary

F09 S2 refutation + S3 ruling (2026-09-05) stand on re-verification at master@2d35375: this is an absent feature, not a regression. `useApplyAdvanceToInvoice` (apps/web/lib/api/invoices.ts:483-500) still has zero callers under apps/web/app; the duplicate `useApplyAdvancePayment` was deleted (R12 shipped — apps/web/lib/api/customers.ts now carries only useCustomerAdvancePayments :271 and useCreateAdvancePayment :279). Web can take money INTO the wallet (customer detail "Record Advance Payment", customers/[id]/page.tsx:3747, :3998-4021) but only mobile can spend it (ApplyAdvanceSheet, apps/mobile/app/(operator)/(tabs)/invoices/[id].tsx:1067-1075, :1086-1160). The ledger has no refuted / won't-fix state (queued, in-flight, proven, done, already-fixed, regressed), so the row sits queued as F09's only open item. Owner decision: BUILD (dev-pipeline feature, T2 REG-B13) or DECLINE (delete the dead hook, close via already-fixed citing that PR).

## What this feature is for

An operator records a deposit / prepayment from a customer as an AdvancePayment (a wallet row with a running `balance`), then later draws that wallet down onto an open invoice instead of taking cash again. The server side is complete: POST /customers/:id/advance-payments/:apId/apply → customers.service.ts:1326-1395 `applyAdvancePaymentToInvoice` — refuses invoices in CREDIT_NOT_APPLICABLE (:1341), caps at min(wallet balance, invoice balance, requested amount) (:1353), writes an InvoicePayment with method ADVANCE + reference AP-<id8> (:1357-1365), decrements the wallet (:1367-1370), recomputes PARTIAL/PAID/OVERDUE (:1372-1387) and syncs commissions (:1391), all in one tenantTransaction. Web shows the wallet (Advance Balance :2399, :3724; the "Advance Payments" card :3753) and creates rows; the missing piece is the spend action on web.

## Root cause

Refuted as a bug (F09 S2 refutation + S3 ruling, 2026-09-05), re-verified at master@2d35375: `git log -S` shows the web hook was added once (d689ab61) and no commit ever added or removed a caller — nothing regressed, the UI was never built. Current state: apps/web/lib/api/invoices.ts:483-500 defines `useApplyAdvanceToInvoice` (typed, correct endpoint, invalidates invoices + the customer's advance-payments); grep of apps/web/app for ApplyAdvance / applyAdvance / useApplyAdvanceToInvoice returns no JSX caller. Web invoice detail (apps/web/app/(dashboard)/invoices/[id]/page.tsx) has a credit-note apply/unapply flow (:67, :1448, :1936) but no advance flow; its only ADVANCE reference is the payment-method guard at :2675. R12 (delete the zero-caller duplicate `useApplyAdvancePayment` in web customers.ts) HAS shipped — the file no longer has that export. Mobile's own comment (:1084) still says "web's hook is dead code with no UI", which is accurate. Class: scan signature `dead-hook` (exported API hook with zero call sites), .claude/skills/bug-hunt/scripts/scan-signatures.mjs:212 — this hook is exactly that signature's target; siblings are whatever `--only dead-hook` reports today. Ledger note: the F09 ruling said "B13 → refuted", but bugs.mjs has no such state, which is why the row is still queued.

## User impact

Any web-first tenant that takes deposits: money goes into the wallet on web and can only come out on the mobile app. Without mobile the operator's workaround is to record a normal payment against the invoice, which leaves the AdvancePayment balance un-decremented — the customer statement's advanceBalance (customers/[id]/page.tsx:2399) then overstates what the customer is owed, and a later operator may apply the same advance again from mobile. Frequency: every deposit-taking tenant on web; cost: wrong wallet balances / double-application risk, or a forced device switch. Not a silent money write (nothing happens on its own), which is why medium holds and why the pipeline classed it as a feature.

## Fix approach and UX

Two owner options, no code written here (money carve-out). OPTION A — BUILD (recommended: web is the golden reference and mobile mirrors it, so mobile-only is backwards). Ship through dev-pipeline, not bug-pipeline — no red-first test is possible for an absence (F09 refutation.md:222-246). On web invoice detail, next to the credit-note action, add "Apply advance" — enabled when invoice.status is not in CREDIT_NOT_APPLICABLE and balance > 0 — opening a sheet that lists `useCustomerAdvancePayments(invoice.customer.id)` rows with balance > 0.001 and, on pick, confirms "X of the customer's advance will be applied to INV-…" then calls `useApplyAdvanceToInvoice({ customerId, advancePaymentId, invoiceId })` — a mirror of mobile :1103-1122; the server caps the amount, so the client does no money math (no re-derivation, no toFixed). Optional second entry: an "Apply to invoice…" row action on the customer detail "Advance Payments" card (:3753). UX consequence: wallet balance drops, invoice flips PARTIAL/PAID, the payments list gains an ADVANCE row with reference AP-…; both queries invalidate (the hook already does this). OPTION B — DECLINE: delete `useApplyAdvanceToInvoice` (invoices.ts:483-500) as dead code, update mobile's comment at :1084, and close the row with `already-fixed --pr <n> --why "dead hook removed; feature declined"` — the only ledger state that fits a non-bug. Structural: the `dead-hook` signature already exists; the gap is that it only runs at hunt time. Adding `node .claude/skills/bug-hunt/scripts/scan-signatures.mjs --only dead-hook,unimported-component` as a warn-level step in `npm run verify` would surface the next orphaned hook at PR time. Either option is one PR; if A, it must be labelled `feat:` (F09 ruling).

## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** An operator should be able to apply a customer's existing advance-payment wallet balance to an open invoice from the web dashboard, the way they already can on mobile.

**Actually does.** `useApplyAdvanceToInvoice` (apps/web/lib/api/invoices.ts:482-499, NOT customers.ts) has zero component callers anywhere in apps/web — no invoice or customer page renders an 'Apply advance' action; web's `useApplyAdvancePayment` (customers.ts:288) is likewise uncalled. Mobile has a working `ApplyAdvanceSheet` (apps/mobile/app/(operator)/(tabs)/invoices/[id].tsx:1052,1070-1106) wired to `useApplyAdvancePayment` (apps/mobile/lib/api/customers.ts:172), and its own in-file comment confirms 'web's hook is dead code with no UI' (line 1068).

**The gap.** Claim's file location for the hook is wrong (invoices.ts, not customers.ts); the dead-code/mobile-has-it substance is otherwise accurate.

**Evidence.** Evidence · apps/web/lib/api/invoices.ts:482-499 (definition, wrong file per claim); apps/web/lib/api/customers.ts:288 (a different, also-uncalled hook); grep of apps/web for ApplyAdvance/applyAdvance shows only these two definitions, no JSX callers; apps/mobile/app/(operator)/(tabs)/invoices/[id].tsx:1052,1064-1106 ApplyAdvanceSheet; apps/mobile/lib/api/customers.ts:172; code map .claude/code-map/mobile.md:579-580 corroborates.

**Suggested fix (register).** Add an 'Apply advance' action to the web invoice detail page (mirroring mobile's ApplyAdvanceSheet) wired to the existing `useApplyAdvanceToInvoice` hook, or delete the dead hook if the feature is deliberately mobile-only.
