# B355 · Web keeps access and refresh tokens in JS-readable localStorage (F11-002)

**Location** `Auth · web (apps/web token storage / api cookie design)` · **Severity** high · **Batch** F48 · **State** queued

## Summary

_Not yet analysed._

## What this feature is for

_Not yet analysed._

## Root cause

Token persistence chose localStorage for cross-domain web/API simplicity; the cookie design behind COOKIE_SECRET was never wired.

## User impact

Any XSS on the web origin yields a durable, replayable session for the victim, including SUPER_ADMIN; CSP narrows but does not remove the class.

## Fix approach and UX

API sets httpOnly+Secure+SameSite cookies on login/refresh (or a same-site BFF route in Next); web reads identity from a non-sensitive claims endpoint; refresh via cookie; logout clears; tenant-slug cookie stays readable; flag-gated cutover with a migration path for live sessions.

## Test plan

T2 Playwright: after login localStorage holds no token-shaped values; auth cookie flags present; refresh and logout behave. T1 API spec: cookie mode sets cookies and omits tokens from JSON.

## Reported evidence

After sign-in the web app persists both tokens in localStorage for every identity, so any script on the origin can read a durable session. Expected: httpOnly+secure+sameSite cookies (COOKIE_SECRET is provisioned but unused); the tenant-slug cookie stays readable by design.
