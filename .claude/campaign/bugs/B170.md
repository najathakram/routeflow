# B170 · "Restore any time" has no surface after the 8-second undo, and a removed customer's page still looks live

**Location** `Customers · remove/restore lifecycle` · **Severity** medium · **Batch** F15 · **State** queued

## Summary

CONFIRMED at master@2d35375, with one new finding that raises the stakes. `useRestoreCustomer` (apps/web/lib/api/customers.ts:416-425) has exactly one caller — the Undo toast (apps/web/app/(dashboard)/customers/[id]/page.tsx:1980, :1994); ListCustomersDto has no includeDeleted (contrast sales-agents.controller.ts:49 / sales-agents.service.ts:57 and platform-admin.service.ts:102-109); findAll hard-codes `deletedAt: null` (customers.service.ts:126); findOne (:448-467) returns deletedAt but the detail page never reads it (grep: zero hits), so a removed customer's page renders live. NEW: the status buttons on that page call changeStatus (customers.service.ts:763-770), which has no deletedAt gate — clicking "Active" on a removed customer produces a zombie: `deletedAt` set + `User.status ACTIVE`, hidden from every list, refused by every #693 door, yet able to log in (auth.service.ts:60-61 checks User.deletedAt and status only, never Customer.deletedAt). Fix: a `removed=1` list filter with a "Removed" badge + Restore, a Removed banner on the detail page that swaps the status / edit / Remove controls for Restore, and changeStatus / update refusing a removed customer.

## What this feature is for

The confirmation copy promises two things (customers/[id]/page.tsx:4253): "You'll have a few seconds to undo, and you can restore the customer any time." Undo exists (8 s toast, :1990-1995). "Any time" needs a persistent surface — a way to find a removed customer and a Restore control — and a removed customer's own page must read as removed so nobody edits or re-activates a record the lists hide.

## Root cause

Web: the restore hook's only caller is inside `runUndoable` (:1990-1995); nothing else imports it in apps/web or apps/mobile. The list page (customers/page.tsx) sends no removed / includeDeleted param and has no chip for it. The detail page reads `customer.user.status` (currentStatus) but never `customer.deletedAt`, so the status buttons (:2990-3015), the edit forms and — when status is SUSPENDED — the Remove button (:3017-3027) all render for a removed customer. API: ListCustomersDto (dto/list-customers.dto.ts:6-17) has no includeDeleted; findAll :126 hard-codes `deletedAt: null`; findOne :448-467 uses `include`, so `deletedAt` IS in the payload (the verifier's correction confirmed); changeStatus :763-770 does `findCustomerOrThrow` + `user.update({ status })` with no deletedAt check, and update() likewise; restoreCustomer :1965-1984 is complete and idempotent. Mobile has no remove or restore at all (no restore / force call in apps/mobile/lib/api/customers.ts). The house pattern already exists twice: sales-agents.service.ts:57 `if (!query.includeDeleted) where.deletedAt = null` and platform-admin.service.ts:109. Class: soft-delete omission on a mutator (changeStatus) — the same class as B131 / B141 — plus a missing surface for an existing endpoint (POST /customers/:id/restore, customers.controller.ts:406-411).

## User impact

Every restore after the toast: the operator has no UI and needs someone with DB or API access. Meanwhile the removed customer's page is one old link away (order and invoice pages link to the customer; browser history; a colleague's bookmark) and looks normal, so operators edit it, or click "Active" to "bring them back" — which creates the zombie above: hidden from lists and exports, refused for orders / invoices / portal, but able to log in and see nothing work. Frequency: every removal that needs reversing later; cost: a false promise in the dialog, support time, and zombie records no screen can explain.

## Fix approach and UX

API: add `@IsOptional() @IsIn(["1"]) removed?: string` to ListCustomersDto and, in the shared where-builder from B158, `where.deletedAt = query.removed === "1" ? { not: null } : null` (show-removed-only is a clearer chip than include-both and keeps the default exactly as today); rows already carry `deletedAt`. changeStatus (:763) and update() refuse a removed customer with 409 "Restore the customer first" — do NOT put deletedAt into `findCustomerOrThrow`, which statements / documents / history reads rely on. Web list: a "Removed" chip beside "Regulated"; when on, rows show a "Removed <date>" badge and a row action "Restore" (useRestoreCustomer, status ACTIVE), with bulk actions hidden. Web detail: read `customer.deletedAt`; when set, render a banner "Removed on <date> — hidden from lists; cannot order or be invoiced. [Restore]" and hide the status buttons, edit affordances, Remove button and portal actions; Restore calls the existing hook, invalidates, and the page returns to normal. Export (B158's builder) follows the chip. Mobile: out of scope (no remove there today); note it for the mirror. UX consequence: the dialog's promise becomes true; zombies become impossible; nothing about the 8-second Undo changes. Structural: changeStatus's missing gate is the same `soft-delete-omission` signature class (a mutator on a soft-deletable model without a deletedAt gate); the T1 spec below pins it until the signature exists.

## Test plan

Tier T1, apps/api/src/customers/customers.service.spec.ts: `REG-B170 T1: findAll removed=1 returns only soft-deleted customers and the default still excludes them`; `REG-B170 T2: changeStatus refuses a removed customer so deletedAt-set + status-ACTIVE (a zombie) cannot be written`; `REG-B170 T3: update() refuses a removed customer`; `REG-B170 T4 (pin): restoreCustomer stays idempotent and honours the SUSPENDED restore status`. ## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** Per the confirmation copy: "You'll have a few seconds to undo, and you can restore the customer any time."

**Actually does.** restoreCustomer works, but its only caller is the undo toast. No list, filter or search can reach a removed customer, and their detail page still renders fully editable, with a Delete button and no Removed badge.

**The gap.** findAll hard-codes deletedAt:null with no includeDeleted flag, and no client reads the deletedAt the detail response already carries.

**Evidence.** Evidence · apps/web/app/(dashboard)/customers/[id]/page.tsx:4252 (the copy), :1978 and :1993 (the sole use of the restore hook, inside the undo handler); repo-wide grep for the restore hook returns its definition at apps/web/lib/api/customers.ts:411 plus that one caller, and zero mobile callers; apps/api/src/customers/customers.service.ts:108-113, :363-382, :1723-1742; apps/api/src/customers/dto/list-customers.dto.ts:6-16 (no includeDeleted) — contrast apps/api/src/sales-agents/sales-agents.service.ts:57 and platform-admin.service.ts:109, both of which offer one.

**Suggested fix (register).** Add includeDeleted to the customers list DTO and service with a "Show removed" filter on the list, and have the detail page read the deletedAt the API already returns to swap Delete for Restore behind a Removed banner.
