## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** Refuse to delete a route whose runs recorded delivery history, so POD photos, signatures and arrival/completion timestamps can never be destroyed. The guard's own comment states this intent.

**Actually does.** The guard tests only r.status === "IN_PROGRESS" || r.status === "COMPLETED", so a CANCELLED run passes it. Its comment asserts the premise out loud — &ldquo;Drafts (and scheduled/cancelled runs, which recorded nothing) stay deletable&rdquo; — which is false for a run cancelled after deliveries were recorded on it. The transaction then unpins the orders (routeRunId: null, routeRunStopId: null), detaches the delivery mutations and hard-deletes every RouteRunStop.

**The gap.** A run is cancelled mid-route precisely when some stops are already delivered — that is the normal reason to cancel. Deleting its route then destroys the only delivery record those orders have, silently and with no warning, while the sibling guard in deleteRun refuses the same data (&ldquo;This run has recorded deliveries; cancel it instead of deleting&rdquo;). The two guards disagree about what a cancelled run contains. This is also currently the ONLY escape for a cancelled run whose orders need re-dispatching, so an operator following the available path destroys evidence to do it.

**Evidence.** Evidence · apps/api/src/routes/routes.service.ts deleteRoute — the R3 status guard (refuses only IN_PROGRESS/COMPLETED; comment states the &ldquo;recorded nothing&rdquo; premise), then inside its tenantTransaction: tx.order.updateMany({ data: { routeRunId: null, routeRunStopId: null } }), tx.deliveryMutation.updateMany({ data: { routeRunStopId: null } }), tx.routeRunStop.deleteMany(...); contrast deleteRun, whose guard is an existing deliveryMutation rather than a status. Verified at source on master@df1ef9a3 during F10. The comment is the load-bearing part: it stops the next reader from checking, which is the same failure shape as deleteRun's reassuring message and F10's own over-claiming POD comment — three instances in one file.

**Suggested fix (register).** Guard deleteRoute on recorded history rather than on run status — reuse deleteRun's predicate (any deliveryMutation on the route's run stops, or any stop with a completedAt/POD column set) so both paths agree — and correct the comment, which currently asserts more than the code checks. Pair it with F11's CANCEL-path work: once cancel unpins orders with nothing delivered, deleting the route stops being the only recovery, so the guard can tighten without stranding anyone.

> suggested fix for every one of the four bugs while confirming every diagnosis.
