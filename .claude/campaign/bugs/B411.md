## Reported evidence

F4 snapshots the stop-gate5-spec-* tmpdir count before and after, and fails if the count changed. A stale dir left behind by any earlier interrupted run (this host, another session, or a prior failed push) makes the NEXT unrelated push's verify fail on this check even though nothing it did leaked anything. Should instead snapshot the SET of dirs before/after and assert no NEW entry was added, not that the count is unchanged. Found live: a concurrent host verify run transiently pushed the count from 0 to 10 during a rf-F39 push attempt (confirmed not a real leak; count was back to 0 moments later).
