# B411 · stop.gate5.spec's F4 leak check asserts count-unchanged instead of creates-no-new-dir

**Location** `.claude/hooks/stop.gate5.spec.mjs F4 ("leaves no stop-gate5-spec-* dir behind")` · **Severity** low · **State** uncampaigned

## Summary

_Not yet analysed._

## Root cause

F4 (stop.gate5.spec.mjs:164 tmpDirsBefore, :651 the after-count) compares countSpecTmpDirs() before/after IN THE SAME PROCESS. A stale dir already present from an earlier, already-FINISHED run is counted in BOTH snapshots and cancels out -- it cannot trip F4. The real trigger is a CONCURRENT run (a sibling verify/push on the same host) creating stop-gate5-spec-* dirs in the window between the two counts -- exactly what the record's own evidence bullet shows (count 0->10, back to 0 moments later). The originally proposed fix ('assert the SET of dirs before/after, no NEW entry') does not fix this either: a concurrently-created dir genuinely IS a new entry in the ambient tmpdir, so the false positive survives unchanged. Correct fix: assert over THIS RUN'S OWN REPO_DIRS array (:149) -- every path this run itself registered is gone -- never over any ambient measurement of the whole tmpdir, which any concurrent sibling process can perturb.

## User impact

_Not yet analysed._

## Fix approach and UX

Rewrite F4 to iterate the REPO_DIRS this run itself registered and assert each one no longer exists (existsSync false per path), dropping the whole-tmpdir count/set comparison entirely. No UX consequence -- CI/test-harness-only check, no user-facing surface.

## Reported evidence

F4 snapshots the stop-gate5-spec-* tmpdir count before and after, and fails if the count changed. A stale dir left behind by any earlier interrupted run (this host, another session, or a prior failed push) makes the NEXT unrelated push's verify fail on this check even though nothing it did leaked anything. Should instead snapshot the SET of dirs before/after and assert no NEW entry was added, not that the count is unchanged. Found live: a concurrent host verify run transiently pushed the count from 0 to 10 during a rf-F39 push attempt (confirmed not a real leak; count was back to 0 moments later).
