# B141 · A removed customer keeps full buyer-portal access and can still place orders

**Location** `Buyer portal · seller-context guard` · **Severity** high · **Batch** F15 · **State** queued

## Summary

ALREADY FIXED on master by PR #693 (692bdf8, 2026-09-11) — guard-only, per the owner ruling of 2026-09-10 (no refresh-token revocation, DECIDE-22: BuyerRefreshToken is account-wide). Verified at master@2d35375: BuyerSellerContextGuard filters the ACTIVE link on `customer: { deletedAt: null }` and logs the removed case on the refusal path; GET /buyer/sellers hides the removed seller; requestSeller / acceptInvite / getInviteDetails and Google sign-in's invite redemption refuse through their not-found branches; the web buyer context drops a stored activeSeller missing from the fetched list. REG-B141 T6–T12 and W1/W4 landed with it. The ledger row is stale for the same reason as B131 (`Bookkeeping-Follow-Up: pending`). Action: `prove B141 --pr 693`, no code.

## What this feature is for

The Remove dialog promises "their portal access is paused" (apps/web/app/(dashboard)/customers/[id]/page.tsx:4270). A buyer account can be linked to many sellers (one CustomerLink per seller, prisma/schema/tenancy.prisma:401-424); removing the customer record at ONE seller must stop that buyer ordering from — or even seeing — that seller, while their other sellers keep working and a restore brings the seller back untouched (which is why the link stays ACTIVE).

## Root cause

At the hunt sha the guard authorised on `status: ACTIVE` alone and the soft delete never touched CustomerLink. Verified FIXED at master@2d35375: apps/api/src/buyer/guards/buyer-seller-context.guard.ts:43-55 (`customerLink.findFirst({ where: { buyerAccountId, tenantId, status: "ACTIVE", customer: { deletedAt: null } } })`), :57-71 (a refusal-path second query names the removed customer in the log; the happy path stays one query); apps/api/src/buyer/buyer.service.ts:30 (getSellers hides the removed seller), :81 / :121 / :189 (invite details, acceptInvite, requestSeller refuse as not-found); apps/api/src/auth/google-oauth.service.ts:615 (sellerCount ignores the removed link), :647 (invite not redeemed); apps/web/lib/buyer-auth-context.tsx (stored activeSeller dropped when absent from the list). All 45 seller-scoped routes in buyer.controller.ts — including @Post("orders") :527-532 — and the 6 in buyer-payments.controller.ts pass through this guard (train4 cause-ruling.md:31-33), so one choke point covers every order door. Deliberately NOT done: a CustomerLink status change on delete (restore symmetry) and refresh-token revocation (tenancy.prisma:426-435 — BuyerRefreshToken has no tenantId; revoking would log the buyer out of every other seller). Class: soft-delete filter omission at an auth choke point — same class as B131; the guard was the one place the omission granted access rather than minted a document.

## User impact

Pre-fix: a buyer whose customer record the seller removed could keep browsing and POST /buyer/orders — a real Order row for a customer the operator had removed, plus a false promise in the dialog. Post-fix: the very next seller-scoped request returns 403 "No active connection to this seller"; the seller disappears from the buyer's switcher; the in-flight access token (up to 15 min) is not revoked but cannot reach any seller-scoped route. Account-level routes (disconnectFromSeller and friends) still work, which is correct — they act on the buyer's own account, not the seller's data.

## Fix approach and UX

No further code. `npm run bugs -- prove B141 --pr 693 --proof "REG-B141 T6: the seller-context guard refuses a removed customer's ACTIVE link, and names it in the log"`. UX as shipped: the buyer sees the seller vanish (list + stored selection dropped); on restore the seller reappears with the same link, cart and history — nothing to re-invite. Structural: same `soft-delete-omission` scan signature proposed on B131; for guards a narrower, near-zero-noise rule is "any `canActivate` whose Prisma where includes a `customer` / `buyerAccount` relation must also filter that relation's deletedAt" — the guard spec (T6/T7) is the pin until the signature exists.

## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** The Remove dialog states in its own body that "their portal access is paused", so the operator expects the portal login tied to that customer to stop being able to order.

**Actually does.** The soft delete never touches CustomerLink, and the seller-context guard authorises on an ACTIVE link without reading customer.deletedAt. Every buyer endpoint, including POST /buyer/orders, keeps working.

**The gap.** The guard checks tenant status but not customer deletion, so the sentence in the dialog has no code behind it on the seller side.

**Evidence.** Evidence · apps/api/src/buyer/guards/buyer-seller-context.guard.ts:31-35 (tenant status checked), :37-49 (customerLink.findFirst on status ACTIVE only; the customer select does not include or filter deletedAt); apps/api/src/buyer/buyer.controller.ts:81-82, :457-462 (@Post("orders") guarded only by BuyerSellerContextGuard); apps/api/src/customers/customers.service.ts:1786-1792 (soft branch leaves CustomerLink untouched); apps/web/app/(dashboard)/customers/[id]/page.tsx:4252 and 4269-4271 (the dialog copy, verified verbatim); contrast apps/api/src/buyer/buyer-auth.service.ts:168,202,278,418,475 where BuyerAccount.deletedAt is guarded everywhere.

**Suggested fix (register).** Set the customer's CustomerLink rows to a non-ACTIVE status on soft delete (restoring them on restoreCustomer), and add customer: { deletedAt: null } to BuyerSellerContextGuard's link lookup so the omission is closed at the choke point.
