## Reported evidence

After a committed buyer merge, a failed recordIdempotencyKey call is only logged (orders.controller.ts:207-213), so a client retry with the same idempotency key re-runs the fold and computes ABSOLUTE totals a second time over the same cart -- the same swallowed-money-failure class as B58 (F18 sibling-sweep finding, 2026-09-06). A complete fix collides with the standing rule that customer merges serialize through withAdvisoryLock with no transaction threaded into updateOrderItems; recorded in F18's result.json as a deferred owner question (is the accepted failure still acceptable, should recordIdempotencyKey move inside the merge transaction, or should the merge fail closed when the record cannot be written), not fixed by F18.
