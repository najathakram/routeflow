# B140 · Mobile sign-out never clears the query cache — the next tenant sees the previous tenant's figures

**Location** `Auth session · mobile` · **Severity** high · **Batch** F19 · **State** done

## Summary

The offline-queue and cache keys carry no per-tenant prefix, so a shared-tablet flow that signs out one tenant's driver and signs in another's can read/replay data across tenants.

## What this feature is for

_Not yet analysed._

## Root cause

Storage keys (routeflow-offline-queue etc.) are device-global with no tenant segmentation; teardown on sign-out also never ran, so stale state simply persisted into the next session regardless of tenant.

## User impact

_Not yet analysed._

## Fix approach and UX

D1 teardown: session-teardown.ts resets every user-scoped store (podStore, runSettlementStore, mileageStore, routeStore, delivery-plan-store, listUiStore, productPickerStore) and clears the query cache on sign-out, called before apiLogout(); tenant store itself is intentionally kept (Q2 ruling — shared-tablet branded login).

## Test plan

session-teardown.test.ts pins: sign-out clears every user-scoped store and cache; tenant slug survives sign-out.

## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** Signing out ends the session; the next sign-in on that device shows only the newly authenticated user's tenant data.

**Actually does.** The module-scoped QueryClient survives logout. Untenanted keys such as ["analytics","revenue",from,to] and ["reports","ar-aging"] with a 120-second staleTime serve one tenant's cached numbers into the next session with no refetch.

**The gap.** Tokens and Zustand state are cleared on logout; the cache holding the actual tenant data is not, and its keys carry no tenant identity.

**Evidence.** Evidence · apps/mobile/app/_layout.tsx:38 (QueryClient created at module scope with no defaults); apps/mobile/lib/auth-store.ts:67-70 and lib/auth.ts:273-292 (neither touches the cache); apps/mobile/lib/api/admin.ts:886-895, :980-993, :1046-1059 — 12 keys at staleTime 120_000 between :818 and :982, none tenant-scoped; apps/mobile/lib/api/addons.ts:24-29 carries an in-repo comment stating the QueryClient is module-scoped and nothing clears it on logout, with the tenant-scoped mitigation applied only there (:43); apps/mobile/app/(customer)/sellers.tsx:48 is the app's only qc.clear(); apps/mobile/lib/tenant-store.ts:81-84 (clear() has zero callers).

**Suggested fix (register).** Call queryClient.clear() from the staff logout path (export the client from _layout.tsx or hold it in a ref the auth store can reach), and wire useTenantStore.clear() into logout so a stale slug cannot re-key the next session.

> ⚠️ Treat this as a hypothesis, not a plan. On F11 the adversarial pass refuted the
> suggested fix for every one of the four bugs while confirming every diagnosis.

**Verifier's note.** Not a duplicate of B113, which cites the same _layout.tsx:38 line but is about socket-reconnect invalidation. The real-world window is bounded by TanStack's default five-minute gcTime after a screen unmounts, so exposure is roughly "sign back in within a couple of minutes" — the repro as written holds.
