# B327 · The 3-day payment-grace suspension can never fire — nightly rollCycles and the Stripe webhook keep periodEnd fresh

**Location** `Platform billing · API billing.suspendOverdueTenants vs billing-cron.rollCycles` · **Severity** high · **Batch** F42 · **State** queued

## Summary

The 3-day payment-grace suspension can never fire — nightly rollCycles and the Stripe webhook keep periodEnd fresh

## What this feature is for

Context: Platform billing · API billing.suspendOverdueTenants vs billing-cron.rollCycles. This is part of the F42 batch ("The 3-day payment-grace suspension can never fire — nightly …") — see the batch theme in the hunt digest for the surrounding feature's purpose.

## Root cause

Owner-confirmed policy (2026-09-14): the first five customers are free pilots, not charged -- 'non-payers are never auto-suspended' is current POLICY here, not a defect. Do NOT close this by dropping the stripeSubId filter in suspendOverdueTenants() -- that would suspend tenants who were never charged. The Phase 1 charge-loop design (successor row, filed separately) must CREATE a non-payment signal, not start reading one; failedPaymentCount/nextChargeAt are currently dead columns (zero reads/writes). Stays open pending that design work.

## User impact

Severity: high. High — a real operational or financial discrepancy that a user or auditor will eventually notice as a books/behavior mismatch.

Symptom: A non-paying tenant keeps full ACTIVE access until Stripe's own dunning cancels the subscription; the emailed "within 3 days" warning is false and SUSPENDED is unreachable.

## Fix approach and UX

Suggested test: REG-B<id> a tenant whose renewal payment failed is suspended after the grace window even though rollCycles advanced its period (filled with this record's own id at filing time).
