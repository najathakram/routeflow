## Reported evidence

With flag.units_v1 on, a DRAFT invoice can hold a line sold by a unit (created by POST /invoices with unitLabel, #1140, or copied from a New-sale order): stored as unitLabel 'Case', boxes 3, pieces 0, unitsPerBox 288, qty 864, unitPrice 480 (per Case), subtotal 1440. The invoice EDIT page maps that loaded item into its own line state keeping unitsPerBox and boxes but NEVER unitLabel (the web InvoiceItem type does not carry it). On save it derives boxes 3 / pieces 0 and PATCHes with no unitLabel; update() takes the PACK branch, which re-reads the PRODUCT's unitsPerBox (24): the line is stored as 3 boxes of 24 = 72 pieces at 480 per box = still $1,440. The unit label is lost and the stored quantity is 72 pieces instead of 864: inventory and the ledger silently lose 792 pieces while the money and every screen stay self-consistent, so no one sees it until a stock count. WORSE than the money-visible sibling defects (a $480 Case becoming a $42 pack shows as wrong money; B638 shows a wrong price) because the money still adds up. ZERO exposure while flag.units_v1 is OFF (no unit line can exist); this gates granting the flag to a REAL tenant, not the test-tenant flip. Fix (fail closed, fleet lead standing rule: wherever the server refuses a unit line the UI must refuse visibly, never convert, never fall back to the pack, never drop the unit): the edit page refuses to open a draft that holds a unit line, with a visible specific message; update() already refuses a unit request (4c-2 skipped). Also found the same class in the detail page label (3 Cases shown as '3 boxes'). Sibling defects the same night: A1 replaceAll re-denominating a Case to the pack, B638 mobile draft resume, invoice update() refusal becoming a silent conversion. Found while scoping units 5c (#938).
