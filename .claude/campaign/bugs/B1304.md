# B1304 · Super admin 'Sign in as admin' lands on /login when the same browser holds a buyer-portal session

**Location** `apps/web/app/(platform-admin)/admin/tenants/[id]/page.tsx:1965-1981 (impersonate case); apps/web/lib/portal-routing.ts:51-57 (resolveOperatorPathGuard)` · **Severity** high · **Batch** F64 · **State** queued

## Summary

_Not yet analysed._

## What this feature is for

Platform admin tenant page, Sign in as admin: the user is a super admin who opens a tenant and impersonates its admin.

## Root cause

The impersonate case (apps/web/app/(platform-admin)/admin/tenants/[id]/page.tsx:1965-1981) calls setImpersonation (apps/web/lib/impersonation.ts:46-65: localStorage only) and setTenantCookie, then hard-loads /dashboard. It never calls setOpPresenceCookie (apps/web/lib/presence-cookies.ts:36), so rf-op-auth is not 1. When the same browser also holds the buyer presence cookie, resolveOperatorPathGuard (apps/web/lib/portal-routing.ts:51-57, called from apps/web/middleware.ts:38) sees buyerAuthed and not opAuthed on an operator path and redirects to /login (guard added in 7aa20e712b). Exit (doExitImpersonation, impersonation.ts:110-116) clears the tenant cookie and impersonation keys but no presence cookie.

## User impact

A super admin who is also signed in to the buyer portal in the same browser cannot use Sign in as admin: the click ends at the operator sign-in. Risk class HIGH (auth, presence cookies). Workaround: sign out of the buyer portal first.

## Fix approach and UX

Impersonate sets the operator presence cookie (setOpPresenceCookie) after setImpersonation, and exit clears it (clearOpPresenceCookie) so the browser does not keep an operator presence it did not earn. Check that the clear does not log out a real operator session in the same browser. Needs the owner-visible auth review; do not fix unattended.

## Test plan

T1 web jest: impersonate click sets rf-op-auth=1 and exit clears it; middleware spec: buyer cookie plus impersonation does not redirect. Token REG-B1304.
