# B32 · Two identical “Open in Google Maps” buttons

**Location** `Route runs · mobile` · **Severity** medium · **Batch** F20 · **State** queued

## Summary

The operator route-run detail screen renders two simultaneously-visible Pressables both labelled "Open in Google Maps" that compute materially different routes. The bug is CONFIRMED at HEAD (all three adversarial lenses reproduced it at the cited lines). What the adversarial pass DID refute is the register's suggested fix: 1 of 3 lenses showed that deleting the second button and routing everything through `handleOpenInMaps` converts the screen into a silent dead control in a common state — because `openRouteInMaps` promotes `waypoints[0]` to origin and then `return`s with no feedback when nothing is left, so a one-pending-stop run with no live GPS opens nothing at all. The fix below therefore changes the origin contract and the failure contract, not just the JSX.

## What this feature is for

Hand the operator one unambiguous jump from a route run into Google Maps turn-by-turn navigation for the work that is actually left on that run, starting from where the driver is now. It is the bridge between RouteFlow's planned stop order and the device that actually drives it.

## Root cause

Defect class: duplicate-control-divergent-payload — two independently-gated controls in one screen invoke the same primitive with different payloads, and their gates overlap.

`apps/mobile/app/(operator)/route-runs/[id].tsx`:

- Button 1, :350-355, gated `!isTerminal` (`isTerminal = COMPLETED || CANCELLED`, :247) → `handleOpenInMaps` (:151-162): filters `stops` to PENDING|IN_PROGRESS, toasts "No pending stops" when empty, and supplies a live-GPS origin ONLY when `run?.status === "IN_PROGRESS"` (via `readCurrentLocation`, :35-56).
- Button 2, :378-383, gated only `pins.length > 0` → `openRouteInMaps(stops as any)` with EVERY stop (`stops` :86-89, status union includes COMPLETED|SKIPPED, `apps/mobile/lib/api/routes.ts:63`) and no options at all. The `as any` is gratuitous — `stops` is already `RouteRunStop[]`.

For any SCHEDULED or IN_PROGRESS run with ≥1 geocoded stop both gates are true, both read "Open in Google Maps", and they disagree on membership AND on origin. The origin disagreement is worse than the report states: `apps/mobile/components/openInMaps.ts:105-109` promotes `waypoints[0]` to the origin and slices it out of the destination list when no origin is passed (`stopList = hasOrigin ? waypoints : waypoints.slice(1)`), then `if (stopList.length === 0) return;` — a silent, unreportable no-op (`openRouteInMaps` returns `void`). So neither button navigates the operator TO its own first stop on a non-IN_PROGRESS run, and a single-routable-stop run opens nothing.

Two more gates are wrong, not just duplicated: `pins.length > 0` requires numeric lat AND lng (:91-107) while `stopToWaypoint` (`openInMaps.ts:68-83`) builds from ADDRESS TEXT first — two different predicates for one control. And on a terminal run button 1 vanishes while button 2 still renders, leaving a lone "Open in Google Maps" that routes through an already-finished route.

## User impact

Who: every operator/dispatcher who opens a run on mobile — the (operator) role is not dev-gated (`_layout.tsx:174-198` gates DRIVER only), and the screen is pushed from five places (dispatch :193, home :361, routes/[id] :161, trips/new :225, tenant/today :294). The addon gate (`(operator)/_layout.tsx:27`, EITHER routes OR delivery) fails OPEN.

How often: the ambiguous state is the DEFAULT state, not an edge — both buttons render on every SCHEDULED or IN_PROGRESS run with at least one geocoded stop, i.e. every run opened on a delivery day. The payloads actually diverge as soon as one stop is COMPLETED or SKIPPED, and unconditionally on IN_PROGRESS runs (GPS origin vs stop #1) — that is the normal mid-day state.

What it costs, in ascending order of concreteness:

- Wrong tap on an in-progress run: navigation restarts at stop #1 and re-drives already-completed/skipped addresses, losing the live-GPS origin. Cost is fuel, driver minutes, and a dispatcher call to sort it out — real but recoverable, which is why this is medium and not high: nothing is written, no money math, no data loss.
- Silent truncation on both buttons for runs over ~10 routable stops (unchunked `&waypoints=`) — the operator gets a route that quietly omits stops, with no indication. Multi-drop runs of that size are the common case for the delivery product.
- On a terminal run only button 2 survives, so the ONLY maps control on a finished run navigates the whole completed route.
- Single-routable-stop runs already hit the `stopList.length === 0` silent return on button 1 today: tap, nothing happens, no toast.

Not a security or tenancy issue; no money path touched.

## Fix approach and UX

Extract the decision, fix the origin contract, fix the failure contract — then delete the duplicate. Deleting alone is a regression (see summary).

1. NEW `apps/mobile/lib/route-maps-action.ts` — one pure exported resolver, e.g. `resolveRouteMapsAction({ runStatus, stops, hasLiveOrigin, depot })` returning a single discriminated result: `{ kind: "hidden" } | { kind: "unavailable", reason }` | `{ kind: "open", waypoints, origin }`. One return value ⇒ two controls become unrepresentable, the way `apps/mobile/lib/unlisted-affordance.ts` makes two openers unrepresentable. Jest-testable without RN render (mobile Jest is pure-logic only).

2. `apps/mobile/components/openInMaps.ts` — make the two silent returns (:103, :109) reportable: change `openRouteInMaps` from `void` to `"opened" | "no-waypoints" | "no-destinations"`, and make the origin an explicit discriminant (`{ origin: {lat,lng} } | { origin: "first-stop" }`) so "no origin" is a written choice, never a defaulted one.

3. `apps/mobile/app/(operator)/route-runs/[id].tsx` — DELETE the :378-383 Pressable and the `stops as any`. Keep ONE control driven by the resolver, gated on ROUTABLE stops (the `stopToWaypoint` predicate — address text OR coords), not on `pins.length` (coords only). In `handleOpenInMaps`, fall back to the depot (`settings.depotLat/depotLng`, already loaded at :112-129) when `readCurrentLocation()` returns null or the run is not IN_PROGRESS, so `hasOrigin` is always true and no pending stop is ever consumed as the origin. Toast on every `unavailable`/non-`"opened"` result.

4. Route the operator screen through `buildGoogleMapsLegs` (`apps/mobile/lib/gmaps-export.ts:20-46`) as the driver screen does, so runs over 9 waypoints chunk into handoff legs instead of truncating.

5. Sibling: apply the same resolver to `apps/mobile/app/(driver)/route/index.tsx` (:437-447 vs :477-481, plus StartOfDay :266-271) — otherwise the identical trap stays on the driver's primary screen.

UX CONSEQUENCE, stated explicitly (this is a behaviour change, not a cleanup):

- The operator LOSES the "navigate the entire planned route including completed and skipped stops" option that button 2 provided. That option has a real use — re-driving a run, or reviewing a finished one. Give it back as a DISTINCT, differently-labelled control, not a second "Open in Google Maps": on terminal runs the single control becomes "Open full route in Google Maps" (all stops, depot origin); on non-terminal runs it stays "Open remaining stops in Google Maps". The label now carries the payload, which is the actual defect being fixed.
- Multi-leg runs will now present "Leg 1 / Leg 2 …" instead of one link (the existing `buildGoogleMapsLegs` behaviour, already familiar from the driver screen and web). This replaces a silently-truncated route with a visibly-chunked one — better, but it IS a visible change and belongs in the release note.
- On a run with no routable stop the control is disabled with a reason instead of being an inert tap.
- Deliberately NOT mirroring web's `GmapsExportButton` payload verbatim (depot + all stops + end, no status filter): web `routes/[id]` is a route-definition screen, this is a live run. Mirroring endpoints/DTOs is the house rule; mirroring a planning screen's payload onto a run screen would re-introduce the "navigate through completed stops" defect by policy. Recording that as the explicit product call so it is not inherited by accident.

**Structurally preventable — yes.** Three layers, cheapest first.

(1) SCANNER SIGNATURE — add `duplicate-action-label` to `.claude/skills/bug-hunt/scripts/scan-signatures.mjs` (signal: high, register: ["B32"], mandatory offender/clean fixtures per the --self-test rule). Within a single .tsx: collect every user-facing label literal that is a descendant of a JSX element carrying `onPress=`/`onClick=`; flag any multi-word label appearing at ≥2 such sites in one file. Requiring BOTH occurrences to sit under a press handler is what excludes the trigger+modal-title pairs that dominate the false-positive set (verified against `(operator)/customers/[id].tsx` :293/:502, `(customer)/orders/[id].tsx` :372/:426, `(operator)/routes/[id].tsx` :434/:464). This alone catches B32 and the driver-screen sibling's payload split would still slip through, hence (2).

(2) SCANNER SIGNATURE — `maps-launch-divergence` (generalizable as: >1 call site of the same side-effecting launcher primitive in one screen file). Flag any screen with more than one call to `openRouteInMaps` / `openRouteFromHere` / `buildGoogleMapsLegs`. Catches B32, both driver-screen sites, and any future third semantic, and does not depend on the labels matching.

(3) TYPES — the durable one, makes the class unwritable rather than detectable:

- `openRouteInMaps(stops, options)` → require an explicit origin discriminant (`{ origin: { lat, lng } } | { origin: "first-stop" }`). The current optional `originLat?/originLng?` lets a call site silently inherit the waypoint-promotion behaviour; a required union makes every call site state its intent, and `tsc --noEmit` catches the omission.
- Return `"opened" | "no-waypoints" | "no-destinations"` instead of `void`. A `void` primitive with two bare `return`s (openInMaps.ts:103, :109) is structurally incapable of producing a dead-control bug report; a result union lets the caller toast, and makes the silent-no-op class visible.
- Screens should not construct waypoint sets at all: have one exported `resolve*MapsAction()` per feature return a single discriminated value, so "two controls" has no type to inhabit. `apps/mobile/lib/unlisted-affordance.ts` is the existing house precedent for exactly this shape.

A lint rule alone cannot do (3) — the value is in the signature, not the call site.

Extracting the decision into `apps/mobile/lib/route-maps-action.ts` and jesting the resolver is both the testable shape AND the structural fix, so T1 is not a compromise here. `REG-B32` runs pre-merge in `npm run test`. No Playwright: the screen is mobile-only, so T2 has no surface. Add one T3 manual row (tap the single control on a SCHEDULED, an IN_PROGRESS mid-run, and a COMPLETED run on a device and confirm the URL that opens) because `Linking.openURL` is not exercised by T1.

**Proof token:** `REG-B32 route-run maps action resolves to exactly one control with an explicit origin`

**Cases:**

1. resolves exactly ONE action for a run whose stops are all PENDING — never a pair, never both a remaining-work and a full-route result (the core B32 assertion: one return value ⇒ two controls unrepresentable)
2. IN_PROGRESS run with completed + skipped + pending stops and a live origin: waypoints contain ONLY the PENDING/IN_PROGRESS stops, origin is the live coords, and no COMPLETED or SKIPPED stop appears
3. SCHEDULED run, no live origin: origin falls back to the depot and the first pending stop is still present as a DESTINATION — the regression the adversarial pass caught (waypoints[0] must never be consumed as origin)
4. IN_PROGRESS run with exactly one pending stop and readCurrentLocation() returning null: resolves to `open` with a depot origin, NOT to a silent no-op — asserts the dead-control state is gone
5. run whose only stop carries address text but no lat/lng: still routable (stopToWaypoint predicate), so the control is offered — asserts the gate no longer uses the coords-only `pins` predicate
6. run with zero routable stops (no address parts, no coords): resolves to `unavailable` with a reason, so the caller can toast instead of presenting an inert button
7. COMPLETED / CANCELLED run: resolves to the full-route action (all stops, depot origin) under its own distinct label — asserts the terminal-run case is a labelled variant, not a second identically-named button
8. run with 14 routable stops: the plan chunks via buildGoogleMapsLegs into >1 leg with no stop dropped, and stop order is preserved end to end — asserts the >9-waypoint silent truncation is gone
9. openRouteInMaps returns a non-`opened` result for an empty waypoint list and for a single-waypoint no-origin list, rather than returning void — asserts the failure is reportable

## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** A single, unambiguous "Open in Google Maps" action reflecting the driver's actual remaining work (pending stops, from wherever they are now).

**Actually does.** Two separate buttons both labeled "Open in Google Maps" can render simultaneously: one (!isTerminal-gated, handleOpenInMaps) opens only PENDING/IN_PROGRESS stops with a live-GPS origin when the run is IN_PROGRESS; the other (visible whenever pins.length>0, regardless of terminal status) opens ALL stops including COMPLETED/SKIPPED ones with no origin, via openRouteInMaps(stops).

**The gap.** Identical labels hide materially different routes — tapping the wrong one can navigate through already-completed/skipped stops or drop the live-location origin.

**Evidence.** Evidence · apps/mobile/app/(operator)/route-runs/[id].tsx:151-162 (handleOpenInMaps: filters to pending/in-progress + GPS origin), :350-355 (button 1, gated `!isTerminal`), :378-383 (button 2, gated only `pins.length > 0`, calls `openRouteInMaps(stops as any)` with all stops, no origin).

**Suggested fix (register).** Remove the redundant second button (lines 378-383) and route all cases through the single handleOpenInMaps action (adjust its pending-stop filter/gating if a completed run should still support "open all stops", but keep exactly one clearly-labeled control).
