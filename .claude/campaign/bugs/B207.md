## Reported evidence

_Imported verbatim from the bug register — this is the ORIGINAL report, not analysis._

**Meant to do.** An operator scanning a case onto an order that already holds that product bills the combined goods correctly, in boxes.

**Actually does.** The staff merge calls foldMergeItems on the stored lines WITHOUT the stored-side normalizer F06 added. A stored box-unaware line of 2 (= 2 boxes of a upb-12 product at a $10.00 box price, $20.00 of goods) folds as 2 loose PIECES; a scanned case then yields {boxes:1, pieces:2, qty:14}, and the operator replaceAll branch honours that split verbatim — computeLineSubtotal bills $11.67 where the goods are 3 boxes = $30.00. An ~$18 under-bill per merge.

**The gap.** This is B47's mis-bill class on the other caller of the same module. F06 cured the buyer path and deliberately froze the staff path byte-identical (its R12 kept the REG-B199 suite passing unmodified), so the fix sits one import away and was left out of scope on purpose.

**Evidence.** Evidence · apps/api/src/orders/orders.controller.ts, the foldMergeItems call in the POST /orders merge lock; apps/api/src/orders/merge-items.ts normalizeBoxUnawareSnapshots (exists, not used by this caller) and its SCOPE comment, gap 2; apps/api/src/orders/orders.scan-hardening.spec.ts (REG-B199 pins today's staff fold). Found by F06's Fable final pass, 2026-09-01.

**Suggested fix (register).** Apply normalizeBoxUnawareSnapshots to the stored lines on this caller too, with the LIVE unitsPerBox map the controller can already build. Because REG-B199 pins the current fold output, that suite's expectations move with the fix — update them deliberately, in a batch that owns this file, and pin the $30.00 case.
