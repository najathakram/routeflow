## Reported evidence

POST /public/tenants/resend-verification is unauthenticated and mints a 24h email-verify JWT for ANY user with status=INACTIVE, with no way to distinguish a self-signup admin genuinely pending email verification from a staff member an admin deactivated via changeStatus, or a seat-cap downgrade deactivated via BillingCronService. Following the emailed link (verifyEmailAndLogin) flips that account back to ACTIVE, self-reactivating it. Found during an independent Opus review of PR #778 (feat/rescue-auth-invites) -- confirmed pre-existing on master, not introduced by that PR; #778 narrows it slightly (a SUSPENDED account can no longer be reactivated this way) but does not close the INACTIVE case. Root fix needs a schema discriminator (e.g. a nullable emailVerifiedAt column or a distinct PENDING_VERIFICATION status) since UserStatus has no column distinguishing "never verified" from "deliberately deactivated".
