## 1. Strategy for this change

A behavior change in the web middleware (redirect targets), a new pure routing module, two new
presence-aware UI affordances, two sign-in-page notices, and a `redirect` parameter on the
operator sign-in. The routing decisions are pure functions of (pathname, search, cookies) and are
proven at unit level with hand-derived oracles; the middleware itself is a thin wrapper that is
proven by raw-request Playwright tests (post-deploy) and by the UI-verify phase against a local
`next dev`. The UI pieces are proven with React Testing Library against `document.cookie`, plus
one server-render test for hydration safety.

| Level       | Used here? | Why / why not                                                                                                                                                                                                                                                                                               |
| ----------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| unit        | yes        | `lib/portal-routing.ts` (guard, landing, redirect sanitizer) and `lib/presence-cookies.ts` (readers/writer) are pure; every branch can fail for the right reason here                                                                                                                                       |
| property    | no         | inputs are a small enumerable set of paths/cookies; a hand-built matrix (T7, T9) covers the boundaries; permissions are not widened (no access is granted anywhere)                                                                                                                                         |
| contract    | no         | no API shape changes                                                                                                                                                                                                                                                                                        |
| integration | RTL        | the sign-in pages and the shared link component rendered with the real providers (`test-utils/render.tsx`) — the wiring between `useSearchParams`, the sanitizer, the router push and the cookie readers is what can go wrong                                                                               |
| e2e         | yes        | raw-request middleware contract in `apps/web/e2e/05-cross-cutting.spec.ts` (extends the existing CC-11…CC-15 block); two read-only assertions on the authenticated menus in `02-operator.spec.ts` and `04-buyer-portal.spec.ts`. These run post-deploy against the deployed site, never inside the red gate |
| manual      | no         | —                                                                                                                                                                                                                                                                                                           |

**Rule applied:** lowest level that can fail for the right reason.

**Deliberately NOT tested, and why**

- The Radix `DropdownMenu` keyboard behavior with `asChild` — framework behavior (assumption A7 in spec §10; reviewed, and exercised post-deploy by T27).
- The exact Tailwind classes — verified by screenshot in UI verify and the design-system lens, never asserted from source.
- Next.js `useSearchParams`/`Suspense` mechanics — framework; the `next build` in the final gate is the check that the boundary exists.

**Risk driving depth:** auth-adjacent routing. Worst credible bugs: an open redirect through `/login?redirect=`, a redirect loop between the guard and the sign-in page, a dual-role user still locked out. Depth: unit + RTL + negative tests on every one of those, plus the mutation probe on the routing module and the sign-in page.

**Characterization tests needed first?** No — the existing CC-11…CC-15 already pin today's landing contract and stay unchanged.

### 2.1 Expanded cases

**Guarded import (T1–T9, T13–T15, T26)** — the modules/exports under test do not exist before
implementation. Import them so their absence is an _assertion_ failure, never a module error:

```ts
// eslint-disable-next-line @typescript-eslint/no-require-imports
function load<T>(path: string): Partial<T> {
  try {
    return require(path);
  } catch {
    return {};
  }
}
const routing = load<typeof import("./portal-routing")>("./portal-routing");
// then: expect(routing.resolveOperatorPathGuard?.({ ... })).toBe("/login?redirect=%2Fdashboard");
```

For the component: `const Comp = (load<typeof import("./PortalSwitchLink")>("./PortalSwitchLink").PortalSwitchLink ?? (() => null)) as React.ComponentType<any>;` — renders nothing, so `queryByRole("link")` is `null` and the assertion fails on its own expectation. For `presence-cookies`, call through a no-op fallback: `(mod.setLastPortalCookie ?? (() => {}))("op"); expect(document.cookie).toContain("rf-last-portal=op");`.

**T10 / T12 — login page with a `redirect` parameter**

- **Given:** `jest.mock("next/navigation", () => ({ useRouter: () => ({ push }), useSearchParams: () => mockParams }))` with a module-level `let mockParams = new URLSearchParams()`; each test sets `mockParams = new URLSearchParams("redirect=…")` before rendering. `@/lib/api-client` mocked exactly as in `apps/web/app/(auth)/login/page.test.tsx:11-18`; `apiClient.post` resolves `{ data: { accessToken, refreshToken, user: { …, forcePasswordChange: false, tenantSlug: "acme" } } }`.
- **When:** type Workspace `acme`, Username `operator1`, Password `s3cret-pw`, click the `Sign in` button (`getByRole("button", { name: /sign in/i })`), as the existing test does.
- **Then:** `await waitFor(() => expect(push).toHaveBeenCalledWith("/orders/abc?tab=1"))` (T10, in the NEW file `portal-switch.test.tsx`); `…toHaveBeenCalledWith("/dashboard")` with `redirect=https://evil.com/x` plus `expect(push).not.toHaveBeenCalledWith(expect.stringContaining("evil.com"))` (T12, in the EXISTING `page.test.tsx` beside T11).
- **Fails today:** T10 receives `/dashboard`. T11 and T12 pass today (pins) — that is why they live in `page.test.tsx`, which the red-gate command does not run. The existing file's `next/navigation` mock gains `useSearchParams: () => mockParams` (same module-level holder pattern) so its existing two tests keep passing once the page calls `useSearchParams`.

**T15 — server render ignores cookies**

- Uses `import { renderToString } from "react-dom/server"` (mapped by `jest.config.js` to the root `react-dom`). Set `document.cookie = "rf-buyer-auth=1"` first. The output string must contain `Buyer portal sign-in` and `/buyer/login`. Effects do not run in `renderToString`, so an implementation that reads cookies during render is the only way this fails after implementation — which is exactly R8.

## 10. Flake risks

| ----------------------------------------------------------------- | ---------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| cookies leaking between tests                                     | all RTL/unit files     | explicit clear of the three cookie names in `beforeEach`                                                                   |

| Windows Jest glob with `<rootDir>`                                | —                      | the config already uses a relative `testMatch` (L-055); the red-gate command uses path regexes without parentheses         |
| turbo cache replaying a green                                     | final gate             | `npx jest --ci` is invoked directly, never through `turbo` (L-009/L-034)                                                   |
| Playwright JSON reporter clobbering `.campaign/runs/web-e2e.json` | UI verify / final gate | every Playwright invocation carries `--reporter=list`; scratch configs live outside the repo                               |
| a mobile UA in UI verify                                          | UI verify              | desktop UA only                                                                                                            |
| the local API on `:3000` belongs to another stack                 | UI verify              | flows never submit the form; failed requests to `:3000` are declared baseline noise                                        |

## 11. Regression watch

- **Runs on every push:** T1–T19, T26 via `npm run verify` (turbo `test` → apps/web jest) and the pre-push hook — milliseconds each.
- **Runs post-deploy:** T20–T25, T27, T28 in the branch/master E2E job (`deployment_status` trigger) alongside the existing CC-11…CC-15.
- **How this regresses unnoticed in six months, and the check that catches it:** someone re-inlines the operator prefix list in the middleware and it drifts from the sanitizer → T7/T9 keep the shared list honest and CC-16/17 catch a middleware that stops using it; someone adds an already-authenticated redirect to `/login` → a loop that CC-16's `maxRedirects: 0` cannot see, but flow 1 in UI verify (a real navigation) and the existing CC-15 journey would.
- A green replay from a build cache is not evidence a test ran — the gates invoke jest directly and read its own counts.
