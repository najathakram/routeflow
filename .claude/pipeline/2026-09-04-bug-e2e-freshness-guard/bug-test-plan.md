# Bug test plan — E2E freshness guard (REG-E2EGUARD-403)

All in `apps/api/src/common/ci-freshness-guard-script.spec.ts` (root-script spec convention; see `ci-audit-script.spec.ts` for the fake-command pattern). A fixture fake `gh` lives in the spec's scratch dir: a node script whose behaviour is chosen by env `FAKE_GH_MODE`: `err403` (prints `{"message":"Resource not accessible by integration","documentation_url":"https://docs.github.com/rest","status":"403"}` to STDOUT, `gh: Resource not accessible by integration (HTTP 403)` to STDERR, exits 1), `match` (prints `[{"sha":"<DEPLOY_SHA>","id":1}]`, exit 0), `newer` (prints `[{"sha":"ffff…","id":2}]`), `empty` (prints `[]`), `garbage` (prints `not json`, exit 0), `hang` (sleeps 5 s). For the YAML-driven case the fake is exposed as an executable named `gh` on PATH (a bash shim `gh` without extension calling `node fake-gh.mjs "$@"` — Git Bash on Windows, bash on CI).

T1 · REG-E2EGUARD-403 · YAML-driven (the bug's own wrong value). Setup: parse `.github/workflows/ci.yml` (js-yaml), find job `e2e` → step with id `freshness` → its `run:` text; execute it with `bash -euo pipefail -c <run>` under env `DEPLOY_SHA=abc123`, `GITHUB_REPOSITORY=acme/repo`, `GITHUB_OUTPUT=<tmp file>`, `PATH=<dir with the gh shim>:$PATH`, `FAKE_GH_MODE=err403`, `GH_TOKEN=x`. Expected TODAY (wrong): the output file contains `run=false` (the error body became `$latest`). Expected AFTER: `run=true` AND stdout contains `::warning::` AND `Could not read the newest deployment`. This test fails today on its own value (`run=false`), not on a missing file.
T2 · REG-E2EGUARD-403 · script-direct: `node scripts/ci-freshness-guard.mjs` with `CI_FRESHNESS_GH_CMD` = the fake in `err403` → exit 0, `run=true`, `::warning::`. Today: the script does not exist → the spec asserts `run=true` in the output file, which is absent → fails on its own value (no `run=` line). Also assert the process exit is 0 and the 403 body is quoted (first 200 chars) in the warning.
T3 (pins, no REG token, outside the red gate): `match` → `run=true` + `::notice::` matches; `newer` → `run=false` + `::notice::Skipping` (a genuine superseded deployment still skips — this pins the guard's purpose); `empty` → `run=true` + `no deployments recorded`; `garbage` → `run=true` + `::warning::`; `hang` with `CI_FRESHNESS_GH_TIMEOUT_MS=500` → `run=true` + `::warning::` within 3 s; missing `DEPLOY_SHA` → exit 0, `run=true`, `::warning::`.
T4 (pin): static read of `ci.yml`: job `e2e` has `permissions.contents == "read"` and `permissions.deployments == "read"`; job `verify` has NO `permissions` key; the `freshness` step's `run` invokes `scripts/ci-freshness-guard.mjs`; the seven `steps.freshness.outputs.run == 'true'` consumers are unchanged (count == 7). The two invariance assertions (`verify` has no `permissions`; consumer count == 7) are **folded into** the two red T4 tests rather than standing alone — alone they pass on the untouched tree and could never be red.
