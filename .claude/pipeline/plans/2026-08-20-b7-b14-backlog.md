## Objective

Fix ten confirmed defects found in a 2026-08-17 deep dive and re-verified against
master on 2026-08-20. Two are cross-tenant/authorization security holes, two
silently mis-bill money, three are read-then-write races that mint duplicate
financial documents, and three are UX/correctness defects that cause double
sends or wasted network calls. Each has an exact anchor and a known-correct fix
that mirrors an existing, already-correct sibling in this same repo — the goal is
to make the broken path identical to its working sibling, not to invent a new
approach.

B5 from the original list is **already fixed on master** (landed in #352) and is
deliberately excluded. Do not "re-fix" it.

## Constraints & conventions

- **Stack**: npm + Turbo monorepo. NestJS 11 + Prisma 7 API (`apps/api`), Next.js
  14 App Router web (`apps/web`), Expo/RN mobile (`apps/mobile`).
- **Tests**: Jest for api + mobile (`*.spec.ts`, `__tests__/*.test.ts`).
  NestJS `Test.createTestingModule`; mock at the module boundary. There is a
  shared prisma mock at `apps/api/src/testing/prisma-mock.ts` — use
  `createMockPrisma()`. **No snapshot tests. No Vitest.**
- **Prettier**: semicolons, double quotes, `printWidth` 100, trailing commas.
- **Money discipline**: all money math goes through `roundMoney` from
  `apps/api/src/common/pricing.ts`. Costs are 4dp via `costDecimal`
  (`apps/api/src/inventory/costing.ts`). Never introduce a second rounding path.
- **Tenancy**: `this.prisma.forTenant()` injects `where.tenantId` on reads and
  `data.tenantId` on writes. **Nested creates bypass that injection** and land
  `tenantId = null`, which `forTenant()` then filters out — so child rows must be
  written directly, not nested, and readers of possibly-null-tenant child rows
  must query through the parent.
- **What must NOT change**: existing public API shapes and route paths; the
  behaviour of any path not named in a work package; the legacy one-shot
  `POST /inventory/stock-count/commit` contract.
- **Every fix must add or extend a spec that FAILS without the fix.** A fix
  without a regression test is not done.

### WP1 — B7: price adjustment silently drops regulated/excise tax (HIGH, money)

- **files:** `apps/api/src/invoices/invoices.service.ts`, `apps/api/src/invoices/invoices.service.spec.ts`
- **brief:** In the inner `applyToInvoice` helper (function starts ~line 4230,
  helper ~4258-4305), the recompute at ~4282-4291 computes
  `subtotal`, `taxAmount = roundMoney(Σ li.subtotal * (li.taxRate ?? 0))`, and
  `total = subtotal - discount + shippingFee + taxAmount`. It never reads
  `li.categoryTaxAmount` and never calls `this.foldCategoryTax`. **Every other
  recompute site in this file does** (see `createSplitInvoices` ~721, and
  ~946, ~1198, ~1892, `update()` ~2313-2321, ~3108). `update()` at ~2313-2321 is
  the structurally closest correct sibling — match its shape. The shortfall then
  propagates to the linked order because line ~4304 calls
  `recomputeOrderFromInvoices(inv.orderId)`.
- **exact code:** inside `applyToInvoice`, replace the tax computation with:
  ```ts
  const regularTax = roundMoney(
    updatedItems.reduce((s, li) => s + Number(li.subtotal) * Number(li.taxRate ?? 0), 0),
  );
  // Category (regulated/excise) tax is persisted per line and is NOT part of
  // taxRate. Every other recompute in this file folds it in; omitting it here
  // silently under-bills excise and propagates the shortfall to the linked
  // order via recomputeOrderFromInvoices below. No exemption re-derivation is
  // needed: categoryTaxAmount is already zeroed at creation for exempt
  // customers, and a price adjustment never changes exemption.
  const categoryTaxTotal = roundMoney(
    updatedItems.reduce((s, li) => s + Number(li.categoryTaxAmount ?? 0), 0),
  );
  const taxAmount = roundMoney(regularTax + categoryTaxTotal);
  ```
  Keep the existing `total = subtotal - discount + shippingFee + taxAmount` line
  as-is (it now picks up the corrected `taxAmount`).
- **spec:** add a case to `invoices.service.spec.ts` proving a price adjustment on
  an invoice whose line carries `categoryTaxAmount > 0` keeps that amount in the
  recomputed `taxAmount`/`total`. It must fail without the fix.

### WP2 — B11: PO receive clobbers STANDARD-costed products' cost (HIGH, money)

- **files:** `apps/api/src/inventory/inventory.service.ts`, `apps/api/src/inventory/inventory.service.spec.ts`
- **brief:** `receivePurchaseOrder` (~672-741) computes
  `newAvgCost = nextAverageCost(...)` at ~704-706 with **no `costingMethod`
  guard**, stamps `avgCostAfter: newAvgCost` on the movement at ~715, and writes
  `averageCost: newAvgCost` to the product at ~735-739. A STANDARD-costed
  product is valued from its operator-set cost, so this destroys it. Two sibling
  writers already guard correctly and must be mirrored exactly:
  `recordPurchase` (~164-243) uses
  `const updatesAverage = product.costingMethod !== CostingMethod.STANDARD;`
  (~185) then `if (updatesAverage) costUpdate.averageCost = newAvgCost;`
  (~219-224); and `apps/api/src/vendor-bills/vendor-bills.service.ts` (~686-734)
  has the identical guard at ~694 with the comment "STANDARD keeps its
  operator-set cost — mirrors recordPurchase; bill receive used to clobber it
  (G7)". **This exact bug class was already fixed once for the vendor-bill path
  and never for PO receive.**
- **exact code:** after the product is fetched (~703):
  ```ts
  // STANDARD products are valued from their operator-set cost, so a receipt
  // must not move averageCost. Mirrors recordPurchase and the vendor-bill
  // receive path, which already guard this (the bill path was fixed for this
  // exact bug class; PO receive was missed).
  const updatesAverage = prod ? prod.costingMethod !== CostingMethod.STANDARD : true;
  ```
  Then stamp the movement with `avgCostAfter: updatesAverage ? newAvgCost : (prod?.averageCost ?? null)`
  and spread the product update as
  `data: { currentStock: stockAfter, ...(updatesAverage ? { averageCost: newAvgCost } : {}) }`.
- **spec:** add a case proving receiving a PO for a `costingMethod: "STANDARD"`
  product leaves `averageCost` untouched (and one proving an AVCO product still
  updates, so the guard isn't over-broad).

### WP3 — B8: estimate re-accept / convert race mints duplicate invoices (MED)

- **files:** `apps/api/src/estimates/estimates.service.ts`, `apps/api/src/estimates/estimates.service.spec.ts` (NEW FILE — none exists today)
- **brief:** `accept()` (~191-193) is a bare
  `estimate.update({ where: { id }, data: { status: "ACCEPTED" } })` with no
  status check at all — it will flip a **CONVERTED** estimate back to ACCEPTED,
  after which `convertToInvoice()` will mint a second invoice for the same
  estimate. `convertToInvoice()` (~205-251) reads the estimate (~206-208), checks
  `est.status !== "ACCEPTED"` (~210-211), then ~40 lines later creates the
  invoice (~222-248) and only at the very end writes `status: "CONVERTED"`
  (~249) — all as separate unguarded calls. There is **no transaction anywhere in
  this file**. Both `POST :id/accept` and `POST :id/convert-to-invoice` (plus a
  `:id/convert` alias) are exposed to any OPERATOR, so a double-click reproduces
  it.
- **exact code:**
  ```ts
  // Atomic claim: a CONVERTED estimate must never be re-accepted, or the
  // convert path below will mint a second invoice for the same estimate.
  async accept(id: string) {
    const { count } = await this.prisma
      .forTenant()
      .estimate.updateMany({ where: { id, status: { not: "CONVERTED" } }, data: { status: "ACCEPTED" } });
    if (count === 0) {
      throw new BadRequestException("Converted estimates cannot be re-accepted");
    }
    return this.prisma.forTenant().estimate.findUniqueOrThrow({ where: { id } });
  }
  ```
  For `convertToInvoice`, wrap the whole body in `this.prisma.tenantTransaction(async (tx) => { ... })`
  and **claim the status FIRST**, before any invoice work, swapping every
  `this.prisma.forTenant()` inside for `tx`:
  ```ts
  // Claim before creating anything: two concurrent converts both passed the
  // old read-then-check and both minted an invoice. Claiming inside the tx
  // means a later failure rolls the claim back too.
  const claimed = await tx.estimate.updateMany({
    where: { id, status: "ACCEPTED" },
    data: { status: "CONVERTED" },
  });
  if (claimed.count === 0) {
    throw new BadRequestException("Only ACCEPTED estimates can be converted");
  }
  ```
  This mirrors the existing in-repo idiom at
  `apps/api/src/billing/billing.service.ts:100-107` (`transitionAndEmit`).
- **spec:** new spec file. Cover: re-accepting a CONVERTED estimate throws and
  does not change status; a second concurrent convert (simulate by making the
  claim `updateMany` return `count: 0`) throws and creates no invoice.

### WP4 — B9: recurring-invoice generation can mint duplicates (MED)

- **files:** `apps/api/src/recurring-invoices/recurring-invoices.service.ts`, `apps/api/src/recurring-invoices/recurring-invoices.service.spec.ts`
- **brief:** `generateInvoiceFromTemplate(ri)` (~169-216) creates the invoice
  (~170-184), links it (~203-206), and only **last** advances `nextRunAt`
  (~208-213) — three statements, no transaction. `runNow(id)` (~158-165) and the
  daily cron `generateDueRecurringInvoices` (~220-259) can both hand the same
  stale `ri.nextRunAt` to it concurrently, and both pass through to invoice
  creation before either advances. There is no DB-level uniqueness tying
  `Invoice.recurringInvoiceId` to a period, so nothing backstops it.
- **exact code:** move the `nextRunAt` computation to the TOP of the function
  (it depends only on `ri.frequency/dayOfWeek/dayOfMonth/ri.nextRunAt`, not on the
  invoice) and convert the advance into an atomic CAS claim performed **before**
  invoice creation:
  ```ts
  // Claim the cycle BEFORE creating anything. Previously the advance was the
  // last statement, so a crash after create — or runNow racing the cron —
  // minted a duplicate invoice for the same cycle. Claiming first turns that
  // failure mode into "one missed cycle", recoverable via runNow.
  const nextRunAt = this.calcNextRunAt(ri.frequency, ri.dayOfWeek, ri.dayOfMonth, ri.nextRunAt);
  const claimed = await this.prisma.forTenant().recurringInvoice.updateMany({
    where: { id: ri.id, nextRunAt: ri.nextRunAt },
    data: { nextRunAt, lastRunAt: new Date() },
  });
  if (claimed.count === 0) {
    this.logger.warn(`Recurring invoice ${ri.id}: cycle already claimed, skipping`);
    return null;
  }
  ```
  Then proceed to `invoicesService.create(...)` and the link update, and **delete
  the old end-of-function advance block**. Callers must tolerate a `null` return.
- **spec:** prove that when the CAS claim matches nothing (`count: 0`) no invoice
  is created and the function returns null; and that the happy path still creates
  exactly one invoice and advances `nextRunAt` exactly once.

### WP6 — B12 (SECURITY, HIGH): uploads serve leaks files across tenants

- **files:** `apps/api/src/uploads/uploads.controller.ts`, `apps/api/src/uploads/uploads-tenant-scope.security.spec.ts`
- **brief:** `serveFile()` (~81-95) tenant-checks **only** the `tenants/`,
  `regulated-filings/` and `tobacco-reports/` key prefixes:
  ```ts
  const tenantMatch = key.match(/^(?:tenants|regulated-filings|tobacco-reports)\/([^/]+)\//);
  ```
  `UploadsAccessGuard` only requires a valid signed URL **or any valid JWT of any
  role/tenant** — it performs no ownership check, leaving it entirely to that
  regex. So any authenticated user in any tenant who knows or obtains a key under
  an unguarded prefix gets the file streamed back. The unguarded prefixes are
  **more than originally reported** — the complete set of writers is:
  | prefix | id segment | owning model | guarded today |
  |---|---|---|---|
  | `tenants/<tenantId>/…` | tenantId | — | YES |
  | `regulated-filings/<tenantId>/…` | tenantId | — | YES |
  | `tobacco-reports/<tenantId>/…` | tenantId | — | YES |
  | `products/<productId>/…` | productId | `Product` | **NO** |
  | `customers/<customerId>/tax-documents/…` | customerId | `Customer` | **NO** |
  | `customers/<customerId>/documents/…` | customerId | `Customer` | **NO** |
  | `payments/<paymentGroupId or paymentId>/…` | either | `InvoicePayment` | **NO** |
  | `expenses/<expenseId>/…` | expenseId | `Expense` | **NO** |
  | `invoice-scans/<scanId>/…` | scanId | `InvoiceScan` | **NO** |
  | `invoice-pdfs/<invoiceId>.pdf` | invoiceId | `Invoice` | **NO** |
  | `statement-pdfs/<customerId>/…` | customerId | `Customer` | **NO** |
  Eight of eleven prefixes do not embed a tenantId, so extending the regex cannot
  fix them — each needs a lookup of the owning row's `tenantId`. Every one of
  those models already has a `tenantId String?` column, so **no migration**.
- **exact code:** keep the existing signed-URL exemption and the existing
  regex branch untouched, then add an id-based branch. Use the **unscoped**
  `PrismaService` (this endpoint sits outside the tenant-scoped request path) with
  select-only queries:
  ```ts
  // Eight of the eleven storage prefixes embed only the OWNING ROW's id, not a
  // tenantId, so the regex above cannot gate them — resolve the owner's tenant
  // and compare. Without this, any authenticated caller in any tenant who knows
  // a key streams the file (a former employee, a low-priv account, or any IDOR
  // that leaks an id). SUPER_ADMIN stays exempt, as does a signed URL, which is
  // itself a per-key capability.
  const OWNER_LOOKUPS: Record<string, (id: string) => Promise<{ tenantId: string | null } | null>> =
    {
      products: (id) =>
        this.prisma.product.findUnique({ where: { id }, select: { tenantId: true } }),
      customers: (id) =>
        this.prisma.customer.findUnique({ where: { id }, select: { tenantId: true } }),
      expenses: (id) =>
        this.prisma.expense.findUnique({ where: { id }, select: { tenantId: true } }),
      "invoice-scans": (id) =>
        this.prisma.invoiceScan.findUnique({ where: { id }, select: { tenantId: true } }),
      "invoice-pdfs": (id) =>
        this.prisma.invoice.findUnique({ where: { id }, select: { tenantId: true } }),
      "statement-pdfs": (id) =>
        this.prisma.customer.findUnique({ where: { id }, select: { tenantId: true } }),
      payments: async (id) =>
        await this.prisma.invoicePayment.findFirst({
          where: { OR: [{ id }, { paymentGroupId: id }] },
          select: { tenantId: true },
        }),
    };
  ```
  Then, still inside the `if (!reqAny.signedUrlAuthorized)` block and after the
  existing regex check, resolve `const [prefix, idSegment] = key.split("/")`,
  strip any file extension from `idSegment` for the flat `invoice-pdfs/<id>.pdf`
  case, and if `OWNER_LOOKUPS[prefix]` exists and the caller is not SUPER_ADMIN:
  look up the owner; **throw `ForbiddenException("Cross-tenant file access denied")`
  when the row is missing OR its `tenantId` differs from `caller?.tenantId`, and
  also when the caller has no `tenantId`.** Fail closed — a missing row must deny,
  never allow.
- **⚠️ The existing spec currently ASSERTS THE LEAK.**
  `uploads-tenant-scope.security.spec.ts:102-105` has a passing test titled
  _"does not tenant-gate non-scoped prefixes (products/)"_ asserting **200** for a
  cross-tenant `products/` fetch. **Invert that test** — it must now assert 403 —
  and rename it accordingly. Add coverage for at least `products/`, `customers/`,
  `invoice-pdfs/` and `payments/`, plus: same-tenant still 200, SUPER_ADMIN still
  200, signed URL still 200, and a missing owner row denies.

## Acceptance criteria

1. **B7**: a price adjustment on an invoice with `categoryTaxAmount > 0` on a line
   preserves that amount in the recomputed `taxAmount` and `total`; a spec fails
   without the change.
2. **B11**: receiving a PO for a `STANDARD`-costed product leaves
   `Product.averageCost` unchanged and does not stamp a new `avgCostAfter`; an
   AVCO product still updates normally. Both covered by specs.
3. **B8**: `accept()` on a CONVERTED estimate throws and leaves status CONVERTED;
   `convertToInvoice` claims the status atomically inside a transaction before
   creating the invoice, and a losing concurrent caller throws without creating
   one.
4. **B9**: `generateInvoiceFromTemplate` claims the cycle via a CAS on
   `nextRunAt` **before** creating the invoice, returns null when the claim fails,
   and no longer advances `nextRunAt` at the end.
5. **B10**: return creation validates cumulative returned qty and writes the
   return inside a single transaction, re-validating inside it.
6. **B12**: a cross-tenant authenticated request for a key under `products/`,
   `customers/`, `payments/`, `expenses/`, `invoice-scans/`, `invoice-pdfs/` or
   `statement-pdfs/` returns **403**; same-tenant returns 200; SUPER_ADMIN returns
   200; a valid signed URL still returns 200; a missing owner row returns 403.
   The pre-existing test asserting a 200 leak for `products/` is inverted, not
   deleted.
7. **B13**: a DRIVER-supplied below-list `unitPrice` on `POST /orders` is ignored
   — the line bills at list price with `priceType: STANDARD`; an OPERATOR override
   still yields `DISCOUNTED`; the CUSTOMER tier/promo ladder is unchanged.
8. **B4**: mobile offers "Record payment" only for SENT/VIEWED/PARTIAL/OVERDUE.
9. **B6**: the mobile Send and Send-reminder tiles are disabled while their
   mutation is pending, and their handlers early-return if already pending.
10. **B14**: all four listed web pages pass `debouncedSearch` (not `search`) into
    their list query while the input stays bound to `search`.
11. Every API fix ships with a spec that fails without it. No snapshot tests, no
    new dependencies, no changes to public route paths or response shapes.

## Risks & rollback

- **B12 is the highest-risk change**: over-tightening breaks legitimate file
  access. Mitigations: signed URLs stay exempt (the signature is a per-key
  capability); SUPER_ADMIN stays exempt; the three already-guarded prefixes keep
  their existing regex path untouched. Watch in review for any prefix used by a
  **buyer-portal** reader — buyer tokens are a different auth strategy, so confirm
  whether buyer-facing PDF/statement fetches go through this endpoint with a JWT
  or a signed URL, and do not break them. If a buyer path does use a plain token,
  extend the check rather than dropping it.
- **B13** must not disturb buyer pricing — buyers never send prices, so the change
  is limited to ignoring a staff-only field for non-staff.
- **B9** trades a duplicate-invoice failure mode for a possible missed cycle; that
  is the correct trade (a missed cycle is recoverable via `runNow`, a duplicate
  invoice is not), but note it in the fix comment.
- **Rollback**: every package is an independent commit-sized change; revert the
  single file (plus its spec) to undo one fix without touching the others.
