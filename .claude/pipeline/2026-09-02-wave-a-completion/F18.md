### B73 — confirmed · L-029 L-031 L-026 L-034 L-036

**Root cause.** commission-engine.service.ts runSync (184-309) reads the invoice with a plain include of commissionAccruals.adjustments (185-200) and no lock; syncAccrualRow computes priorAdjTotal from that snapshot (332-335), decides drift (343-357) and inserts the CommissionAdjustment unconditionally (416-426). CommissionAdjustment has only @@index, no @@unique (schema.prisma model at 4348: indexes on agentId/accrualId/tenantId), so a duplicate cannot fail at the database. Two syncs of the same invoice that overlap — the :30 cron (commission-reconciliation.service.ts:29, 58 → syncInvoiceCommissionSafe with no db → its own tenantTransaction, which passes no isolationLevel (prisma.service.ts:36-51) = READ COMMITTED) and any READ COMMITTED hook caller (bookkeeping.service.ts:227, customers.service.ts:1230, and the invoices.service.ts sites outside the two Serializable blocks — e.g. 1457, 1879, 3879, 3995, 4117, 4484, 4668, 4839, 4907, 4952, 5114, 5202, 5341, 5645; orders.service.ts:5480) — each read zero prior adjustments, each compute the same negative drift, each append a CLAWBACK: the agent is deducted twice and the ledger invariant drift = payable − claimed − Σadj goes to −|drift|. Callers already inside Serializable transactions (invoices.service.ts:3448/3654 under 3451/3657; credit-notes 256/566/603/1059 blocks) are protected by SSI today (both syncs also UPDATE the accrual row at 402-413, which SSI aborts), so the exposure is exactly the READ COMMITTED set above plus the cron — which is the pair the register names. CORRECTION to the register's implied symmetry with the accrual path: the create path's pre-insert re-check (477-481) does NOT by itself prevent a double insert under READ COMMITTED (both syncs can pass the re-check before either commits) — that path is actually saved by the @@unique([tenantId, invoiceId, agentId]) backstop at 4343, with the re-check only avoiding a P2002 inside the caller's tx (its own comment at 470-476 says so). Copying the re-check to the adjustment path would therefore NOT fix B73; a lock (or a unique key) is required.

**Fix.** ONE shared guard at the single seam every path funnels through — runSync — so the cron, all 22 hook sites, syncOrderInvoices and recomputeCommissionRange are covered without touching a caller. At the top of runSync(invoiceId, db), BEFORE the invoice findUnique at 185: `await db.$executeRaw\`SELECT id FROM "CommissionAccrual" WHERE "invoiceId" = ${invoiceId} AND "tenantId" = ${tenantId} FOR UPDATE\``(tenantId via this.prisma.getTenantId(), already read at 53 — pass it in or re-read; raw SQL bypasses the tenant proxy so scope it by hand). This is the idiom already used at returns.service.ts:84, invoices.service.ts:4407/4624, routes.service.ts:867. Semantics: a concurrent sync blocks on this statement until the first commits; under READ COMMITTED every later statement takes a fresh snapshot, so the post-lock include sees the committed CLAWBACK, drift computes to ~0, and no second adjustment is appended. Under a Serializable caller the FOR UPDATE on a concurrently-modified row raises the same 40001 the update at 402 already would — no new failure class. The tenant tx proxy passes`$`-prefixed members through bound (prisma.service.ts:79-86) and forTenant()'s $extends client also supports $executeRaw, so `db.$executeRaw`works for every db shape runSync receives. No invoice-row lock (alternative considered:`SELECT id FROM "Invoice" … FOR UPDATE` would also serialize the create-path race, but that race is already backstopped by @@unique and locking Invoice from the hourly cron for every invoice updated in the last 25h briefly blocks live invoice writes — not worth it). Lock order stays Invoice → CommissionAccrual everywhere (hooks already hold Invoice; the cron never locks Invoice; commission-statements.service.ts only updates accruals at 208/276/309 and never writes Invoice), so no inversion. Update the class docblock (20-36) to state the lock is what makes 'append exactly one' true under concurrency.
