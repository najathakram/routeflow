### B53 — confirmed · L-029 L-031 L-026 L-030 L-008

**Root cause.** processRefund (C:/ClaudeCode/routeflow/apps/api/src/returns/returns.service.ts:331-339) prices the refund as Σ qty × (orderLine.subtotal / orderLine.qty) from Order.lineItems, never from the invoice that was actually issued; a delivered-basis reconcile (invoices.service.ts:1373-1378 bills Number(li.deliveredQty)) rewrites only the INVOICE, so a customer billed for 6 of 10 is refunded 10/10 on a full return. Second, :318 selects `invoices: { select: { id } }` with no status filter and :369-372 passes invoiceId only when exactly one row exists — so any order with 2+ Invoice rows (split orders, or one VOID + one live) mints the credit note with invoiceId undefined, and credit-notes.service.ts:107-138 gates its entire cumulative cap on `if (dto.invoiceId)`. The register's third claim — cap create() at deliveredQty and receive() restocks goods that never shipped — is WRONG at master: deliveredQty is written by only one of the three DELIVERED writers (routes.service.ts:2346 completeWithPayment; completeStop :2107-2125 and orders.service.ts:2366 do not), so deliveredQty is 0 for most delivered orders, and routes.service.ts has zero `currentStock` writers, so refused goods (decremented at order creation) are restocked by NOTHING except a Return. The ordered-qty cap at :109-115 is the correct physical ceiling.

**Fix.** (1) Add a private helper `billedBasisFor(returnItems, order)` in returns.service.ts that, given the order's NON-VOID invoices with `items: { select: { productId, qty, subtotal } }`, computes per returned product billedQty = Σ invoiceItem.qty, perUnitBilled = Σ subtotal / billedQty, and refund = min(item.qty, billedQty) × perUnitBilled, rounded with roundMoney; fall back to the existing order-line math ONLY when the order has zero Invoice rows of any status (legacy). (2) Change the processRefund select (:315-321) and findOne select (:454-459) to `invoices: { where: { status: { not: 'VOID' } }, select: { id, total, items: {...} } }`. (3) processRefund and findOne.refundEstimate both call the helper (single source, L-030). (4) invoiceId to creditNotes.create = the single non-VOID invoice id; when 2+ remain, compute headroom = Σ non-VOID totals − Σ(creditNote.aggregate amount where invoiceId in ids AND status != VOID) inside processRefund and throw BadRequestException when refundAmount > headroom + 0.001, instead of skipping the cap. Do NOT change the create() cap and do NOT touch receive() restock quantities. Do NOT edit routes.service.ts (F11's layer, L-008) — hand F11 the finding that completeStop never writes deliveredQty.
