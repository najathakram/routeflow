# Spec — Registry views: waves, directed dependencies, ledger-mirrored status, wave roll-up

**Owner ask (2026-09-02):** "Add dependency-based review and waves of fixes, and the status of each bug fix, to the bug registry. Every time a bug is fixed its status should update from the bug's current status; waves should update based on their bugs' status."

**Builds on** PR #597's in-repo registry (`.claude/campaign/bugs/B###.md` records, `scripts/campaign/bugs.mjs`, Stop-hook Gate 4 `sync`, `render` → `local-assets/docs/routeflow-bug-registry.html`). It extends that model; it does not add a second registry, and it never treats `routeflow-bug-register.html` (the old hand-edited view) as a source.

## Requirements

- **R1 (P0) Wave field.** Every bug and every batch resolves to exactly one roadmap wave (A/B/C) via `waves.json`. Verification: `waves.json` validator — every `status/F##.jsonl` shard appears in exactly one wave; unknown batch names fail; unit test on fixtures.
- **R2 (P0) Directed dependencies.** Batch→batch edges parsed from the fix cards: `Requires X (…)` ⇒ X before this batch; `Must land before Y, Z` ⇒ this batch before Y and Z; lane chains `A -> B -> C` ⇒ consecutive edges; tokens match `F\d\d[ab]?`. Both semantic and positional edges count as "before"; the existing file-overlap graph (#597 `buildGraph`) stays as a SEPARATE class, "not in parallel", and is shown as such — never merged into "before". A bug inherits its batch's edges. Verification: parser unit tests on the literal card lines quoted above plus a card with no line (⇒ no edges, reported, never an error); `deps` prints the parsed edges with their source card and line so a human can audit them against the cards.
- **R3 (P0) Ledger-mirrored status, and derived batch state.** A bug's status chip is its ledger state verbatim (`queued` / `proven` / `proven-pending-deploy` / `done` / `already-fixed`) — never Open/Fixed. A batch is **landed** when none of its rows is `queued` or `proven` (i.e. its code is on master; `proven-pending-deploy` counts as landed). Batch state = `queued` (all rows queued) · `in progress` (some row proven, none landed, or a board claim/open PR exists) · `landed, discharging` (landed but some row not terminal) · `done` (all rows done/already-fixed). `blocked by` = required batches not landed; `unblocked` = not landed and nothing blocking. Verification: pure functions with fixture ledgers covering every state transition, including a batch with zero rows (F00/F01 — landed by definition, never blocking).
- **R4 (P0) Wave roll-up.** Per wave: batches with state, rows terminal/total and %, open Criticals (severity from records), batches landed/total, and the ordered list of batches unblocked now. Verification: fixture arithmetic; the current real numbers must reproduce the ledger count (70/194 terminal at master 70321d0a).
- **R5 (P0) Rendered.** `render` emits, in the registry HTML: (a) a **Waves** section at the top — one card per wave with a progress bar, the batch chips coloured by state, blocked-by annotations; (b) a **Dependency review** table — batch · wave · state · requires · blocked by (open) · unblocks · not-in-parallel-with; (c) per-bug rows and articles carry `wave · batch · state · PR`. The same roll-up is written as markdown to `.claude/campaign/WAVES.md` (committed, reviewable, regenerated). Verification: `render` self-test asserts the sections and the per-row chips exist and that WAVES.md's counts equal the JSON roll-up.
- **R6 (P0) Automatic.** `sync` (already run every turn by Gate 4) also runs `render` and writes `WAVES.md`; idempotent; on any error it reports and never blocks the turn. Verification: run `sync` twice on an unchanged tree ⇒ byte-identical outputs; flip one ledger row in a fixture ⇒ the row's chip, its batch state and its wave bar change in one run.
- **R7 (P1) Execution slots are not waves.** The existing greedy-colouring `computeWaves` (parallel-slot planning under the 4-agent cap) is renamed in all user-facing output to "parallel slots" so it cannot be confused with roadmap waves. Verification: grep of rendered output for the word "wave" finds only roadmap waves.

## Non-goals

Editing `routeflow-bug-register.html`; changing ledger semantics or `campaign-check`; GitHub Issues sync; per-bug (not batch) dependency authoring; scheduling automation (`next` may READ the blocked-by set later — separate change).

## Deploy-day / rollback

Docs and scripts only — no app code, no schema, no CI change. Rollback = revert the PR; `waves.json` and `WAVES.md` are deletable without effect on the ledger.

## Lessons carried

L-041 (a job green is not evidence — the roll-up must read ledger states, not PR colours); L-051 (repo-global stashes — the builder works in its own worktree); the register-debt rule in HANDOFF ("every batch updates the register in its own close-out") becomes automatic under R6.
