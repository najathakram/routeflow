## What "removed" means (applies to every test)

`CustomersService.deleteCustomer`'s soft branch (`customers.service.ts` ~2039-2049) writes only
`Customer.deletedAt = now` and `User.status = INACTIVE`. `restoreCustomer` (~1965-1984) writes `deletedAt = null`. So
"removed" is `customer.deletedAt !== null` and "restored" is `customer.deletedAt === null`. The fix is stateless (a filter
or check on `deletedAt`), so each restore pin is the same fixture with `deletedAt` set back to `null`.

## Why the fakes honor `where` (L-081)

Three of the five fixes are `where`-clause filters (both crons, the guard, getSellers). A mock that injects a fixed result
(`findMany.mockResolvedValue([...])`) cannot see a where-only fix, so the REG test would stay red after a correct fix (L-081).
Each new test therefore stubs the one Prisma read with `mockImplementation` over a two-row fixture and applies the `where`
the service actually sends, through the small strict evaluator `matchesWhere` (exact code in build-plan.md, "Shared test
code"). It throws on filter shapes it does not model, so a differently shaped fix fails loudly rather than passing
vacuously. `InvoicesService.create()` is fixed by a row check (`customer.deletedAt` on the row it just read), so its
tests use a plain `mockResolvedValue` fixture.

## Harness notes (the engine's harness-integrity check verifies these)

- **order-templates.** A NEW file, not an append. `generateDailyOrders` is wrapped by `@LeaderCron`, which calls
  `withAdvisoryLock` from `apps/api/src/common/db-locks.ts`. The new file needs the same pass-through
  `jest.mock("../common/db-locks", ...)` that `recurring-invoices.service.spec.ts` lines 1-12 carry. Putting that hoisted
  mock into the existing `order-templates.service.spec.ts` would change the module under every existing test there, which
  is why a new file is used. `createOrderFromTemplate` is private; spy it with
  `jest.spyOn(service as any, "createOrderFromTemplate")`.
- **recurring-invoices.** Append one new top-level `describe` at end of file. The file-level db-locks mock already covers it.
  The existing cron test ("attempts the second due template after the first one throws") injects `findMany` with
  `mockResolvedValue`, so the new where clause does not affect it. No change needed.
- **invoices.** Append one nested `describe` as the LAST child of `describe("InvoicesService")`, immediately before that
  describe's closing `});`, which sits directly above the `/** Invoice issue/due dates are CALENDAR dates` comment
  (~line 8150). It inherits the top-level `beforeEach` (~line 109), as the RF-1 describe (~758) does; RF-1 has no
  `beforeEach` of its own. No existing `customer.findUnique` fixture sets `deletedAt`, so the row check
  (`customer.deletedAt` truthy → 404) leaves every existing create test green. No mock change needed.
- **buyer-connect.** Append one new top-level `describe` at end of file, copying the providers of
  `describe("BuyerService.getSellers — non-ACTIVE customer redaction (security)")` (~line 510). The three existing
  getSellers tests inject `findMany` with `mockResolvedValue`, so the new where clause does not affect them. No change needed.
- **guard.** No spec exists today. The only other reference, `orders.scan-hardening.spec.ts` REG-B200 (~1556), is a
  guard-metadata check and is unaffected. `buyer.controller.spec.ts` does not exercise `canActivate`.
- All new and edited specs read nothing outside `apps/api` (L-062), and the new `*.spec.ts` names are not in the jest
  `testPathIgnorePatterns`, so the main lane collects them.
