## 1. Core capability

> HQ can put a known customer on a "Lite" plan — orders, invoices, payments, inventory, customers
> and nothing else — for $99/mo via Stripe, without the plan ever being visible or selectable by
> anyone else, and without a single existing tenant noticing anything changed.

## 6. Overlap and scope fence

- **Overlaps:** `SELF_SERVICE_ADDON_SKUS` filter (CP §3) → **extend** the same pattern for plans;
  `DARK_PLAN_FLAGS` (CP §5) → **extend** with one plan-keyed predicate (R3a), never a second dark
  mechanism; `addons.ts` `{enabled,resolved}` hooks (CP §7) → **mirror** for plan flags;
  `LockedPage` → **reuse**. Nothing here creates a second way to gate, price, or hide.
- **In scope:** everything in §9.
- **Out of scope / non-goals:** manual invoicing (Q1 default = Stripe; `INVITE_ONLY_PLAN_SELF_SERVE_CHECKOUT` is the one-line lever); any self-serve path _to_ Lite; gating the buyer-facing portal controllers (seller-context guard — follow-up **F-1**); flipping any dark flag to enforced for existing plans (owner's blast-radius call — **F-2**); a plan-flag registry (owner's precondition for removing `DARK_PLAN_FLAGS` — **F-3**); mobile billing UI; changing STARTER's price or features; `expo-print`/flavor (L1, shipped).
- **Do-not-introduce check:** no new dependency, HTTP client, or test runner. One new Prisma migration (additive). One new shared types file.

## 8. Rollback

- **Kill switches (no deploy):** per LITE tenant — admin plan-change to STARTER restores every surface (R8.2). Payment CTA — `INVITE_ONLY_PLAN_SELF_SERVE_CHECKOUT = false` (one constant, redeploy). `PLAN_FLAG_ENFORCEMENT` is untouched and still governs existing plans only.
- **Code rollback:** safe. The migration is **additive-only** (c4's hard rule): a rollback **never** removes the enum value — it stops creating/selling LITE tenants. A published v12 left behind is inert for existing plans (superset) and for LITE (no tenants, or tenants moved off it first). Reverting the guard change only _widens_ what a LITE tenant can reach (dark-allow) — never denies an existing tenant, never mis-charges.
- **Data rollback:** nothing to reverse. Any LITE tenant created before a revert is moved to STARTER by admin plan-change (their `Tenant.plan` value stays valid because the enum value stays).
- **Blast radius:** worst case = a guard bug denying an existing tenant (caught by R7.1 + R3a.4 + the compose boot gate, L-113) or a wrong LITE price (R1.7 pins 9900 cents). No cross-tenant path exists (all reads keyed by the JWT tenantId). No message is sent to any customer.
- **Detection:** PLAN_GATE 403s / `addon gate denied` warns for any non-LITE tenant after deploy = red; `npm run post-deploy-check` on `test`; `audit-tenant-entitlements.mjs` against prod.

### R3a — RULING: plan-keyed enforcement (the CP §5 gap)

**Decision: option (a), generalized to a named set.** `DARK_PLAN_FLAGS`/`PLAN_FLAG_ENFORCEMENT` stay exactly what they are — one global courtesy per flag key — and a second, orthogonal, **plan-keyed** predicate says which plans never receive that courtesy: `ALWAYS_ENFORCED_PLAN_KEYS = new Set<PlanKey>(["LITE"])`. One predicate, two consumers (`PlanFlagGuard` and `AddonGuard`'s every-key-dark path), one line to add a third tier.

_Rationale (for a hostile reviewer):_ Option (c) is dead on arrival — "backfill an allow-grant onto every existing plan's row" cannot reach tenants pinned to superseded versions v1–v11 without either editing published versions (forbidden by R1) or re-pinning every live tenant (a per-tenant write on production data, the largest possible blast radius, for a launch whose only new tenants are LITE). Option (b) — a per-flag × per-plan exemption matrix — buys generality nobody has asked for: every new flag in this lane is enforced for LITE and dark for everyone else, and a future third tier would want exactly the same all-or-nothing treatment; the matrix is more surface, more tests, and a second place where "is this flag enforced" is answered. Option (a) keeps the existing single-boolean semantics for every existing plan byte-for-byte (the courtesy is skipped only when the resolved plan is in the set, and resolution failure keeps the courtesy — so existing plans cannot lose a surface even with the DB down), needs one exported set, one `EntitlementsService` method, and two guard insertions, and satisfies L-128 (a named set, not an inline `=== "LITE"`) and L-130 (the same predicate feeds the client's `flags`). It survives the planned removal of `DARK_PLAN_FLAGS` (once nothing is dark the set is inert) and slots into a future plan-flag registry as a per-plan column.
