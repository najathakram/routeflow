## 1. Strategy for this change

This is a new-surface feature (an invite-only `LITE` plan) layered on an existing plan/flag
entitlement system: one new Prisma enum value, one new plan-keyed enforcement predicate
(`ALWAYS_ENFORCED_PLAN_KEYS`, ruling R3a) alongside the existing global `DARK_PLAN_FLAGS`
courtesy, five newly-enforced feature flags wired onto five controllers, a v12 catalog publish,
and client-side (web + mobile) nav hiding / locked-panel rendering. What proves it works is: (1)
exhaustive finite-domain matrix tests over {plan key} × {flag key} × {enforcement on/off} proving
the guard decision is unchanged for every existing plan and newly enforced for LITE only (R7.1,
R3a.4); (2) a superset pin proving v12 changes nothing for the four existing plans (R7.2); and (3)
one Playwright pass driving the six ux-spec flows end-to-end against a real invite-only tenant.

| Level       | Used here? | Why / why not                                                                                                                                                                                                                                                        |
| ----------- | ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| unit        | yes        | pure entitlement/predicate logic (`allowsFlag`, `planRank`, guard bodies with mocked collaborators) — the bulk of T1–T22                                                                                                                                             |
| property    | no         | the input domain is finite and small (5 plan keys × 21 flag keys × 2 env states) — hand-rolled exhaustive matrices (T4, T5, T7, T11) give full coverage without a generator; no `fast-check` use in this lane, matching this repo's existing table-driven convention |
| contract    | no         | the wire-shape pin (`SubscriptionView`'s 16 keys, R7.6) is folded into the unit-level `subscription.service.spec.ts` (T11) — no separate contract-test framework in this repo                                                                                        |
| integration | yes        | T15 (`*.db.spec.ts` against the compose Postgres) — the publisher's idempotency and transaction behavior cannot be proven with a mocked Prisma client                                                                                                                |
| e2e         | yes        | T23 — the six ux-spec flows (nav hiding, deep-link lock panel, choose-plan exclusion, Settings→Billing CTA, marketing pricing) are the one user journey worth the Playwright cost                                                                                    |
| manual      | yes        | T24 — the full compose boot + `local:validate`/`local:validate:features`/`local:drift`/`local:test:db` chain is HOST-gated and cannot run inside the engine                                                                                                          |

**Rule applied:** prefer the lowest level that can fail for the right reason.

**Deliberately NOT tested, and why:**

- `R8.3` (code-revert leaves LITE tenants with more access, never less) — reasoning pinned by
  T5's R3a.4 negative (dark never denies, even with the DB down); not independently re-tested.
- `R8.4` (PR body + code map record the deploy order) — review, not a test.
- `R3b.1`'s docs line (`docs/design-package/project/specs/pricing-plans.md:62` gains the five
  keys, per ruling C9) — review, not a test.
- `R2.4`'s admin-form half (`admin/tenants/new/page.tsx` offering LITE, `page.test.tsx` pinning
  the set) — owned by the Backoffice T12–T15 lane per the ruling's §4 scope boundary; this lane
  proves only the service half (T10) and the shared `PLAN_KEYS` mirror (T1/T2) the form reads.
- `R4.7` — **cut** by correction C1/C7 (`A5` refuted: `grep entitlements|EntitlementClaims
apps/web/lib` is empty). No test exists for it because the requirement itself is out.

**Risk driving depth** (blast radius decides depth, not code volume): money is touched (Stripe
checkout at $99/mo, R1.7) and authorization/tenancy is touched (five new plan-flag gates, one new
plan-keyed enforcement tier). Per spec.md §8: worst case is a guard bug denying an _existing_
tenant a feature it's entitled to, or a wrong LITE price — both are caught by R7.1 + R3a.4 + the
compose boot gate (L-113). No cross-tenant read path exists (every guard keys off
`req.user.tenantId`); no message is sent to any customer. Six of the thirteen work packages are
Baseline-classified HIGH risk (WP1, WP2, WP3a, WP3b, WP3c, WP4, and WP5a/b/c via authz
auto-classification).

**Characterization tests needed first?** Yes, for WP4's extraction of v11's `DefinitionSeed`/
`AddonSeed` types and `*_FLAGS`/`DEFINITIONS`/`ADDON_SEEDS` arrays into
`plan-catalog-v11.definitions.ts` (a "non-behavioral edit" the spec explicitly allows, R7.2). T14's
superset pin (`v12.featureFlags ⊇ v11.featureFlags`, price/caps/`isCustom` equal, `V12_ADDON_SEEDS
deep-equals V11_ADDON_SEEDS`) is that characterization test — it must hold before the LITE row is
layered on top, proving the extraction itself changed nothing.

## 11. Regression watch

- **Runs on every push:** T1–T22 (the full `verifyCommands.perRound`/`final` Jest invocations in
  build-plan.md) — cheap (mocked unit/rtl/mobile tests, no network or real DB).
- **Runs nightly or on demand:** T15 (`local:test:db`, needs the compose Postgres), T23
  (`local:e2e`/post-deploy Playwright), T24 (the full compose chain) — all HOST-gated or
  DB-backed, off the push path by the ruling's own `verifyCommands.final` exclusion list.
- **How this regresses unnoticed in six months, and the check that catches it:** a future flag or
  plan added without updating `FLAG_KEYS`/`DARK_PLAN_FLAGS` mirrors would silently stay
  unenforced for LITE — caught by T2's set-equal parity pin and T4's `DARK_PLAN_FLAGS` deep-equal
  pin failing the moment the sets diverge. A future guard refactor that reorders the
  `tenantId`/dark/resolve checks would silently reopen the DB-outage-denies-existing-tenants
  class of bug — caught by T5's R3a.4 negative and mutation probe #1. Production-only detection:
  `PLAN_GATE 403`s or `addon gate denied` warns for any **non-LITE** tenant after deploy is a red
  signal (spec.md §8 Detection); `apps/api/scripts/audit-tenant-entitlements.mjs` run against
  prod is the standing check.
- A green replay from a build cache is not evidence a test ran. Trust only the runner's own
  report of work actually performed — this is why `verifyCommands.final` names explicit
  per-workspace `jest` invocations rather than a turbo cache replay (ruling §5).
