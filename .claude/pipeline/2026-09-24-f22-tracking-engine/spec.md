**Vocabulary used below**

- **Registers** — `.claude/roadmap/features.jsonl`, `deferred.jsonl`, `releases.jsonl`.
- **registersHash** — sha256 hex over the raw bytes of the three register files concatenated in
  that fixed order. A content hash, never an mtime (discovery §8 prior art, L-179).
- **Render dir** — `local-assets/roadmap/` (gitignored, default `--out` of `render.mjs`), holding
  `roadmap.html`, `tracker.html`, `deferred.html`, plus the new `lag.json`, `.rendered.json`,
  `.published.json`, `plane-pages-probe.json`.
- **Render stamp** — `.rendered.json` = `{ renderedAt, day, registersHash, headSha }`;
  **publish stamp** — `.published.json` = `{ publishedAt, day, registersHash, target, refs }`.
  `day` is the UTC calendar date `YYYY-MM-DD` the LAG was computed against.
- **Stale (render)** — any of the three HTML files or the render stamp missing, OR stamp
  `registersHash` ≠ current registersHash, OR stamp `day` ≠ today (UTC). **Stale (publish)** —
  same rule over the publish stamp. The day rule exists because the LAG section is date-relative.
- **Trailer** — a line `Feature: F-##`, `Bug: B###` or `Defers: D-##` in a commit body
  (`.claude/roadmap/README.md` convention); a **PR number** is the `(#N)` suffix of a squash
  commit subject (present on 96/96 commits since the convention landed — discovery A4).
- **Publish target** — Plane Pages if the probe (R10) confirmed them; otherwise the fallback: one
  pinned ROAD work item per rendered page, updated in place.

## 1. Core capability, in one sentence (G2·Q1)

> Anyone on any machine can trust that the roadmap registers are consistent, see which PRs git
> says belong to each feature, and read an hourly-fresh published copy of the roadmap, tracker
> and deferred views — and every new session is told, in one screen, whether that copy is stale
> and the one command that fixes it.

## 4. States, per surface (G2·Q4)

### Surface: SessionStart status block (terminal) — `node scripts/roadmap/render.mjs --status`

Exact text shape. Four lines maximum in the normal case, a fifth only for INVALID. Every line
starts with `Roadmap`. Hard cap 768 bytes (truncate the LAG list with `+N more`). Exit code 0 in
every state below. Zero network, zero `gh`, zero child processes other than `git rev-parse HEAD`
(for `headSha`, tolerated to fail).

```
Roadmap: 22 features (10 in-progress · 10 planned · 2 at-risk · 0 done) · 26 deferred (26 open) · next: R1.1 ships 2026-09-25
Roadmap LAG: 9 features past target (F-01 -2d, F-02 -2d, F-03 -2d, F-04 -2d, F-05 -2d, F-06 -2d, F-07 -1d, F-08 -2d, +1 more) · 0 deferred past revisitBy
Roadmap render: STALE — rendered 2026-09-22T09:41Z (day 2026-09-22, registers a1b2c3d) but registers are now e4f5a6b → node scripts/roadmap/render.mjs
Roadmap publish: never published on this machine → npm run roadmap:publish   (or, when a key is absent: "publish: no PLANE_API_KEY on this machine — the PC's hourly job publishes")
```

(The counts and LAG ids above are today's real values, 2026-09-24, computed from the registers
with the renderer's own rule — `targetDate < today && status !== "done"`; the stamp hashes are
illustrative. Note the rule is strict `<`: F-22 itself joins the list tomorrow.)

### Surface: from-git report (terminal) — `node scripts/roadmap/from-git.mjs [--since <ref>] [--apply]`

Default `--since` = the commit that introduced `.claude/roadmap/README.md` (`c73b0897`), read
from `git log --diff-filter=A`; `..HEAD`. Output sections, in order: **Proposed prs[] appends**
(per feature id: numbers not yet in that row's `prs[]`, each with sha + subject), **Unknown ids**
(trailer names an id no register has), **Bug/Defers trailers seen** (informational; nothing to
write), **Coverage** (`N of M commits since <sha> carry a roadmap trailer (X%)`; the untagged
subjects listed, capped at 20 with `+N more`). Exit 0 always except an unusable git (exit 2).

| State                    | Required behavior                                                                                                                                          | Req ID |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| Empty                    | No trailers in range: the Proposed and Unknown sections say `none`; Coverage prints `0 of M (0%)` — this is the expected output today and is not an error  | R6     |
| Loading                  | n/a — one `git log` call, < 1 s for 100 commits                                                                                                            | R6     |
| Partial                  | A commit whose trailer id is unknown is listed under Unknown and never proposed; the rest proceed                                                          | R6     |
| Error                    | Not a git repo / bad `--since` ref → one line on stderr, exit 2; registers invalid → report still runs (it is read-only) but `--apply` refuses             | R6, R7 |
| Offline / request failed | n/a — git only, never `gh`, never network                                                                                                                  | R9     |
| Unauthorized             | n/a                                                                                                                                                        | —      |
| Too much data            | Untagged list capped at 20 + `+N more`; proposals are never capped (they are the point)                                                                    | R6     |

## 7. Deploy day (G2·Q7)

There is no production deploy: "deploy" is the code PR merging to `master` and every machine
pulling it. Railway skips it (docs/scripts outside `watchPatterns`) — but `.github/` and
`scripts/` count as code for `SKIP_VERIFY` purposes, so the PR runs the full `verify`.

- **Existing users on deploy day:** every session on every machine, on its next start after a
  pull, prints the new `Roadmap` block under the triage brief. First run on each machine says
  `render: never rendered on this machine` (no stamp yet) and `publish: never published on this
machine` (or `no PLANE_API_KEY …`) until someone renders / the PC's job runs. That is the
  intended, honest first state — not a bug.
- **Existing data:** the registers need no change to satisfy the new rules (`--validate` already
  passes on them today: `roadmap validate: OK — 22 features, 26 deferred, 4 releases`). Existing
  renders in `local-assets/roadmap/` on any machine have no stamp → reported STALE once, fixed by
  one render. The 1/96 trailer baseline means the first from-git report proposes little; expected.
- **Backfill:** none for the registers. Optional, human-run, once: `from-git.mjs --since c73b0897`
  and read the proposals into the next bookkeeping PR (R7's `--apply` is the one-command form).
- **Migration (G4·Q5):** none. No schema, no DB.
- **The one manual step:** the owner installs the hourly task on the PC (R15) — machine-local,
  after the PR merges, following the one-line instruction in `.claude/roadmap/README.md`. Until
  then the publish is manual (`npm run roadmap:publish` from any machine with the key).
- **The F-22 row itself (finding F-1):** the bookkeeping PR that closes this pipeline should set
  `release: "R2"`, `targetDate: "2026-10-01"` (or `2026-09-28` if the owner keeps it in R1.1) —
  see discovery §11 Q5. Not part of the code PR.

## 8. Rollback (G2·Q9)

- **Kill switch:** for the session block — remove the second `hooks.SessionStart` element (one
  JSON edit, no deploy). For the hourly job — delete the machine-local task on the PC
  (`mcp__scheduled-tasks__delete_scheduled_task` or remove `~/.claude/scheduled-tasks/routeflow-roadmap-hourly/`).
  For the verify gate — none needed; it only fails on inconsistent registers, which is the point.
- **Code rollback:** safe to revert the PR. Nothing in app code depends on it. A revert leaves
  the second hook element gone (it is in the same PR) and the `roadmap:*` npm scripts gone.
- **Data rollback:** (1) gitignored files in `local-assets/roadmap/` — harmless, delete or ignore;
  (2) the Plane page(s) / ROAD work item(s) created by publish — they stay; delete by hand in
  Plane if wanted (no tool deletes — harness convention); their creation is in
  `.plane-writes.jsonl`; (3) `prs[]` appends from `--apply` are ordinary register edits in a
  bookkeeping PR — revert that PR; (4) the machine-local scheduled task is NOT reverted by git —
  the runbook line in the README says so explicitly.
- **Blast radius (G4·Q1):** worst realistic cases, all LOW: (a) a rendered page carrying a live
  client identifier reaching Plane — blocked by `scanForbidden` before any write (R12), and the
  registers are client-free by policy; (b) the hourly job burning the write budget — publish is ≤ 3
  writes/run and `plane-sync` keeps its own `syncMaxWrites` knob; (c) the SessionStart block
  blocking or slowing every session — exit 0 always, no network, < 300 ms (R3, R5, R9); (d) a wrong
  `--apply` — working tree only, diff printed, `git checkout` undoes it (R7). No money, tenancy, or
  customer message can be touched by any path here.
- **Detection:** (a) the status block on the next session start (`publish: STALE … last published
<when>`); (b) `runs.jsonl` `roadmap-publish` lines with `exit ≠ 0`; (c) `npm run verify` red on
  the validate gate; (d) `plane:check` drift (unchanged, F-09's).
