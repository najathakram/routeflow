## Non-goals

Reshaping `updateOrderItems`; threading a transaction through it; Redis locks; cron leader lock
(PR-3); changing replica count; any schema change; touching other worktrees.

## Deploy day

No data change. A merge that has to wait > 20 s (another merge for the same customer in flight)
now returns 409 `MERGE_IN_PROGRESS` instead of racing; the web/mobile merge flows already handle
409 (`MERGE_CHOICE_REQUIRED` uses the same status). Pool of up to 8 extra connections per API
process (`max: 8`, `connectionTimeoutMillis: 5_000` so exhaustion surfaces as a 503 within 5 s,
not an unbounded wait).

## Rollback

Revert the PR: the in-process Map returns; single-replica behaviour is unchanged either way.

## Lesson L-053 (draft)

- **Symptom:** a money-critical read-fold-write was serialized by an in-process promise chain that
  a second replica cannot see; the deferral note said scaling would corrupt lines silently.
- **Root cause:** the lock lived where the code was, not where the data is.
- **Lesson:** a lock that guards a read-then-absolute-write must live in the system of record
  (`pg_advisory_lock` on a pinned connection, or inside the write's transaction) — never in process
  memory; and it is proven by two sessions on a real database (`*.db.spec.ts`), never by a mocked
  service.
- **Guard:** `db-locks.db.spec.ts`; the retitled controller spec.
