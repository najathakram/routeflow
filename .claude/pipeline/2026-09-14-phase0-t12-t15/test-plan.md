## 1. Strategy for this change

New service (`TenantMirrorService`) with a real cross-tenant write invariant, one new config
wrapper, one new idempotent bootstrap script, and three small web edits to existing screens. Money
display is a seam-class risk (L-119), not a math risk (the server-side computation is already
correct and shared — the residual risk is entirely in how the web renders it).

| Level       | Used? | Why                                                                                                                                      |
| ----------- | ----- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| unit        | yes   | `TenantMirrorService`, `PlatformConfigService`, `PlatformAdminService` wiring, `getStats()` — all mockable at the Prisma-client boundary |
| property    | no    | No arbitrary-input money math here — `MrrService`'s own math was already proven in T9; this phase only wires it                          |
| contract    | no    | No new wire shape shared across multiple clients                                                                                         |
| integration | yes   | DB-lane spec for `TenantMirrorService` (real Postgres, real Prisma) — the only way to prove the schema-shape claims (L-113)              |
| e2e         | yes   | Two flows: create-tenant-with-GROWTH-plan-shows-Growth-label, and dashboard/billing MRR parity                                           |
| manual      | yes   | T15's exit-criteria walkthrough (mirror count query) — genuinely a one-time human confirmation, not automatable within this phase        |

**Deliberately NOT tested:** `MrrService.computeOverview()`'s own math (already covered by T9's
existing spec, unchanged here); Prisma's own upsert/transaction semantics (framework behavior).

**Risk driving depth:** a wrong `tenantId` on any write in `TenantMirrorService` is a cross-tenant
data leak inside the house tenant — the DB-lane spec (T13-9) and the explicit `data.tenantId`
assertions in every unit test are the direct response. The dashboard MRR card is the platform
admin's headline money figure and the exact seam class L-119 names.

**Characterization tests needed first?** No — this is new capability, not a refactor.

### 2.1 Expanded — T13-9 (DB-lane)

- **Given:** real Postgres via the compose stack; a fresh `qa-hq-<rand>` tenant (class `INTERNAL`)
  used only as the mocked `getHouseTenantId()` return; a fresh `qa-mirror-<rand>` tenant (class
  `PRODUCTION`) with one `TENANT_ADMIN` user `username: "qa_owner"`.
- **When:** `upsert(mirrorTenant.id)` called twice; then the tenant is renamed to `"Renamed"`;
  `upsert` called a third time.
- **Then:** after call 1 and 2, exactly one `Customer` row exists with
  `representsTenantId = mirrorTenant.id`, `tenantId = hqTenant.id`, `contactName = "qa_owner"`;
  its backing `User` has `tenantId = hqTenant.id`, `email = mirror+<mirrorTenant.id>@placeholder.local`,
  `role = "CUSTOMER"`; exactly one `ContactPerson` exists on it (if R14 is kept — see brief note
  in build-plan WP-B). After call 3: `businessName = "Renamed"`, `contactName` still `"qa_owner"`.
- **Oracle:** the schema's own required/unique/FK constraints plus the deterministic identity
  scheme — an incorrect field name throws at the database layer, not a silent pass.
- **Fails today because:** the file (and the service it tests) does not exist.
