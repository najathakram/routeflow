=== SINGLE BEST
Build the gate registry — a checked-in table of every @RequireAddon / @RequirePlanFlag key with its routes, added date, state (dark|enforced), grant path and backfill decision — pinned by a reflection test in the style already running at apps/api/src/routes/dispatch-addon-gate.spec.ts, and have AddonGuard read that registry's state column as its kill switch. One artifact does three jobs: it is the merge gate no author can skip (an unregistered key fails `npm run verify`), it is the switch that makes deploy day harmless because a new row defaults to dark, and it is the list a blast-radius audit iterates before any flip. The runner-up is the plain observe-first copy that five of six lenses converged on — a DARK_ADDON_KEYS Set plus ADDON_ENFORCEMENT lifted from plan-flag.guard.ts — and it loses on exactly the property that failed here: the Set is opt-in, so the same author who wrote in the commit note that the gate would 403 every ungranted tenant is the person who must remember to add "ocr" to it, and PlanFlagGuard's own Set already shows the decay (seven hardcoded keys, a removal date living as a comment, nothing asserting either). The registry inverts that default, so forgetting produces a red test instead of an outage, and the same test can assert a dark row has not outlived its date — closing the reverse failure no lens raised. It also costs barely more, because the reflection pattern is written, green, and already in the verify chain, and it generalizes to the ~20 existing call sites and the other three ocr routes that this deploy also broke, which a per-incident Set never would. Pair it with the denial log and the ScanInvoiceModal message fix; those are the detection half, and the registry is the half that makes the next gate incapable of shipping the way this one did.

=== LATEST
For this class of problem — a new authorization gate silently revoking an in-use capability — there is essentially no 2025-2026 invention; the load-bearing practices are old and the new labels are packaging. The genuine substrate is Parallel Change / expand-contract (Danilo Sato on martinfowler.com, 2014) applied to authz, dark launching (Facebook, ~2009), and OWASP's Logging Cheat Sheet rule that access-control failures are an always-log event (current revision, 2025); OPA Gatekeeper's enforcementAction dryrun/warn (warn since v3.4, 2021) is the most mature productized form of shadow enforcement and is exactly what a dark AddonGuard would be. Two things are legitimately newer and relevant: RFC 9457 Problem Details (July 2023, obsoleting RFC 7807) is the current wire standard a coded 403 body should conform to, and OpenTelemetry's HTTP semantic conventions (stable since the v1.23 semconv line) make http.route a stable dimension for per-route counters — with the honest caveat that the OTel spec does NOT set error.type for a 4xx server response, so a 403 is not an error under a standard SLI and burn-rate alerting cannot see this incident at all. OpenFeature (CNCF incubating since Dec 2023, SDKs GA through 2024-2025) is the only development that changes a build-vs-buy calculus, and RouteFlow should decline it: an env var plus a registry column covers this, and the repo's DO-NOT-introduce discipline is worth more than vendor neutrality here. "Progressive delivery", "guarded releases" (LaunchDarkly, announced Nov 2024, GA at Galaxy 2025) and "entitlements platforms" (Stigg, Schematic, 2024-2026) are renames of deploy≠release plus a metrics pipeline Railway does not give this project, so treating them as the state of the art would import cost without importing the control.
