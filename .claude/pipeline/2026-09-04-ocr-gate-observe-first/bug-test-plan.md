## Harness notes (verified by the engine's harness-integrity check)

- `addon.guard.spec.ts` builds the guard as `new AddonGuard(reflector, addonService)` with
  `reflector = { getAllAndOverride: jest.fn() }` (lines ~17-25). The fix therefore adds the Logger as a
  **property initializer** and imports the registry as a plain module — the constructor signature does not
  change and the nine existing cases need no edit. Import `Logger` and `ForbiddenException` from
  `@nestjs/common` in the spec for T2/T3.
- The registry module is real, not mocked: `ocr` is dark and `tobacco_dealer` is enforced in the shipped
  registry, which is exactly what T1/T3 assert. Do not `jest.mock` it.
- `apps/api/src/routes/dispatch-addon-gate.spec.ts` reads `REQUIRE_ADDON_KEY` metadata from specific
  controllers; the fix does not change the decorator or the controllers, so it stays green.
- `vendor-bills.security.spec.ts` / `vendor-bills.service.spec.ts` do not exercise `AddonGuard`; untouched.
- P1 uses `fs.readdirSync(dir, { recursive: true })` (Node ≥ 20.1; CI pins Node 20) relative to
  `path.resolve(__dirname, "..")` (= `apps/api/src`). Windows separators are fine — filter on
  `.endsWith(".controller.ts")`.
- OP-17b in `02-operator.spec.ts` already mocks `**/vendor-bills/scan-invoice` with `page.route`; T5 copies
  its setup and replaces the fulfil body with the 403. Keep the title prefix `OP-17g` so the operator
  project's grep conventions hold, and the token `REG-OCR-2` for `-g`.
