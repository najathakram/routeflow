# Web landing 2026-11-12, windows 32 and 34 (master `5fc866853e` after window 32, `c05d8e25f5` after window 34)

Paths under `apps/web/`; `app/(dashboard)/` is shortened to `D/`. Api parts are in `api/landing-2026-11-12-w32-w34.md`. Facts below were read on master `c05d8e25f5`. #4294, #4274 and #4296 touch no web file.

## Window 32

- **#4292 the buyer drags their own order's lines (W-1187 PR-2c, head `bad5be8da9`).** `app/buyer/portal/[seller]/orders/[id]/page.tsx` mounts `useOrderLineOrder({ orderId, updatedAt: order?.updatedAt, lineItems, enabled: editWindowOpen && !editMode, buyer: true, labelOf })`, wraps the lines in `SortableLines`, shows `SortLinesButton`, and draws each row with `LineRow` and `LineHandle`. New `components/MovableTableRow.tsx` (`LineRow`: a sortable `<tr>` when `movable`, a plain one otherwise; `LineHandle`: the 24 px handle at the cell's left edge, `[&>button]:ml-0` cancels the staff layout's `max-md:-ml-3`, which clipped half the button inside the table's overflow box below 768 px). New `lib/api/buyer.ts` `useBuyerReorderOrderLines` (`PUT /buyer/orders/:id/line-order`, `meta: { localErrorToast: true }`). `lib/use-order-line-order.ts` gains the `buyer` flag (the mutation and the `["buyer", "order", id]` query key follow it) and a 403 path in `fail`: a non-busy 403 rolls the list back, refetches and shows one warning toast with no Undo, `readOnlyRefusalCopy()` for a READ_ONLY refusal and `LINE_ORDER_CLOSED` otherwise; the 409 busy and stale paths are unchanged. New `components/LinesRearrangedNote.tsx` ("Customer rearranged the lines", with the time today and the date as well on another day) rendered by `D/orders/[id]/_components/OrderLineItemsTable.tsx` and `OrderLineItemCards.tsx`, which take `linesRearranged`; `D/orders/[id]/page.tsx` passes `order.linesRearranged`; `lib/api/orders.ts` `Order` gains `linesRearranged?`. Tests: `app/buyer/portal/[seller]/orders/[id]/page.line-order.test.tsx`, `D/orders/[id]/_components/OrderLineItemsTable.line-order.test.tsx`.

## Window 34

- **#4297 "Sign in as admin" works when the browser also holds a buyer session (B1304, head `6d5724810b`).** `lib/impersonation.ts` `setImpersonation` now calls `setOpPresenceCookie()` (the same helper a normal operator sign-in uses, `lib/presence-cookies.ts`, no second copy of the cookie name or options), so the middleware guard `resolveOperatorPathGuard` (`lib/portal-routing.ts`) no longer reads the browser as buyer-only and bounces `/dashboard` to `/login`. `doExitImpersonation` clears the cookie unless the browser holds operator tokens of its own (`OP_KEYS.accessToken` or `OP_KEYS.refreshToken`). New `lib/impersonation.presence.test.ts` (5 tests, the real guard and the real helpers, no mocks); `D/layout.register.test.tsx` and `D/layout.register.screen.test.tsx` add the two presence helpers to their `presence-cookies` mock. Known gap, left open: the automatic exits in `lib/api-client.ts` (the expired-token branch and the 401 branch) call `clearImpersonation()` but not `clearOpPresenceCookie()`, so the cookie waits for the `AuthProvider` clear on the next full load (`lib/auth-context.tsx`).
