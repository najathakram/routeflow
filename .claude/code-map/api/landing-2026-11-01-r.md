## #4063 `eed3681b9a` the first question on a new account, owner alerts (W-1095 W1/W2)

Rule: a public sign-up starts with one open question ("How do orders reach your customers?"); the account's own admin answers it through the SAME planner and apply sequence the back office uses, but it only FILLS BLANKS. No existing tenant holds the marker row, so none ever sees the card.

- `billing/first-run-marker.ts` (new): `FIRST_RUN_KEY = "signup.firstRun"` (a `SystemConfig` row, `tenantId_key`), `type FirstRunMarker = "pending" | "answered" | "closed"`, `readFirstRun(db, tenantId)` (unknown value reads as `null`), `createPendingFirstRun(db, tenantId)`, `closeFirstRun(db, tenantId, to: "answered" | "closed"): Promise<boolean>` (`updateMany` where value is `pending`: update-only, never creates a row, never moves a closed one).
- `tenants/tenants.service.ts`: `register()` calls `createPendingFirstRun(tx, tenant.id)` inside its transaction, right after `tenantConfig.create`, so the marker exists exactly when the tenant does. Constructor gains a last `@Optional() ownerAlerts?: OwnerAlertService`; when the verification mail reports not delivered, or the send throws, it calls `ownerAlerts?.verificationMailFailed(...)` (fire and forget, `.catch(() => undefined)`).
- `auth/auth.service.ts`: constructor gains a last `@Optional() ownerAlerts?`; `verifyEmailAndLogin` calls `ownerAlerts.trialVerified(tenantId, email)` after the activation and before `login`, never awaited into the sign-in (only when the user has a `tenantId`).
- `settings-fulfilment/first-run.service.ts` (new, `FirstRunService`, provided by `SettingsFulfilmentModule`, which now imports `EmailModule`):
  - `parseFirstRunAnswer(body: unknown): Required<FirstRunAnswer>`: only keys `delivery`, `shipping`, `counter`, each a boolean; anything else 400 `FIRST_RUN_INVALID` (door payments and opens-as can never come through the tenant path); nothing ticked 400 `FIRST_RUN_EMPTY`.
  - `status(user): Promise<FirstRunStatus>`: tenant from the request context only (`requireTenantContext`; a token for another tenant is 403 `FULFILMENT_TENANT_MISMATCH`). No marker, or a `READ_ONLY` tenant, returns `state: null` with the three ticks false (no card). Otherwise `state` = marker, `workspaceId` = tenant slug, ticks from `BusinessProfileService.capabilities`, `hasOrder` = any order exists.
  - `answer(body, user): Promise<FirstRunResult>`: inside `BusinessProfileService.withConfirmLock` it re-reads the marker (not `pending` = 409 `FIRST_RUN_CLOSED`), drops the 30 s mode cache (`featureConfig.forgetCachedModes`), plans with `planFirstRun`. If `!fillsBlanks(plan)` it writes only the marker `closed`, audits `FIRST_RUN_KEPT` (`meta.answer`) and returns `{ outcome: "kept", state: "closed" }`. Otherwise `BusinessProfileApplyService.applyResolvedLocked(...)` with actor `{ id: user.sub, kind: "TENANT_USER", source: "signup.setup" }` and an `ApplyIo` whose `disableAddon` / `createOverride` / `revokeOverride` throw (unreachable under fills-blanks), then `closeFirstRun(..., "answered")` LAST (an apply that stops halfway leaves the marker open, so the same answer finishes it) and returns `{ outcome: "applied", state: "answered" }`. After the lock is released, `kept` calls `ownerAlerts.keptSetup(tenantId)`.
- `settings-fulfilment/settings-fulfilment.controller.ts`: constructor gains `FirstRunService`. `GET /settings/fulfilment/first-run` (`firstRunStatus`, `@Roles(TENANT_ADMIN)`) and `POST /settings/fulfilment/first-run` (`firstRunAnswer`, 200, `@Roles(TENANT_ADMIN)`, `@NoImpersonation("billing")`, `@Throttle(EDIT_THROTTLE)` = 10 per minute). Neither sits behind the dark `FulfilmentEditGuard`: the gate is the marker.
- `auth/permissions/permission-map.pinned.ts`: `SettingsFulfilmentController.firstRunAnswer` and `.firstRunStatus` = `ADMIN`.

## #4062 `2e55138e39` weekly sign-up funnel on the platform admin dashboard (W3 M1)

- `platform-admin/platform-admin.service.ts`: exports `interface WeeklyFunnelWeek { weekStart (Monday UTC, YYYY-MM-DD); signups; verified; firstOrder; firstRoute; demoBookings }` and `type WeeklyFunnel = { weeks: WeeklyFunnelWeek[] } | { unavailable: true }`; `getStats()` (the `GET /platform-admin/stats` route, no new route) adds `weeklyFunnel` to its response via private `_weeklyFunnelOrUnavailable(now)`, which catches any read failure, logs `Weekly funnel read failed`, and returns `{ unavailable: true }` so the page never fails over it. `_weeklyFunnel(now)` looks back `FUNNEL_WEEKS = 8` weeks (current week included): `signups` = tenants created, `verified` = tenants with a `user.activate` audit row whose `meta.reason` is `email_verify` (counted once, in the week of the first one in the window), `firstOrder` / `firstRoute` = tenants signed up inside the window whose earliest order / route falls that week (cohort-bounded `groupBy` with `having _min createdAt >= windowStart`), `demoBookings` = demo bookings made that week. Every tenant count leaves out non-`PRODUCTION` and soft-deleted tenants. An `answered` column is NOT included (the code says it joins with the marker; the web card says it is not counted yet).
- `onboarding/onboarding-intake.service.ts`: `PRIVACY_VERSION` `"2026-09-17"` to `"2026-10-31"` (the Privacy page now names Umami; Terms version unchanged).
- Tests: `platform-admin/platform-admin.service.spec.ts` (funnel buckets, cohort bounds, filters, unavailable on a failed read), `platform-admin/platform-admin-weekly-funnel.db.spec.ts` (Postgres).
