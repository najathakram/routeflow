## #4208 `f710764668` the office demotion out of DELIVERED refuses a live return (SA-1101 A-5, A-6 Part 1)

The PR and its specs call this bug **B1272**; in the register B1272 is a different row (the super admin billing page at 390px), so this bug is registered as **B1278** (closed here, F64). Spec and comment text keep "B1272".

- **Guard at the edge.** `orders/order-ship-state.ts` `guardDeliveredDemotion(tx, order, to)`: when the order is DELIVERED and `to` is CONFIRMED or PARTIALLY_DELIVERED it calls `lockThenAssertNoLiveReturn(tx, [order.id], DEMOTE_RETURN_MESSAGE)` (Order row lock a return create also takes, then the live-return count). It is the **first statement** of each of the three transaction bodies that write a delivered demotion: the plain -> CONFIRMED write (moved into `prisma.tenantTransaction` only when it is a delivered demotion), the -> PARTIALLY_DELIVERED transaction, and the SHIP-billing marker transaction (`SHIP_STATE_REOPENED`). `409 ORDER_HAS_RETURN` ("This order has a return. To change its delivery status, cancel the return first."); `assertDeliveredDemotionAllowed` (paid walk-in, route stop) still runs first in `changeStatus` and keeps its answers. No line in `orders.service.ts`. Why the edge and not the cancel: a live return on an open order has four double-credit sinks (cancel, a line edit's stock settle, a delete, a customer delete); the invariant is that a live return exists only on a POST_DELIVERY order (DELIVERED, REFUSED). Before the fix a legacy DELIVERED order of 10 with a received return of 4 (stock 94) reopened and then cancelled to stock 104.
- **Census is three callers.** `returns/live-return-guard.ts`: callers are exactly `orders/deliver-again.ts`, `orders/order-ship-state.ts` and `routes/routes.service.ts` `reopenStop`, each call the first statement of its transaction (`returns/live-return-guard.structure.spec.ts` RO-30). A transitions-table walk (`orders/demote-live-return.spec.ts` RO-29) turns any new exit edge from a POST_DELIVERY status red until it is named and guarded.
- **A-6 Part 1: one predicate for "a live return stands on these orders".** `liveReturnWhere(ids)`: status not in `DEAD_RETURN_STATUSES` and `OR [orderId in ids, items.some.sourceOrderId in ids]`. `assertNoLiveReturn` counts through it, so Deliver again, Undo the stop and the demotion move together; no caller changed. ## #4207 `b57b637ef3` the janitor keeps nothing for a tip already on master (dev tooling)

`scripts/janitor.mjs` `hasUnpushedCommits` first asks the existing `isAncestorOrSelf(worktreePath, branch, "origin/master")`: a tip that is `origin/master` or an ancestor of it has nothing unpushed. A train deletes a branch's origin ref after it merges, so every landed worktree used to look unpushed and the whole-tree step never freed it. A squash-landed tip is not an ancestor, so it still needs its upstream or a same-named origin branch; a detached tree and a branch with no origin ref stay unsafe. Runbook step 2 (`docs/runbooks/disk-cleanup-janitor.md`) states the rule. Tests: `scripts/janitor.self-test.mjs` (four new cases), `common/janitor-self-test-script.spec.ts`. Not a tenant feature, no money path.
