## Feature modules (`src/<module>/`)

### `auth/`

- **controller** `auth` — `@Post login|refresh|logout|change-password|set-password|verify-email|request-password-reset|reset-password`, `@Get/@Delete sessions`. Google OAuth: `@Get google`, `@Post google/exchange` (single-use code handoff), `@Get google/:tenantSlug/callback`.
- **service** — `login`, `refresh`, `logout`, `changePassword`, `setPassword` (first password for Google-only accounts; only when `password IS NULL` read fresh from DB — never a JWT claim; revokes all sessions + reissues via shared `mintSessionForUser`), `listSessions`, `requestPasswordReset(email, surface)` (surface `web|mobile` → config `urls.web|mobileWeb` base, default mobile), `resetPassword`, `verifyEmail`; Google `getGoogleAuthUrl`, `exchangeGoogleCode`, `linkGoogleAccount`.
- `hasPassword` (= `!!user.password`) rides the JWT payload + login/refresh `user` responses (rendering hint); authoritative read = `GET /users/me` (`users.service.findById`). Refresh-token default TTL **30d** (`configuration.ts jwt.refreshExpiresIn`, idle cutoff — rotation slides it).
- **`refresh()` rotates the session row IN PLACE (B155, F14 2026-09-02)** — the old rotation
  `deleteMany`'d the presented row and `storeRefreshToken`'d a brand-new one (new `id` + new
  `createdAt` every ~15 min), so the web Active Sessions list showed a session's LAST rotation as
  "Signed in just now" no matter how old the session really was, and revoking a row by an id the
  client had cached 403'd the moment that row rotated out from under it. Now a compare-and-swap
  `updateMany({where: {id: stored.id, tokenHash: stored.tokenHash}, data: {tokenHash, expiresAt,
lastUsedAt, userAgent?, ipAddress?, deviceName?}})` — the update itself IS the invalidation of
  the old token hash; `id`/`createdAt`/`userId`/`tenantId` are never written, so the session's
  identity and true sign-in time survive every rotation. Device columns pass `undefined` (not
  `null`) when `deviceInfo` is absent, so Prisma leaves them untouched rather than clearing them.
  **Race fallback preserved byte-for-byte**: `count === 0` (another concurrent refresh already won
  the CAS) falls back to the OLD delete-then-upsert path via `storeRefreshToken`, so both racing
  refreshes still succeed — only the winner rotates in place. **Inactive-user ordering preserved**:
  the presented token is still consumed (`deleteMany({tokenHash})`) before the 401, now inside the
  `!user || status !== ACTIVE || deletedAt` branch instead of unconditionally up front, or a
  suspended user's row would survive forever in `listSessions`. Web mirror:
  `settings/page.tsx SessionsCard` below. Spec: `auth/auth.service.spec.ts describe("refresh —
in-place rotation (B155)")`.
- **F5-003 refresh realm claim**: refresh tokens now carry `type:"staff"` (all staff sign sites: `auth.service` login/refresh/`mintSessionForUser` + `google-oauth.service.issueUserTokenPair`) / `type:"buyer"` (`buyer-auth.service.issueBuyerTokenPair` + `google-oauth.service.issueBuyerTokenPair`). Each refresh handler rejects a present-but-wrong `type` **before** the per-table hash lookup; a legacy no-`type` token is still allowed (grace). Specs: `auth/auth.service.spec` + `buyer/buyer-auth.service.spec` (realm-discriminator blocks).
- **SEC-4 / F11-002 refresh cookie**: staff `login`/`refresh` ALSO set an httpOnly, Secure, SameSite=Lax `rf_refresh` cookie (`Path=/api/v1/auth`); `refresh` reads the cookie first, falls back to the body token (mobile unaffected); `logout` clears it. Additive — body token unchanged. No cookie-parser: cookie read by hand from `req.headers.cookie` in `auth.controller`. `RefreshDto.refreshToken` is now optional (cookie-only refresh). Spec: `auth/auth.controller.cookie.spec`. Buyer flow unchanged.
- **`logout` no-op under impersonation (B138, F14 2026-09-02)** — an impersonation token's `sub`
  IS the tenant's TENANT_ADMIN (`platform-admin.service.ts impersonate()`), so the pre-fix
  `authService.logout(user.id)` revoked THAT ADMIN's real refresh tokens on every device the
  moment a super-admin exited an impersonation session — a super-admin action locking out a
  paying customer's own sign-in. `logout` now branches on `user.impersonatedBy` (reaches
  `req.user` via the strategy propagation above): impersonated → clear the cookie only, return
  `{message: "Impersonation session ended"}`, never call `authService.logout`; otherwise unchanged.
  An impersonation session was never issued its own refresh token, so there is nothing to revoke.
  Web mirror: `lib/impersonation.ts exitImpersonation()` below never POSTs `/auth/logout` at all —
  this handler exists for defense-in-depth / any other impersonated caller. Spec:
  `auth/auth.controller.cookie.spec.ts` `describe("AuthController.logout under impersonation")`.
- Buyer mirror (`buyer/buyer-auth.*`): `BuyerAccount.passwordSet` flag (false on Google auto-create) gates `POST /buyer/auth/set-password`; buyer forgot/reset flow (`request-password-reset`/`reset-password`, `BuyerPasswordResetToken` model, links to `${urls.web}/buyer/reset-password`); registration email verification (`verify-email`/`resend-verification`, `BuyerEmailVerificationToken` model — see the buyer/ section entry) feeding `requestSeller`'s auto-connect gate; `GET /buyer/auth/profile` = authoritative `hasPassword`/`googleLinked`/`emailVerified`. Specs: `auth/set-password.spec`, `buyer/buyer-set-password.spec`, `buyer/buyer-password-reset.spec`, `buyer/buyer-email-verification.spec`, `auth/google-oauth.buyer-autocreate.spec`.
- **F12-005 OAuth device-state**: `GET /auth/google?device_state=` threads a device nonce into the OAuth `state` blob (`google-oauth.service` `OAuthState`/`GoogleProfile.deviceState`); mobile deep-link callback echoes it back as `&state=` so the app can reject unsolicited `routeflow://` deep links. Optional/additive server-side.
- **B349 (2026-09-13) OAuth state is signed**: `state` = `base64url(payload).base64url(HMAC-SHA256)`, key HKDF'd from `JWT_SECRET` (`signState`/`verifyStateSignature` in `google-oauth.service.ts`); nonce in Redis now stores `sha256(payload)`, checked on callback (single-use, content-bound) — a rewritten `linkUserId` or any field now fails closed with `state_invalid`. Spec: `auth/google-oauth.service.spec.ts` (REG-B349).
- **Phase 0 T5/T6 (2026-09-14) device info for Google sign-ins**: `extractDeviceInfo(req)` moved from a private `AuthController` method to `auth/device-info.util.ts` (both the credential-login controller and `platform-google-auth.controller.ts` `handleCallback` now import it). `GoogleOAuthService.findOrCreateUser(profile, deviceInfo?)` threads an optional `DeviceInfo` (from `auth.service.ts`) through `handlePlatformAuth`/`handleTenantAuth` → `issueUserTokenPair` → `storeUserRefreshToken`, which now writes `RefreshToken.userAgent`/`ipAddress` on create/update — previously always null for Google-issued sessions ("Unknown device"). `auth.controller.ts`'s tenant-side `googleCallback` still calls `findOrCreateUser(profile)` with no device info (out of this task's file list) — only the platform-admin callback passes it today. Spec: `auth/google-oauth.service.spec.ts` `describe("GoogleOAuthService device info threading (Phase 0 T6)")`.
- **`strategies/jwt.strategy.ts` propagates the driver capability claim (2026-08-28)**: `validate()` now copies `canActAsDriver` from the JWT payload into `req.user` (default false). Before this it was dropped, so `RolesGuard`'s dual-role branch (OPERATOR/TENANT_ADMIN with `canActAsDriver` satisfying `@Roles(DRIVER)`) could never fire — the capability was client-gated only. Flag is minted at login, so a driver-permit change still needs re-login. **`isAdmin` is deliberately NOT propagated** (and must not be added casually): it is not a role-hierarchy input but the gate on `PATCH /users/:id/admin` (`users.controller.ts` — `user.isAdmin || role === TENANT_ADMIN`), which today only TENANT_ADMINs pass because the claim never reaches `req.user`. Surfacing it would let any admin-flagged OPERATOR assign admin rights — a live authorization change needing its own owner decision (and a matching web gate, which derives from role only).
- **`impersonatedBy` propagated to `req.user` (B165/B138, F14 2026-09-02)** — `jwt.strategy.ts
validate()` and `buyer/strategies/buyer-jwt.strategy.ts validate()` both now copy
  `payload.impersonatedBy ?? undefined` onto the returned user object. Before this the claim was
  minted onto impersonation tokens (`platform-admin.service.ts impersonate()` /
  `buyer-admin.service.ts`) but dropped at the strategy boundary, so every downstream reader that
  wanted "who is REALLY typing" (the audit trail, `AuthController.logout`) saw nothing — see the
  `audit/` and this file's `logout` entries below. `isAdmin` is deliberately still NOT propagated
  (2026-08-28 reasoning above still holds — it is an authorization input, `impersonatedBy` is not;
  `RolesGuard` never reads either). Buyer side: propagated for logging/UI only in this batch, no
  buyer-logout change (spec §4.4). Specs: `auth/strategies/jwt.strategy.spec.ts` (new).
- side effects: User/PasswordResetToken/RefreshToken (+Buyer mirrors) writes; reset + password-set notification emails; JWT signing.

### `platform-admin/`

- **controller** `platform-admin` — `@Get stats|stats/growth|audit-logs|audit-logs/facets|billing/overview|tenants/:id/entitlements`, tenants CRUD, `@Patch tenants/:id/{config,status,plan}`, `@Post tenants/:id/{impersonate,extend-trial,activate-subscription,reset-admin-password}`, addons + billing checkout/portal. Mutation endpoints thread `@CurrentUser` adminId; addon enable/disable are async + audit-logged.
- **service** — tenant CRUD, `updateStatus`/`updatePlan` (invalidate TenantStatusGuard cache), `impersonate`, `getGrowthStats`, `getAuditLogs` (enriched: resolves actor `{username,email,isPlatform}` + tenant `{slug,name}` + friendly `actionLabel`), `getAuditLogFacets`, `recordAdminAction(tenantId,adminId,code,meta)`. Every lifecycle mutation + impersonation emits a purpose-built AuditLog row keyed to the TARGET tenant (entityType='tenant', structured code from `audit-actions.constant.ts`) so per-tenant audit filters surface platform actions — the generic AuditInterceptor still writes its `tenantId=null` row too. side effects: Tenant/TenantSubscription/TenantAddon writes; billing (Stripe) calls; AuditLog.
- **`updatePlan` writes the catalog plan + moves the MRR ledger (2026-08-24)** — resolves `planKeyFromEnum(dto.plan)` against the PUBLISHED PlanVersion (404s if unseeded / plan absent) and, in ONE `$transaction`, writes `Tenant.{plan,planVersionId}` + `TenantSubscription.{currentPlan,planKey,planVersionId,basePriceSnapshot}` — the same shape `SubscriptionMutationService.subscribe()` writes — then `EntitlementsService.invalidate(id)`. `basePriceSnapshot` falls back to `priceOverrideMonthly` when the definition has **no** catalog price (custom/Enterprise): writing `planKey` with a null snapshot would enter the tenant in the rollup at $0 base while its add-ons book MRR behind it (`mrr.service.ts:63-66`). Because the write MOVES the snapshot run-rate it also emits `PLAN_CHANGED` with a signed `amountDelta` **inside the same transaction** (`BillingEventService`, now exported by `BillingModule`) — without it `mrr` and `ledgerMrr`/`momDelta` diverge permanently on every admin plan change. Contribution mirrors `BillingService.emitPayingDelta`: base + Σ active add-ons − discount, over MrrService's paying predicate (ACTIVE + `planKey != null`); add-ons/discount are only queried when the tenant CROSSES into/out of the paying set (a manual `activateManualSubscription` tenant leaves `planKey` null, so this is the write that makes it paying). **F18 (2026-09-06):** both `updatePlan` and `activateManualSubscription` now also clear `downgradeToPlanKey`/`downgradeEffectiveAt`/`retainedUserIds` in the same write — the one-armed-transition invariant `subscription-mutation.service.ts` documents — so an admin plan change or manual activation can no longer be silently undone by the next 02:00 scheduled-downgrade sweep (`updatePlan` leaves `cancelAtPeriodEnd` untouched on purpose: revoking a tenant-requested cancellation is `resume()`'s job, not an admin plan edit's). **⚠️ This description is the pre-ADMIN-UPDATEPLAN-1 shape for an UPGRADE (and for a same-rank/custom/off-catalog pick) only — a DOWNGRADE now takes a different path; see the row directly below.**
- **`updatePlan()` branches like the tenant path — instant upgrade w/ proration, downgrade schedules at period end ONLY for an ACTIVE tenant, and refuses either direction while a cancellation is armed (ADMIN-UPDATEPLAN-1, 2026-09-13, lead ruling; FINDING-1/FINDING-2, same day, in-lane review)** — before this, EVERY change (upgrade or downgrade) applied instantly with no prorated figure at all: an admin upgrade charged nothing for the rest of the cycle, and an admin downgrade stripped a paying tenant's plan mid-cycle with no credit — strictly worse than the tenant-facing path B58 already fixed (`subscribe()`/`upgrade()`/`downgrade()` in `subscription-mutation.service.ts`). Now reads `priorSub.{cycle,periodStart,periodEnd,cancelAtPeriodEnd}` (the flag join is FINDING-1 — this branch used to be blind to it entirely) and ranks `fromKey`/`targetPlanKey` via `planRank()` the same way the tenant path does. **FINDING-1 (money, MUST-FIX): refuses the WHOLE mutation — either direction — up front, before either branch below runs, whenever `priorSub.cancelAtPeriodEnd` is armed** (`BadRequestException` "cancellation pending", nothing written, no event) — the wave's original downgrade branch instead wrote `cancelAtPeriodEnd:false`, silently revoking a tenant's own pending cancellation with no `SUBSCRIPTION_RESUMED` event and no audit line; `downgrade()` may clear its OWN tenant's flag (the tenant replacing their own choice), but an admin acting on someone ELSE's subscription has no standing to. A same-rank/custom/off-catalog pick keeps today's instant, no-proration behaviour untouched (B58 never built a "change" for that bucket either); an UPGRADE still applies instantly but now returns `proratedNow` from the shared `ProrationService.proratedDiff()` (injected 6th ctor dep; same inputs the tenant path uses — the sub's cycle/period window + the catalog monthly-price delta). **FINDING-2 (money, MUST-FIX): a DOWNGRADE only SCHEDULES when `before.status === "ACTIVE"`** (`before` read once at the very top of the method, before this call writes anything) — `billing-cron.service.ts applyScheduledDowngrades()` sweeps ACTIVE tenants only, so scheduling one for a READ_ONLY/TRIAL/SUSPENDED tenant armed a downgrade the cron could never fire, stranding the tenant on the higher plan's entitlements/MRR forever (a regression this wave introduced — pre-wave behaviour was instant apply for every status). An ACTIVE-tenant downgrade writes `downgradeToPlanKey`/`downgradeEffectiveAt`(=`priorSub.periodEnd`)/`retainedUserIds:[]` inside a `$transaction` — **`cancelAtPeriodEnd` is never part of this write** (FINDING-1 above already guarantees none is armed by the time this runs, and this path has no standing to touch it regardless) — and returns WITHOUT touching `Tenant.plan` or upserting the subscription row; any OTHER status falls through to the shared instant-apply path below instead. 400s FIRST (`BadRequestException`) if the row has no `periodEnd` to schedule against (mirrors `downgrade()`'s own guard: a schedule written with `downgradeEffectiveAt:null` is filtered OUT by `applyScheduledDowngrades()`'s query, so the UI would otherwise report an accepted downgrade the cron can never apply). **The ledger trap:** a scheduled downgrade emits `PLAN_DOWNGRADE_SCHEDULED` with `amountDelta:0` — NEVER `PLAN_CHANGED` — because the run-rate has not moved yet; `applyScheduledDowngrades()` books the real delta when it actually fires (booking it at request time too would double-book MRR). No `prorate?`/comp-flag was added: the DTO carries only `plan`, the one caller conveys no comp intent, and the admin UI has no charge-today field — an immediate downgrade, if ever wanted, is an explicit future feature. Specs: `platform-admin.service.spec.ts`'s `updatePlan — ADMIN-UPDATEPLAN-1 proration + downgrade scheduling` describe (upgrade calls the shared helper and surfaces `proratedNow`; downgrade schedules + never touches `tenant.plan`/upserts; no `plan.changed` ledger emit at request time), `updatePlan — FINDING-1 refuses an admin plan change while a cancellation is armed` (upgrade AND downgrade attempts both refused, nothing written, no event), `updatePlan — FINDING-2 gates scheduling on the tenant actually being ACTIVE` (READ_ONLY/TRIAL apply instantly, never schedule).
- **`updateStatus()` LEAVES an armed scheduled downgrade alone and AUDITS it (B216 → FINDING-4, 2026-09-14)** — B216 was filed as "a downgrade armed before a tenant lapsed survives an admin reactivation and fires later against a paying tenant", and the round-2 build cleared `downgradeToPlanKey`/`downgradeEffectiveAt`/`retainedUserIds` on a real non-ACTIVE→ACTIVE transition to match the Stripe-webhook paths' `disarmedDowngrade()`. **FINDING-4 (round-3 independent review, lead ruling 2026-09-14) REVERSED that**: only two code paths ever ARM those fields — the tenant's own `downgrade()` and `updatePlan()`'s scheduled branch — so the field set is always a CHOSEN schedule, never a dunning threat the system armed. Clearing it on reactivation revoked the tenant's own choice by someone else's action, with no event and no audit line, leaving them on the higher plan they had asked to leave — the same consent seam as `cancelAtPeriodEnd` (`updatePlan()` refuses outright while that flag is armed). `updateStatus()` now writes NOTHING to `TenantSubscription` on any path: on a won CAS it READS `{downgradeToPlanKey, downgradeEffectiveAt}` and surfaces them in `recordAdminAction`'s meta as `downgradeLeftArmed`/`downgradeEffectiveAt`, so the reactivation records what it left armed; `applyScheduledDowngrades` then applies the schedule when due (one that came due during the lapse applies on the next pass, which is the tenant's stated intent). The **FINDING-3** atomicity still holds and still matters: the CAS `tx.tenant.updateMany({where:{id,status:{not:"ACTIVE"}}, data:{status}})` (`count===1` IS the "was this a REAL transition" read) and the schedule read are ONE `$transaction`, so the audited schedule is the row as it stood AT the transition and not one a concurrent `downgrade()` armed a moment later; the plain `tx.tenant.update()` still follows either way (`updateMany` doesn't return the row, and a LOST CAS still needs the idempotent re-write for every other target status). **Registry consequence: B216's admin half is NOT a defect as filed** — the row's remaining substance is the Stripe-webhook disarm already on master (#692/#695/#696); a revert probe against master `14801139` confirms `updateStatus()` there has zero `tenantSubscription` references.
