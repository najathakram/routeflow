- **B216 — a Stripe REINSTATEMENT no longer disarms a tenant-chosen downgrade; it records that it left it armed (owner ruling 2026-09-14, `fix/b216-webhook-disarm`)** — `onCheckoutCompleted` (~~:574) and `onPaymentSucceeded` (~~:660) each ran a post-commit `tenantSubscription.update(disarmedDowngrade())` whenever they won the non-ACTIVE→ACTIVE CAS. The stated rationale was that a schedule which came due DURING the lapse would otherwise fire on the first `applyScheduledDowngrades` pass after reactivation — but firing is the tenant's stated intent, and only the tenant ever arms these fields (`downgrade()` and `updatePlan()`'s scheduled branch are the only writers), so the disarm silently revoked a choice only they had made, with no event and no audit line, leaving them on the plan they had asked to leave. **Paying an invoice settles a debt; it is not a statement about which plan you want.** Both call sites are gone. The `SUBSCRIPTION_RESUMED` ledger event now carries `downgradeLeftArmed` + `downgradeEffectiveAt` (new module-level `scheduleLeftArmed(sub)`, returning `{}` when nothing is armed — the SAME meta keys `platform-admin.service.ts`'s `updateStatus()` writes into the admin audit, so admin and webhook reinstatements read identically). **Known recording gap, deliberate:** `emitPayingDelta` short-circuits when `planKey` is null (the legacy Stripe cohort — exactly the cohort most likely to be reinstated this way), so for those tenants NO ledger event exists and a `logger.log` line is the only record; the invariant that always holds is that the schedule survives. `disarmedDowngrade()` itself REMAINS, used by the two paths where a CANCELLATION genuinely supersedes a downgrade: `onSubscriptionDeleted` (~~:746) and `onSubscriptionUpdated` when the event arms `cancel_at_period_end` (~~:773).
