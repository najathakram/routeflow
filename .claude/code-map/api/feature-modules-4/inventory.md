### `inventory/`

- **controller** `inventory` — overview, movements (+purchase/adjustment), stock-count/commit, **valuation**, **`@Patch products/:id/cost-basis`**, **`@Post cost-basis/bulk`**, **`@Post recompute-costs`**, **`@Post variant-assign`** (PR-D, generic→variants), suppliers CRUD, purchase-orders CRUD + send/receive/close (list = `ListPurchaseOrdersDto`), forecasting.
- **DRIVER dropped from the four writes that still carried it (B168, F14 2026-09-02)** —
  `recordPurchase`/`recordAdjustment`/`createPO`/`receivePO` each had a handler-level
  `@Roles(OPERATOR, DRIVER)` that OVERRODE the class-level `@Roles(OPERATOR)` (`RolesGuard`
  resolves `getAllAndOverride(handler, class)` — a handler decorator always wins, never merges).
  Those four decorators are simply DELETED (not replaced), so the handlers now inherit the
  class-level OPERATOR-only gate. `commitStockCount`/`sendPO`/`closePO` already carried no
  handler-level override and needed no change — all seven inventory writes now resolve to exactly
  `[OPERATOR]`. The four inventory **reads** (`getStockOverview`, `listMovements`, `listPOs`,
  `getPO`) deliberately keep `DRIVER` — out of scope, pinned in the spec. Spec:
  `inventory.controller.roles.spec.ts` (new — asserts `getAllAndOverride` resolution per handler,
  not just the decorator's own metadata, since a containment check on the handler alone would
  pass even if DRIVER also sat on the class).
- ⚠️ **`recordSale` HAS NO CALLER on master and has not had one since `c5f579c2` (2026-07-16) dropped the `/orders/:id/complete` route** — it was wired only 2026-07-04→07-16. Consequences, all live: **zero `StockMovement type:"SALE"` rows exist**, so `bookkeeping.getProfitAndLoss` reports `cogs = 0` (gross profit = revenue) and five analytics/forecasting readers read an empty source (those readers were re-sourced to invoiced sales, cherry-picked from `claude/priceless-matsumoto-abc131` @ `eaa46ecc`). It is also the only writer that draws `StockLot.remainingQty` DOWN, so lots only ever grow while `orders.service.ts` decrements `Product.currentStock` directly — which used to inflate valuation for the 98% of products labelled FIFO — since fixed by valuing everything at the weighted average (see `getValuation` below). The system is AVCO on every write, and now on every read. Treat the entries below as describing code that exists, not code that runs.
- **service** — `getStockOverview`, `listMovements`, `recordPurchase`, `recordAdjustment`, `commitStockCount`, **`recordSale(productId,qty,ref,userId,tx)` — the sale-costing path, currently UNCALLED (see above)** (per-method unitCost: AVCO=avg, FIFO/LIFO=lot blend w/ avg fallback, STANDARD=standardCost, **LAST_COST=most recent PURCHASE StockMovement unitCost (typed; `orderBy [createdAt desc, id desc]`), avg fallback, not lot-consuming — MUST use the PURCHASE movement not the latest StockLot, since adjustments/stock-counts create avg-cost lots that would poison last-cost**; writes SALE movement WITH unitCost + snapshots, decrements stock, consumes lots, returns `{unitCost, stockAfter}`; never throws on negative stock). `CostingMethod` enum incl. **LAST_COST** (additive migration `20260706040000_add_costing_last_cost`; selectable per-product; tenant-default→product propagation = follow-on, QUESTIONS.md #10), PO CRUD + receive (Decimal AVCO), `getForecasting` (signed SALE sums), **`setCostBasis`/`bulkSetCostBasis`** (COST_BASIS movement qty 0 + product.averageCost; **also writes `standardCost` when the product is STANDARD** so the stock table clears its "no cost" state; optional applyToLots), **`recomputeCosts({productIds?,dryRun?})`** (replays movement history → rebuilds averageCost + backfills avgCostAfter/stockAfter snapshots; reports noHistory + stockDrift; **STANDARD products keep averageCost FROZEN — `replayProduct` mirrors `recordPurchase`'s no-average rule, so recompute/backdated-repair never fabricates a bogus correction**), **`getValuation`** + `getStockOverview`. **VALUATION is weighted-average for EVERY method (2026-08-09): the shared `effectiveValue` helper returns `averageCost` (STANDARD → `standardCost ?? averageCost`) and no longer reads stock lots — `openLotSums` is deleted. Lot-based FIFO/LIFO valuation was only sound while lots were drawn down, and `recordSale` has had no caller since c5f579c2, so lots only grew while stock fell and the read reported the cost of everything ever received (prod: +$12,463.06 over 54 products, 5 valued at zero stock). Every write already maintains `averageCost` via `nextAverageCost` regardless of label, so this makes the read match the write. `costingMethod` now defaults to AVCO (migration `20260809000000_costing_default_avco` sets only the column DEFAULT; existing rows keep their label, which no longer affects any number).** `commitStockCount` is **idempotent** — a re-posted `sessionId` (lost response / 502 retry) short-circuits on the existing `STOCK_COUNT-{sessionId}` movements (returns `{alreadyCommitted:true}`) instead of double-applying ADD deltas + duplicating lots. Cost/qty DTOs carry `@Max` bounds matching the Decimal(10,4)/(10,3) columns (overflow → 400, not a Prisma 500). Backdated purchase/adjustment auto-replays the product in-tx.
- **B562 (CRITICAL, #934, 2026-09-19) — `replayProduct`/`recomputeCosts`/`recomputeProductInTx` refuse a sales-blind average instead of corrupting it.** Order creation/edits decrement `Product.currentStock` directly with NO `StockMovement` row (every OTHER writer — purchase/adjustment/PO-receive/stock-count/variant-assign — pairs the stock write with a movement), so replaying the ledger from 0 and landing short of real `currentStock` (`stockDrift`) is an exact, cheap proxy for "this replay is blind to real consumption." `replayProduct` now does a no-write pass-1 (stage snapshots) before ever persisting, computes `stockDrift`, and skips the persist (pass-2) entirely when nonzero — reports the product under new `gapsDetected` (`recomputeCosts`) instead of writing a wrong `averageCost` and destroying the pre-replay `stockAfter` evidence. `recomputeProductInTx(tx, productId, {throwOnGap})` — `recordPurchase`/`recordAdjustment` call it with the default `throwOnGap:true` (409 `INVENTORY_LEDGER_GAP`, whole write rolls back); `vendor-bills.service.ts receive()` passes `throwOnGap:false` (one bill = one tx across every line; a gapped line still receives its quantity, just skips the backdated replay, reported in the response's new `gapsDetected[]` — `vendor-bills/[id]/page.tsx` shows a non-alarming "cost history not recomputed" toast for it). `InventoryController.recomputeCosts` — **web/mobile UI entry points removed** (interim mitigation, #931): `inventory/page.tsx`'s "Recompute"/"Costs"-fallback buttons are removed, and mobile's `(operator)/(tabs)/warehouse.tsx` menu no longer offers its "Recompute costs" item (the target route/screen `apps/mobile/app/(operator)/products/recompute-costs.tsx` is left in place, just unreachable) until the root cause — order paths writing no `StockMovement` — is fixed. **Bulk-import opening-stock follow-up:** `products.service.ts` bulk-import create and `import/import.service.ts` Zoho product import both used to write `currentStock` with no movement (a permanent, self-inflicted gap) — both now wrap the create in a `tenantTransaction` and add a `PURCHASE` `StockMovement` ("Opening stock (bulk import)" / "Opening stock (Zoho import)") so the replay always has a real baseline. Specs: `inventory.service.spec.ts`, `vendor-bills.service.spec.ts`, `products.service.spec.ts`, `import-robustness.spec.ts`.
- **PR-C durable stock-count sessions (2026-08-20, MIGRATION `20260820000000_add_stock_count_sessions` — purely additive: 2 enums + 2 tables + indexes/FKs, no ALTER of an existing table):** new `StockCountSession` (OPEN|REVIEW|COMMITTED|DISCARDED, `startedById`, `committedById`, `movementReference`, `amendsSessionId`) + `StockCountLine` (`@@unique([sessionId, productId])`, `countedQty`/`boxes`/`pieces`, `expectedQty`, `unitCostOverride` 4dp, `countedById`, `mode` REPLACE|ADD). **Before this a count lived ONLY in the client (localStorage on web, component state on mobile) — `lib/api/stock-count.ts` literally said "there is no server-side session model"** — so it could not resume on another device and left no history. Routes: `POST|GET /inventory/stock-counts`, `GET|POST /stock-counts/:id` (+`/commit`, `/discard`), `PUT /stock-counts/:id/lines`, `DELETE /stock-counts/:id/lines/:productId`. **The pre-existing one-shot `POST /inventory/stock-count/commit` is UNCHANGED and still works.**
  - **Both commit paths share `applyStockCountItemsInTx`** (extracted) so stock semantics can never drift between them; both keep the `reference = STOCK_COUNT-<id>` idempotency guard, and the session path additionally short-circuits on `status === COMMITTED`.
  - **MONEY, load-bearing order:** a line's `unitCostOverride` writes the audited COST_BASIS path (`setCostBasisInTx`) **BEFORE** its quantity adjustment, and the adjustment re-reads the product inside the tx — otherwise the ADJUSTMENT's `avgCostAfter` and any StockLot opened for a positive delta would be stamped with the STALE cost. Spec pins the `["COST_BASIS","ADJUSTMENT"]` order and the lot's corrected unitCost.
  - `expectedQty` is snapshotted on the FIRST count of a line only, so the variance means "what changed since you started counting" rather than tracking stock moving under the counter. Uncounted products are NEVER touched. `increment:true` is the live-scan path (+1, deliberately NOT idempotent); edits send the absolute total. Boxes/pieces recompute qty via `normalizeBoxesPieces`. Amending a COMMITTED session opens a NEW pre-filled one that **re-snapshots `expectedQty` from CURRENT stock** and never rewrites history. A concurrent OPEN session is returned as `otherOpenSessions` — a WARNING, never a lock.
  - The LIST endpoint computes `netVarianceMoney` per session server-side (same delta rule as the commit, at each product's current `averageCost`, via `roundMoney`) and DROPS the raw lines from the payload — otherwise every history row would need its own detail fetch (N+1) to show its headline number, and web/mobile could drift from the server.
  - ⚠️ Lines are written ONE BY ONE (`stockCountLine.create`), never nested under the session create: a nested write bypasses the tenant extension and lands `tenantId = null`, invisible to `forTenant()`.
- **`costing.ts`** — pure Decimal helpers (same rounding discipline as @routeflow/pricing, 4dp): `costDecimal`, `nextAverageCost` (stock≤0 ⇒ reset to unitCost), `reverseAverageCost` (**null = KEEP previous avg** when reversal empties stock — never zero the basis), `planLotConsumption`. Spec: `costing.spec.ts`. ALL inventory writers must go through these.
- **StockMovement snapshots**: every movement now stamps `avgCostAfter`/`stockAfter` (product state AFTER) — point-in-time avg cost = latest movement ≤ T. `MovementType.COST_BASIS` = audited manual cost set (qty 0). Migration `20260704000000_inventory_cost_accounting`.
- side effects: StockLot/StockMovement/PurchaseOrder(+Item)/Product.averageCost writes; ledger. Specs: `inventory.service.spec.ts`.

- **Receiving box→piece conversion (2026-08-23, branch fix/receiving-box-conversion — the client-stock-corruption fix):** stock is PIECES system-wide, but `recordPurchase` (Quick Restock) and `receivePurchaseOrder` wrote the RAW entered number — an operator thinking in boxes under-received by `unitsPerBox`, driving on-hand hugely negative. Now: `RecordPurchaseDto` gains optional `boxes`/`pieces` (`quantity` became optional but KEEPS meaning pieces when sent — never reinterpreted); both receive paths resolve `qtyPieces` once up front via `normalizeBoxesPieces` when the payload is explicitly boxed. `receivePurchaseOrder` also: REPLACED the silent `Math.min(receivedQty, maxReceivable)` clamp with a LOUD BadRequest (a box-denominated legacy `qtyOrdered` vs a piece receipt would silently under-receive and flip the PO to RECEIVED forever), Decimal-safe outstanding math, cost basis pinned to the STORED per-piece `item.unitCost` (the Create-PO web form converts cost-per-box→per-piece before posting; receive-payload shape never changes valuation). PO detail/list selects now include `product.unitsPerBox`. Web: Quick Restock + Create/Receive-PO collect boxes+pieces for boxed products (`inventory/page.tsx`), on-hand renders pieces + `(X boxes + Y pcs)` via shared `apps/web/lib/stock-label.ts` (`unitsLabel` tolerates non-finite → "—"). Mobile: `purchase-orders/record.tsx` + `[id]/receive.tsx` collect boxes+pieces (receive seeds the split from remaining via `normalizeBoxesPieces`). Read-only `apps/api/scripts/report-receiving-unit-drift.mjs` (assertTestTenant-guarded, no --execute) reconstructs suspected under-received products per tenant for the owner-approved data repair. ⚠️ `qtyOrdered` on POs created via mobile/pre-cutover may be box-denominated — receiving them now FAILS LOUDLY with guidance instead of corrupting.
- **P5-03 stock-alert fire hooks:** `InventoryModule` imports `StockAlertsModule`. `recordPurchase`/`recordAdjustment`(qty>0 only)/`commitStockCount`(count-up products)/`receivePurchaseOrder`(actually-received items) each call the service's private `fireStockAlerts(productIds)` AFTER their `tenantTransaction` resolves (never inside it, try/catch, non-throwing) — see `buyer/` `stock-alerts/ StockAlertService` for the fire semantics.
- **PR-D WP1 — `POST inventory/variant-assign` / `assignToVariants` (2026-08-20, no migration):** atomically moves stock from a generic parent `Product` to its variants inside ONE `tenantTransaction` at **`isolationLevel:"Serializable"`** (the pool check is a read-then-write invariant; READ COMMITTED let two concurrent splits both pass and drive the parent negative). "Unassigned stock" = the parent's own `currentStock`, not new state. DTO `VariantAssignDto` (`dto/variant-assign.dto.ts`): `parentProductId` + `assignments[]` (each: existing `productId` OR inline `newVariant:{name}`, plus `qty` or `boxes`/`pieces`, optional `unitCostOverride`). Flow: load parent (404; 400 `"A variant cannot itself be split"` if the parent is itself a variant) → resolve each assignment's qty (`boxes`/`pieces` win via `normalizeBoxesPieces` against the PARENT's `unitsPerBox`; qty≤0 dropped; **400 if `boxes`/`pieces` are sent for a parent with `unitsPerBox`≤1** — `normalizeBoxesPieces` would resolve those to 0 and silently drop the row) → **pool check INSIDE the tx** against a freshly-read `parent.currentStock` (400 `{code:"INSUFFICIENT_UNASSIGNED"}`, writes nothing — this is what makes two concurrent splits of the same generic safe) → resolve every target BEFORE any write (existing `productId` must be `findFirst({id, parentProductId, isActive:true})` — an **ACTIVE** child of THIS parent, 400 otherwise, since a deactivated variant is invisible to every sellable surface; a new-variant name collision also 400s; **a duplicate `productId` or repeated new-variant name 400s too** — both rows would be costed/stock-stamped off the same pre-write snapshot) → draw the parent's `StockLot`s down for the TOTAL via `planLotConsumption` (always, NOT gated on costingMethod like `recordSale` — a transfer must conserve lots for every costing label; **only the COVERED quantity is re-lotted** — `lotPlan.uncovered` (a generic whose opening stock was imported straight onto `currentStock` has no lots) is left un-lotted rather than invented on the variant side) → one negative `ADJUSTMENT` on the parent for the total (parent's `averageCost` is NEVER touched) + one positive `ADJUSTMENT` per variant + one new `StockLot` per variant (for its covered share), all sharing `reference = "VARIANT_ASSIGN-"+randomUUID()` → variant cost = `unitCostOverride ?? parentEffectiveCost` where **`parentEffectiveCost` = the same rule as `effectiveValue()`** (`STANDARD ? standardCost ?? averageCost : averageCost`) — reading the raw `averageCost` column alone moved a STANDARD generic (whose `averageCost` is legitimately null, `recordPurchase` never writes it) at $0; `nextAverageCost` applies only when `variant.costingMethod !== STANDARD` (mirrors `recordPurchase`'s guard) **and a cost is actually known** — with no cost anywhere the variant's `averageCost` is left untouched rather than stamped 0 (a fabricated 0 reads as a real cost in `getValuation` and drops off the "no cost set" report) → parent/variant `currentStock` updated → `fireStockAlerts` on variants that gained stock, after commit. **A new inline variant is NOT created via `ProductsService.create()`** — `InventoryModule` importing `ProductsModule` was out of WP1's file scope, so `InventoryService.createVariantRowInTx` hand-rolls the SAME parent-inheritance fields `create()` would have applied (price tiers, category, isTobacco, costingMethod, standardCost, unitsPerBox, regulated set) directly via `tx.product.create`, plus a matching SKU auto-gen (`generateVariantSku`, same 3-letter+4-hex algorithm as `products.service.ts`). If `ProductsModule` is later wired into `InventoryModule`, this hand-rolled path could be replaced by a real `ProductsService.create()` call. Spec: `variant-assign.spec.ts` (INSUFFICIENT_UNASSIGNED writes-nothing, partial assignment, paired-movement/reference sharing, non-child target 400, variant-of-variant 400, boxed boxes+pieces conversion, unitCostOverride vs parent-average fallback, STANDARD averageCost guard, lot conservation, new-variant inheritance, STANDARD-parent standardCost costing, no-cost-anywhere leaves averageCost alone, ACTIVE-child-only target, duplicate-target 400, boxes-on-unboxed-parent 400, uncovered-lot capping).
