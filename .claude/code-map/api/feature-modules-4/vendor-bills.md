- **Duplicate-invoice guard (2026-08-07):** `VendorBill.supplierInvoiceNumber` (migration `20260807000000_...`, normalized uppercase/no-whitespace, `@@index([tenantId, supplierInvoiceNumber])`) finally gives the SUPPLIER's number a column — `billNumber` is our own `BILL-YYYY-NNNN`, and the supplier's lived only as free text in `notes`. Deliberately **NOT unique**: prod predates it, the same number recurs across suppliers, and a VOID bill must never block a re-scan; enforcement is app-level in `create()`. `create()` resolves the number as `dto.supplierInvoiceNumber ?? extractSupplierInvoiceNumber(dto.notes)` (so OLD web bundles that only send the notes phrase stay guarded + backfilled), persists it, and unless `dto.allowDuplicate` throws `ConflictException({code:"DUPLICATE_VENDOR_BILL", message, duplicate})` — same structured-conflict shape as `UNLINKED_ITEMS`, message self-explanatory because un-updated clients render `response.data.message` raw. `checkDuplicate(dto)` is the read-only pre-flight behind the endpoint. DRAFT match ⇒ `resumable` (finish it); RECEIVED ⇒ hard. **Only `matchedBy === "number"` may BLOCK a create** — an invoice number is document identity; a fuzzy (supplier + date ±1d + total) hit is a hint for a human, and hard-blocking on it made legitimate manual entry impossible (the web manual bill modal always sends supplierId + billDate, so every hand-entered bill went through the fuzzy layer; two same-day same-total deliveries from one supplier could never be entered). `checkDuplicate` still RETURNS fuzzy hits so the scan modal can warn. Backfill: `apps/api/scripts/backfill-supplier-invoice-number.mjs` — idempotent (`IS NULL` guard), batched in a transaction, normalization kept byte-identical to the service via a startup drift guard that greps `duplicate-match.service.ts` plus a before/after denormalized-count rollback. Note `VendorBill.id` is TEXT, not uuid: casting the batched VALUES rows to `::uuid` makes every UPDATE throw `operator does not exist: text = uuid`, and because the dry-run path returns early that failure only ever appears under `--execute`, i.e. against prod.
- **scan/create hardening (batch-scan companion):** `create()` folds optional `dto.taxAmount` into `totalOwed` and rounds the write (`roundMoney`) — scanned supplier invoices carry sales tax the line items don't. NOTE: `update()` is untouched — it recomputes `totalOwed` from `items` only, so a scan-created bill's tax is lost on the first edit after `revertToDraft()` (pre-existing gap, not fixed here; needs a persisted tax column to close). `scanInvoice()` maps failures to TYPED HttpExceptions the web modal switches on: Anthropic 401/403 → 400 `AI_KEY_INVALID`, other non-retryable 4xx (400/404/409/422 — bad/corrupt image, malformed request; excludes 429) → 400 `AI_SCAN_REJECTED`, genuine outage/rate-limit (429/5xx) → 503 `AI_UNAVAILABLE`, unparseable AI output → 422 `AI_PARSE_FAILED`; `new Anthropic({apiKey, maxRetries:0})` + per-request timeout 110s (client waits 120s) — `maxRetries:0` is required for the timeout to actually be a ceiling (the SDK default of 2 retries would each get their own fresh 110s window); the UI's own per-invoice Retry button is the intended retry path. An unreadable HEIC page is SKIPPED + disclosed in `notes` (throws only if every page unreadable). Specs in `vendor-bills.service.spec.ts` (SDK + sharp jest-mocked) incl. the 400→AI_SCAN_REJECTED / 429→AI_UNAVAILABLE boundary. **2026-08-28 metering:** key resolution unified through `platformConfig.resolveAnthropicKey(tenantKey)` (ConfigService injection dropped) and every call records an `AiUsageEvent` (`ocr.vendor_bill`, model `claude-haiku-4-5`, tokens on success / `success:false` on call failure) — cache-hit rescans record nothing.

- **AP payment allocation + on-account supplier credit (PR-E, 2026-08-20).** `recordSupplierPayment(RecordSupplierPaymentDto)` = the AP mirror of `invoices.recordStandalonePayment`: one lump sum across N of ONE supplier's bills, one `randomUUID()` `paymentGroupId` on every `BillPayment` (new nullable column + index), all in one `tenantTransaction`. Guards, in order: tenant-scoped `supplier.findUnique` → 404 (without it an unknown/foreign id 500s on the SupplierCredit FK or mints an invisible credit row); per allocation `bill.supplierId === dto.supplierId` → 400; **`bill.status === "VOID"` → 400** (the ONE status comparison here — a void bill keeps `totalOwed` and has no offsetting rows, so the arithmetic still shows a balance and the update below would resurrect it as PAID); `amount ≤ totalOwed − ledgerPaid + 0.001` → 400. Eligibility is ALWAYS `totalOwed − Σ BillPayment.amount` (landmine 1: `PARTIAL` means short-receipt OR part-payment). Unallocated remainder → `SupplierCredit` (new model, AP mirror of `AdvancePayment`; no status machine, fully drawn = `balance 0`), never a rejection. `getSupplierStatement(supplierId)` = pure running-balance timeline (bills up, payments/credits down), `outstanding = Σ(totalOwed − totalPaid)` over non-VOID bills. **`applySupplierCreditToBill` (called from `create()` and from `update()`, inside their tx) draws against `totalOwed − totalPaid` and writes `totalPaid` ONLY — the bill stays DRAFT.** Flipping it to PAID/PARTIAL there locked a never-received bill out of its whole draft lifecycle (`update()` DRAFT-only, `revertToDraft()` rejects PAID and rejects PARTIAL with null `receivedDate`, `delete`/`bulkDelete` DRAFT|VOID-only, `findAll` needsMapping is DRAFT-scoped) — the list already shows owed/paid/balance arithmetically, so status stays the RECEIPT lifecycle. Each draw is a `BillPayment` with **`supplierCreditId`** (new nullable FK + index, mirrors `InvoicePayment.advancePaymentId`) — that column, never the operator-typable `reference: "SUPPLIER_CREDIT-<id8>"` text, is what `getSupplierStatement` excludes from the timeline and what `refundDrawnSupplierCredits(tx, billId)` matches. **`voidBill` (both branches, the non-reversal one now transactional), `delete`, and `bulkDelete` all call `refundDrawnSupplierCredits` first**: it restores each draw to its originating credit (capped at that credit's `amount`), deletes the draw rows so a void-then-delete cannot refund twice, and returns the total so `totalPaid` is corrected. **`update()` is credit-aware for the same reason**: because the draw leaves the bill DRAFT, an edit can move both the amount the draw was sized by and the supplier it was drawn from, so `update()` calls `refundDrawnSupplierCredits` FIRST (correcting `totalPaid` via `totalPaidAfterRefund`) and then re-applies against the edited `totalOwed`/`supplierId` — without it, correcting a total downwards stranded the difference (statement `outstanding` went negative) and re-pointing `supplierId` funded the new supplier's bill out of the old supplier's account. Specs: `supplier-payment.spec.ts`; the prisma mock predates `SupplierCredit`, so tests graft the model onto `prisma`, `forTenant()`, and the tx surface.
