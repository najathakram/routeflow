### `sales-agents/` (flag.sales_agents — PR-C, engine ships DARK)

Agents bring customers in and earn a % on those customers' invoices. **Engine + API here; the
UI shipped in PR-D** — web `app/(dashboard)/sales-agents/` + `finance/commissions/` + the
customer-page agent box (see web.md) and a read-only mobile row (mobile.md). Everything is
gated by `flag.sales_agents`, granted ONLY by the `SALES_AGENTS` addon (no plan grants it) —
flag OFF ⇒ the engine returns before touching a commission table and every route 403s.

- **`commission-math.ts`** (pure, `pricing.spec.ts` style — no Nest, no mocks) — `COMMISSION_EPS = 0.005`, `commissionBase`, `collectionRatio`, `resolveRate`, `passesGrandfathering`, `accruedCommission`, `payableCommission`. **Money semantics (owner-locked):** base = `max(0, subtotal − discount − nsfFees)` — tax, shipping, and NSF penalty fees NEVER enter (NSF items identified by the server-written `NSF_FEE_DESCRIPTION_PREFIX` on the invoice item, exported here, written by `invoices.service` setCheckStatus); `collectionRatio` deliberately keeps NSF fees in its denominator (conservative under-release, commented in-file); a CREDIT_NOTE application reduces base by its **pre-tax share** (`creditApplied × goods / total`), not its face value. `ratio = cashCollected / (total − creditApplied)` with a full-payment snap at ε; credit rows are excluded from BOTH sides. Commission is computed ONCE per document, never per line.
- **`commission-engine.service.ts`** — `syncInvoiceCommission(invoiceId, db?)` (derive-from-current-state, idempotent: unchanged state writes nothing), `syncInvoiceCommissionSafe` (**the hook wrapper — catches everything, logs, never throws**; a commission bug must never block an invoice/payment write), `syncOrderInvoices(orderId, db?)`, `removeInvoiceCommission(invoiceId, db)` (409s when `claimedAmount > 0`), `recomputeCommissionRange({agentId?,customerId?}, fromDate)` (backdate sweep, own tx per invoice, audit-logged `commission.recompute`). **Unconditional accrual lock (B73, F18, 2026-09-06):** `syncInvoiceCommission` now wraps ANY non-transactional `db` client in its own `tenantTransaction` before taking the row lock — previously the lock was skipped whenever a caller passed a plain (autocommit) client, so two concurrent settlements on the same invoice could both read the pre-accrual state and each append a `CLAWBACK`. A real transaction client is used as-is (no nested transaction). REG-B73 T5 (concurrent sync appends exactly one CLAWBACK) / T5b (non-tx client wrapped; tx client used as-is) in `commission-engine.service.spec.ts`.
  - **Issued** = `status !== DRAFT && !== VOID` (`WRITTEN_OFF` counts — it froze, it didn't un-happen). **Cash math counts ONLY `InvoicePayment.status = PAID`** (the DRAFT-payment trap; VOID are dead) — deliberately diverges from `invoices.service.ts recomputeStatus`, which filters only `!== VOID`.
  - `basisDate = order.orderDate ?? invoice.issueDate`; attributed agent = the `AgentAssignment` covering it. **Rate precedence:** `Order.commissionRatePct` (`0` IS a value = exempt) → newest `CustomerCommissionRate` → newest `SalesAgentRate` → `NONE` (writes a zero row so a later backdated rate has something to fix).
  - **Ledger invariant:** `drift = payable − claimedAmount − Σadjustments`. Accrual rows are mutable until claimed; claims move ONLY via statements. `drift < −ε` ⇒ append exactly ONE `CommissionAdjustment` (MANUAL is never auto-emitted) — the formula self-limits, so a re-run emits none. **Kind is chosen by CAUSE, not by the forced-zero target:** agent no longer holds the customer ⇒ `REASSIGNMENT`; invoice no longer issued (void / revert-to-draft / reopen) ⇒ `CLAWBACK`; rate or rateSource moved **while the row still earns** ⇒ `RATE_CHANGE`; otherwise `CLAWBACK`. Positive drift is just unclaimed payable that the next statement sweeps. Convergence is why backdating, clawbacks, reassignment and order edits are all ONE code path.
  - **Row retention:** a row is deleted only when it stopped **earning** (agent lost the customer, or invoice un-issued) AND has no claims and no adjustments. A resolved agent at rate 0 — `rateSource NONE`, or an explicit `0` = exempt order override — **keeps its placeholder row** (that is the row the backdated-rate sweep later fixes), so a re-sync of it writes nothing. New rows are inserted after a `findFirst` re-check of the double-accrual lock, **never** by catching its P2002: `db` is usually the caller's invoice/payment tx and Postgres aborts the whole tx on a constraint violation, so swallowing it would only defer the failure to COMMIT — the one thing `…Safe` cannot save the caller from.
  - Lifecycle: `PAUSED` blocks **creation** only (existing rows keep releasing; pause DEFERS, never forfeits). `STOPPED_FOR_NEW` + `stopNewBusinessAt` grandfathers via `order.orderTemplate.createdAt` / `invoice.recurringInvoice.createdAt`. Soft-delete only.

  are **ON DELETE RESTRICT**, so one surviving NULL-tenant child aborts its parent's delete (P2003)
  and rolls the whole wipe back. A relation filter is also parameter-free — no id list in memory,
  no 32767-bind-variable ceiling on the biggest tenants. (4) ⚠️ **Runs on `prisma.$transaction`,
  NOT `tenantTransaction`** — see the proxy lesson below; it re-scopes the child filters and

  re-admits `OPERATOR` alongside `TENANT_ADMIN` — and `RolesGuard` grants on
  `requiredRoles.some(...)`, i.e. exactly the role the gate exists to exclude.
  Spec `settings.controller.clear-financial.spec.ts`.
- ⚠️ **Durable lesson, BOTH directions — `prisma.tenantTransaction` is a pass-through when
  `tenantId` is null and an INJECTOR when it is not.** (a) With no tenant it hands back the raw
  client (`prisma.service.ts` — `if (!tenantId) return fn(rawTx)`), same as `forTenant()`; that is
  a fall-through, not a guard, so a destructive bulk handler must refuse a null tenant itself.
  (b) With a tenant it hands back `_wrapTxWithTenant`, whose `SCOPED_METHODS` include `deleteMany`
  and which rewrites EVERY call as `where: { ...args.where, tenantId }`. That injection is
  invisible at the call site and silently re-scopes a deliberate parent-scoped filter back onto the
  row's own `tenantId`. Since `tenantId` is `String?` (nullable) on finance/child models and
  nested-created child rows carry `tenantId: null`, a handler that must reach those rows CANNOT use
  `tenantTransaction` — use `prisma.$transaction` with explicit filters (plus a null-tenant refusal
  to make that safe), and match children through a relation filter on the parent. Mocks hide this:
  both `createMockPrisma` and hand-rolled fakes usually implement `tenantTransaction` as
  `(fn) => fn(models)` with no injection, so a spec that must observe it should call the real
  `_wrapTxWithTenant` (as `settings.controller.clear-financial.spec.ts` does).
