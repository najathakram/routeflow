## #4212 `1a6d9c35ff` AI keys stay encrypted, one entry for every AI call, a monthly cap (SA-1102 PR-A, A-1, A-3, A-4, PR-B1; ops W-1156)

- **Secrets at rest.** `common/secret-at-rest.ts` (`encryptIfSecret`, `decryptIfSecret`, `secretPreview`, `ENCRYPTED_FORMAT`, `SecretCipher`): the one AES-256-GCM helper both `SystemConfig` and `PlatformConfig` use. `PlatformConfig` `claude.apiKey` is written encrypted; a legacy plaintext row still reads (decrypt passes non-encrypted text through) and is reported, not rewritten here. `secretPreview` shows an ellipsis plus the last 4 characters and nothing else. RouteFlow's Railway env `ANTHROPIC_API_KEY` is read first; the stored row only when env is unset.
- **Fail closed without a business.** `system-config/system-config.service.ts`: a secret read (`get`, or a `getAll` whose prefix covers a secret key) and every `set` throw a coded 500 `SYSTEM_CONFIG_TENANT_REQUIRED` when no business is in context (before this, `forTenant()` returned the unscoped client and read or overwrote another business's row). Other reads still work and log one WARN per key per process (`WARNED_TENANTLESS_READS`). Pins: `system-config-callers.census.spec.ts` (callers with no business: NONE = 0), `secret-keys.pin.spec.ts` (a secret-named config key outside the secret list fails), `system-config.tenant-required.db.spec.ts`.
- **One entry point.** `platform-admin/platform-config.service.ts` `prepareAiCall(task, businessKey?)`: `requireAiTenant()` (403 `TENANT_CONTEXT_REQUIRED`), then the key by task (a business key for `bill_scan` only, then env, then the stored row), then `assertAiBudget` when the key is RouteFlow's (403 `AI_MONTHLY_CAP_REACHED`, `resetsAt` = next UTC month start), then the task's model. `key` null means none configured and the caller keeps its own not-configured answer. The five Anthropic call sites use it (`vendor-bills` `scanInvoice`, `bookkeeping` `extractExpenseItems`, `supplier-statements` `scanStatement`, `route-optimization/route-analysis.service.ts` `analyzeRoute` and `analyzeRouteRun`); each calls `requireAiTenant()` as its first statement (A-4 M3, so a tenantless call is refused before any read). `testConnection` is the one reviewed exemption. Pins: `ai-call-sites.census.spec.ts` (a new site that skips it fails; includes a source-order check), `ai-sites.tenant-first.spec.ts` (M3-1..5), `platform-config.prepare-ai-call.spec.ts`, `anthropic-key-readers.census.spec.ts`.
- **Monthly cap (B1, no migration).** `monthlyCapUsdFor` reads `ai.monthlyCapUsd` (default `DEFAULT_MONTHLY_AI_CAP_USD = 25`; `0` is the kill switch); spend is summed from the business's `AiUsageEvent` rows for the UTC month through the one `modelPrice`. A business's own-key bill scan is never refused. Pin: `platform-config.ai-budget.db.spec.ts`.
- **Route analysis degrades, it does not break.** `route-analysis.service.ts` result gains `aiUnavailable: "cap" | "unavailable"` and `aiResetsAt` (`configured` kept for old clients); over the cap the ETAs still return without the AI notes (rows RA-1/RA-2; the web half is in the web note). - **Checks.** `system-config/plaintext-secrets-report.service.ts` (boot report) and `scripts/report-plaintext-secrets.mjs` (read-only; keys and counts only) count plaintext secret rows; `npm run local:plaintext-secrets` and `local:validate` run it (a warning, not a failure). Receipts leave Opus for Sonnet 5.5 (`platform-admin/ai-models.ts` `receipt_scan`), pinned: no task falls back to Opus or Fable (`ai-models.spec.ts`).

## #4213 `ada54508a5` a read-only report of stranded superseded checkouts (SA-1103 (c); ops W-1157)

**No billing code changed.** B1281 (the 5-level Stripe expand that refused a second paid checkout) was already fixed on master by `2596cae347` (#4150, 11-02): `StripeService.getSubscriptionPaymentState` expands `latest_invoice.payments` and reads the PaymentIntent by id; the class pin `stripe-expand-depth.pin.spec.ts` stays. #4213 ships the report that finds the businesses the bug may have left with two live subscriptions in Stripe.

- `scripts/report-b1281-superseded-checkouts.mjs` (built on `report-b2436-stripe-missing-sub.mjs`): per business with a `stripeCustomerId` it lists, from Stripe, subscriptions and completed subscription checkouts since `--since` (default 2026-10-08). Findings: more than one LIVE subscription (active, trialing, past_due, unpaid, pinned equal to `stripe-period.ts` by a spec); any live subscription on a soft-deleted business; a completed checkout whose subscription is not the stored one (`orphanStillLive` when live; "Revivable, superseded" when paused or incomplete, not when terminal); a read that hit the 500-row cap.
- **Read-only twice:** the database session is `default_transaction_read_only = on` with statement and lock timeouts, and Stripe is called only through `list` and `retrieve` on `subscriptions` and `checkout.sessions` (allow-list pinned). Output is tenant ids, counts and the last 4 of Stripe ids; a rethrown Stripe error is scrubbed. LIVE and TEST tenants are reported apart; exit 0 when LIVE is clean, 3 on any LIVE finding (`LIVE FINDINGS: n` closes the output), 2 usage, 1 other failure. `--self-test` prints `self-test ok`.
- **Not run against live.** The live run needs the owner's per-call yes, a read-only restricted key and `railway run --service postgres`; no repair script exists (the owner decides repairs from the report). Test: `report-b1281-superseded-checkouts-script.spec.ts` (29 rows, scripts lane).

## #4215 `6744dc6ade` the live-return guard takes the customer returns lock first (B1279, SA-1101 A-6 Part 2; ops W-1158)

Closes the race between an office change that moves an order out of DELIVERED and an inline-return capture, return create or approve for the same customer. Part 1 (#4208, window 5) made the guard count both links; the guard still took only the Order row locks, and an unpinned capture takes its source order from the matching set (DELIVERED orders) without locking it, so a capture could source and restock against an order the demotion was about to move.

- `returns/return-customer-lock.ts` (new): `returnCustomerLockKey(customerId, tenantId, keys?)` is the one derivation of the customer-scoped returns advisory key (`IdempotencyService.hashFor(…, "returns.customer")`; the optional `keys` lets the two existing lock sites keep their injected service), and `lockReturnCustomersOf(tx, orderIds)` reads the orders' customers and takes each distinct customer's lock in key order. The scope literal `"returns.customer"` lives in this file only (pinned, RO-39).
- `returns/live-return-guard.ts` `lockThenAssertNoLiveReturn`: customer lock first, then `lockOrderRows`, then the count (advisory, then Order rows: the house order, SA-214). This covers Undo the stop (`reopenStop`) and the demotion (`guardDeliveredDemotion`, three transaction bodies) in one edit; the census stays three callers.
- `orders/deliver-again.ts`: Deliver again takes the customer lock as the first statement of its transaction, re-reads the order's customer under the Order row lock and refuses `ORDER_CHANGED_DURING_EDIT` on a mismatch. `returns/inline-returns.service.ts` (`lockCustomerInTx`) and `returns/returns.service.ts` (STANDARD create) derive their key through the helper.
- Semantics: a capture in flight finishes and is counted by the guard; one that starts later reads the order as already moved. The tenant for the key comes from the `Order` row, so no caller signature changed.
- Tests: `orders/demote-live-return.db.spec.ts` (RO-37, a capture holds the customer lock and the demotion waits, then 409 `ORDER_HAS_RETURN`), `returns/live-return-guard-customer-lock.b1279.db.spec.ts` (RO-38, the real `InlineReturnsService.capture` waits behind a demotion and its matching set excludes the order), `returns/return-customer-lock.spec.ts` (RO-39), seat pins in `live-return-guard.structure.spec.ts`, `deliver-again.spec.ts`, `demote-live-return.spec.ts`, `live-return-guard.spec.ts`. One expected value moved on purpose: `inline-returns-source-pins.spec.ts` now expects `returnCustomerLockKey(` where it pinned the scope literal.
- Registry: **B1279 closed here** (fixed by #4215, F64 T1).
