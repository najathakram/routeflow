# `returns/`

> Split from [`../feature-modules-3.md`](../feature-modules-3.md) (verbatim, lines 194-201 of the pre-split file) on 2026-09-16. Originally itself split from `.claude/code-map/api.md` (verbatim, lines 1344-1592) on 2026-09-13. See [`../../INDEX.md`](../../INDEX.md).

- **controller** `returns` — `@Get/:id`, approve, reject, in-transit, receive, refund, cancel. **F08:** `findAll`'s `GET /` gains `@Query('search')`; `@Query('limit')` still parsed with bare `+limit`, no upper clamp (B223).
- **service** — `findAll`/`findAllForUser(user, options: FindAllReturnsOptions)` (CUSTOMER filtered to their own customerId; DRIVER unscoped — B221), `findOne`, `create`, `approve`, `reject`, `markInTransit`, `receive` (RETURN movement restocks at current averageCost with unitCost+snapshots stamped), `refund`, `cancel`. side effects: Return/ReturnItem writes; RETURN movement on receive; credit-note auto-gen on refund; email.
- **`create` over-return guard (B10)** — rejects a non-array/empty `dto.items` with 400 up front (`POST /returns` binds `@Body() dto: any`, so nothing validates the shape and the loop used to 500). Then, inside one `tenantTransaction`: `tx.$executeRaw SELECT id FROM "Order" … FOR UPDATE` **first** (tenantTransaction is READ COMMITTED — the tx alone does not serialize concurrent creates; mirrors `invoices.service.recordPayment`), then the `tx.return.findMany` cumulative read, per-line validation, and `tx.return.create`. Each validated line accumulates into `alreadyReturned` so one payload repeating a productId can't over-return. Spec: `returns-overreturn.spec.ts`.
- **`processRefund` → store-credit dispute (P5-13)** — flips RECEIVED→REFUNDED, then (sequentially, NOT nested — `CreditNotesService.create` opens its own Serializable tx) mints a **lump-sum** ISSUED `CreditNote` (**no line items** — the regulated ledger was already reversed at `receive()` via `reverseReturnEntries`; a line-linked credit would double-reverse), skips create on $0. Pricing formula **SUPERSEDED by F08 B53 below** (was `Σ item.qty × (orderLine.subtotal ÷ orderLine.qty)`, the order-line basis — see the F08 bullet for the current `priceReturn`/`billedBasisFor` basis). Single source invoice → passed as `invoiceId` (engages the cumulative over-credit cap); 0 or 2+ invoices → standalone credit (F08 narrows this — see below). Links via `Return.creditNoteId`. Injects `CreditNotesService` (`ReturnsModule` imports `CreditNotesModule` — acyclic, no `forwardRef`). **F09 lens A2 (2026-09-06):** the order's invoice select is now scoped to live sources (`where: { status: { notIn: CREDIT_SOURCE_EXCLUDED } }`, from `invoices/invoice-status-sets.ts`) — before this fix, a sole VOID/WRITTEN_OFF invoice reached `create()`'s new B66 guard and threw **after** the atomic RECEIVED→REFUNDED claim had already committed, losing the refund with no recovery path (the return was terminally REFUNDED with `creditNoteId` null). Now zero live invoices falls into the same "2+ invoices" branch and mints the credit UNSOURCED instead — **F08 supersedes this too**: zero invoices now falls back to the legacy order-line basis instead (see below), so the UNSOURCED-mint case is narrower (invoices exist, none creditable → refuse). Spec: `returns-refund.spec.ts` "F09 A2: refund against a voided source mints an unsourced credit note" (pinned as a tripwire, still green post-F08).
- **PR-1a/§5, M6/§2.3 (2026-09-15/16) — `Return.kind` (STANDARD|INLINE) + INLINE endpoint boundary + pooled cross-line accounting, prep for the (PR-1c/1d) INLINE capture flow:** `create()` now stamps `kind: "STANDARD"` on every row it writes; `findAll`'s `where` is hard-scoped `kind: "STANDARD"` (an INLINE return gets its own list/queue later, and its money fields are priced at capture — not shaped for `priceReturn()`/`billedBasisFor()`). Every OTHER standard-path method (`approve`, `reject`, `markInTransit`, `receive`, `processRefund`, `cancel`, `findOne`) now 400s `INLINE_RETURN_USE_INLINE_ENDPOINTS` the moment a fetched row's `kind === "INLINE"` — refused for EVERY caller, CUSTOMER included, on `cancel()` too. New **`returns-pieces.util.ts`** (pure + one DB-hitting helper), shared by the future INLINE flow from day one: **`soldPiecesForProduct(order, productId)`** — sums a product's qty across every non-CANCELLED line (was a single `.find()`-matched line; a product split across a re-add/post-edit line was previously undercounted, and a per-line-rate refund priced the WHOLE return at one line's rate when lines differed in price — both fixed by pooling qty+subtotal per product before dividing). **`firstNonCancelledLine`** (position-ordered, nulls-last tiebreak) + **`standardReturnPieces(order,productId,qty)`** — a named seam for a future box/piece-aware DTO conversion; today `OrderItem.qty`/`ReturnItem.qty` are both already total pieces (`@routeflow/pricing normalizeBoxesPieces`), so it's an identity function. **`returnedPiecesByProduct(tx,orderId)`** (async, DB-hitting) — the shared "already returned" reader, sums STANDARD `Return.items` (scoped `orderId`+`kind:STANDARD`) AND (wired from day one, empty until INLINE ships) INLINE `ReturnItem` rows via `sourceOrderId`, both REJECTED/CANCELLED-excluded; replaces `create()`'s old inline reduce. `create()`'s over-return validation and `refundEstimate`'s legacy no-invoice basis both now pool per-product across lines this same way; `findOne`'s `orderedQty` enrichment does too (was a single-line `.find()`, could show an operator a lower cap than `create()` actually enforced) — `unitPrice` stays single-line, display-only. `lineItems` selects across the file gained `status`/`position` (CANCELLED exclusion + the position axis were previously silent no-ops — nothing selected those columns). **§5 customer-level serialization:** `create()` now also acquires `idempotency.acquireLock(hashFor(order.customerId, tenantId, "returns.customer"), tx)` (after the idempotency check, before the order-row `FOR UPDATE`) — the future INLINE flow shares `returnedPiecesByProduct`'s accounting across a customer's orders, so two concurrent returns (one STANDARD, one INLINE, different orders, same customer+product) must not both read a stale snapshot; the existing per-order `FOR UPDATE` alone doesn't cover a cross-order race. Specs: `returns-kind-branch.spec.ts` (every INLINE-refusal site), `returns-lineitems-select.spec.ts` (status/position selected + CANCELLED excluded), `returns-customer-lock.spec.ts` (lock acquired with the right key/order), `returns-pieces.util.spec.ts` (pure-function + `returnedPiecesByProduct` unit coverage), `returns-overreturn.spec.ts`/`returns-refund.spec.ts` extended for pooled cross-line cases.
- **F08 (2026-09-06, #645) — billed-basis refund, compensating claim, fresh-lock cancel, quota/restock/search/refundEstimate:** `priceReturn(items, order)` is the ONE pure pricer every read path shares (`processRefund`, `findAll`, `findOne`) — prices each returned line off the order's `CREDIT_SOURCE_EXCLUDED`-filtered (VOID+WRITTEN_OFF, from `invoices/invoice-status-sets.ts`) non-VOID invoice items, never the order line, and returns `{amount, refusal?}` so a $0 that could not be priced is distinguishable from a genuine $0 (surfaced as `refundEstimateReason`, rendered as prose on web). `billedBasisFor` (mint-time only, DB-hitting) additionally GATES the write: a single creditable invoice becomes the credit-note source (`invoiceId` set, engaging `credit-notes.service.create`'s own per-invoice cap); 2+ creditable invoices mint against the LATEST one after an order-level `headroom = Σ creditable invoice totals − Σ non-VOID credit notes linked to the order` check (refuses `BadRequestException` naming the invoice's `invoiceNumber`, degrading to the raw id if the select lacks it, BEFORE the RECEIVED→REFUNDED claim); zero invoices at all falls back to the legacy order-line basis (pre-invoicing orders); invoices exist but none creditable refuses outright. **B68:** a failed `creditNotes.create` compensates the already-committed claim (2nd `updateMany` back to RECEIVED, clearing refundMethod/refundAmount/refundedAt, guarded on `creditNoteId:null`) and always rethrows the original error — never masked by a failed compensation. **B69:** `cancel()` now does `tx.$executeRaw SELECT ... FOR UPDATE` on the Return row inside the transaction (unconditional, every call), then a fresh `tx.return.findUnique` (with items) decides the undo — the OUTER pre-tx read stays only for 404/ownership/early-status checks, never for what to undo (closes the race where a concurrent `receive()`'s restock flags were read stale). **B82:** the over-return quota query excludes `{ notIn: ['REJECTED','CANCELLED'] }`, not a single-status `not:'REJECTED'`. **B20:** the nested item map persists `condition`/`notes` onto the real `ReturnItem` columns. **B61:** `NO_RESTOCK_REASONS` (DAMAGED, QUALITY_ISSUE) drives `defaultRestockForReason`, used whenever an item omits `restock`; an item-level `reason` outside the allowed set is REJECTED rather than silently deciding restock. Mirrored byte-for-byte in `apps/mobile/lib/returns-logic.ts`'s `restockForReason`, pinned set-equal by the STATIC-SCAN `returns-restock-parity.spec.ts` (no runtime cross-workspace import is possible — api may not import a workspace package at runtime per `no-runtime-workspace-imports.spec.ts`, mobile's jest stubs `@routeflow/types` — so both files are read as TEXT and diffed as literal sets, mirroring `enum-parity.spec.ts`'s pattern). **B166:** `@Query('search')` → `FindAllReturnsOptions` object (`findAllForUser`/`findAll` both take it) → `where.OR` (returnNumber / order.orderNumber / customer.businessName, insensitive), ANDed with existing filters so CUSTOMER's `customerId` scoping still applies. **B75:** `findAll` enriches every row with `refundEstimate`/`refundEstimateReason` via the same `priceReturn`, fetching (then stripping back off the wire) each row's order.invoices/order.lineItems purely to price it — see B223 below (perf + no limit clamp). **NOT done — filed, not fixed:** `deliveredQty` composition (B53×B128 — a return on a delivered-basis invoice cannot yet tell billed-but-undelivered units from billed-and-delivered ones within one billed line; needs a `ReturnItem.deliveredQty` migration; the "derive it from `OrderItem.deliveredQty` instead" shortcut is REJECTED — it would zero every post-delivery return on a delivered-basis invoice) — **B220**. DRIVER role scoping on `GET /returns` (`findAllForUser` scopes only `user.role === 'CUSTOMER'`; DRIVER — role-allowed by the controller — falls through to the unscoped tenant-wide `findAll`, now carrying `refundEstimate` money) — **B221**. The order-level headroom aggregate (counts `OrderCreditNote`-linked credit INTENT broadly) vs `credit-notes.service.create`'s own cap (scoped to the single source invoice) disagreeing on scope, so the mint-time guard can refuse a refund `create()` would accept — **B222**. `findAll`'s per-row invoice-graph join plus `@Query('limit')` parsed with `+limit` and passed straight through with NO clamp (web's KPI fetch already sends `limit:500`) — **B223**.
