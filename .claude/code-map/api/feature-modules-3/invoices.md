The regulated ledger follows for free (`soldAt = invoice.issueDate` ⇒ `periodBucket` lands in that PAST month — owner-accepted restatement of re-generated regulatory reports). **`resyncInvoiceLedger` is deliberately untouched**: its reversals must keep booking in the CURRENT period (explicit never-backdate rule). `resyncOrderInvoicesForEdit` still never touches `issueDate`. — **`InvoicePayment.settledAt`** (migration `20260807000200_...`, `@@index([tenantId, settledAt])`) is when the money actually LANDED in the bank, vs `paidAt` = when the instrument was received; it MAY be a FUTURE date (post-dated checks) and nothing clamps it. Distinct from `clearedAt`, which stays a server-stamped CHECK-lifecycle audit mark. Accepted on Record/Update/Standalone/SetCheckStatus DTOs; `updatePayment` distinguishes key-absent (preserve) from explicit `null` (clear); `recordStandalonePayment` writes it across every row of the `paymentGroupId` group; `setCheckStatus` CLEARED lets an explicit date win (setting both `clearedAt` and `settledAt`) but otherwise **leaves `settledAt` alone** — `clearedAt` still defaults to the clock because it is the audit stamp of the transition, while `settledAt` is operator-supplied truth about the bank and is never inferred from when someone clicked. Defaulting it to now (as the first cut did) silently yanked an old check out of its original cash-basis period into the current one, restating already-reported numbers — and no shipped client can pass an explicit date yet, so that was the only reachable behaviour. Driver at-door `recordDeliveryPaymentInTx` stays unchanged (settlement unknown at the door). `listAllPayments`/`exportPayments` sort on it; CSV gained a `Bank Date` column.

Specs: `invoices.service.spec` single-group full-discount (20/20 → discount 20, total 0), split two-group order (discount 15 → shares sum to exactly 15, Σ sibling totals == order total), zero-discount byte-equality.
