# `credit-notes/`

> Split from [`../feature-modules-3.md`](../feature-modules-3.md) (verbatim, lines 178-193 of the pre-split file) on 2026-09-16. Originally itself split from `.claude/code-map/api.md` (verbatim, lines 1344-1592) on 2026-09-13. See [`../../INDEX.md`](../../INDEX.md).

- **controller** `credit-notes` — create, list, get, apply, void. `POST :id/issue` **deleted (F09/B18, 2026-09-06)** — the `CreditNoteStatus` enum never had a DRAFT value, so the flow could never run; web/mobile issue affordances removed with it.
- **service** — `create`, `findAll`, `findOne`, `apply`, `void`. `issue()` **deleted (F09/B18)** — was `return this.findOne(id)`, a no-op. side effects: CreditNote writes; ledger entries; optional auto-apply to invoices.
- **Wallet (P5-13, money-critical)** — `CreditNote` += `expiresAt DateTime?`/`appliedAt DateTime?`/`autoApplied Boolean @default(false)` (migration `20260725000000_add_credit_wallet`, additive, after `20260724000000_add_check_lifecycle`). **Canonical open-credit predicate** (every wallet/auto-apply site must match): `status != VOID && (amount − amountUsed) > 0.001 && (expiresAt == null || expiresAt > now)` — "expired" is a computed FILTER, never a status flip, never claws back an `InvoicePayment`. `create()` accepts optional `expiresAt` ISO (validated in-service — no `CreateCreditNoteDto` class exists, controller takes `dto: any`; rejects non-date/past dates). **`applyCreditInTx(tx, cn, inv, requestedAmount?, opts?)`** — private, tx-safe (never opens its own tx), the single money core: `roundMoney`s every figure, sums `alreadyPaid` **excluding `status:VOID` payments** (P5-12 bounced checks must not count as paid), `applyAmount = roundMoney(min(remaining, invoiceBalance, requestedAmount))`, writes one `CREDIT_NOTE` `InvoicePayment` + bumps `amountUsed` + stamps `appliedAt`/`autoApplied` + flips `APPLIED` only when exhausted; returns `{applied:0}` (never throws) so callers can skip. `applyToInvoice` (public) keeps its own `Serializable` tx + all guards (expired/APPLIED/VOID/customer-mismatch/invoice-status) + throws on 0, delegates the money to `applyCreditInTx`. **`autoApplyOldestCreditsInTx(tx, invoiceId, customerId)`** — **PUBLIC** (cross-service call from `InvoicesService`; the only reason it's public — `applyCreditInTx` stays private), oldest `createdAt` first, `where` filters `status != VOID` + `OR expiresAt null/gt now` (Prisma can't compare two columns, so the `remaining > 0.001` half is a JS filter after fetch); loops credits passing the **running invoice balance as `requestedAmount`** — a hard clamp so it can never over-apply even on a stale re-read; idempotent (re-send finds nothing to apply). One or the other, never both: a credit reduces the invoice AS a `CREDIT_NOTE` payment AND leaves the wallet via `amountUsed` — never separately.
- **F09 (2026-09-06) — the money-write gate + create()/find()/void() fallout:** `applyCreditInTx` now returns `{ applied: 0 }` up front when `CREDIT_SETTLE_EXCLUDED.includes(inv.status)` (`[VOID, WRITTEN_OFF]`) — the ONE gate that covers `settleOrderCreditsInTx`, `autoApplyOldestCreditsInTx` (`send()`/`sendEmail()`) and any future caller (B67 had two unguarded doors; a query-level fix on `settleOrderCreditsInTx` alone would have missed the auto-apply one). The settle `where` (`autoApplyOldestCreditsInTx`'s candidate query and `settleOrderCreditsInTx`'s invoice list) deliberately keeps only `status: { not: "VOID" }` — WRITTEN_OFF stays IN on purpose so the SHRINK pass still sees written-off invoices and can un-apply their now-excess credit (T3/T3b pin this; narrowing that `where` would strand money). `create()` now selects `status` and refuses **`CREDIT_SOURCE_EXCLUDED`** (`[VOID, WRITTEN_OFF]`) with `BadRequestException("Cannot issue a credit note against a <status> invoice.")` (B66) — **DRAFT stays allowed on purpose** (returns' pending-mirror invoices go through `create()`; T7b pins it). `findAll` now includes `invoice: { select: { id, invoiceNumber } }`, matching `findOne`'s existing shape (B19, T12 — list/detail render `invoice?.invoiceNumber ?? invoiceId` instead of a raw UUID). `applyToInvoice`'s own hand-typed `["PAID","VOID","WRITTEN_OFF"]` literal is re-pointed at the new `CREDIT_NOT_APPLICABLE` set. All four exclude-lists live in the new `invoices/invoice-status-sets.ts` (see that section). Gate: `credit-notes/credit-notes.wallet-integrity.spec.ts` (REG-B67 T1/T2/T5, REG-B66 T6/T7/T9-T12) + `.pins.spec.ts` (T3/T3b/T4/T7b/T8/T11). Lesson **L-081**: gate a money write inside the primitive that performs it, on the row it just read — a sibling primitive or a result-injecting mock bypasses a `where`-only fix.

- **Credits ON ORDERS (2026-07-18, money-critical)** — new `OrderCreditNote` INTENT table (see schema entry) + service primitives: **`restoreCreditFromPaymentInTx`** (private, inverse of `applyCreditInTx` — deletes/shrinks the CREDIT_NOTE payment, decrements `amountUsed`, APPLIED→ISSUED, recomputes invoice status), **`validateSelectionsForCustomer`** (tenant/customer/VOID/expired/duplicate; deliberately does NOT require remaining>0 — idempotent resubmits), **`syncOrderCreditSelections(tx, orderId, customerId, selections|undefined)`** (undefined=untouched, []=remove all, else full-set diff; removed/amount-changed pairs un-apply first), **`settleOrderCreditsInTx(tx, orderId)`** (idempotent shrink-then-apply reconcile of intents → payments across the order's non-VOID invoices, base before -R# siblings; re-reads rows between passes — stale-snapshot under-apply was a caught+fixed review finding), **`unapplyFromInvoice`** (Serializable; restores pair + reduces/deletes the intent), **`updateCreditNote(id,{reason?,expiresAt?})`** (reason editable any status — makes reason edits real; expiresAt only ISSUED). `autoApplyOldestCreditsInTx` gained `opts.excludeCreditNoteIds` (send-time sweep skips EXPLICIT-amount order selections). Controller += `POST :id/unapply {invoiceId}` + `PATCH :id` (OPERATOR). Description renders AT READ TIME via `payments[].creditNote.reason` / `orderCreditNotes[].creditNote.reason` relations — never copied text. `prisma-mock.ts` += `orderCreditNote: modelProxy()`. Wiring: `createSplitInvoices` settles at the end of its creation tx (**payment rows stamp `tenantId` explicitly — fire-and-forget delivery path was tenant-orphaning them, caught+fixed**); `send`/`sendEmail` pass exclusions + **stuck-SENT fix** (fully-pre-credited draft now lands PAID via post-auto-apply recompute); `deletePayment`/`voidPayment` REFUSE CREDIT_NOTE (point at unapply); **ADVANCE orphan FIXED (follow-ups PR): both paths inline-restore `AdvancePayment.balance += payment.amount` in the same tx (advances have no status machinery — a balance increment is the complete inverse of `applyAdvancePaymentToInvoice`'s decrement); deletePayment's restore is gated `payment.status !== "VOID"` (void already restored — the void-then-delete double-credit was a caught+fixed review finding); mobile `paymentActionFlags(status, method?)` hides Void for CREDIT_NOTE**; orders: `AppliedCreditNoteDto[]` on create/sale/update-items DTOs (staff-gated on edit), create() validates up-front + post-commit sync+settle, **controller merge branch passes appliedCreditNotes through (silent-drop on merge was a caught+fixed review finding)**, updateOrderItems ALWAYS settles after reconcile routing (incl. partial-billing skip), changeStatus DELIVERED best-effort settle (warn-only; send catches up).
  - ⚠️ **F07/B108 correction (2026-09-01):** "send catches up" was FALSE as written. `send`/`sendEmail` exclude EXPLICIT-amount order selections from `autoApplyOldestCreditsInTx` (that is the `excludeCreditNoteIds` above), so the documented catch-up deliberately skipped exactly the credits a swallowed delivery settle was responsible for — an operator-attached credit with an explicit amount could be applied by nothing. Both methods now call **`settleOrderCreditsInTx(tx, updated.orderId)` BEFORE computing `explicitIds`**, which makes the catch-up real; the exclusion is deliberately KEPT so the oldest-first sweep still cannot override an explicit amount, and settle clamps so money never moves twice. The delivery settle itself retries 3× (100/300ms) and logs at ERROR on final failure — delivery still never fails on it.
  - **B315 fix (2026-09-13, F39, money):** `settleOrderCreditsInTx`'s SHRINK pass (a) only ever unwound `CREDIT_NOTE` payments — the `deletePayment`/`voidPayment` ADVANCE-orphan fix noted above never covered THIS third path, so an applied ADVANCE whose invoice then shrunk (order edit) just stayed "spent" against a total that no longer existed, silently losing the customer's prepaid dollars. New private `restoreAdvanceFromPaymentInTx` (mirrors `restoreCreditFromPaymentInTx`'s payment-row shrink/delete, recompute-invoice-status, and commission-resync steps) runs in the SAME shrink loop right after the CREDIT_NOTE pass, sharing the same `excess` budget (credit notes first, then advances — an arbitrary but stable priority since both fully cover their own excess before the other is touched). **`AdvancePayment.balance` itself is restored via ONE atomic raw UPDATE** — `SET balance = LEAST(amount, balance + ${restore}) WHERE id = ...` — never a `findUnique`-then-`update` read-modify-write: an Opus review caught that the original draft used exactly that read-then-write shape on the SAME column B310 (above) had just closed the identical lost-update race on, from the apply side. Spec: `credit-notes.service.spec.ts` `settleOrderCreditsInTx` → "an invoice total dropped below an applied ADVANCE restores the excess to the wallet's AdvancePayment.balance" (asserts the raw SQL shape and that `advancePayment.update` is never called, not just the resulting number).
- **CANCEL / VOID / DELETE now give the credit back (2026-08-13, money-critical)** — a credit applied to an order was consumed FOREVER once the order was cancelled: cancel voided only the pending DRAFT (`findOpenOrderDraft`), the CREDIT_NOTE payments survived on the dead invoice with `amountUsed` still up, and `settleOrderCreditsInTx` filters VOID invoices out, so no path could ever return it. `deleteOrder` was worse — it hard-deleted those payment rows without decrementing `amountUsed` (credit gone, no trace). A SENT invoice on a cancelled order also stayed live and collectible.
  New primitives: **`releaseOrderCreditsInTx(tx, orderId)`** / **`releaseInvoiceCreditsInTx(tx, invoiceId)`** over a shared private `releaseCreditsInTx(tx, invoiceWhere)` — restores every non-VOID CREDIT_NOTE payment in scope via `restoreCreditFromPaymentInTx`, **deliberately WITHOUT an invoice-status filter so already-VOID invoices are swept** (that filter is exactly what stranded the money; safe to re-run because each restore DELETES the payment row it consumed), and the order-scoped one also `deleteMany`s the `OrderCreditNote` intents so a later settle can't re-apply what was just returned. **`previewOrderCreditRelease(orderId)`** is its read-only twin for the confirmation UI. `restoreCreditFromPaymentInTx` now **REVIVES** a note whose `expiresAt` has passed (clears the stale expiry; a FUTURE expiry is untouched) — owner decision 2026-08-13, since money handed back to an expired note is invisible to every open-credit reader.
  Invoices: **`externalPaidOn(payments)`** splits WALLET money (CREDIT_NOTE/ADVANCE — returnable) from EXTERNAL money (cash/check/card — software can't un-take it); **`releaseWalletPaymentsInTx(tx, invoiceId)`** returns credits + re-credits `AdvancePayment.balance`; **`voidInvoiceInTx(tx, id, orderId)`** is the guard-free core (status→VOID, `adjustInvoicedQtyForInvoice(-1)`, ledger reverse). **F09/B66 (P3):** after the commission sync and before the final read, `voidInvoiceInTx` caps the credit notes the invoice sourced (`tx.creditNote.findMany({ where: { invoiceId, status: { not: CreditNoteStatus.VOID } } })`, in-loop `invoiceId` re-check): unused (`amountUsed ≤ 0.001`) → `status: VOID`; partly used → `amount = roundMoney(amountUsed)` + `status: APPLIED`. Never deletes an `InvoicePayment`, never writes `amountUsed` (R6). Pinned by REG-B66 T9/T10/T11 in `credit-notes/credit-notes.wallet-integrity.spec.ts`. `voidInvoice` now blocks ONLY on external money (was: any PAID/PARTIAL) and releases wallet money first, so a credit-only-paid invoice is voidable instead of dead-ending. **F09 lens A5:** `voidInvoice`'s `tenantTransaction` now runs with the same options as the orders-side void caller (`{ isolationLevel: "Serializable", timeout: 15_000 }`, matching `orders.service.ts`'s per-invoice void loop) — at the default READ COMMITTED, a concurrent `applyToInvoice`/`settleOrderCreditsInTx` on a _different_ invoice could raise a sourced note's `amountUsed` between the cap's `findMany` and its blind full-column `update`, landing `amount < amountUsed`.
  Orders: `changeStatus(CANCELLED)` calls **`assertCancellableOrThrow`** BEFORE the status write (a refused cancel leaves the order untouched), then in ONE Serializable tx releases credits and voids **every** live invoice. `deleteOrder` reuses the same guard + release. New **`cancelImpact(id)`** + `GET /orders/:id/cancel-impact` (OPERATOR) returns `{invoicesToVoid, creditsToRestore[{creditNoteNumber,amount}], advanceToRestore, blockingPayments, deliveredUnits, canCancel}` (**`deliveredUnits` added by F07/B56 — `canCancel` now also requires it be ≤ 0.001**) — the guard and the warning read the SAME function so they cannot disagree. Client copy lives in the `{web,mobile}/lib/cancel-impact.ts` mirrors (`describeCancelImpact`), whose `deliveredUnits` is deliberately **optional**: a client build can be older or newer than the API answering it, and an absent field must read as "no delivered goods" rather than crash the only warning shown before live invoices are voided. Specs: credit-notes (5 release + 1 preview), orders (void-all-invoices, credits-returned, cash-blocks-and-leaves-untouched).
