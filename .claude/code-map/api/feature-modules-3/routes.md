- **Driver Collect-payment now records the InvoicePayment (money-critical fix)** — `completeWithPayment`'s payment block previously looked up the invoice by a CLIENT-supplied `dto.payment.invoiceId` and decremented a **non-existent `Invoice.balance` column**. But mobile always sent `invoiceId: undefined` (Order has NO `invoiceId` scalar; the run/stop payload never carries one), so the guard was always false and **every driver-collected cash/check/card payment silently vanished** (stop completed, customer told "paid", no `InvoicePayment` row). Fix = new tx-safe **`InvoicesService.recordDeliveryPaymentInTx(tx, orderIds, amount, method, reconcileOrderIds?)`** that resolves the invoice SERVER-side: per delivered order ensure a DRAFT invoice (`createInvoiceFromOrder` when none), then **reconcile it to the DELIVERED quantity** (`reconcileOrderDraftInvoice(basis:"delivered")` — bills `OrderItem.deliveredQty` so short/refused lines don't over-bill), then apply the lump-sum across the orders' **PAYABLE** invoices (`DRAFT|SENT|PARTIAL|OVERDUE` — excludes VOID **and** terminal WRITTEN_OFF, so a bad-debt invoice can't swallow the cash) **oldest-first** (base before regulated `-R#` siblings), each **`FOR UPDATE` row-locked then paid FRESH** (serializes a concurrent back-office payment), capped at each remaining, **finalizing DRAFT→SENT** (recomputeStatus treats DRAFT as terminal) and recording each as an `InvoicePayment` + `recomputeStatus` over non-VOID sums — NEVER a `balance`. Refuses `CREDIT_NOTE`/`ADVANCE` (need a source-balance debit). **Delivered-basis is double-gated (adversarial-review catches): (1)** reconcile only orders in `reconcileOrderIds` — the subset ACTUALLY delivered this completion (`completeWithPayment` builds `deliveredOrderIdSet` from `dto.deliveries`' orderItems and passes it) so an order merely linked to the stop but delivered elsewhere (deliveredQty 0) is never zeroed; **(2)** the delivered-basis rebuild is **sibling-aware** — **`reconcileOrderDeliveredInvoices(orderId, tx)`** rebuilds EACH of the order's open DRAFTs from ONLY its own lines (the `InvoiceItem.orderItemId` provenance `createSplitInvoices` established) at `deliveredQty`, so a regulated `SEPARATE_INVOICE` order's `-R#` sibling bills its delivered qty and the base never absorbs the regulated line (no double-bill); a refused line bills 0. Order tax is re-allocated across siblings by delivered subtotal (remainder to the largest → Σ==order tax on a clean delivery); each line's `invoicedQty` is SET to its sibling's delivered qty. Single-group orders are byte-identical to `reconcileOrderDraftInvoice(basis:"delivered")`. **Clean-partition GUARD (adversarial-review catch):** it fetches ALL non-void order invoices and BAILS (returns null, leaves invoices as created — never a double/over-bill) if provenance isn't a clean per-line partition — a line shared by two open drafts, or also billed by a finalized/delivery-batch invoice (reachable via `createPartialFromOrder` or a prior group-unaware `basis:"order"` reconcile); rebuilding those from a prior of 0 would double/over-bill, so the conservative full-qty bill wins there. Feeding it: `completeWithPayment`'s delivery loop writes `OrderItem.deliveredQty` per line (`REFUSED`→0 else `quantityDelivered`); mobile `payment.tsx` sends an EXACT-qty deliveries array for every line of every stop order (no `Math.round` — the DTO accepts decimals and billing is now on deliveredQty). `StopPaymentDto.invoiceId` is `@IsOptional()` (server ignores it); mobile sends `{amount, method}` only. `RoutesModule` gained an `InvoicesModule` import (acyclic). Specs: `invoices.service.spec` `recordDeliveryPaymentInTx` (10 cases) + `reconcileOrderDeliveredInvoices` (9 cases: split clean / short-pick / refused, tax invariant Σ==order total, single-group, no-draft, 2 guard-bails [shared-line + finalized-share], base-SENT-clean) + `routes.service.spec` (payment WITHOUT invoiceId → resolver called; delivered subset passed). **Remaining deferrals (not double/under-bills):** (a) ~~the regulated-sales ledger is NOT re-synced to delivered qty~~ **FIXED** — the sibling-aware reconciles now re-sync the regulated-sales ledger via **`resyncInvoiceLedger(invoiceId, orderId, items, db)`** in `rebuildSiblingDrafts` (reverse the invoice's prior SALE rows via `reverseInvoiceEntries`, then `writeSaleEntries` from the rebuilt items → a short/refused regulated line reports its delivered qty, current-period). Called ONLY from the sibling-aware paths (NOT the group-unaware legacy single-draft rebuild, which would double-count a folded line vs a live sibling SALE). **`reverseInvoiceEntries` is now NET-AWARE** — it aggregates each line's remaining un-reversed net (Σ signed SALE+REVERSAL rows) and reverses only that, so a void/reconcile of a partially-RETURNED line reverses the remainder (not the full sale, not skip); a fully-reversed line nets ~0 and is skipped (double-void/full-return no-op). Fixes the old "any reversal ⇒ skip" over-report (void-after-partial-return now nets to 0). The reconcile RE-SYNC preserves prior returns: `resyncInvoiceLedger` calls `reverseInvoiceEntries({preserveReturns:true})` — which EXCLUDES return/credit-note reversals (those carrying a `returnId`/`creditNoteId`) from the remaining, cancelling only the sale-record + prior re-sync reversals, so a re-reconcile after a return nets to (delivered − returned), idempotent (a prior re-sync reversal has no returnId → counted). Void/delete keep `preserveReturns` false (reverse full net → 0). ~~REMAINING follow-up: the return/credit cumulative cap keys on `invoiceItemId`, which a reconcile rotates, so a 2nd full credit/return across a reconcile can over-reverse~~ **FIXED** — the cumulative cap in `reverseReturnEntries`/`reverseCreditNoteEntries` now keys on the **ORDER LINE** (`orderItemId ?? invoiceItemId` fallback for freeform lines), and computes the per-line remaining as the NET of ALL that line's ledger rows (Σ signed SALE+REVERSAL across old+new invoice items) so it survives the reconcile's invoiceItemId rotation — a 2nd full return/credit after a reconcile books nothing (SUM floors at 0, never negative), while a valid partial after a reconcile still nets to (delivered − alreadyReturned). Credit-note CREATION also gained a **cumulative per-line cap** (`credit-notes.service.create`: Σ prior non-void `CreditNoteItem.amount` per `invoiceItemId` + new amt ≤ line subtotal) so a multi-line invoice's under-credited-line slack can't let another line be over-credited past its subtotal (the header invoice-total cap alone missed this). Single-group non-SEPARATE regulated edits via the legacy path remain unsynced (pre-existing); (b) ~~the `basis:"order"` reconcile double-bills split orders on the edit/merge paths~~ **FIXED** — `reconcileOrderDraftInvoice` is now sibling-aware for splits via **`reconcileSplitOrderDrafts`** (partitions CURRENT lines by category through `groupOrderLinesForInvoicing` — handles edits/added lines, unlike provenance — matches each group to its draft, rebuilds via the shared **`rebuildSiblingDrafts(order, pairs, basis, db)`** core also used by the delivered path; bails to the untouched legacy single-draft rebuild for single-group / finalized-present / count-mismatch / ambiguous-category, so single-group stays byte-identical). Specs: `reconcileOrderDraftInvoice — split order (basis:order) sibling-aware` (4 cases: no-double-bill, edit-added-line billed on base, single-group→legacy, finalized→legacy bail); (c) when the clean-partition guard bails (operator partials / a finalized invoice on the same line) the split order bills full ordered qty (conservative over-bill on a short-pick, never a double). **R1 post-delivery edit resync:** new **`resyncOrderInvoicesForEdit(orderId, tx?)`** (called by `updateOrderItems` for OFD/PARTIALLY_DELIVERED/DELIVERED edits, in its own `tenantTransaction`) rebuilds the order's FINALIZED / PAID / delivery-batch invoice(s) IN PLACE at **basis "order"** (the edited order qty — the only basis that survives the replace-all edit paths, which reset `deliveredQty`; correct for fully-delivered/OFD, and a documented "edit re-bills the edited qty" semantic for the short-pick case). Maps each order line → the invoice already billing it (via `InvoiceItem.orderItemId`), assigns NEW/unprovenanced lines to the **primary** invoice (the lone open draft, else earliest), and rebuilds via the shared **`rebuildSiblingDrafts(..., {preserveStatus:true})`** — which now, when `preserveStatus`, KEEPS payments and sets `status = recomputeStatus(Σ non-VOID payments, newTotal, dueDate, currentStatus)` instead of forcing DRAFT (an open draft stays DRAFT/terminal; a paid invoice shows the new balance: up→PARTIAL, down→PAID-overpaid). Re-syncs the ledger + resets each billed line's `invoicedQty` (removed/cancelled lines cleared to 0). **BAILS (null, writes nothing)** if a line is billed by two invoices, or any invoice line has no `orderItemId` provenance (never double-bills). Specs: `invoices.service.spec` `resyncOrderInvoicesForEdit` (8 cases: null-no-invoice, SENT rebuild+keep-payment→PARTIAL, PAID edited-down→PAID, VOID-payment-excluded, new-line-on-primary, ledger re-sync, 2 bails) + `orders.service.spec` (DELIVERED edit routes to resync, no revert, no throw-on-payment).
- **F05 — driver at-door money truth and run settlement (B49/B83/B148/B152/B167, PR #TBD).** Five changes that share one cause: the run payload never carried the billed line money, so every driver screen re-derived it. (1) **G7 — `RUN_LINE_ITEMS_SELECT`** (`routes.service.ts`, declared directly above `RUN_STOP_INCLUDE`) is now the ONLY run-read lineItems select: one const referenced by `RUN_STOP_INCLUDE`, `findOneRun`'s main query and its unlinked-orders fallback (three copies of the same literal before), carrying `subtotal`/`boxes`/`pieces`/`unitsPerBox` on top of the old six fields. **F10/F11/F12/F22 consume this const — extend it, never re-inline it.** `getRunPackingList`'s narrower include-only shape is deliberately NOT part of it. (2) **`recordDeliveryPaymentInTx` no longer discards the residual** — see the bullet above: it returns `excess`/`advancePaymentId` and books over-collection as an `AdvancePayment` (single-customer guarded; `reference` = **`RUN:<runId>:STOP:<stopId>`, a load-bearing token** `getRunCashCollections` matches by prefix). The zero-payable-invoice path (all invoices already PAID — the post-`reopenStop` re-collection case) used to drop the WHOLE amount and now advances it. (3) **`RunDeliveryDto.productId`** — the mobile payload always sent it and the global `forbidNonWhitelisted` pipe 400'd **every** stop completion; the DTO now accepts it and both `deliveryMutation.create` sites persist it (previously null, which also left `reopenStop`'s `mutation.productId`-gated stock restore dead). (4) **Server cash truth** — private `getRunCashCollections(runId, startedAt?)` sums CONFIRMED (`invoices/payment-predicates` `CONFIRMED_PAYMENT`) CASH/CHECK `InvoicePayment`s via `invoice.order.routeRunId` windowed on `paidAt >= startedAt`, plus RUN-referenced advances; surfaced as `collectedPayments` on `findOneRun` always and on `findAllRuns`/`findMyRuns` **only when driver-scoped** (batched over the page's runIds — operator-wide lists skip it deliberately). (5) **Settlement** — `POST /route-runs/:id/settlement` (`SettleRunDto`, a NEW endpoint: `PATCH :id` takes an unvalidated inline body that shipped mobile builds still use). Server computes expected itself and never trusts a client total; `varianceReason` required past a 1¢ tolerance; writes the dedicated `settlementNote`/`settlementVariance` columns (F01) — **never `run.notes`**, whose only renderer is hidden once a run closes (B167). DRIVER settles once and must own the run; OPERATOR may amend. Accepts IN_PROGRESS/COMPLETED/**CANCELLED** (a run cancelled mid-route still has cash in the truck — refusing would strand it), refuses SCHEDULED. **Three gates, because one was not enough:** `updateRunStatus` refuses COMPLETED while unsettled physical money exists, AND the **RF-016 auto-complete branches in both `completeStop` and `completeWithPayment`** apply the same predicate — they flip the run COMPLETED inside their own tx and bypass `updateRunStatus` entirely, so on the common path (last stop closed with cash in hand) the `updateRunStatus` guard alone never fires. ⚠️ **The CANCEL path and `deleteRun` are still ungated — handed to F11** (`Run cancel and skip reconciliation`), which owns those transitions.
- **F10 — reopenStop and stop-state guards (B54/B55/B71/B72/B120/B121, PR #TBD).** Six register bugs, one seam: the stop/run state machine mutated money-, stock- and compliance-bearing state without guarding WHERE a transition came from or WHO made it. (1) **B54 — reopen's payment guard read a dead model.** The `transaction.findMany` check could never fire (repo-wide there is **no** `.transaction.create` writer; the live at-door writer is `InvoicePayment` via `recordDeliveryPaymentInTx`), so a paid delivery reopened freely, stranding a PAID invoice on an order the system then called undelivered — and the re-collection went unrecorded because `PAYABLE` excludes PAID. `reopenStop` now also reads `invoice.findFirst({ orderId: { in: orderIds }, OR: [status in PAID/PARTIAL, payments: { some: CONFIRMED_PAYMENT }] })` and 400s **before** the transaction opens; **the legacy guard STAYS** (historical rows must still block). The predicate is the shared `invoices/payment-predicates` `CONFIRMED_PAYMENT`, never a literal — same rule as F03/F05. (2) **B55 — the stock loop was a double-credit, deleted.** See the `reopenStop` note above: delivery writes no stock, so there was nothing to reverse; the loop permanently inflated `currentStock` and minted uncosted positive SALE rows into COGS. Its removal makes the conservation rule uniform: **creation decrements with no movement row, delivery writes nothing, reopen writes nothing.** ⚠️ Historical damage is enumerable ONLY via the pre-fix rows (`type:SALE`, `quantity>0`, `reference LIKE 'Reopen stop %'`) — that reference prefix is now load-bearing for the D4 repair flight; never reuse it for a new writer. (3) **B71 — `updateStopStatus` had no from-state guard at all**, so a COMPLETED stop could be PATCHed straight to SKIPPED, blinding `orders.service.ts`'s demotion guard (which keys on `stop.status === "COMPLETED"`). It now 409s on a COMPLETED stop and on any transition under a COMPLETED/CANCELLED run, and loads the run for **every** caller (previously driver-only). (4) **B72 — `forbiddenRunTransition(from,to)`** in `dto/update-run-status.dto.ts` is a deliberate **deny-list, not a whitelist**: only CANCELLED→COMPLETED and COMPLETED→SCHEDULED are refused, same→same stays legal (idempotent retries). ⚠️ **CANCELLED is deliberately NOT absorbing** (narrowed in review): the un-cancel (CANCELLED→SCHEDULED/IN_PROGRESS) is the ONLY recovery an accidentally cancelled run has — `deleteRun` refuses any run carrying a `deliveryMutation`, `reopenStop` refuses a cancelled run, and the dispatch sweep needs `routeRunStopId: null`, which F11's `releaseUndeliveredOrders` now clears inside the cancel transaction — see the F11 bullet below. WHO may un-cancel is gated in `updateRunStatus`, not in the matrix: a DRIVER caller on a CANCELLED run gets `ForbiddenException("This run was cancelled — ask your operator to restart it.")`, so a stale device cannot resurrect a called-off run by replaying "start run". Censused first — web sends only CANCELLED, mobile sends IN_PROGRESS/COMPLETED, and an operator SCHEDULED→COMPLETED backfill is spec-pinned; a whitelist would have broken all three. COMPLETED→IN_PROGRESS stays allowed **deliberately**. Ownership: DRIVER callers must match `run.driverId` in `updateRunStatus`, `completeStop` **and** `completeWithPayment` — the latter two fetched the driver row and never compared it, and the check now sits before POD ingest and before the tx opens, so a hijacker's capture is never stored. (5) **B120 — reopen nulled the only pointers to stored POD artifacts** (`signatureUrl`/`podPhotoUrls` are storage keys since #477) with no deletion anywhere, orphaning regulated-delivery evidence. It now writes an `AuditLog` row (`action: "route_stop.reopened"`, entityType `RouteRunStop`) carrying the discarded capture **inside the same transaction** — evidence stays recoverable and the objects stay referenced; storage is deliberately NOT deleted. That row is also the forward-looking reopen trail the pre-fix era lacked. The same reset also appends `{archivedAt, signatureUrl, podPhotoUrls, reason:"reopen"}` to `RouteRunStop.podHistory` — the column F01 declared for exactly this write: the audit row is the who/when trail, `podHistory` is the stop-local archive a read surface joins to without an AuditLog query (nothing is appended when a reopen displaces no pointers, e.g. a SKIPPED stop). (6) **B121 — `attachPodArtifact` took no user at all** and overwrote `signatureUrl` unconditionally for any new artifactId, so any in-tenant caller could substitute a completed regulated stop's compliance signature months later. It now takes `user: JwtPayload` (controller passes `@CurrentUser`), applies the driver-run binding **before** the idempotent read, and 409s a `kind:"signature"` write on a COMPLETED stop that already has one. Photos stay appendable and the same-artifactId offline replay still returns the stored artifact. Its sibling READ `getStopPod` (`GET .../pod`) takes `user` and carries the same binding — it presigns the signature and every POD photo, and `RouteRun.driverId` is mutable via `updateRun`, so an unbound read left a reassigned driver pulling that evidence forever while the write was blocked. **NOT F10's:** `deleteRun`/`deleteRoute` gates remain open.
