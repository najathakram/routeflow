## #4126 `c213966381` inline returns capture in one transaction (SA-1090 A-1, IR1)

Rule: a standalone STORE_CREDIT inline capture mints its credit note in the same transaction as the return, so a failed mint rolls the whole capture back (no return, no restock, no half-done credit) and a same-key retry starts clean.

- `returns/inline-returns.service.ts`: `capture()` runs `tenantTransaction` with `{ timeout: INLINE_CAPTURE_TX_TIMEOUT_MS }` (new export, 15 s, the budget the order paths use). Inside it, after `lockCustomerInTx`, a REFUND capture calls `captureInTx` (`minted: null`, it only stores its intent); a STORE_CREDIT capture calls `captureAndIssueInTx(tx, dto, user, { capIntentToOrderBalance: false })`. `captureAndIssueInTx` gains that option (default `true`, the order create/edit path); the standalone intent stays the whole credit, as `issueCredit()` wrote it.
- Busy path: an expired transaction (`isTransactionExpired`, P2028), a lock wait that gave up (`isLockUnavailableError`, 55P03) or a conflict / deadlock (`txConflictState`: P2034, 40001, 40P01) now throws `refundBusy()` (retry with the same key); nothing was written. Imports from `returns/standard-refund-claim`, `common/db-locks`, `common/tx-retry`.
- After commit, `emitCreditNoteCreated` fires once for a fresh mint (never from inside the transaction). The old "stuck RECEIVED row" re-issue stays, but only for a replay of an older capture whose credit was never minted; a fresh mint skips `issueCredit` and the reload answers with the issued row.
- Tests: `returns/inline-returns.service.spec.ts` (extended), `returns/inline-returns-source-pins.spec.ts` (new pins), `returns/inline-returns-capture-concurrency.db.spec.ts` (new, DB lane).
- Behaviour to know: a deadlock is possible by design (an order create locks Products then the RETURN number, capture takes the number then Products); holding the number through the mint widens that window, and the answer is the retryable busy error.

## #4125 `369226661b` served cash tendered, one gate for three surfaces (row 638, SA-821, F09)

Rule: `Order.counterCashTendered` is stored once and a later card retry or an on-account sale never clears it, so it is served only while the sale holds a counter-tender CASH row it could have been handed over for. Otherwise null.

A card-first sale with a cash leg still serves it, as before.
