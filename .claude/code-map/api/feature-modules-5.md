### `supplier-statements/` (PR-F, 2026-08-20 — AI statement reconciliation)

- `SupplierStatementsModule` **is** registered in `app.module.ts` (next to `VendorBillsModule`), so `GET /supplier-statements`, `GET /:id`, `POST /scan` and `POST /:id/apply` are all live.
- **model** `SupplierStatementScan` + enum `SupplierStatementScanStatus` (SCANNED|APPLIED|DISCARDED), migration `20260822000000_add_supplier_statement_scan` (**additive only** — no DROP, no data migration). Deliberately shaped like `InvoiceScan`: `fileHash` dedups a re-upload without re-calling the model, `extractedPayload` Json keeps the model's verbatim output for audit, `appliedPaymentGroupId` makes an apply reconstructable (and undoable by voiding that group). Indexes `[tenantId, fileHash]`, `[tenantId, supplierId]`, `[tenantId, status]`; back-relations on `Tenant` and `Supplier`.
- **module** imports `PrismaModule, ConfigModule, SystemConfigModule, DuplicateMatchModule, StorageModule, PlatformAdminModule, BillingModule` (PlatformAdminModule for key resolution + AI metering 2026-08-28; BillingModule for the scan endpoint AddonGuard/@RequireAddon(ocr) gate 2026-08-29); providers/exports `SupplierStatementsService` + `StatementApplyService`. **`DuplicateMatchModule` directly, never `ImportModule` or `VendorBillsModule`** — it was split out precisely to avoid the `ImportModule ↔ VendorBillsModule` cycle.
- **controller** `supplier-statements` — class-level `@UseGuards(JwtAuthGuard, RolesGuard)` + `@Roles(OPERATOR)`. `GET /` (list, `?status&page&limit`), `GET /:id`, `POST /scan`, `POST /:id/apply` (`@Body() ApplyStatementBodyDto` → `StatementApplyService.applyStatement(id, dto, user)`; `user` comes from `@CurrentUser()`, which carries both `sub` and `id`). **Field name is `files`, NOT vendor-bills' `images`** (multer matches exactly — a client sending `images` gets "No file provided"); 10 files × 25MB via `FilesInterceptor` plus a hand-rolled 60MB aggregate guard (multer's limit is per-file only), and a mime allowlist of jpeg/png/gif/webp/heic/heif/pdf.
- **service** `scanStatement(files, scannedById)` mirrors `vendor-bills.service.ts`'s `scanInvoice` closely — read that entry first, the differences are the point:
  - `hashFile(buffers)` (`../vendor-bills/invoice-scan.fingerprint`) → a prior non-DISCARDED scan with that hash returns immediately, **re-running the matcher against today's bills** (`rematchStoredScan`) but never re-calling the model.
  - **`STATEMENT_MODEL = "claude-sonnet-5"` is its own constant**, separate from the invoice scanner's, so the two can diverge: statements vary far more by supplier and a misread here moves money.
  - `new Anthropic({ apiKey, maxRetries: 0 })` + `{ timeout: 110_000 }`. **`maxRetries: 0` is load-bearing** — the SDK default would give each retry its own fresh 110s window and blow past the web client's 120s axios ceiling.
  - Key (2026-08-28): `platformConfig.resolveAnthropicKey(systemConfig.get("anthropic.apiKey"))` — tenant → platform → env; missing everywhere ⇒ plain `BadRequestException` with **no** `code`. Each model call records an `AiUsageEvent` (`ocr.supplier_statement`; tokens on success, `success:false` on call failure).
  - Same four typed error codes as the invoice scanner (401/403 ⇒ 400 `AI_KEY_INVALID`; other non-retryable 4xx excl. 429 ⇒ 400 `AI_SCAN_REJECTED`; 429/5xx/network ⇒ 503 `AI_UNAVAILABLE`; non-text block or `JSON.parse` throw ⇒ 422 `AI_PARSE_FAILED`). Same HEIC/HEIF → `sharp().rotate().jpeg({quality:85})` conversion with a failed page pushed to `skippedPages` and disclosed in `notes` rather than failing the upload; same ` ```json ` fence strip then `{[\s\S]*}` regex fallback before `JSON.parse`.
  - Helpers: `normalizeLines` (coerces `kind` to `STATEMENT_LINE_KINDS`, amounts to numbers), `resolveSupplierId` (name → tenant supplier), `matchAgainstBills`/`fetchMatchableBills`, `persistScan` + `storeScanFiles` (`supplier-statements/<scanId>/<n>.<ext>` via `StorageService`). Also `listScans`, `getScan`.
  - **`rematchStoredScan` also returns `appliedPayments`** (via `fetchAppliedPayments`, never throws): the `BillPayment` rows sharing the scan's `appliedPaymentGroupId`, each `{ id, billId, billNumber, amount, impliedPaid, paidAt }`. That is the read half of AC 9 — without it a scan reopened after the session that applied it shows a bare "already applied" date. `impliedPaid` is derived from the `STATEMENT-IMPLIED-` reference prefix `statement-apply.service.ts` stamps, the only thing distinguishing the two loops' rows.
- **`statement-matcher.ts` — PURE and deterministic; no Prisma import, no SDK, no model involvement.** Money-critical logic lives here specifically so it is auditable and unit-testable with zero mocks. Exports `MatchTier` (`EXACT_REF|FUZZY|UNMATCHED`), `MatchableBill`, `StatementLineMatch`, `MatchStatementLinesOptions`, `matchStatementLines(lines, bills, options)`.
  - Uses **`normalizeInvoiceNumber`** from `import/duplicate-match.service` (that is the real export name — the plan called it `normalizeNumber`).
  - Tolerances: amount `0.005`, date `±1 day`, closing balance `0.01`. VOID bills are filtered internally **whatever the caller passes**.
  - `preChecked` is true **only** for an `EXACT_REF` whose amount also agrees — an exact ref with a differing amount is still `EXACT_REF` (it IS the right document) but never pre-checked, and FUZZY is never pre-checked.
  - Collision resolution is **global, not per-line**: every (line, bill) opportunity is sorted by tier → amountDiff → dateDiff → lineIndex → billId and claimed greedily, so a bill is the PRIMARY match of at most one line and the same input always resolves identically. **`candidates` is deliberately left un-deduped** so the review screen's picker can still offer a bill another line won.
  - **Closing-balance sanity guard:** if `opening + Σ signed(lines)` doesn't reconcile to the stated `closingBalance`, **every** row is demoted out of `preChecked`. `signedAmount` treats INVOICE as +, PAYMENT/CREDIT as −, and passes ADJUSTMENT through with the model's own sign.
- **`statement-apply.service.ts`** — `StatementApplyService.applyStatement(scanId, dto, user)`, one `tenantTransaction`, PR-E's payment mechanics duplicated rather than importing `VendorBillsModule` (cycle). Exports the `ApplyStatement{ConfirmedLine,ImpliedPaid,Dto}` / `AppliedStatementPayment` / `ApplyStatementResult` shapes. Idempotency is checked **twice** — before the tx (cheap) and again inside it (closes the back-to-back race), mirroring `commitStockCountSession`; an already-`APPLIED` scan returns its stored `appliedPaymentGroupId` and writes nothing. Per confirmed bill, in order: bill exists → `bill.supplierId === scan.supplierId` → **`status !== "VOID"`** (the one status comparison; a void bill keeps `totalOwed` and the recompute would resurrect it) → a statement line actually backs it → `amount ≤ that line's own amount` → `amount ≤ totalOwed − Σ payments`. **The statement-line cap is re-derived by re-running `matchStatementLines` against CURRENT bills**, never a persisted match — the scan row stores only the raw parsed statement. Any violation rejects the whole apply. `impliedPaid` is a separate input, validated separately, never folded into `confirmed` — and rejects **`DRAFT` as well as `VOID`** (marking a never-received draft PAID would lock it out of edit/revert/delete and the needs-mapping queue permanently).
  - **`resolveBackingLine(matches, billId, lineIndex?)`** picks the capping line. It searches **every line's `candidates`**, not just `match.billId` — the review screen's picker offers all candidates, so a primary-pick-only lookup 400s on any hand-picked alternative and fails the whole apply. Optional `lineIndex` (sent by the web client) says which row the operator used and the bill must be a candidate of THAT line; without it, the bill's primary-pick line wins, then the first line listing it. The same `billId` twice in `confirmed` is rejected up front (one bill, one line).
  - **NEVER mints `SupplierCredit`** — `ApplyStatementResult.excess` is always `0` (kept only for wire parity with `recordSupplierPayment`). PR-E's excess is `dto.totalAmount − allocatedTotal`, i.e. real cash minus allocations; this DTO has **no cash total**, and every amount is already capped at the bill's outstanding, so a surplus is impossible. Banking `line.amount − confirmed` would fabricate spendable credit from an accounting discrepancy and let the tenant under-pay the supplier.
  - **`paidAt` is left to the column default (`now()`)**, never `line.date` — the matched line is an INVOICE line, so its date is the supplier's issue date; backdating would move cash into a closed period (`bookkeeping.getCashFlow` buckets by `paidAt`).
  - The tx opens with **`SELECT id FROM "SupplierStatementScan" … FOR UPDATE`** before re-reading status: `tenantTransaction` is READ COMMITTED, so without the lock two concurrent Applies both see `SCANNED` and both write a full payment set under different groups.
- **`dto/statement.dto.ts`** — interfaces `ScanStatementFile`, `StatementLineKind` + `STATEMENT_LINE_KINDS`, `ParsedStatementLine`, `ParsedStatement` (internal shapes, no validation — the scan body is multipart), **plus the `class-validator` classes for the one JSON body**: `ApplyStatementBodyDto` (`confirmed` `@ValidateNested`+`ArrayMaxSize(500)`, optional `impliedPaid`, optional `notes` `@MaxLength(1000)`+`@StripHtml`), `ApplyStatementConfirmedDto` (`@IsUUID` billId, `@IsNumber`+`@Min(0)` amount, optional `@IsInt`+`@Min(0)` `lineIndex`), `ApplyStatementImpliedPaidDto` (`@IsUUID(…,{each})` billIds). It is the validated wire form of the service's `ApplyStatementDto` interface — the controller call site is what compiler-enforces the two staying identical.
- **specs** `statement-matcher.spec.ts` (pure, no mocks), `supplier-statements.service.spec.ts` (hash short-circuit skips the model; each of the four error codes), `statement-apply.spec.ts` (double-apply writes once; over-cap rejects and writes nothing; **no credit is ever minted from a line/confirmed gap**; `paidAt` never backdated; a non-suggested candidate is accepted and a wrong `lineIndex` rejected; the same bill twice rejects; an implied-paid DRAFT rejects; `FOR UPDATE` precedes the in-tx status re-read; one payment group ties the rows).
- **`matchable-bills.ts` (NEW, F16 2026-09-07, #656 — B117/B169):** `fetchMatchableBills(prisma, supplierId, normalize?)` is the ONE shared source for the candidate-bill pool both `SupplierStatementsService` and `StatementApplyService` used to each carry as a byte-identical private `take:500`/no-`orderBy` query — a supplier with >500 open bills silently lost every bill past the 500th to whatever order the DB returned rows in, so a real match for a newer bill came back UNMATCHED. Now: `where: {supplierId, status:{not:"VOID"}}` (unchanged — the file's own rule is never narrow further on `status`/`totalPaid`), `orderBy: [{billDate:"desc"},{id:"desc"}]` (B169 tiebreaker — `billDate` alone can collide across many same-day bills), **no `take` at all**. `normalize` defaults to the standalone `normalizeInvoiceNumber` (what `StatementApplyService` used directly); `SupplierStatementsService` passes its injected `DuplicateMatchService.normalizeNumber` instead. `matchable-bills.guard.spec.ts` (static, precedent: `common/no-bare-cron.spec.ts`) fails the build if either service file re-grows its own `take: 500` copy or a private `vendorBill.findMany` for this pool, or stops importing `fetchMatchableBills` from `./matchable-bills`.

- **REG-B106 — outcome recording, and the claim/rollback contract.** The cycle is CAS-claimed on `nextRunAt` (B9) and that same `updateMany` now stamps a PROVISIONAL outcome (`lastRunAt`, `lastRunStatus: FAILED`, `lastError: RUN_INTERRUPTED_ERROR`), so a crash between the claim and the create leaves an honest FAILED behind rather than a fresh `lastRunAt` that reads as success. SUCCESS is written LAST, after the invoice exists AND is linked. Three failure shapes, deliberately different: (1) **create throws** — nothing was billed, so the schedule is given back, but as a **compare-and-set `updateMany({where:{id, nextRunAt: <the ADVANCED value this run's own claim wrote>}})`**, never a plain `update({where:{id}})`; `count === 0` means a newer claimant (Run Now, or the next tick) owns the row and may already have billed the cycle, so it logs at warn and **writes nothing**, and the original error still rethrows. (2) **link/finalize throws after the invoice exists** — the cycle IS billed: `nextRunAt` is never restored and `lastError` is rewritten to `RUN_UNFINALIZED_ERROR` so operator surfaces suppress the retry hint; the error is not rethrown (the caller gets the invoice).
