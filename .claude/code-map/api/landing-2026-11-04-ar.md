## #4189 `5f92cf807e` Undo rebuilds the order's open draft (SA-1098 Undo gap, B827)

- New `invoices/undo-draft-rebuild.ts` (`rebuildDraftsAfterUndo`): `routes/routes.service.ts` `reopenStop` calls it in the same transaction that deletes the stop's delivery evidence (after the delivered-quantity recompute, before the proof columns are archived). With no evidence left on the order the draft goes back to the ORDER basis; with another stop's evidence left it goes to the DELIVERED basis. Before this, Undo left the draft on the last visit's numbers, and an issued invoice is never restated by the next completion, so it stayed under-billed.
- Only an open DRAFT follows the Undo; an issued invoice and a deposit mirror are untouched. Orders go in id order so two Undos that share orders take their locks in one sequence (order row, then the order's invoices id-sorted, SA-760 R-1). `invoices/invoice-partition.ts` is touched so a split order's drafts are rebuilt per group and an unreadable partition is left as it was.
- Tests: `invoices/undo-draft-rebuild.spec.ts`, `routes/driver-stops-web.db.spec.ts` (UG-1 to UG-5 and D-44, D-52 to D-54), `routes/routes.reopen-cancelled-lines.spec.ts`, `routes/routes.service.stop-state-guards.spec.ts`.

## #4188 `e78cd762ba` the run settlement writer (SA-1098 PR-S, A-1 and A-6)

- New `routes/run-settlement.ts` (`settleRunInTx`): `routes.service.ts` `settleRun` does everything after its role and ownership checks in one `retryRouteTx` transaction. Stop rows are locked first (`lockRunStopsForTerminalStatus`), the run is re-read, then (1) a driver with a note on record gets `RUN_ALREADY_SETTLED`, (2) an IN_PROGRESS run with a stop not COMPLETED or SKIPPED gets `RUN_HAS_STOPS_LEFT` for every role, (3) the expected figure is read through `tx`, (4) a missing variance reason gets `RUN_VARIANCE_REASON_REQUIRED`, (5) the write. A count above `SETTLE_MAX_COUNT` gets `RUN_COUNT_TOO_LARGE` (the column is DECIMAL(10,2); it was an uncoded 500). When the run already has a note, the new note ends with `Earlier count:` and the whole old note.
- `reopenStop` re-reads the run through `tx` after its stop update and uses that for the settlement drop and the status; `updateRunStatus` stamps `completedAt` only when the run is not already COMPLETED.
- The money rule is one function set in `packages/pricing/src/run-settlement.ts` (`expectedPhysicalCash`, `computeVariance`, `isReconciled`, `varianceNeedsReason`, `shouldForceSettlement`, `SETTLE_MAX_COUNT`), imported by api, web and mobile (`apps/mobile/lib/run-settlement.ts` re-exports); `packages/pricing/src/no-mirrors-run-settlement.spec.ts` pins it. The new codes live in `common/api-error-codes.ts`, `packages/types/api/error-codes.ts` and the mobile jest stub (parity spec). The old message text for a missing reason is word for word the old one, because the native screen matches `includes("varianceReason")`.
- `common/order-lock-callers.guard.spec.ts` lists `run-settlement.ts#settleRunInTx` (stop rows then the run, no Orders). Office cash counted as run cash is a follow-up that needs a migration; not built.
- Tests: `routes/run-settlement.db.spec.ts` (rows SE-1 to SE-4, SE-6 to SE-11, SE-14, SE-15 and SE-18 in the file, real Postgres), `routes/routes.service.spec.ts`, `routes/routes.service.stop-state-guards.spec.ts`, `packages/pricing/src/run-settlement.spec.ts`.
