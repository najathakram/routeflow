## Counter day close and Z report (SA-750r3): one window per (tenant, register)

- `orders/counter-sale/day-close/day-close.controller.ts` (NEW) `CounterDayCloseController`, base `orders`, OPERATOR (TENANT_ADMIN through the hierarchy), every route refused `COUNTER_SALES_DISABLED` for a tenant with counter sales off: `GET counter-sale/day-close` (`state`: last close, sales since, live preview), `GET counter-sale/day-close/latest`, `GET counter-sale/day-close/:id`, `POST counter-sale/day-close` (`close`, also the re-close), `POST counter-sale/day-close/:id/reopen`, `POST counter-sale/day-close/:id/report` (resend the Z email). Registered in `orders.module.ts` with `CounterDayCloseService` and `EmailModule` (a separate controller because the counter-sale controller's constructor is pinned by specs).
- `day-close/day-close.service.ts` (NEW) `CounterDayCloseService`: `state(rawRegisterKey?, now?)`, `close(dto, user) -> DayCloseSnapshot`, `reopen(id, user)`, `resendReport(id)`, `closeById(id)`, `sendReport(row, {manual})`; exports `Z_REPORT_MILESTONE` ("ZREPORT"), `Z_REPORT_ENTITY` ("CounterDayClose"), `zReportKey(row) = <id>:<closedAt ISO>` (a re-close sends a corrected report). The close tx takes the EXCLUSIVE counter-close lock, reads its cutoff from the database clock AFTER the grant, recomputes every figure (a client `counted` or `expected` is never read), stores a snapshot (totals, never rows or customer names), and sends the Z email after commit; a send failure never fails the close. 409 `DAY_ALREADY_CLOSED` on a first-close race; a re-close records who re-closed; reopen writes the `COUNTER_DAY_CLOSE_REOPENED` audit row (`platform-admin/audit-actions.constant.ts`) inside its tx with the old snapshot as meta.
- `day-close/day-close.dto.ts` (NEW) `DayCloseQueryDto {registerKey?}`, `DayCloseDto {openingFloat, denominations, notes?, registerKey?}`; `day-close/day-close-register.ts` `parseRegisterKey(raw)` (absent or blank is the default register), `registerOrderWhere(registerKey)` (`COALESCE(registerKey,'main')`), re-exports `REGISTER_KEY_PATTERN` (home: `@routeflow/pricing` `counter-register.ts`); `day-close/day-close-lock.ts` `lockCounterCloseExclusive(tx, ...)` (`SET LOCAL lock_timeout` first), `isLockTimeout`, `isUniqueViolation`.
- `day-close/day-close-facts.ts` (NEW) `readWindowFacts(db, ...)` and `countSalesSince(...)` reuse Today's-sales where-builders with the register filter (L-167; a VOID invoice alone drops its payments, so written-off cash stays in the drawer); `day-close/day-close-fold.ts` (NEW, pure) `foldDayClose(facts: WindowFacts) -> DayCloseFold`, `expectedCashOf(...)`, types `WindowPayment`, `WindowFacts`: a payment is till money only when `isCounterTenderRow` says so (a counter order's ungrouped row or a POS pickup hand-over's own-group row); anything else shows apart as `notAtTill`; store-credit applications are not money in; a refund with no recorded tender is never cash.
- `day-close/z-report-email.ts` (NEW) `buildZReportEmail(input) -> ZReportEmail`, `zMoney(n)`: built from the stored snapshot only, sections and order from `dayCloseZSections` (`@routeflow/pricing`, the same builder the web renders); email kind `Z_REPORT` (`email/email-kinds.ts`, `packages/types/api/messaging-delivery.ts`). `day-close/testing/fake-day-close-db.ts` (test support, no entry) `makeFakeDayCloseDb(opts)`, `TENANT`, `OTHER_TENANT`.

## Closed-day guards: a closed day's totals never move

- `common/db-locks.ts`: `withAdvisoryLock` opts +`sharedAlso: {family, key}` (a SHARED advisory lock taken on the SAME pinned connection right after the first lock and released before it, even when `fn` throws; a typo family or empty key throws `TypeError`); `SHARED_LOCK_FAMILIES = ["counter-close"]`. Lock order: counter-tender, then counter-close (shared), then Order/Invoice rows.
- `returns/counter-close-lock.ts` `counterCloseKeyOf(tenantId, registerKey)`, `registerKeyOfOrder(order)` (a counter order's key, null reads as `main`; a non-counter order is not a till event), `dbClockNow(tx)`, `lockCounterClose(tx, ...)` (SHARED form), `COUNTER_DEFAULT_REGISTER`; `returns/counter-close-window.ts` `counterWindowClosed(db, tenantId, registerKey, at)` (a reopened close is open again), `dayClosedConflict()` (409 `COUNTER_SALE_DAY_CLOSED`), `assertCounterWindowOpen(db, tenantId, registerKey, at)`. `returns.service.ts` and `inline-returns.service.ts` call it with the refund's `refundedAt`.
- `orders/counter-sale/counter-tender-window.ts` (NEW) `pickupRegisterOf(order, requested?)` (stamped `Order.registerKey`, else the request's, else `main`), `counterCloseShared(tenantId, order, register?)` (the `sharedAlso` argument), `counterTenderPaidAt(db, tenantId, order, register?)` (the database-clock instant, refused inside a closed window; undefined for a non-till order). Used by `counter-sale.service.ts` (the tender: the allocation is made first and the closed-day check runs before ANY write and before the cash-tendered write), `pickup-complete.service.ts` (EVERY hand-over tender takes the shared lock; the cashier is stamped after the tender section by `stampSoldBy`, only on an order with no cashier, so a refused hand-over stamps nothing) and `counter-sale-void.service.ts` (void also takes the shared lock and refuses 409 `COUNTER_SALE_DAY_CLOSED` at step 7b when the sale or a tender it reverses is dated inside a closed window).
- `orders/counter-sale/counter-tender-row.ts`: `isCounterTenderGroup(orderId, paymentGroupId, order)` and `isCounterTenderRow(...)` now REQUIRE the order kind (`TenderOrderKind {counterSale?}`): a counter sale accepts ungrouped rows or its own `pickupTenderGroupId`; any other order (a POS pickup hand-over) accepts ONLY its own `pickupTenderGroupId(orderId)`. `orders/counter-sale/counter-till-cash.ts` (NEW) `isTillCashRow(...)` = a counter tender row whose method is CASH, the only payment that moves a closed report's expected cash. `orders/counter-sale/pickup-complete.dto.ts` +`registerKey?` (`IsRegisterKey`).
- `invoices/counter-payment-guard.ts` (NEW) `counterPay = {scope, lock, assertOpen, assertDatesOpen, assertPaymentOpen, assertDatedOk, assertEditDated}`, `CounterPaymentScope`, `PaymentRowState`, `CounterPayOpts {tillLockHeld?}`, `TILL_LOCK_HELD`: the payment-edit paths (`invoices.service.ts` `recordPayment`, void, delete and update payment, check bounce; `bookkeeping/bookkeeping.service.ts` payments) of a counter sale or a POS pickup order join the close (lock order counter-close shared, then Invoice FOR UPDATE; the scope is read BEFORE the tx; any other invoice gets null and every helper is a no-op). An undated card or check takes the database clock; a till-CASH row dated before a standing close is refused 409 `DAY_CLOSED_FOR_PAYMENT_DATE` (body carries `closedThrough`); the refusal is per ROW.
- `tenant/tenant-status.guard.ts` +`READ_ONLY_ALLOWED_ROUTES` (POST-only close, re-close and reopen stay allowed while READ_ONLY); superseded in Release 5. `system-config/settings.controller.ts` financial-data wipe also deletes `counterDayClose` and `counterParkedCart` rows (the close's tenant FK is RESTRICT); `testing/prisma-mock.ts` +`counterDayClose`, `counterParkedCart`.

## Overdue, reminders and statements (rows 308, 309, 318, SA-770 follow-ups)

- `invoices/invoice-balance-classify.ts` `classifyInvoiceBalance`: only an ISSUED invoice (`OPEN_INVOICE_STATUSES`) can be overdue; a past-due DRAFT keeps its `balanceDue` but reads `isOverdue:false`. `invoices/invoice-detail-read.ts` `deriveInvoiceDetailFields(inv, now?, timeZone?)` and `invoices.service.ts` list rows judge overdue and the deposit's "today" in the tenant's zone, resolved once per request, with the same cutoff as the list filter; `invoices/invoice-list-query.ts` uses `[...OPEN_INVOICE_STATUSES]`; `invoices/deposit-fields.ts` doc only.
- `invoices/invoice-balance-sql.ts` NEW `assertReminderIssued(status)`: a reminder needs SENT, VIEWED, PARTIAL or OVERDUE, else the coded 400 `REMINDER_NOT_ISSUED` (`invoices.service.ts` `sendReminder` calls it before `assertReminderOwes`).
- `customers/customer-statement.ts`: the statement's overdue figure is `statementOverdueAmount(open, timeZone)`, the sum of `classifyInvoiceBalance` balances for invoices the one rule calls overdue, in `tenantTimeZone(prisma)` (due today is not overdue; an overpaid invoice adds 0).
