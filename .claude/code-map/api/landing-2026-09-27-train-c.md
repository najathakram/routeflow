# Landing batch 2026-09-27 — merge train C (#2383)

Docs-only bookkeeping (Option B) for merge train C: 14 PRs squash-landed as #2383 (`7e23c614af25ea0b134c300aabd28d61f9ad349f`), tooling/testing. #2224 (window G bookkeeping, PR 14 of this train) already covers its own scope (#2149/#2129/#2186; lessons L-223/L-224) and is not repeated here. Each bullet is derived from the PR body and checked against the merged code (train C's own commit, since this checkout was built before train C).

- **#1349:** yes — a `tsconfig.json` `exclude` glob that drops a whole directory (`prisma/**`) can silently exempt hand-written scripts with production-safety logic (`assertSafeTarget`/`assertTestTenant`) from type-checking; scope excludes to the specific artifact type (e.g. `prisma/migrations/**` for generated SQL) rather than the whole directory.
- **#2238:** yes — a jest CLI flag (`--maxWorkers`) overrides a config file's value, so a test lane whose specs share one database and can't tolerate parallelism needs enforcement at two points: a wrapper script that strips worker overrides *and* a `globalSetup` guard that refuses a run that resolved to >1 worker regardless of how jest was invoked.
- **#2246:** yes — a DB-backed test lane sharing a database with a running application (its API container, its cron jobs) produces flaky failures indistinguishable from real bugs; give such a lane its own uniquely-named, migrated, auto-dropped database per run instead of pointing it at a shared dev database.
- **#2283:** yes — a newly added self-test/spec file that isn't wired into `verify`/CI/pre-push protects nothing after it merges; have each self-test assert its own presence as a standalone step in `package.json`'s `verify` string, so an accidental un-wiring (or one that was never wired) fails loudly instead of silently.
- **#2271:** no candidate — this is a correctness fix specific to `from-git.mjs`'s own commit-walking logic (documented with its own regression test); it doesn't generalize into a rule beyond "test `--first-parent` behavior with a real merge fixture," which is really restating #2283's lesson from the other direction.
- **#1134**: yes — a CI "skip because superseded" gate must positively CONFIRM the thing it claims covers the commit (a live run for the successor), not merely detect supersession and assume coverage; fail closed (red) when that confirmation itself can't be obtained, rather than silently skip.
- **#2279**: yes — driving a Nest app through supertest via `request(app.getHttpServer())` without first binding it (`app.init()` alone) leaves supertest to `listen(0)` per request (IPv6 wildcard bind while it connects via IPv4 loopback), which races other processes for `127.0.0.1:<port>` under parallel workers; always bind the loopback address explicitly (`app.listen(0, "127.0.0.1")`) once in test bootstrap.
- **#2228**: yes — specs that spawn real child processes (node/git/shell) compete for CPU with jest's own parallel worker pool and time out under load; isolate spawn-heavy specs into their own serial lane rather than raising timeouts or worker counts.
- **#2203**: no strong new candidate — narrow, single-file "wait for animations before a Playwright screenshot" fix; already the kind of thing the existing UI-proof discipline should cover.
- **#2136**: yes — any script that can arm a real, time-delayed side effect (here: a 45-min repo-visibility flip) must validate its arguments and take a single-instance lock BEFORE that side effect starts, including treating `--help`/an unknown flag as a hard stop; a "probe" invocation must never be able to arm anything.
- **#1336 (deep dive requested)**: the general "full-lane red on this one suite is a known flake, verify alone before treating as a blocker" framing is **wrong** for this case, and should not be generalized from it. The root cause was not a stale-count race that a retry masks (that pattern already existed and is *kept* in this file's `applyLiveWithRetry`, as defense-in-depth, for a different, narrower symptom — n drifting between two of this spec's OWN preview/apply calls). The B824 failures were **real cross-suite contamination**: `publish-and-repin.mjs`'s `computeDiff()` correctly scans the *whole* database for a real prod run, but under `--maxWorkers=2` it also picked up sibling `*.db.spec.ts` files' own `Tenant.class='PRODUCTION'` (schema-default) fixture tenants mid-flight — causing three distinct, reproduced failure modes: (a) `--only-test-tenants` refusing the whole batch on a foreign tenant that was never this spec's own; (b) an unscoped `--apply --live` granting `GRANT`/`GRANDFATHER` overrides onto a concurrent sibling's fixture tenant; (c) this spec's own fixture receiving unwanted writes from a sibling's equally-unscoped apply. Running the suite alone trivially "fixes" all three by construction (no siblings present) — which is exactly why "verify alone" is the wrong signal to trust here; it would hide a genuine data-isolation defect rather than confirm safety. The actual fix was real isolation (`--only-tenants`, an explicit slug allowlist threaded through every CLI call the spec makes), not a retry or a skip. The specific, generalizable rule: **a `*.db.spec.ts` file that computes a diff/apply (or any read+write) over a shared, unscoped table under parallel jest workers must explicitly scope every call to its own fixture rows (e.g., an id/slug allowlist flag on the tool it drives) — "green alone, red in the full lane" for such a spec is a signal to look for a missing scope, not a flake to rerun past.**
- **#2317 (#1732) janitor counts a squash-merged branch as merged, not just one linked by exact PR-head or first-parent ancestry:** `scripts/janitor.mjs` gains `mergedPrCoversTip(repoRoot, tip, prs, masterRef)` — a MERGED PR (from `gh pr list --json headRefOid,mergeCommit`) covers the local tip when its merge commit is an ancestor of `masterRef` AND the tip equals or is an ancestor of the PR head (a tip ahead of the head is never covered); `ghPrMergedAtTip` now delegates to it instead of requiring `headRefOid === tip` exactly. Also adds `cherryAllMatched(repoRoot, tip, {masterRef})` — `git cherry <master> <tip>` with >=1 line and no `+` line, proving every commit reached master one-by-one (cherry-pick/rebase-merge), gated behind the same inference ordering as the pre-existing `squashMergedByPatchId` (B748): both run only when direct proof is silent, and an open PR at the tip vetoes them. `isMergedEvidence` now takes `{tipIsAncestor, tipOnMainline, prMergedAtTip, squashPatchId, cherryMatched}`. Self-test: `scripts/janitor.self-test.mjs` (tip behind/ahead/equal the PR head, merge commit off master, missing objects, `gh`-unavailable fallback to patch-id, cherry-picked-commit-by-commit branch, open-PR veto).
- **#2326 (supersedes #1346) the delete-time dirty re-check now also covers worktree REMOVAL, not only the node_modules clear:** in `scripts/janitor.mjs`'s exported `buildPlan`, the `kind: "worktree"` removal action (step 2) now also carries `worktreePath: wt.path` (previously only the `node_modules` action had it); `execute()`'s re-check `if (a.worktreePath && deps.isDirty(a.worktreePath))` therefore now fires for the worktree-removal path too, refusing (`removeWorktree` never called) when the tree went dirty between plan and execute. `deleteRefusal`/`refuseDelete` are unchanged. New pin in `scripts/janitor.self-test.mjs` drives the real `buildPlan` against a real git repo (bare origin, a linked worktree merged `--no-ff` into master, pushed with upstream, idle via a backdated HEAD reflog): asserts the planned `worktree` action carries `worktreePath`, that `execute()` refuses when dirty, and removes when clean.
